# Frontend cart calls refused at a gRPC endpoint nothing answers

## What the responder saw first

Pages alerted from four places almost together: frontend, frontend-proxy, checkout and the load-generator. That spread looks alarming — thirteen services were inside the blast radius — but the shape of the alert set is misleading. frontend-proxy and load-generator sit directly upstream of frontend on the same request path, so all three were reporting the same failures seen from different chairs. The only alert that genuinely needed separate explanation was checkout's, which arrived late (around T+91m) and never got worked.

The first thing worth confirming was whether this was real. It was: frontend's error ratio ran about 41× over its own baseline (mean 0.035 against 0.00084), peaking near 28% of calls erroring, with a baseline maximum of roughly 2%. That also kills the "noisy metric" theory early, which is worth doing before spending an hour chasing it.

## Where the clock actually starts

The declared window opens at T+0, but nothing was wrong then. Change-point analysis on the frontend error ratio put the first step up at roughly T+41m, about forty minutes into the window. A second, smaller shift followed around T+88m. The first step was higher (~0.096) than the second (~0.075), so the rate came partly down between phases without ever returning to baseline.

Anchoring on the declared window start is the first dead end available to a responder here, and it's an easy one to fall into — the useful anchor is T+41m, not T+0.

## The logs give it away quickly

Frontend logs show the process starting fresh at about T+39m and reaching ready in 344ms. One second after that, it began emitting gRPC status 14 UNAVAILABLE carrying `connect ECONNREFUSED 172.18.0.24:7071`. That error never stopped — it is present at the first second after startup and still present in the final seconds of the window, with no gap. The message originates from a compiled server-side bundle, so this is the frontend's own server making the call, not anything browser-side.

Two plausible readings die here. It is not the frontend itself being sick — the process came up clean and fast, and every error is a refusal from the other end of a socket. And it is not an HTTP 5xx story: status 14 with ECONNREFUSED is a TCP-level refusal underneath gRPC, which means nothing was accepting on that address and port at all. It is also not a flap; continuity of the error from T+40m to the end rules out brief unavailability followed by recovery.

## Chasing cart — the longest dead end, and the one that proves the point

The obvious next move is to go blame cart, since that is who the frontend was trying to reach. Three separate lines of evidence say cart was fine.

Its error ratio was exactly zero — mean, min, max and standard deviation all zero — across both baseline and incident windows, with no departure at either change point. The metric was defined and populated across 129 samples, so this is not "zero because no traffic"; cart was actively serving.

Its logs agree. From roughly T+60m through the end, cart emitted nothing but info-level ValkeyCartStore AddItemAsync and GetCartAsync lines. No startup banner, no bind message, no panic, no crash. The retrieved log run is truncated in the middle, so the interior of that window is technically unsampled, but both boundaries show ordinary steady-state work.

And the change log has nothing for cart at all across a full day of history: no deployment, no configuration edit, no flag toggle, no restart. An empty answer, but an observed one.

So: cart was alive, serving other callers, unchanged, and still refusing the frontend's connections. That combination is the hinge of this investigation. It means the destination the frontend was dialing was not where cart was listening.

## Traces put the break on the caller's side

One trace carries the whole story. Its deepest ERROR span is `frontend/grpc.oteldemo.CartService/AddItem`, and it is a leaf — there is no cart-side child beneath it. The call failed before anything downstream ever recorded a span. From there the ERROR propagates straight up the stack: the api route handler for /api/cart, POST /api/cart, POST, the frontend-proxy spans, and finally the load-generator span. That is one failure reported four times, which explains the alert spread.

Of ten sampled traces, only this one — the add-to-cart path — carries any error status. Browse, recommendations, reviews, index and ads all completed without error. Some of them were slow, with latency concentrated in product-reviews and product-catalog spans, and that slowness is a genuine second dead end: it looks like a lead, it is error-free, and it has nothing to do with the refusals. Those services never appear in the one trace that failed.

## Conclusion and fix class

The frontend's server-side gRPC client for CartService is pointed at 172.18.0.24:7071, where nothing accepts connections. The misdirection was picked up when the frontend process came up at T+39m; errors begin one second later and the metric step follows within two minutes. Cart was healthy and serving the whole time. The fix class is reverting the frontend's CartService destination to the correct value.

Confidence is medium, deliberately. The destination edit is inferred from behaviour, not read off a record.

## Left open — read this before you repeat the work

Three gaps, in the order I would close them.

First: no change history was ever pulled for the frontend. We queried cart's history and found it empty, which was useful, but the service that actually changed was never checked. That is the single query that would turn this from medium to high confidence.

Second: nobody established what, if anything, listens at 172.18.0.24, and which port cart actually binds. Without that, we cannot say whether this is a wrong port against the right host or a stale host entirely. The remediation differs.

Third: the second change point around T+88m is unexplained, and so is checkout's alert near T+91m. Checkout also calls cart and was never dispatched on. If the frontend's bad destination were the whole story, checkout should have been unaffected — so either checkout shares the same bad value, or there is a second thing happening late in the window that this record does not cover.
