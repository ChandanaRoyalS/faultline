# Checkout failures traced to a stale shipping quote endpoint address

## What we saw, in order

The page arrived on checkoutservice, critical, twelve services in the blast radius, with alerts following from loadgenerator, accountingservice, quoteservice, emailservice and frauddetectionservice. The first metric look narrowed things quickly: checkoutservice's error ratio stepped from roughly 1% to roughly 4% with a single change point about two minutes before nominal onset. Errors were intermittent, peaking near a quarter of requests and repeatedly falling back to zero, so the service was never hard-down and no crash-loop story was warranted.

Logs then told us what was not happening rather than why. Before onset each order produced a clean four-line sequence: order start, payment success with a transaction id, confirmation email, then a message write with an increasing offset. From onset through T+4m only the order-start line survived, at a steady cadence right up to the window edge. Since payment-success lines vanished too, the break was at or before payment, not in the email or queue steps. Both USD and CAD orders stalled identically. Crucially, checkoutservice logged no errors or warnings at all, so it never named its own culprit.

## Dead ends worth keeping

First we hunted a change on checkoutservice. The change log came back completely empty across a window running from onset forward about twenty-four hours. Two caveats for the next reader: the query was scoped to the seed service alone, so it says nothing about cartservice, productcatalogservice, currencyservice or paymentservice; and the window opened *at* onset, so anything landing in the minutes just before could not appear. It did legitimately exclude an in-window deploy, a rollout loop explaining persistence, and any recorded remediation on that service. Roughly twenty minutes went into this for nothing but exclusions.

Second, we sought metric confirmation at the callee and found an empty shelf: shippingservice's error-ratio series had no samples in the incident window and none in the preceding baseline either. Because both adjacent ranges were empty, this is a standing condition — the service likely does not emit these span metrics, or the service-name label does not match — and not a traffic collapse at onset. The detector's "no departure from baseline" verdict is vacuous; it had nothing to compare. Do not read that emptiness as health.

Third, and the most time-consuming confusion: traces showed the error only on the caller's side. shippingservice's server span for GetQuote and its outbound HTTP child both completed cleanly, and its logs were pure INFO with no errors, panics or restarts. For a while "shippingservice is broken" looked unsupportable, and an internal handler failure there remains ruled out.

## What actually broke

Ten sampled failing traces agreed unanimously: the deepest, earliest error span was checkoutservice's client call to ShippingService/GetQuote, reached via prepareOrderItemsAndShippingQuoteFromCart, with the error propagating up through PlaceOrder and the frontend spans — those were inheriting, not causing. Siblings (cart, product catalog, currency, feature flags, cart Redis) were all clean and sub-millisecond. Traces finished in 8.5–11.3ms with the erroring span at 2.6–3.7ms, which kills any deadline or load-pressure explanation: these were prompt error returns.

The unlock came from comparing shippingservice log *shape* across the window instead of reading only the late portion. Half an hour before onset, each inbound GetQuoteRequest was followed within about 10ms by a quote value, then a ship-order request, then a tracking ID. From onset to T+4m only request receipts appeared — about two dozen of them, arriving to the window edge, with no quote, ship-order or tracking line. The requests were structurally perfect, full address and item list, same gRPC client user-agent as the healthy period, so malformed payloads, field validation and schema mismatch all fell away.

Widening the change search to shippingservice and one hop out returned seventeen records, all scoped to shippingservice and all made by platform-automation; no neighbour change and no human deploy. About three minutes before onset, QUOTE_SERVICE_ADDR was set to a host whose name indicates it no longer exists. The same edit had been applied four times earlier in the window and reverted each time within about half an hour; this application was never reverted, so the value was live through onset. Prior harmlessness came from the revert, not the value. The last image change was reverted about three hours earlier, so no rollout is in play. Mechanism: with that address in effect, shippingservice accepts well-formed quote requests and never answers; checkoutservice fails on the shipping-quote branch and stalls at or before payment, which explains the accounting, email and fraud-detection alerts. Confidence high; fix is a configuration revert.

Still open: the status code checkoutservice actually receives, and whether shippingservice returns a degraded or empty quote rather than an error; the total absence of shippingservice call metrics, leaving onset unconfirmed at the callee; and quoteservice, which alerted independently around T+3m but was never dispatched against, so we cannot say whether it is separately unhealthy or merely starved of traffic.
