# Checkout stalls silently after shipping pod comes up as the wrong artifact

## What happened, in order

Eleven services in the blast radius, five alerting, checkoutservice as the seed. About two minutes before onset an automated platform process rewrote shippingservice's container image reference to a pinned demo image tagged for a different service. From roughly a minute after onset, the pod behind the shipping label is a JVM that boots, loads its agent, and dies again on a ~65-second cycle across five observed cycles, never reaching an application-ready or request-serving line. Shipping's gRPC surface is effectively dead.

What the responder actually saw first was checkout. It looked healthy: PlaceOrder entries arriving every 3-13 seconds right up to the last second of the window. But early in the window each entry was followed within ~25ms by a payment line, an order-confirmation email line, and a successful message-write with incrementing offset. In the last three minutes only the bare PlaceOrder entries remain. Checkout is alive and accepting traffic, and blocking somewhere after request entry and before payment — which is where the shipping quote call sits.

Remediation class is rollback: restore the correct shipping image, and stop the automated cycle that keeps re-applying the wrong one. The change history shows the same four-step cycle (bad quote address, revert, image update, image revert) repeating every four to five hours, always attributed to automation, never to a human. Prior cycles self-reverted the image after 10-12 minutes; this one had not yet at window close.

## Dead ends worth remembering

These cost the most time, and are the reason this record exists.

First, everything on checkoutservice came back clean and stayed clean. No changes of any kind on record for it across 24 hours — no deploys, no config, no flags — so there is nothing on checkout to roll back. Its aggregate error ratio during the incident sat essentially on top of the preceding baseline, around 7%, spiky in both windows, with no step and no onset signature. That correctly excluded a checkout-wide error surge and a hard-failing mandatory dependency (which would have pushed the ratio toward 1.0, not left it under 0.30). Both conclusions were true and both were misleading: the calls were hanging, not erroring, and a hung call produces no error sample. Do not go hunting for status codes in checkout's logs either — every retained line is info severity, and the failure is silent there. The signal is absent success lines, not present error lines. Also excluded along the way: a currency-specific problem (both USD and CAD stall) and a tail-end email or publish failure (the payment line is missing too, so the break is earlier).

Second, the quote-endpoint decoy. The same automation had pointed QUOTE_SERVICE_ADDR at a non-existent endpoint about 25 minutes before onset — but reverted it roughly 13 minutes before onset, so it was not in effect. Same source as the real cause, wrong step of the cycle.

Third, shipping's error-ratio metrics return zero samples — but the baseline window hours earlier is equally empty. That is a telemetry gap of at least four hours, not a signal, and building the timeline on it would have been wrong. Related: the container is not failing to pull or schedule, and the Rust binary is not crashing on its own startup. A process starts repeatedly and emits JVM output. The image runs fine; it is simply not the shipping application.

## What remains unsettled

Confidence in the cause is high, but three links are inferred rather than measured.

No trace or latency evidence was gathered on the checkout-to-shipping edge. The connection rests on call ordering within PlaceOrder plus the absence of completion lines — sound, but not a directly observed hop. Similarly, the alerts on quoteservice, accountingservice and loadgenerator were never dispatched on; their symptoms are assumed downstream of shipping being unserviceable, and that assumption is untested.

The Java process under the shipping label is identified only by a generic agent banner. It is consistent with the image named in the change record but not positively confirmed. No pod status, exit code or memory-kill evidence was collected, so the ~65-second restart cadence has no established mechanism.

Finally, given that prior cycles self-reverted after 10-12 minutes, this incident may be self-clearing and recurring on a four-to-five-hour cadence. Whether it has already cleared by the time you read this is unknown, and if so the one-off rollback is cosmetic — the durable fix is disabling the automation. One more caveat: checkout's metrics were only queried in aggregate with no per-dependency breakdown, so a second concurrent failure on another checkout dependency cannot be excluded.
