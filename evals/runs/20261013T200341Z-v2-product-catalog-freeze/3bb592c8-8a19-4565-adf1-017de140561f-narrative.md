# Critical errors reported at the edge proxy, traced to stalled request handling one hop in

## What was visible first

The page came from frontend-proxy and the load-generator, severity critical, three services in the blast radius. The first thing to check was whether the proxy itself had gone bad. It had not: its error ratio sat at exactly zero across the whole preceding half hour — 128 samples, zero mean, zero spread — and then stepped up once, to roughly 2% mean with a peak near 27%. That step is the clock for this record: call it T+0. The alert text pointed at a moment about two minutes later (T+2m), so if you are reading the alert timestamp as the start, you are two minutes late. Only one step was detected, so this was a single onset rather than flapping, and the large majority of requests kept succeeding throughout — worth knowing before you start reasoning about a total outage.

The metric aggregated only by service name, so it told us nothing about which upstream or which status codes were involved. That breakdown had to come from traces.

## Reading the one error trace

Ten proxy traces were sampled in the window. Nine were clean: cart, index, browse_product and view_cart all finished in 2–18ms with no error flags. Exactly one carried errors — a recommendations request beginning a little before T+0 with a total duration of ~15.01s. Fifteen seconds, round, is a deadline, not a computation.

The shape of that trace is the whole finding. The proxy's ingress span (~15.007s) is flagged ERROR, and so is the load-generator GET above it. Everything below — the proxy's egress to frontend, and frontend's own GET — is not flagged. The deepest span of any kind is frontend/GET, which holds essentially all ~15.006s as self-time and has no children at all. The request was routed, the upstream accepted it, and then nothing further happened inside frontend: no downstream call was ever emitted, no error was ever raised there. The error flags appear only above the stall, which is what a caller-side cutoff looks like from the outside.

For scale: healthy traces on the same recommendations path complete in 20–36ms. This is not degradation, it is a stop.

## Dead ends worth keeping

Several plausible lines were opened and closed, and re-walking them costs time if they aren't written down.

A downstream culprit. The natural guess is that recommendation, product-catalog or cart threw and the error propagated up. Those spans do not exist in the error trace. It terminates at frontend/GET with no children. Likewise the recommendation fan-out to GetProduct, visible and slowest at ~8.5ms in a healthy trace, was never issued in the error case and cannot account for fifteen seconds.

The storage layer. Every SQL and Redis span in the window is sub-3ms and error-free, and none appear in the error trace at all.

Proxy routing. Because the egress span and a frontend child span both exist, the proxy did route and the upstream did accept. Routing was not broken; the response simply never came back.

Breadth of impact. Only the recommendations path errored. Four other route families were clean in the same window.

Change history on frontend-proxy. Empty — no deploys, route edits or flag events. Note the trap: the window actually queried begins about two minutes after onset and runs forward a day, so it rules out any in-incident change or recorded remediation, but it does not cover the hours before T+0. If you need pre-onset coverage for the proxy, that query still has to be run.

## The change trail on frontend

Frontend has exactly four recorded changes in the day-long window, all from the platform automation actor, all touching one and the same environment variable (CART_ADDR). They form two complete set-then-revert pairs, each revert roughly nine minutes after its set, so the net state at onset is identical to the state before the first edit — the variable ends unset. All four landed between about 17.6 and 18.6 hours before T+0, leaving more than seventeen quiet hours immediately beforehand.

That closes a handful of stories at once: no deploy or release preceded this, no flag flip, no human last-minute edit, no lingering wrong-address configuration in effect at onset, and no wide change surface to triage. The one loose thread is the pattern itself — an automation actor setting and reverting the same key twice looks like a contending reconciliation loop. It is not the cause here and this record does not identify its driver, but it is worth a separate ticket.

## The silence, and why it cuts both ways

Frontend's own span-metrics error ratio is flat zero across the entire window, matching its zero baseline exactly — the service recorded no error-flagged spans at all. That is consistent with the trace: frontend never raised an error, it just stopped answering. It also means you cannot anchor onset from frontend metrics; there is no excursion there to find.

More striking, and more ambiguous: a label-only query for frontend logs over the ~32-minute window returned zero lines of any severity, not merely zero errors. The same query against frontend-proxy also returned nothing — no error lines and no healthy baseline traffic either. A total absence rather than a thinning points at a collection or labelling gap as readily as it points at a process producing no output. Do not read the empty proxy result as evidence the proxy was down; it was plainly serving, since most requests succeeded.

## Where it landed

frontend-proxy is the reporter, not the culprit. It routed correctly, frontend accepted the request, and the time was consumed entirely inside frontend's own handling with no downstream work and no error of its own. The ERROR flags sit only on the spans above, which is the signature of callers abandoning at their deadline rather than a failure coming back up the stack.

The mechanism that fits what we have is frontend's request-serving process stalling while its listening socket keeps accepting: callers hang to their deadlines and the process writes nothing. Fix class is a restart of frontend. Confidence is medium, and the reason it is only medium is set out below.

## Still open for the next responder

Three things were not settled and would move confidence either way.

First, the empty log streams. Because both services return nothing, frontend's silence is equally explainable as a log pipeline or label problem. Confirm whether lines are being shipped under a different label before treating silence as a symptom.

Second, no process-level telemetry was collected for frontend — no CPU, memory, thread-pool or connection-pool series. Resource starvation would produce the same fifteen-second stalls and the same absence of downstream calls, and it was never tested.

Third, and the sharpest objection to the conclusion: only the recommendations path errored, while cart, index and browse_product traces completed in milliseconds in the same window. A whole-process stop should hang everything. So either the stalling is partial — one worker, one pool, one handler — or the sampled traces are not representative. Pull a wider trace sample across routes before accepting the whole-process story.
