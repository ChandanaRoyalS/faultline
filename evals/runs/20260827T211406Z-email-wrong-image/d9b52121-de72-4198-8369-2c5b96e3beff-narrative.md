# Checkout order-confirmation failures traced to a mis-targeted email service artifact

## What was visible, in order

The page came from checkoutservice; nothing else alerted. Triage drew a blast radius of nine services with four unmeasured edges, and almost none of that turned out to matter.

The first panel was checkoutservice's aggregate error ratio: non-zero but partial, peaking near 8.3 percent across fifty-seven samples and returning to zero in between. That shape said discrete failure on a subset of work, not an outage. It also warned that absolute volumes might be tiny — one failure in twelve calls looks identical — and we never retrieved call counts.

The reflex was to look for what changed on checkoutservice. The change log came back completely empty: no rollout, config edit, flag toggle or dependency bump. That removed the obvious remediation in one step. Caveat for the next reader: the query covered only about fifteen minutes around onset, so an earlier change surfacing late would not have appeared. We ran the same query against cartservice and got the same empty result.

Logs then named the failing edge. Every checkout order emitted one warning: the outbound order-confirmation POST to the emailservice host on port 6060 failed at name resolution against the embedded Docker resolver, before any TCP connection. Payment, shipping, cart-empty and the orders publish all still succeeded, with message offsets advancing contiguously — which explains the partial error ratio exactly. Ten minutes earlier the same path had sent confirmations cleanly.

## The cause

emailservice's error-ratio metric read flat zero at every one of sixty-one samples, unbroken. Read naively that clears the service, and it briefly did. Read correctly it is the strongest hint in the record: a process that dies during configuration parse never serves a request it could fail, so it emits no error-status calls. Zero here is absence, not health. Note the inference that it was 'receiving traffic throughout' was indirect — we never queried an up-metric or replica count.

emailservice logs settled it. Early in the window it served confirmations with 200s at about 2ms. Roughly three minutes before the alert it changed character entirely: Apache startup output under pid 1, an unresolved config variable warning, then a fatal ports-configuration syntax error and exit, repeating on a sixty-second cadence. The process never bound a listener. That excludes a planned restart, gradual degradation, and any downstream dependency of emailservice.

The emailservice change log holds exactly one entry in the window: a platform-automation actor updating the image reference to an artifact tagged for a different service, quoteservice. From that point emailservice is not the email application. No instance becomes ready, so the name stops resolving for callers — which is the resolver error checkoutservice was logging. Replica changes, DNS-record deletion, config edits and human operators are all excluded by the same record. The wrong artifact is the mechanism. Fix class: rollback. Confidence medium.

## Dead ends and what is still open

The most persuasive lead did not resolve. Failing traces show frontend POST and PlaceOrder spans of 1.5s to 29s, with checkoutservice PlaceOrder carrying nearly the whole duration while its children sum to tens of milliseconds. The one ERROR span — the confirmation POST — lasts about 2ms and fails fast. We chased downstream slowness and found none: every downstream span completes under about 11ms, no downstream span errors, fraud-detection consumption is ~0.1ms, and the frontend-to-handler gap is 1-3ms. Multiple seconds of unattributed self-time inside the checkout handler remain unexplained — possibly resolver retry and backoff outside instrumentation, possibly a second concurrent failure. Start here.

Onset timing is unproven: checkoutservice logs were truncated across the ten minutes containing the alert. The rollback target is unestablished: the change record lists the prior image reference as null, so recover it from the registry or deployment history first. No latency percentile or saturation data was ever pulled for checkoutservice, so a resource-side contribution cannot be excluded. Change status for productcatalogservice, shippingservice, currencyservice, paymentservice and frauddetectionservice was never queried, and the four unmeasured edges remain uninspected. Most pressing: whether the same automation run pushed the mis-targeted image to other services is unknown — only three change logs were read.
