# Checkout failures traced to cart crashing on startup against a wrong cache endpoint

## What was visible, in order

Pages fired on frontend, loadgenerator, and checkoutservice at T+0. Frontend's own error ratio was genuinely elevated — roughly 3.8x the prior baseline hour (about 0.075 versus 0.020), peaking near 34% of calls, but never a total outage. The important correction came early: this did not begin at T+0. Four threshold crossings appear, the earliest at about T-59m, then T-52m, T-39m, and finally T-2m. Anyone anchoring onset to the page time is an hour late.

Frontend logs pointed straight downstream: repeated gRPC 14 UNAVAILABLE with a no-connection-established detail, plus a code 13 INTERNAL from the checkout path naming the cart dependency. The failing call was checkout's fetch of the user cart, dialing a resolved IP on port 7070 and refused at the TCP layer. That shape excluded slowness (immediate receive-status error, empty metadata, not DEADLINE_EXCEEDED), service discovery (a concrete IP was dialed), auth/TLS/quota (wrong codes, empty metadata), and any bug in frontend itself (all frames in the gRPC client library).

Checkoutservice looked deceptively fine: no lines above info severity anywhere, and PlaceOrder start entries continuing at steady cadence through the end of the window, so the process was alive and accepting orders. What was missing was every stage after the start line. The oldest retained lines showed the full healthy sequence — start, payment confirmation, email, queue write with incrementing offset — while the later span had only starts. Both USD and CAD truncated identically, so not currency-specific, and not the email or publish steps, since requests never reached them.

## Dead ends worth keeping

Change history on the two alerting services came back completely empty — no deploys, config edits, or flag flips for frontend or checkoutservice. That legitimately closes off in-incident rollouts, flag flips at impact, and post-onset remediation edits, and means there is no rollback target on either. But both queried windows began at the incident timestamp and ran roughly 24 hours forward, so they never covered the pre-incident hours the question was actually about. I nearly filed "no changes" as a finding before noticing the window direction. Check that boundary before trusting an empty change log.

Cartservice metrics were a second dead end. The error-ratio series returned nothing in the incident window and nothing in the baseline window either, so the emptiness was pre-existing and could not be read as telemetry going dark when the process died. The selector simply does not match what this service emits, and an empty series cannot distinguish an absent process from a crash-looping one from one that is up but not serving. Restart, uptime, and resource series were never returned, so this leg contributed only the knowledge that the path is a hole.

My own working theory mid-investigation — that the first downstream step after PlaceOrder was hanging, i.e. the charge path — was also wrong. The truncation was real; the attribution was not.

## The cause, and what remains open

Cart's logs settled it. The service was not silent; the tail was a repeating loop. Each iteration: an attempt to connect to the cart Redis endpoint, connect failure after roughly 25–45 seconds, then an unhandled exception from the Redis cart store initialization path during startup, then another attempt. The exception came from the store's connect step as called from the main entrypoint, so the process died before ever reaching a listening state — which is exactly why frontend's dials at :7070 were refused. The recorded target used a non-default port, 6380 rather than 6379, with TLS and abortConnect off. Around T-2h cart had been serving normal cart operations, so the mode began after that.

Cart's change log — which, unlike the others, covered the full 24 hours — shows automation setting the cache endpoint variable to that exact host and port, previously unset, at about T-3m, two minutes before the checkout page. All 29 recorded changes belong to the same automated actor, and the same six-step set/revert sequence recurs every four to five hours, so the activity is baseline for this service. That does not make the value harmless; the wrong address is the mechanism. Confidence medium; fix class is a config revert.

Three things stay open. First and largest: frontend error crossings begin around T-59m and cart-refused errors already appear near T-60m, an hour before the endpoint override and inside a change-free cart gap running roughly T-3.5h to T-41m. An earlier, distinct cause of cart unavailability probably preceded this one. Second, nobody verified whether the cart Redis actually listens on 6380 or only 6379; no dispatch was run against it. Third, crash-looping is inferred from application logs alone — an external or memory-related kill is strongly but not absolutely excluded, since such records live outside app logs.
