# Frontend gRPC UNAVAILABLE against a single ad upstream endpoint

## What the responder saw first

The page came from frontend and frontend-proxy. The blast radius was drawn as eight services, which made the first instinct a broad shared-infrastructure outage. That instinct was wrong and cost time.

The first hard number was frontend's error ratio. Across the half hour before the alert it averaged about 0.21%; across the alerting window it averaged about 1.26%, with a single detected crossing at onset (treat that crossing as T+0) where the ratio reached roughly 6.5% and peaked near 8.5%. The minimum in the window stayed at zero and the spread was wide relative to the mean, which told us this was an abrupt onset late in the window rather than a slow creep. It also told us frontend was not down: over 91% of calls still succeeded at the worst point. Only an aggregate service-level ratio was available — no latency percentiles and no per-dependency breakdown — so this evidence could not name a downstream on its own.

## The log line that actually pointed somewhere

Frontend's logs in the window contained exactly one kind of error, repeated: a gRPC client failure with status code 14 (UNAVAILABLE) raised out of the server bundle, always against the same address and port — 172.18.0.19:9555. Every stack trace was identical. That single-endpoint pattern is what collapsed the eight-service blast radius down to one hop.

The shape of the failure changed over the window. Earlier entries (roughly T-9m through T-3m) reported the connection being actively refused; later entries (from about T+4m) reported the host as unreachable. Refused means something is listening on the host but nothing is accepting on the port; unreachable means the address itself has gone. The newest entries all replayed a cached connection failure from a single attempt around T+3m30s, and the error recurred at least five times in the final twenty seconds of the window, so this was unresolved when the record closes.

Two things this evidence rules out cleanly. Frontend itself was not broken — every line is a transport-layer connect failure, with no application exceptions, no memory messages, no route handler errors. And the upstream was not slow or saturated — there were no deadline-exceeded or timeout errors, because no connection was ever established for a request to time out inside.

## The change that lines up

Frontend's own change history over the full 24-hour window contained only six environment-variable events, all from platform-automation, all setting and then reverting one variable (CART_ADDR). Three complete set/revert pairs, each reverted within ten to twenty minutes, the last revert completing about 4.2 hours before onset. Frontend's effective configuration at onset matched its long-standing baseline. No deploy, no image rollout, no flag flip. This was a clean dead end for frontend, but a useful one: it establishes that nothing changed on the service that paged.

The ad service's history was the opposite. Eleven entries in the window, every one a memory-limit adjustment by the same automation actor, forming five complete lower-then-restore cycles over about eighteen hours. The limit was restored roughly 1.1 hours before onset, then lowered again to 144m about four minutes before onset — and this last lowering has no matching restore recorded. The constrained limit was in force when frontend errors began.

## Dead end: traces showed nothing wrong

The trace sample taken over the same window contained no error spans at all. Every sampled trace ran cleanly from load-generator through frontend-proxy down to datastore calls. There was no deepest-error-span to find, which is why the trace path consumed effort without converging.

What the traces did surface was a latency story that turned out to be unrelated. One product-reviews read totalled ~319ms, of which frontend's GetProductReviews call took ~119ms (~61ms of handler work, ~46ms of frontend-side self time beyond the child span). The single largest self-time block in that trace — ~191ms — sat on the load-generator's client GET before the proxy ingress span even started, so a good chunk of it was client-side or queueing. A checkout trace totalled ~163ms with the email confirmation hop dominating. Everything else (add-to-cart, view-cart, browse-product, recommendations) finished in 6–53ms.

Along the way the traces eliminated several plausible suspects: cart's Redis operations were sub-millisecond to ~3ms; product-catalog SQL queries stayed under ~3ms and its server spans under ~10ms; the one flag resolution observed took ~1.5ms; payment, currency and shipping in checkout were single-digit milliseconds; the proxy layer added only a few milliseconds of self time. None of this explains an UNAVAILABLE error, because none of it is on the failing path. The ~119ms product-reviews hop is still unexplained and is, as far as this record can tell, unrelated noise.

## Dead end: the ad-side evidence was from the wrong window

Both ad-side queries — metrics and logs — were run against a six-hour window ending roughly eighteen hours before onset. Neither covers the incident. This is the single biggest gap in the record and the thing to fix first if it recurs.

The ad metric result returned only an error-ratio series; request rate, restart count and memory usage were all absent. Within its (wrong) window it showed a late change point where the ratio jumped to about 38%, and 64 intervals where the ratio was undefined — meaning no ad spans were recorded at all, so the service genuinely stopped serving for stretches rather than merely erroring. That is suggestive of the same pattern repeating on each earlier lowering cycle, but it is not evidence about this one.

The ad log result, over the same misaligned window, showed only ordinary request handling: no crash, no panic, no startup or re-initialization lines, traffic continuous at both ends. It was also truncated to the oldest eight and newest thirty-two lines, leaving almost six hours unobserved. Do not read this as 'ad was healthy during the incident' — it says nothing about the incident at all.

## Where this landed

Frontend is the service that noticed, not the one at fault. The visible symptom is a caller unable to open a TCP connection to one endpoint — first refused, then with the address gone entirely — with no timeouts and no slow responses anywhere on that path. From outside, that is what a container being terminated for exceeding a too-small memory allowance looks like: the listener stops accepting, then the address disappears, then it comes back and the cycle repeats.

The timing is the load-bearing part. The memory limit on ad was dropped to 144m about four minutes before frontend's error ratio crossed, and unlike the five preceding cycles it was never restored. Fix class is a configuration revert: put the limit back where the earlier restores put it.

Confidence is medium, and the reasons are worth naming. No dispatch ever resolved 172.18.0.19:9555 to a named service — the mapping to ad rests on port convention, not on evidence in this record. No ad-side data covers the incident window, so the termination, exit code and restart are inferred rather than observed, and no memory-usage or restart-count series for ad was ever returned. Six of the eight services in the blast radius were never queried. Anyone revisiting this should start by resolving that IP and port to a service and pulling ad's memory and restart series across the onset.
