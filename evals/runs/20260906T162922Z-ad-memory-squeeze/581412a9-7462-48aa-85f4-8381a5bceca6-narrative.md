# Ad-serving branch of frontend fails at connection setup after an unreverted memory-limit change on adservice

## What was visible, in order

The page came from loadgenerator and frontend. The first metric a responder reaches for is the least useful: frontend's aggregate outbound error ratio averaged about 6%, dipped to zero, and peaked near 37%. Two traps in it. The baseline hour returned no samples, so the apparent rise from zero is missing data, not a measured quiet period; any fold-change claim is unsupported. And the series is aggregated by service name only, with no per-callee breakdown, so it names no target. The burstiness argued against a single dependency going hard down, which was misleading — only one of frontend's routes was affected, so the aggregate never stepped cleanly.

Frontend logs gave the failure shape and not the target. Every error line is a Node gRPC client error, code 14 UNAVAILABLE, detail saying no connection was established, raised from the @grpc/grpc-js receive-status path. That rules out a frontend-side handler bug, rules out a slow-but-alive callee (which would be code 4 DEADLINE_EXCEEDED), and rules out auth/permission/argument rejections (codes 16/7/3, non-empty metadata). But no line names a host, port, service or method. The result was also truncated to the oldest eight and newest thirty-two lines, so the exact onset minute was inferred from the identical surrounding pattern, not observed.

Traces closed it. Only two sampled frontend traces carried errors; in both, the deepest failing span is a frontend-emitted tcp.connect of about 3.06s under frontend's call to AdService/GetAds, with loadgenerator parents failing at ~3.07–3.08s — one timeout budget unwinding, not queueing, since nearly the whole parent duration sits in that one leaf. No adservice server span appears at all, so the request never became work on the backend.

## Dead ends worth keeping

Checkout was not involved: no checkoutservice span in either failing trace, and the one full PlaceOrder trace completed end-to-end in ~30ms with cartservice, productcatalogservice, currencyservice, shippingservice/quoteservice, paymentservice, emailservice and the orders messaging hop all healthy. Every other sampled frontend route was sub-40ms and error-free.

The adservice error-ratio query returned nothing in the incident window — and nothing in the three-hour baseline either. Do not read the emptiness as the symptom; the series was never populated, so its absence cannot be dated to onset. It cannot distinguish a healthy adservice from a dead one.

Change history for frontend and productcatalogservice was empty over the queried span (which runs forward from onset, so it says nothing about the prior hours). Cartservice was the richest false lead: 29 entries, all platform-automation, all paired set/revert cycles — a hotfix image swap, a traffic-shaping sidecar at 300ms delay, a REDIS_ADDR port override. The nearest pair was applied ~44m before onset and reverted ~35m before. The image change was ~9h earlier and itself a revert; the sidecar was detached ~8.5h earlier and never reattached; no flag changes exist; no human actor. Nothing landed on cartservice in the half hour before symptoms.

## The cause, and what remains unproven

Adservice's change log holds exactly one class of entry: platform-automation lowering the container memory limit to 256m and later restoring it, nine events alternating apply and revert. Four earlier cycles were each reverted within tens of minutes to about ninety. The ninth, applied around T-3m, has no matching revert and was in force throughout. No deploy, image swap, flag flip, sidecar, environment override, pod kill or human actor is recorded against the service.

Adservice logs bracket the transition tightly. Through about T-3m it served normally with steady per-request lines and no errors. Roughly twenty seconds after the change the stream changes character: the same three-line JVM/OTel startup banner repeats seven times, from about T-2m40s to T+1m15s, with no request logging between and gaps lengthening geometrically (~9s, 16s, 29s, 54s, 63s, 63s) — a supervisor backing off repeated exits. No incarnation reaches a gRPC listening line. Nothing was bound, which is exactly why frontend failed at connection setup. This also kills three alternatives: the stream did not go silent (banners continue past onset), adservice was not still serving, and this was not one rollout restart. It corrects the timeline too — onset is ~T-3m, and the reported incident moment is mid-loop.

Open items for whoever reads this next. No direct kill evidence: no OOM event, no exit code 137, no JVM OutOfMemoryError, no port-bind failure — and that negative rests on a truncated log result. Memory saturation and restart-count metrics for adservice were never queried, and they are the obvious first step. Frontend gRPC errors appear from roughly 40 minutes before the adservice transition; whether that is the same failure, another callee, or noise is unresolved, since the lines name no target. The intermittency of the frontend error ratio, the unmeasured edge triage flagged, and loadgenerator's earlier alert were never investigated. Fix class: revert the configuration.
