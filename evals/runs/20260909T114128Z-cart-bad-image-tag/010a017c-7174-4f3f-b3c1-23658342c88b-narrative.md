# Checkout aborts at the cart fetch after cartservice stops serving

## What was visible first, and the time spent on the wrong service

The page named checkoutservice, frontend, and loadgenerator. Blast radius was twelve services seeded at checkoutservice, with four unmeasured edges in the call graph. The alert set pointed the first stretch of work at checkoutservice, which turned out to be a victim.

All three probes on checkoutservice came back clean. Change history returned nothing — but note the window started at onset (11:45) and ran forward, and covered no dependencies, so it only establishes that nothing landed after onset. The pre-onset window was never queried. Error ratio against a two-hour baseline sat slightly below baseline (~0.073 vs ~0.085), spiky in both windows, so short error bursts are pre-existing. One incident-window interval had no defined ratio, meaning no traffic at all; that blank was never chased.

Logs were the useful part. No error- or warning-severity lines anywhere. Early in the window each request produced a full pipeline: order entry, payment authorization with a transaction id, confirmation email, queue write with incrementing offset. From roughly 11:42 to 11:47, only the order-entry line appears, at a steady several-per-minute cadence including inside the 11:45 minute. The process was alive and accepting work but never reaching completion.

Ruled out by this: checkoutservice as origin; a downstream failure propagating outward as error responses (though this cannot see a dependency failure that checkoutservice absorbs); checkoutservice having crashed or lost traffic; a broken log pipeline (logs kept arriving, only certain message types stopped); and orders completing normally with the problem elsewhere.

## Traces relocate the problem to the cart hop

Five failed checkout traces in the 11:45–11:46 minute abort at the same place: frontend POST, frontend PlaceOrder, checkoutservice PlaceOrder, prepareOrderItemsAndShippingQuoteFromCart, then checkoutservice's client span for CartService/GetCart. That client span is the error-marked leaf carrying nearly all its own duration as self-time (2.2–3.9ms, 63–73% of each short trace).

It has no cartservice server-side child and no Redis child, unlike successful traces which nest both. Failed traces are five spans total — the error exists only on the caller side, with no sign the cart backend responded. Nothing downstream appears: no payment, currency, shipping, email, or orders-send spans. Successful traces from 11:33–11:40 are intact at 36–48 spans and ~24–25ms, dominated by the shipping-to-quote hop at ~5–6ms.

Dead ends closed here: the four unmeasured edges (payment, currency, accounting) are never invoked in failures and near-zero in successes; the shipping-to-quote hop appears only in the healthy traces; timeouts and saturation inside checkoutservice are excluded because failures run 3.2–5.6ms end to end with 0.1ms self-time — fast-fails; and a cache slowdown behind cartservice is excluded because no cart or Redis span exists to be slow.

One loose end: a single 11:46 failure was a lone frontend error span with no checkoutservice child, unexplained.

## The cause, and what is still open

cartservice logs run normally until 11:41:33 and then stop entirely for the remaining five and a half minutes. The final ~32 lines are ordinary cart handling with no error, timeout, or refusal text. The last line is an orderly framework shutdown notice — a signal received, not a crash. No startup lines follow. This puts onset earlier than the alerts suggested and explains the trace shape exactly: callers fast-fail because nothing is listening.

Change history shows a cartservice image-reference update to the v1.2.1-cartservice-hotfix.2 tag applied by platform-automation at 11:41:34, one second after the shutdown line, with no revert recorded — the only change still in effect at onset. The log is noisy around it: 25 automated changes cycling roughly every five hours, including a REDIS_ADDR repoint (last active 08:47–08:55) and a 300ms traffic-shaping container (last active 08:29–08:39). Both were dismissed on timing, hours before onset. No human actor appears anywhere. Fix class is rollback; confidence high.

Still open. No pod-level data was gathered — no image pull events, exit codes, restart counts, or readiness — so whether the artifact failed to pull, stopped before logging, or was never scheduled is unsettled. The same tag was applied and reverted at least four times earlier in the window with no reported impact, and why this application caused an incident is unexplained. cartservice call metrics returned nothing in both incident and baseline windows, so the emptiness predates the incident and is a data-availability problem, not a symptom; there is no independent metric confirmation of outage timing. And the pre-onset change window for checkoutservice and other dependencies was never queried.
