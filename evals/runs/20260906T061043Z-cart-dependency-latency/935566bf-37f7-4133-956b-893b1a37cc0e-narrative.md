# Uniform ~300ms egress delay on cartservice inherited up through frontend and checkout

## What was visible, in order

The page named cartservice, frontend, checkoutservice and loadgenerator, warning severity, twelve services in the blast radius, four edges crossed with no measurement behind them.

First look was frontend, since that is where user-visible pain lands. Its error ratio did move — baseline mean around 0.054 rising to roughly 0.083, a single change point, a peak near 0.40 and dips back to zero, so frontend never hard-failed. A step, not a ramp. But the series aggregates by service name only, with no downstream-target dimension and no latency, so it named no culprit.

The change log for cartservice was the productive pull. At about T-3m a platform-automation traffic-shaping container was attached to cartservice's network namespace, applying a fixed 300ms egress delay with zero jitter on eth0, with no matching removal before onset. The same attach/remove pattern appears twice earlier in the window (about 5.1h and 3.7h prior, each removed 35–60 minutes later), and all twenty changes belong to the same automation actor — no human edit anywhere.

Traces matched that shape exactly. Every cartservice Redis egress span, HGET and HMSET alike, sits at a uniform 300–305ms floor with no fast examples. GetCart runs ~302ms over a ~301ms child, leaving about a millisecond of self time; AddItem runs ~602–611ms over two round trips. The penalty is inherited upward — frontend cart spans ~605–918ms, frontend HTTP POSTs ~1510–1528ms — while currency, productcatalog, payment, shipping, quote and email all stay at baseline in the same traces.

## Dead ends worth keeping

A bad cartservice build. A hotfix image tag was applied and reverted five times in the window; the last revert landed about thirteen minutes before onset, so that artifact was not running. Plausible and wrong.

A wrong Redis endpoint. Two edits pointing at redis-cart:6380 appear, both reverted, the last roughly 3.3 hours before onset. Wrong again.

Shared infrastructure — node network, mesh, DNS. Excluded by the traces: only the cartservice→Redis hop is slow, everything else in the same traces is at baseline.

Queueing or saturation. A queue disperses; what is present is a near-constant additive value across dozens of independent operations and both reads and writes.

cartservice being down, crash-looping, or failing its Redis connect. Logs show one clean startup — Redis connect, passing self-test, listener up — and continuous served cart operations through the end of the window. Checkout likewise shows a single process start and, in its retained tail, eight consecutive complete order flows with sequential queue offsets and no error lines. Requests were waiting, not failing.

## Conclusion, unmeasured ground, and what stayed open

The cause is the traffic-shaping attachment on cartservice's network namespace about three minutes before onset: a fixed 300ms egress delay, still in place at onset. Cost scales with Redis round trips and is inherited upward. Fix class is a configuration revert. Confidence high.

Unmeasured ground, which is the part to fix before the next page: cartservice has no error-ratio series at all — zero samples across incident and baseline, four hours or more. That is not a clean result, it is an unmeasured one, and because the baseline is equally empty the gap predates the incident. Rate, latency, restart count and readiness were never queried. Both log pulls were truncated to the oldest 8 and newest 32 lines, so the minutes containing onset were never retrieved. The trace sample carries no timestamps and is capped at 200 spans, so it cannot itself pin onset.

Still open. Frontend's only error change point sits at 05:53, roughly eighteen minutes before the attach at 06:10:51 — a change cannot explain elevation that precedes it, and that gap was never resolved. Checkout's calls into cartservice run ~1206–1213ms against ~302–305ms children, leaving about 900ms unaccounted for. And there is no removal record for the shaping container, though flows looked clean by 06:15:32; whether it is still attached was not confirmed.
