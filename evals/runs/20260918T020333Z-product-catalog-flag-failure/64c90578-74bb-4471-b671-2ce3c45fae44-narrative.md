# Product catalog GetProduct returning INTERNAL on an enabled fail flag

## What we saw first

Three alerts arrived close together: loadgenerator, frontend, and productcatalogservice. The natural entry point was frontend, since that is where user-visible failures surface, and the blast radius spanned seven services with one edge we had no measurement for. At T+0 the working assumption was the usual one for this shape — a frontend dependency degrading and frontend amplifying it. Note for the reader: loadgenerator alerted first and was never examined during the investigation. If you are reading this because it recurred, start there; we did not.

## The first dead end: frontend metrics

The obvious first move was to check whether frontend's error rate was actually elevated, and to attribute the rise to one of its outbound edges. It was not elevated. Frontend's aggregate error ratio during the incident window averaged roughly a fifth of the immediately preceding baseline, with a lower peak and less variance, and no sustained departure was flagged. Worse, the series was aggregated by service name only, with no breakdown by downstream peer, so even if there had been a rise it could not have been attributed to the productcatalog, cart, ad, or recommendation call paths. No latency series came back either. This step consumed time and produced nothing except a caution: the service-level error ratio at frontend is not a usable detector for this incident, and on its own it argues — wrongly — that nothing is happening.

## The second dead end: productcatalogservice metrics

We then did the same exercise one hop down. The error ratio for productcatalogservice did rise, but modestly: mean from about 0.29% to 0.46%, so still over 99% of calls succeeding. There were two short spikes near 6%, at roughly 22:31 and 02:05, but the incident-window peak (~9.8%) was essentially indistinguishable from the baseline-window peak (~10.3%), and variability was comparable. On this evidence alone one would rule out productcatalogservice as the origin, and rule out any step change in its error regime — and that is exactly what the metric analysis concluded. Instrumentation was healthy (the series was fully populated), so this was not a reporting gap. No latency percentiles or CPU/memory series were returned, so saturation was left unaddressed at this stage. The lesson: the quantitative signal here is muted enough to be actively misleading, and the reason it is muted is still open (see Loose ends).

## The third dead end: chasing a change

With a suspect service identified, we queried change history for productcatalogservice. It came back empty — no deploys, no config edits, no flag flips anywhere in the window. That emptiness was used to rule out an in-window release, an in-window config edit, an in-window flag flip, and ongoing churn as the sustaining factor; it also killed the tempting remediation of "roll back the last change." The trap is in the window itself: it began at the onset timestamp and extended roughly 24 hours forward. It covers the incident but gives zero visibility into the hours before onset, which is precisely where the change would be. We ran the change query twice with the same forward-looking window and got the same nothing both times. Treat these as unlocated, not disproven.

## The fourth dead end: a bad label selector

We tried to read productcatalogservice's own logs and got zero lines over a 32-minute window. The query executed cleanly and returned a well-formed empty result, so the log pipeline and retention were fine — the selector was wrong. It used a hyphenated label value rather than the unhyphenated service name used everywhere else in the investigation. We never re-ran it with the corrected value. Consequently nothing in this record rests on the failing service's own logs, which is the single largest hole in the evidence.

## The turn: frontend logs

Frontend's logs broke the case open. They carry gRPC INTERNAL (code 13) errors that name productcatalogservice as the callee and quote a message attributing the failure to a deliberately enabled product-catalog fail feature flag. The stack frames are all grpc-js client-side receive-status frames — frontend is relaying a status authored downstream, not failing internally. That ruled out frontend as the broken component, ruled out cartservice and adservice (no other dependency is named anywhere in the sampled errors), and ruled out generic transport trouble: these are INTERNAL with an application-level message, not DEADLINE_EXCEEDED or UNAVAILABLE. The same error class appears from about 02:03:54 and continues to the end of the window, so this is a sustained condition straddling the 02:07 onset marker, not a blip. Checkout is affected too: frontend also logs an order-preparation failure because a specific product ID could not be fetched.

## Confirming it server-side with traces

Traces put the error on the productcatalogservice server span for GetProduct, and did so caller-independently: the frontend-initiated path and a checkoutservice-initiated path fail identically, so this is not one caller's client or channel. All 121 sampled spans belong to GetProduct and a single ListProducts; ListProducts was clean. Every productcatalogservice server span was at or below 1.5ms, typically 0.0–0.1ms, which removes latency saturation or a slow datastore read from consideration — the time in these traces sits in caller self-time and, in the checkout trace, in the shipping/quote hop. The error-marked GetProduct spans each have a fast, successful FeatureFlagService/GetFlag child (0.7ms and 1.4ms, no error status), so the flag lookup hop is healthy and a timeout there is not the mechanism; the flag *value* is. GetFlag also appears under clean GetProduct spans, so its presence is normal rather than diagnostic by itself. productcatalogservice's only outgoing call in the samples is that flag lookup, which clears the other dependencies. Failure is partial: inside the failing checkout trace, two sibling GetProduct calls succeeded while a third failed. One caveat worth keeping — both error traces land in the last ~2 seconds of the queried window, which reads as abrupt onset from traces alone but is contradicted by the log evidence of a sustained condition from ~02:03:54. Trust the logs on duration; the trace window was simply positioned badly.

## Conclusion and fix

productcatalogservice's GetProduct handler is deliberately returning gRPC INTERNAL because a product-catalog fail feature flag is enabled. Frontend is a victim relaying a downstream-authored status; checkout is affected through the same path. Confidence is high. The fix class is a config revert — turn the flag off — not a code rollback, since no code change is implicated and none is recorded.

## Loose ends for the next responder

First, who enabled the flag and when is unknown. Both change queries covered onset forward 24 hours and returned nothing; re-run them over the hours *before* onset. Second, where the flag value actually lives is unknown — featureflagservice's store was never inspected, and productcatalogservice's own logs were missed because of the wrong label selector. You cannot revert what you have not located. Third, the mismatch between muted quantitative signals (sub-0.5% mean error ratio, peak no higher than baseline) and a sustained condition visible in logs from ~02:03:54 is unexplained; probabilistic firing or firing scoped to particular product IDs would fit, and the partial failure inside a single checkout trace supports that. Fourth, loadgenerator alerted first and was never looked at. Fifth, no latency percentiles or CPU/memory series were ever retrieved for either service, so resource questions are unanswered rather than cleared — though the sub-1.5ms server spans make saturation unlikely.
