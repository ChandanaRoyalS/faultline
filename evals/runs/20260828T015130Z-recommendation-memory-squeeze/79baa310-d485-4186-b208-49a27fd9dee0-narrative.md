# Frontend UNAVAILABLE errors traced to a single recommendation edge after an automated memory-limit edit

## What was visible, in order

The page came from frontend and loadgenerator only. Frontend was not down: its aggregate error ratio peaked near one request in five and returned to zero at other samples across the window, which ruled out both a total outage and a pre-existing steady state, but carried no per-dependency attribution. From about T+6m40s frontend logged repeated Node.js gRPC client exceptions, status 14 UNAVAILABLE, detail indicating no connection was established, with stack frames entirely inside the @grpc/grpc-js client path. That placed the failure on the outbound call path rather than in frontend handling code, and the empty trailing metadata excluded any authorization or rate-limit rejection. Note the limits: those log lines name no target service, host or method, and the result was truncated to the newest thirty-two lines, so the true first occurrence and the error rate are not established from logs alone. Errors were still present at the last visible sample around T+12m.

## Dead ends worth keeping

The frontend change history returned nothing at all, which killed the tidy self-inflicted-frontend story — but read it narrowly. The query as executed covered only frontend and only fifteen minutes, not the intended two-hour lookback, and none of the five direct dependencies. It proves no same-window frontend change exists to blame, nothing more.

The unmeasured checkout edge was the natural place to suspect something hidden. It was not the problem: traces show a complete PlaceOrder path at roughly 22.6ms end to end, largest child GetQuote around 9.3ms, every descendant error-free.

Recommendationservice's own error ratio is flat at zero across sixty-one continuous samples. Read naively that exonerates it. Read correctly it confirms the mechanism: a service that never accepts a connection never returns an error status. It does rule out the error-visible form of a crash cycle and per-replica error contribution; it says nothing about restarts absorbed by retries, memory, restart counts or replica readiness, none of which were retrieved.

## What the evidence converged on

Traces named the edge. Every errored trace has the same shape: a frontend HTTP GET span marked ERROR whose duration is consumed almost entirely by one child, the gRPC call to RecommendationService/ListRecommendations, itself ERROR, at roughly 2.2s, 8.2s and 9.9s against parents only about a millisecond larger. No recommendationservice server span ever appears beneath those client spans, while cart, productcatalog, ad and checkout all show theirs and stay sub-10ms. That excludes frontend-local bottlenecks, a broad backend slowdown, and the loadgenerator as origin, and explains why the frontend error ratio was partial rather than total.

Recommendationservice's logs show normal INFO request intake at steady cadence until T+6m30s, then abrupt silence — no shutdown line, no traceback, no restart banner, and no startup banner anywhere, so the process predated the window and did not restart. At exactly that timestamp, platform-automation lowered the container memory limit to 32m. Confidence is medium and the gap is honest: no kill events, working-set metrics or restart counts were retrieved, and the log result was truncated at that same moment, so the starvation mechanism is inferred from timing and silence rather than observed. The change record shows no prior value, so the size of the reduction is unknown, as is which policy emitted it and whether it touched other services. Indicated fix class is a revert of that limit; whether the condition self-resolved after T+12m is unsettled.
