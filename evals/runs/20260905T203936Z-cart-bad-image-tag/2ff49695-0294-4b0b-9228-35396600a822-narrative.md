# Checkout fails fast at the cart lookup; cart workload absent

## What was visible, in order

Three alerts arrived together at T+0: checkoutservice, frontend, loadgenerator. Twelve services in the blast radius, four crossed edges with no measurement on them. The walk started from checkoutservice on the assumption that the alerting service is the broken one. That assumption cost time — checkoutservice was healthy and reporting someone else's problem.

Traces were the pivot. Across forty failing checkout traces the deepest errored span was always checkoutservice's outbound CartService/GetCart call, nested under order preparation; it errored first and propagated ERROR up through PlaceOrder and the frontend HTTP POST. Everything completed in single-digit milliseconds — roughly 3.4ms of a 3.7ms parent — uniform, no long tail, so slowness and saturation were ruled out. There was no fan-out at all: no shipping, currency, product catalog, payment, email, or ordering spans anywhere, which clears every other downstream service. Every trace showed the identical path, so this was total, not partial.

Cartservice logs then settled it. Startup showed a healthy cache connection with a passing connectivity test and no error lines anywhere; the newest retained line is a clean application shutdown at roughly T−3m35s, with nothing after. At T+0 there is no log coverage because there is no process. The change log for cartservice shows five platform-automation image-reference changes in the window, the nearest landing one second after that shutdown, setting a hotfix tag. The pattern is a flap — the same tag applied and reverted repeatedly — and every applied state used the identical tag, so no new build was introduced. The replacement workload never came back up. Confidence medium; fix class rollback.

## Dead ends worth keeping

The change log for checkoutservice returned nothing across the window, which does rule out an in-window change to that service. But the query was scoped to the seed only, zero hops, so its six dependencies were never covered, and the window began exactly at onset — anything landing in the minutes before the alert fell outside it. Empty here meant unsearched, not quiet.

The checkoutservice error-ratio baseline was actively misleading. It showed a bursty in-window ratio near 0.27 against a flat pre-window 0.67, reading as though the errors predated onset and had improved, and it was used to argue against a single uniformly-unavailable dependency on the grounds that failures looked intermittent. The baseline held nine samples against 240 in the window. The traces contradicted that reading flatly. It did correctly establish that checkoutservice was not failing every request.

Checkoutservice application logs held only info-severity request-entry lines with user id and currency — no completion records, no downstream RPC targets. Steady cadence through onset ruled out a crash, restart, or upstream cutoff, but the stream is structurally incapable of naming a dependency. A currency-path theory died here too: both currencies logged identically and cleanly.

Cartservice metrics were useless and will be again. The error-ratio query returned no samples in the incident window and none in a three-hour prior baseline either — a collection gap predating the incident, not a service going silent. An empty result is not a zero result; it can show neither a spike nor health. Cache-timeout and empty-user-id-validation theories were both tested and failed: connectivity was healthy, a timeout would not produce a 2-3ms failure, and empty-id calls had been served routinely earlier.

## Still open

No container-runtime evidence was gathered: restart counts, exit codes, memory kills, image-pull errors and readiness state for cartservice are all unobserved. So "never started" versus "restart loop" versus "image pull failure" remains unresolved — that is the first thing to pull next time.

Cartservice emits no call-count series in any window, so its health can never be confirmed from metrics as instrumented today. Worth fixing before the next incident.

The roughly three and a half minute gap between the shutdown line and alert onset is unexplained, and the cartservice log result was truncated to the oldest eight and newest thirty-two lines, leaving about twenty minutes before the shutdown unobserved.
