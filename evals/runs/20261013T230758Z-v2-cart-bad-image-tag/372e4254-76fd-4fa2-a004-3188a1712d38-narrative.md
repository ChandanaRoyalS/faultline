# Checkout order failures traced to a cart workload that never came back up

## Summary

Checkout began failing orders in two bursts. Both bursts line up with windows in which cart was running a hotfix image reference pushed by platform automation. In the second window the cart process shut down cleanly and the replacement workload never produced a single line of output - no startup, no readiness, no bind. Checkout's calls to cart first hung and timed out, then began failing instantly because service discovery returned zero addresses for cart. Checkout itself was never at fault. Fix class: return cart to the pre-change image reference and keep it there.

I am using T0 = the first checkout error-ratio threshold crossing. The page landed roughly T+24m, which is why the first instinct - look for something that broke a few minutes before the page - was wrong and cost time.

## What was on the screen first

Alerts fired on checkout, frontend, frontend-proxy and load-generator. That shape is misleading: all four sit on the same request path, and the upstream three inherit the error from the checkout child span. The recorded blast radius of 13 services reflects path propagation, not 13 independent problems.

The first useful number was checkout's error ratio. The baseline hour was flat zero across every sample - no pre-existing error floor at all - then the incident window averaged about 11 percent with peaks near two thirds. Crucially there were two separate threshold crossings, at T0 and again around T+22m, with the signal falling back between them. That said this was not a single escalating condition but an exposure applied, removed, and applied again.

## Traces: where the path actually stops

Tempo settled the direction in one query. In every failing trace the deepest erroring span is checkout's gRPC call to cart's GetCart, made from prepareOrderItemsAndShippingQuoteFromCart. The checkout root error is a straight propagation of that.

Two distinct signatures appear on the same hop, in time order. Around T+21m, a dial timeout of roughly twenty seconds against cart on port 7070 - long enough that the frontend proxy gave up at its own fifteen-second cutoff first. Then from about T+22m onward, failures returning in under a millisecond with a name-resolution error reporting zero addresses. Cart went from present-but-unreachable to absent from discovery entirely.

Failing traces are truncated to nine or eleven spans and simply stop at the cart call. Concurrent successful traces in the same minutes completed end to end in 100-165ms with cart, product-catalog, currency, shipping quote, payment, email and flagd all answering in single-digit milliseconds.

## Cart's own record

Cart logged normal add, get and empty cart-store traffic with no error-level lines right up to T+20m30s. At that moment the hosting lifetime logged an orderly application shutdown, followed by the flag lifecycle manager and feature provider tearing down in sequence. That is the last thing cart ever emitted in the window - nothing for the remaining five minutes, no startup, no readiness, no listen address.

One second after that shutdown, platform automation re-applied the image reference ghcr.io/open-telemetry/demo:2.2.0-cart-hotfix.2 to cart. The change log holds three entries for cart, all from the same automated actor, all image-reference edits to that same tag: applied around T-1m, reverted around T+8m, re-applied at T+20m30s. The final state in the window is the hotfix image, not the reverted one.

Cart's own error ratio corroborates this: a single change point at about T+3m where the ratio reaches 1.0, and twenty sampling intervals in the incident window with no defined ratio at all - meaning zero recorded calls, nothing serving.

## Dead ends worth keeping

Branches I spent time on that did not pay, recorded so the next responder can skip them.

Checkout change history. I queried the change log for checkout first, assuming a bad push to the alerting service. It returned empty - but the window I chose started at the page timestamp and ran forward a day, so it never covered the pre-page hours. The empty result does legitimately rule out a concurrent or post-onset change to checkout, and rules out a silent mid-incident remediation push, but it did not answer the question I thought I was asking. Query backward if you repeat this.

Checkout logs. I pulled every line for checkout over the full hour with the broadest possible selector and got nothing - zero lines of any severity, not merely zero errors. For a service demonstrably serving traffic that is not a clean bill of health. I lost time considering narrower filters; do not bother, any narrower selector is a strict subset of an already-empty result. This is a telemetry gap, not a clue.

Downstream dependencies of checkout. Payment, shipping quote, email, currency and product-catalog were all suspects on the alert list. Failing traces abort before any of those spans are created, and where they do appear in healthy traces they are fast and error-free. Ruled out.

Checkout as the culprit. Checkout's self time in failing traces is sub-millisecond; essentially all elapsed time sits in the outbound cart call, and the error text is transport and resolution, not application logic. No CPU or business-logic theory survives.

Cart being merely slow. Tempting after seeing the twenty-second timeout, and it would have suggested raising timeouts or adding retries. The later sub-millisecond failures with zero resolved addresses kill that: no connection is attempted at all, so no timeout value helps.

Cart's backing store or the flag lookup. Failing traces contain no cart-internal spans whatsoever - requests never reach cart. In healthy traces the store and flag spans are sub-millisecond to a few milliseconds. Cart's own logs immediately before shutdown show store calls at info level with no connection or timeout errors.

A crash or kill of cart. The orderly hosting-lifetime shutdown with ordered component teardown is not what an abrupt kill or unhandled exception produces. Likewise there are no bind-conflict lines and no readiness or health-probe failures anywhere in the window.

A human operator acting ad hoc. All three cart changes are attributed to the platform automation actor.

## Conclusion

Cart is not running the artifact it should be. The process stopped cleanly at T+20m30s and the workload that was meant to replace it, carrying the hotfix image reference, never started. Checkout's cart hop first timed out and then could not resolve an address, and every downstream step of order placement was never attempted. The two checkout error-ratio crossings correspond to the two windows in which that image reference was in effect, and cart's single change point to a 1.0 error ratio falls inside the first of them. Confidence: high. Remedy class: rollback.

## Still open

Three things this record cannot answer.

First, there are no log lines at all for the cart workload after T+20m30s. The evidence cannot distinguish an image that could not be pulled, a process that died before logging initialised, or a pod that was never scheduled. A container or kubelet status query would settle it in one step and should be the first move next time.

Second, checkout returned zero log lines of any severity across a full hour while demonstrably serving traffic. That is a separate observability defect - a label mismatch, a broken shipping path, or something else - and it went unexamined here. It will cost the next responder the same time it cost me.

Third, why the automation churned apply, revert, re-apply within roughly half an hour is unknown. In particular it is unknown whether a manual revert would simply be re-applied again by the same actor. Confirm that before rolling back by hand.
