# Storefront latency traced to a network-layer delay on the cart path

## What was visible, and the one change that explained it

The page was warning-severity: cartservice, checkoutservice, frontend and loadgenerator alerting, twelve services in the blast radius, cartservice named as origin, four unmeasured edges in between. The alert set was the first hint — every alerting service sat on one call path (loadgenerator drives frontend, frontend reaches cartservice directly and via checkoutservice). Nothing off that path complained.

Changes touching cartservice in the surrounding fifteen minutes returned exactly one entry, and it was decisive: at 07:30:09Z, roughly three and a half minutes before the 07:33:30 incident timestamp, a platform-automation principal attached a traffic-shaping container to cartservice's network namespace, applying a fixed 300ms egress delay on eth0 with jitter explicitly zero.

Three properties shaped the rest of the work. It is infrastructure, not application — no image, no version, no flag, no config key, and no cartservice deploy recorded. The actor is automation, not a human pipeline, so there was no obvious owner to page. And zero jitter predicts a uniform latency shift on every egress call rather than a heavy tail or burstiness — a falsifiable prediction to carry into the traces. Because a concrete latency-producing mechanism landed minutes before onset, we held off on organic traffic and capacity explanations until this candidate was tested.

## The metrics dead end, and what the logs did settle

Two dispatches tried to quantify cartservice error rates from the span-derived call-count metric family. Both returned nothing — and critically the unfiltered denominator was empty too, so this is missing series, not a measured zero. Unavailable from that source: error ratio, latency percentiles, CPU, memory, pool saturation, and any comparison against checkoutservice or frontend. It also could not confirm cartservice served any traffic, which briefly kept a total-traffic-stop hypothesis alive. The second dispatch was additionally scoped to cartservice alone with no selector for the downstream candidates it was meant to compare, so it did not answer its own question. If you are here again: check the label schema and collector ingestion before re-querying, do not spend a third dispatch.

Logs closed the traffic-stop branch. cartservice over 07:23:30–07:38:30 returned only routine info-level handler entries — cart read, add item, empty cart — with no error, warning or exception severity, no named backing store or timeout, and no startup or reload lines, so no mid-window restart. Handling continued at a few operations per second through the newest kept line near 07:36:21. checkoutservice was similar: PlaceOrder, payment success, confirmation email, queue write with advancing offsets through 07:37:33, roughly one to two seconds per order — degraded but not stalling, and never aborting before payment. Both results were truncated to the oldest 8 and newest 32 lines, leaving about 07:23:36–07:35:48 on cartservice and 07:23:37–07:37:05 on checkoutservice unobserved, and neither query passed 07:38:30. Sustained errors are excluded, since a continuous stream would appear in the retained 07:37 tail; a burst inside the gap is not.

## Traces, conclusion, and what stayed open

The trace sample turned the change record into a mechanism. Every sampled cartservice Redis client span, HGET and HMSET alike, sat at ~300–310ms across roughly forty samples with a spread of a few milliseconds and not one fast outlier in 200 spans. That tightness is the argument: queueing, pool exhaustion, throttling and GC all produce heavy right tails, never a near-constant mode. The penalty is per-outbound-call — GetCart with one Redis call ~302ms, AddItem with two ~603–612ms — which rules out a single per-request overhead such as an ingress interceptor. cartservice self-time is about 1ms, so there is no slow code path to find. No error or failed spans appear, arguing against retries or backoff.

One unpredicted finding: a further ~300ms sits on the caller hop into cartservice (frontend GetCart client ~605–614ms against server ~302–310ms; AddItem ~908–919ms against ~602–612ms), consistent with the response leg also traversing the shaped interface. Upward propagation is arithmetic: checkoutservice cart calls ~1210ms, PlaceOrder ~2470ms, frontend HTTP ~1517–1530ms, while currencyservice, productcatalogservice, paymentservice, shippingservice, quoteservice and emailservice in the same traces all stay under 20ms. That excludes a mesh-wide problem and, since parent durations decompose cleanly onto the innermost cart spans, excludes frontend or checkoutservice as origin. The traces carried no timestamps and no sub-10ms cart Redis spans, so additivity rests on the change record, not a measured baseline.

Conclusion: cartservice is not failing or erroring — it is waiting on a path the change made slow, and its callers are waiting on it. Confidence high; fix class is a revert of the change.

Still open: why the span-derived metric family returned no series at all, leaving the alerted error rates unquantified; no pre-change baseline was ever observed; whether a short error burst occurred inside the log gaps, or after 07:38:30; whether the caller-side ~300ms really is the response leg, since an ingress-side component would change the remediation; whether the automation will re-apply the shaper after removal, as no intent, ticket or owning workflow was identified; and the Redis backend itself plus the other downstream candidates (productcatalogservice, adservice, emailservice, shippingservice, recommendationservice) were never examined.
