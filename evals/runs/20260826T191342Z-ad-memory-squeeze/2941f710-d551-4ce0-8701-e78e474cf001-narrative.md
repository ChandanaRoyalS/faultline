# Partial frontend error rate traced to an adservice memory ceiling change

## What we saw first

The page came from frontend and loadgenerator. Frontend was the entry point of the blast radius, which by the time triage handed it over covered seven services. The important early read is that frontend was hurting but not down: its span-derived error ratio ran across the whole fifteen-minute window with a clean floor of exactly zero and a worst point near 9.9%. That floor matters more than the peak — it means there was at least one interval inside the window with no errors at all, so the transition happened here, in view, and was not a pre-existing steady state we had wandered into. Roughly nine of ten requests still completed at the worst moment. Anyone arriving at this record expecting a hard outage should recalibrate: this was a partial degradation, the shape you get when one non-fatal dependency spoils only the fraction of requests that touch it.

One caveat that never got closed: the frontend query aggregated by service name only, so it collapsed any per-endpoint or per-instance structure. We never proved which call path owned the failing ~10%.

## Walking the change logs — five empty results

The first working theory was the obvious one: something shipped. We pulled change history for frontend, checkoutservice, productcatalogservice, cartservice, and recommendationservice. All five came back empty — no deploys, no rollouts, no config or flag flips, no rollbacks, no scaling or limit edits.

This is the largest block of dead end in the record and it is worth keeping. It closes, for each of those five services, the deploy-triggered story, the flag-flip story, the in-flight-rollback story, and — most usefully for a responder under time pressure — the instinct to go hunting for 'the last change to roll back.' On those five services there is no such change. Do not spend the first twenty minutes looking for one.

The honest limit on all five: each query covered roughly T-10m to T+5m, a fifteen-minute band, not the full hour before onset that we set out to check. A change landing in the preceding forty-five minutes on any of these services would not appear. Nobody went back and widened the window.

## The one change that was there

adservice was the exception. A single record: at roughly T-4m, an automated platform actor lowered the ad-service container memory limit to 256m. Machine-originated, not an operator push — the shape of an automated rightsizing or policy job rather than a human release.

Three things this record does and does not say. It does place a concrete change four minutes ahead of onset. It does rule out a code deploy or new image on adservice (the entry touches container resource limits only, not a version), and it rules out an application-level config or flag change for the same reason. It does not record the prior value of the limit, so the size of the reduction is unknown from this artifact — we know only where the ceiling landed, not how far it fell. And it was the only change in the window, so there is no competing edit to disentangle.

## Ruling out the catalog path

Before settling on adservice we checked whether the trouble came from further down the read path. productcatalogservice reported a populated error-ratio series at all sixty-one sample points across the window, and every one of them was zero — including the entire stretch before onset. Because the series exists at all, the denominator was non-zero: the service was taking traffic and reporting call counts throughout. These are real zeros, not a gap.

That closes three variants at once: no error onset ahead of the frontend degradation, no gradual ramp preceding it, and no hard outage. The catalog path is not where this started.

## The absent series, and what we read into it

The query for adservice error ratio returned nothing at all — not a zero rate, but no series. Critically the unfiltered denominator was absent too, so this cannot be read as 'adservice had no errors.' It means either the service produced no completed calls in the window, or it is not publishing under the metric name and labels we queried.

The reading we settled on: a container repeatedly killed for exceeding a memory ceiling below its working set emits no completed spans, and so has neither numerator nor denominator. The new 256m limit and the missing series line up. That is the mechanism the conclusion rests on — pressure against a ceiling, not a wrong artifact and not an application misconfiguration. The limit edit is how it began; the killing is what was still happening.

Be aware this is inference, not observation. Nobody retrieved pod events, container logs, or a restart-count metric. The alternative — an instrumentation or labelling gap — was never eliminated, so the 'no traffic at adservice' reading is a soft elimination only.

What weakens it further: cartservice returned exactly the same empty shape, denominator and all. Either cartservice was also degraded, or these span metrics are labelled differently for some services in this deployment. We could not tell which, and that ambiguity cuts directly against the adservice reading, since it offers a benign explanation for the same absence.

## Where the record runs out

Confidence here is medium, and the gaps are specific.

No latency or saturation data was obtained for any service in the radius — the metrics budget was spent (four queries, four used) before that dimension was touched. A contribution from slow downstream calls has therefore not been affirmatively excluded, only crowded out by a more compelling story.

checkoutservice and recommendationservice have nothing but empty change logs behind them; no metric was ever pulled. Their part in a seven-service radius is unmeasured.

Triage reported one unmeasured edge crossed. Which edge, and whether it conceals a seventh contributor, was never resolved.

And the prior memory limit is unrecorded, so we cannot state that 256m is genuinely below the working set, nor what the correct restored value is. That is a real obstacle to the fix, which is a config revert of the limit change.

## If this recurs

Start where we ran out. Pull pod events, restart counts, and container logs for adservice first — one of those confirms or kills the memory-ceiling reading in a single query, which is what we could not afford here. Second, resolve the metric labelling question against cartservice; if its series is simply named differently, the adservice absence loses most of its evidentiary weight and the investigation reopens. Third, before reverting, find the prior limit value from the platform's own history rather than the change record, which does not carry it. Finally, widen the change queries to the full hour — every one of the six we ran covered only a fifteen-minute band.
