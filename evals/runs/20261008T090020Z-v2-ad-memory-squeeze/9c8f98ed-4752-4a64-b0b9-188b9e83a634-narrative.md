# Frontend GetAds failures traced to an ad service restart loop after a memory ceiling change

## What was visible first

The page came from frontend and frontend-proxy; nothing else in the eight-service radius alerted. Frontend's error ratio had been exact zero across the whole two-hour baseline (489 samples, no variance), so this was new rather than chronic. In the incident window the ratio averaged well under one percent with a peak near seven, spiky rather than sustained, with threshold crossings late in the window (~08:43 and ~09:03). That shape ruled out a total frontend outage, ruled out a gradual leak-style ramp, and told us onset was late rather than at the window boundary. No latency or dependency series came back, so at this point we had an error signal with no direction.

Frontend's logs supplied the direction: one repeating outbound gRPC status 14 UNAVAILABLE, failing at TCP connect to a single peer, 172.18.0.19:9555. One address, every line. That killed the broad shared-infrastructure theory, killed DNS (the IP was already resolved), and killed TLS/auth (nothing negotiates before a refused socket). It also killed the instinctive timeout theory: never status 4 DEADLINE_EXCEEDED, always a connect failure. Stack frames placed the calls in server-side rendering, not the browser. Two details stayed loose: the mode shifted from connection refused (~08:39) to host unreachable (09:06–09:07), and the log result was truncated with the oldest kept line at 08:39:23, so pre-08:39 behaviour is invisible.

## Narrowing, and the dead ends worth keeping

Traces reduced it to one hop. The only error-marked trace was user_get_ads: the error propagated from frontend's client span on the ad GetAds RPC up through /api/data, frontend-proxy and the load generator. The failing span was sub-millisecond with no child span on the ad side — an immediate rejection, not a slow backend. Everything else sampled was clean: cart under ~3ms with healthy Redis children, product-catalog under 2ms with healthy SQL children, checkout completing PlaceOrder end to end in ~22ms. End-to-end latencies were 4–37ms, so there was no broad degradation to chase.

The frontend change-history query is the dead end most worth preserving. It returned nothing across a full 24 hours either side — no deploy, no flag flip, no config push, no rollback. An empty answer, but load-bearing: it individually retires four tempting theories. Its limitation matters equally: it was scoped to the seed service at zero hops and says nothing about ad or any other downstream. Reading it as 'no changes anywhere' would have been a serious mistake.

## The cause, and what is still open

Ad's metrics were misleading if read quickly: its error ratio did not rise, it fell to about a third of baseline. The real signal was in the gaps — 33 intervals with no defined ratio value against zero in baseline, meaning intervals with no ad traffic at all, plus thinner sample density. Ad was not degrading; it was intermittently absent.

Ad's logs confirmed it was cycling, not silent: a full JVM boot and the application's own start line roughly every 63 seconds across five cycles (09:02:37 through 09:06:49), after serving normally at 08:35–08:36. Each cycle got past init and agent attach, then ended on benign SLF4J warnings — no exception, no OutOfMemoryError, no shutdown signal, no teardown logging. Termination from outside, on a fixed clock. Each death took the 9555 listener with it, which is exactly what frontend reported at connect.

The change: platform-automation lowered ad's container memory limit to 144m about four minutes before onset, having flapped the same value on at ~25 minutes and off at ~17 minutes before. No deploys, flag flips, scaling events or application config changes for ad in the window, and no human actor. Fix class is a revert of that limit.

Still open. The kill mechanism is inferred — no termination event, exit code, restart count or memory-usage series for ad was ever retrieved, and a fixed ~63s cycle fits a liveness-probe timeout just as well; that was never examined. Onset timing does not fully reconcile: frontend crossings at ~08:43 and ~09:03 against limit changes at ~08:40, reverted ~08:47, reapplied 09:00, with frontend log coverage truncated before 08:39. And six of the eight services in the radius were never queried, with no service-discovery record confirming 172.18.0.19:9555 is in fact ad.
