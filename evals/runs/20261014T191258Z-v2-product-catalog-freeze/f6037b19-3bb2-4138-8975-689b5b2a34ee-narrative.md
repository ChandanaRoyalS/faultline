# Ad upstream refusing connections after a lowered memory ceiling

## What was visible, in order

The page came from the edge: frontend-proxy and load-generator at T+0, frontend about a minute later. Nine services in the radius, seeded at frontend-proxy, seven crossed edges unmeasured. The ordering was the first useful signal — the proxy and the traffic generator noticed together, frontend a beat behind, which reads as a failure being surfaced at the entry point rather than born there. The change log for frontend-proxy over the preceding week was completely empty: no deploys, no routing or timeout edits, no flag flips, no resource adjustments. That removed a self-inflicted change at the edge and pushed the search downstream. Note the scope limit — that query covered the seed only, zero hops, so frontend and the downstream candidates were unqueried rather than cleared.

## Two dead ends worth keeping

Every Prometheus error-ratio baseline failed with HTTP 400 Bad Request — for frontend-proxy, for frontend, and for ad. That is a parsed, deliberate rejection from a live server, not a timeout and not an outage. Three dispatches burned on it before the pattern was recognised. The trap is reading the empty payload as a clean negative: it says nothing about error concentration by route, nothing about frontend's error ratio, nothing about ad restarts or memory against limit. Fix the query before trusting any metric-shaped claim here.

The trace sample looked reassuring and was not. Ten traces, 118 spans through frontend-proxy, zero error spans, every chain running to a healthy leaf; proxy self-time sub-millisecond, catalog SQL 0.2-1.2ms, cart Redis 0.1-0.7ms, slowest trace 59ms. It appeared to exonerate the proxy, the catalog database, the cart Redis layer, and any hanging backend. Then: despite a seven-day request, all ten traces fell inside a ~93-second stretch roughly fifteen hours before onset. Those exonerations hold for that stretch and are worthless for the incident. No error-terminating span was ever seen.

## What actually carried the signal, and what is still open

Frontend's logs broke it open: repeated gRPC status 14 UNAVAILABLE, with the detail naming a refused TCP connection to 172.18.0.19:9555, last attempt around T-19m, recurring every few seconds. A refusal at connect time with a resolved address rules out DNS and discovery; it is not DEADLINE_EXCEEDED, so the upstream was not merely slow; there were no auth or certificate errors; and every onset-era line named one peer, so this was one dead dependency, not broad egress loss. Frontend itself logged continuously with no internal exceptions or restart markers — reporter, not origin. A week-old status-14 line with a dropped-connection detail at the window's start is a different event; ignore it.

Port 9555 pointed at ad by convention. Ad's change log showed a memory limit of 144m imposed at T-24m where none existed before, restored at T-17m, all 28 changes in the window from platform-automation, no human edits, no flag or replica changes, and the only image activity six days earlier. The same lower-then-restore pair recurs — four more times that day alone. Ad's own logs were truncated exactly across the critical minutes; the retained tail shows normal request handling from T-3m onward.

Conclusion, medium confidence: the newly imposed ceiling was below ad's working set, the container was killed for exceeding it, nothing bound the gRPC port, and the refusals propagated to the edge. Fix class: configuration revert. Still open — no restart counts, exit reasons, or memory-versus-limit series were ever retrieved; the 172.18.0.19:9555-to-ad mapping is unconfirmed; the limit was restored at T-17m yet alerts fired at T+0, so either alerting lagged or something else was still active; and the other services in the radius were never queried.
