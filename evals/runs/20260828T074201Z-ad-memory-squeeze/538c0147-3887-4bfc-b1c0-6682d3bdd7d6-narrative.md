# Ad path outage from an adservice memory ceiling reduction

## What alerted and what we saw first

Three alerts landed close together: loadgenerator, frontend, and adservice. The responder started at the frontend, which is where the pain was visible to users, and where the blast radius nominally began. The first useful reading was frontend's own outbound error ratio: non-zero, peaking around 7.4 percent of calls, with a full 61-point series and no gaps in collection. Two things followed from that number. First, frontend telemetry was healthy, so an absence of signal elsewhere would mean something real rather than a broken scrape. Second, 7.4 percent is a partial-failure signature — the overwhelming majority of frontend calls were still completing. This was never a frontend-wide outage, and treating it as one would have wasted the first ten minutes. The series also touched zero inside the window, so this was an onset rather than a long-standing elevated baseline. The aggregation was by service name only, so it could not tell us which dependency was failing; that had to come from elsewhere.

## Naming the failing dependency

Frontend logs settled the question quickly. The errors were gRPC client status code 14 UNAVAILABLE, and the newest lines in the window (roughly T+14m to T+15m relative to the start of the query span) consistently named DNS name resolution failing against the adservice target on port 9555. No other downstream host appeared in any kept line. The failure mode mattered: name resolution, not connection refused, not reset, not deadline exceeded. The client was never reaching a listening socket at all, which points upstream of the adservice process — at service discovery or endpoint records. Stack frames sat entirely in the Node grpc-js receive-status path, confirming frontend was healthy enough to originate calls and was only propagating a downstream connectivity error. One nuance worth keeping: the earliest kept line, at roughly T+7m, was also code 14 but carried a no-connection-established detail rather than a name-resolution detail. The intervening lines were dropped by log truncation, so we could never date the transition between the two details. Repetition through the last kept line meant the condition was still active when the query ended.

## A dead end worth keeping: the adservice metric

The obvious next move was to pull adservice's error ratio around its own alert. That returned nothing at all — not zero, but an entirely empty result. Both the error-filtered numerator and the unfiltered denominator failed to match. No request rate, no error rate, no latency, no saturation. The trap here is reading an empty panel as a quiet, healthy service. It is the opposite: empty means the service stopped reporting. This cost some time but was informative in the end, because it ruled out the standard span-derived call metric as a triage path for this service and forced the investigation into logs, traces, and change records. If you find yourself in this position again, skip straight past the metric panel.

## Bounding the blast radius with traces

Before chasing adservice further, we checked whether anything else was actually broken. Trace sampling from the frontend showed the ad path was the only place errors lived. The two ERROR traces in the sample were frontend GET spans of roughly 9ms each with a failing child client span for AdService/GetAds completing in under a millisecond — failures returning immediately, as you would expect when resolution fails before a connection exists. Checkout, cart, catalog, currency, payment, email, and recommendation traces all completed cleanly. This also killed a plausible-looking distraction: the slowest requests in the window were checkout POSTs at around 34ms, dominated by the shipping-quote preparation subtree (about 18.5ms, of which GetQuote was ~10.6ms resolving into shippingservice's HTTP client span and quoteservice's handler). That is a real latency profile, but it is not an error and it is not this incident. The checkoutservice hop was fully instrumented end-to-end, so there was no blind segment hiding a second problem there. Sub-millisecond error spans and clean checkout traces together are inconsistent with timeouts or knock-on failures from the slow path.

## What adservice was actually doing

adservice logs were not silent, which itself ruled out a broken log pipeline. Early in the window the service was handling ad requests normally, each line carrying trace and span identifiers. From roughly T+7m onward the content changed character completely: the only lines emitted were JVM and Java-agent startup banners — tool-options pickup, VM class-sharing warning, OpenTelemetry agent version. No ad request handling appeared again. The banner triple repeated at least eleven times, initially clustered seconds apart and then settling into a near-exact 63-second cadence running through the end of the window. Every cycle reached the agent version banner and then stopped; no application-level line ever followed before the next restart. That is a crash loop during or shortly after JVM initialization, with the process never reaching readiness. There were no shutdown, drain, or termination messages anywhere, so this was not a graceful stop or a completed rolling deploy. It also means restarting the pod would have achieved nothing — it was already restarting itself on a fixed cadence and failing the same way each time.

## The change

The adservice change log for the window contained exactly one entry: platform-automation lowered the container memory limit on ad-service to 256m, roughly six minutes before the incident marker and within seconds of the point where the logs switch from serving to startup banners. The actor was automated, not a human operator, which makes this a policy- or controller-driven mutation rather than an ad-hoc edit. No deploy, no image rollout, no replica-count change, no service definition or DNS-record edit appeared. That last absence matters: the frontend symptom looked like a DNS problem, but nothing touched DNS. Resolution failed because the crash-looping pod never became ready, its endpoints were withdrawn, and the target had nothing behind it to resolve to. The chain reads: memory ceiling lowered, JVM cannot complete init inside it, container killed and restarted repeatedly, no ready pod, endpoints gone, frontend resolution fails on 9555, ad path errors at roughly 7.4 percent of frontend calls while everything else completes.

## Ruled out along the way

Frontend was checked for changes first, on the assumption that the service where symptoms surfaced was the service that broke. The change log over the roughly 15-minute window around onset returned nothing of any kind for frontend — no deploys, no config edits, no flag flips, no rollback or mitigation attempts. That closed off the same-window frontend-deploy hypothesis cleanly. Note the coverage limit honestly: the query spanned only the 15 minutes around onset, not the preceding hour, and covered frontend alone. Also ruled out: a different downstream as the error source (every kept frontend error line named only adservice on 9555); timeouts or deadline-exceeded (all errors were code 14, failing before a connection existed); adservice being up but refusing connections or returning application errors (the failure was at name resolution); TLS or credentials rejection (empty metadata, no handshake status); and the whole thing being an already-resolved transient (the same failure repeated through the last line in the window).

## Fix and what remains open

The fix class is a revert of the memory limit change. Three things were still unresolved when this record was written, and a future responder should treat them as work rather than settled facts. First, we never obtained direct runtime confirmation of an out-of-memory kill — no exit-code or working-set evidence was pulled. The memory ceiling as the mechanism is inferred from change timing plus a JVM-init crash loop, which is a strong inference but an inference. Second, the prior memory limit was not recorded in the change entry, so the correct value to restore is unknown, and it is unclear whether the automated actor will simply re-apply 256m after a manual revert. Pin or exempt the service before reverting. Third, loadgenerator alerted but was never dispatched on, and change logs for the other five services in the blast radius — cartservice, checkoutservice, productcatalogservice, recommendationservice, and the rest — were never queried. A concurrent second contributing factor is therefore not excluded, only unobserved.
