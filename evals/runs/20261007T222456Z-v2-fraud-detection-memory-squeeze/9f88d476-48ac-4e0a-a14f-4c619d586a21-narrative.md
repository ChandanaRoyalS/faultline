# fraud-detection stops staying up after its memory ceiling is lowered

## What was visible first, and the wrong instinct

The page named one service: fraud-detection, severity critical. The first instinct was to look for errors, and that instinct was wrong. Error ratio came back below baseline: mean roughly halved with comparable maxima, no sustained departure. The real signal was in the gaps - 49 of 80 incident samples had no defined value at all, meaning intervals with zero traffic, against full baseline coverage. A wider ninety-minute pull agreed: 49 of 320 undefined, zero undefined in baseline. The low error rate was an artifact describing a thin remnant of served traffic, not health. The failure mode was absence, not degradation.

Logs then showed no application lines whatsoever - only JVM and OpenTelemetry agent startup banners, repeating on a roughly 60-second cadence near T-3m to T+1m and twice in the oldest retained lines around T-30m. Discrete restarts, not gradual decline, and already underway at the window start. A hard limitation surfaced here: the service falls back to a no-op SLF4J logger, so any in-process exception is discarded before collection. Loki was returning lines throughout, so this is an application-side gap, not a pipeline outage. Searching logs for the cause was a dead end by construction.

## Dead ends: flagd and the clean trace island

Traces complicated things before clarifying. There were 10 traces and 20 spans, all between 22:12:23 and 22:24:30 - a twelve-minute island in a thirty-minute window, with nothing before and a silent ten-minute tail. Inside it everything was fine: inbound work arrives as asynchronous order messaging, every trace closed out in 8-95ms with no error status. That ruled out crash-looping with no telemetry, refused callers, hung handlers, and fraud-detection as a latency bottleneck.

The one error path was fraud-detection's own outbound long-lived stream to flagd, ending on a server-side timeout after ~600s. It looked like a lead and was not: it sits in its own isolated trace while the order traces in the same period are clean and fast. Chasing flagd further paid nothing - the change log held no entries for flagd across the full 24 hours, and flagd's error ratio ran below its own baseline with continuous span-metric coverage, so it neither errored nor went dark. The useful fact from traces was the shape, not the content: the service demonstrably worked during one specific interval.

## The change log, the control window, and what is still open

Three changes landed on fraud-detection, all container resource limits, all authored by platform-automation. No code deploys, no config pushes, no flag toggles, no human actor - which collapsed the search to one parameter. A 160m memory limit was applied about 30 minutes before onset, removed at 22:11:47, and re-applied identically at 22:25:01, seven minutes before onset.

That removal period is a free control, and the fit is exact: every trace falls inside 22:12:23-22:24:30, within the unconstrained interval; the cold-start banners cluster on both sides, while the limit is in force. A JVM cannot live inside a 160m ceiling, so the process is killed shortly after start and restarts repeatedly, never reaching steady-state serving. It produces no errors because it never gets far enough to answer a request. Confidence high. Fix class: revert the configuration.

Three gaps to close rather than inherit. The kill was never directly observed - no container memory, kill-event, exit-code or restart-count series was retrieved, so the mechanism is inferred from restart cadence plus limit timing. Application logging is dead, so a second concurrent in-process problem would be invisible. And nobody explained why automation applied, removed, and re-applied the same limit, which means a manual revert may simply be re-applied.
