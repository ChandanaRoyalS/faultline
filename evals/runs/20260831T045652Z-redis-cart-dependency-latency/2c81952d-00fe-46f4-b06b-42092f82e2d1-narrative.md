# Cart path slows to a fixed ~300ms per cache round trip

## First look: four alerts, no errors

The page named cartservice, checkoutservice, frontend and loadgenerator at warning severity, blast radius twelve services, cartservice as the starting point. Four services alerting together reads as something breaking loudly, so the first move was to treat cartservice as an origin that had started failing. That was wrong, and disproving it consumed the first three dispatches.

Two separate metric queries against cartservice returned only a span error ratio, flat at zero across every sample, with a populated denominator — a real zero, not a scrape gap. Fifty-eight and sixty-one samples respectively, unbroken through onset. That closed three hypotheses: no errored RPCs, no crash or restart, and no backend problem surfacing as propagated hard errors. Checkoutservice came back identically flat over sixty samples, so there was no error onset anywhere to correlate against.

The dead end worth recording: both cartservice metric dispatches returned the error ratio and nothing else. No latency percentiles, no CPU or memory, no connection-pool or cache-call metrics were ever retrieved. What actually inflected at T+0 was never confirmed from the metrics side.

Logs were quiet in an unhelpful way. The result was truncated to the oldest eight and newest thirty-two lines, discarding roughly T-10m to T+2m — precisely the transition. What returned, T+2m to T+3m, showed routine informational handler entries, many distinct users per second, complete cart flows finishing, no error text and no dependency named anywhere. That ruled out a crash, a deadlock, and a dry-up of inbound traffic, but also killed the hope that the service would name its own culprit. Two oddities remain unresolved: nothing was logged after ~T+3m despite a window running to T+5m, and the selector matched one label value only.

## Traces carried the answer

In cartservice traces nearly all elapsed time sits inside the named cache spans (HGET, HMSET), each ~300-307ms, while the enclosing handler exceeds its child by only 1-3ms. The handler is doing nothing but waiting.

The arithmetic follows. GetCart wraps one HGET at ~302-312ms. AddItem makes two sequential round trips and lands at ~602-618ms — double, purely for calling twice. EmptyCart wraps one HMSET at ~302-308ms. The cost propagates upward unchanged: checkoutservice PlaceOrder at ~647-669ms is almost entirely its GetCart and EmptyCart legs, and frontend POST spans reach ~908-946ms.

Several alternatives died here. Cartservice's own logic, serialization and gRPC layer are not the slow segment. No other downstream explains it — product catalog ~0-3ms, currency near zero, shipping ~14-17ms, payment ~0.4ms, email ~3-6ms. Checkout orchestration is not the source. The frontend-to-cart hop is not the source; caller spans exceed server spans by 1-3ms. It is not read- or write-specific, and not confined to one endpoint or user path.

The most suggestive detail is uniformity: the ~300ms is near-constant across operations, endpoints and trace ids, which reads as a fixed stall floor rather than load-driven queueing.

## Change history, conclusion, and what is still open

The change log for cartservice across the onset window was empty — no deployments, no config updates, no flag flips, nothing touching cache dependency configuration. Productcatalogservice was equally empty, which also closes rollback as a path there since no prior version exists in the window. That is the whole of the change coverage.

Conclusion, at medium confidence: cartservice serves every request successfully, but each cache round trip costs a near-constant ~300ms and the handlers only wait. Best-fit remediation is a restart of the cache tier.

Open items, in the order I would attack them. First, the cache backend was never dispatched to at all — its latency, saturation, connection state, change history and any delay-related configuration are wholly unestablished, and the ~300ms is inferred purely from the client side. Second, no latency, saturation or pool metrics exist for cartservice, so a pool-wait contribution cannot be excluded and the exact onset inflection is unconfirmed. Third, change coverage is missing for the cache component, frontend, checkoutservice and the sync-edge peers, so an edit elsewhere remains possible; because no change explains the onset, remediation is genuinely uncertain and a config revert could be the real fix. Finally, four unmeasured edges were crossed and eight of twelve affected services were never queried.

Note for the reader: this is not the two prior cart incidents in the corpus where the process was not running. Here the service is up, scraped, logging, and succeeding — only slowly.
