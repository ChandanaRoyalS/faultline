# Ad service crashlooping under a lowered memory ceiling

## What was visible, in order

The page named frontend-proxy at T+0, then frontend, load-generator and ad. Ten services sat in the blast radius; only four alerted and eight edges were never measured.

The proxy's error picture was the least useful evidence in the record. Across 125 samples it averaged about 2.8%, peaked near 11%, and touched zero — bursty, not broken. The query aggregated only by service and status code, so it could not separate an upstream-returned error from a client-side deadline, and it carried no per-timestamp series, so nothing in it places the first error at or after the page. The pre-incident baseline returned no samples at all, meaning the tidy "rose from zero" reading is an artifact of missing data. Do not reuse that framing.

Asking whether ad was erroring produced the longest dead end. Its ratio averaged roughly 0.3% over 96 intervals with no sustained departure, which read as exoneration. The detail that mattered was that 29 of those intervals had no defined ratio at all: the denominator was zero, so ad served nothing in a third of the window. The low percentage was computed only over the intervals ad was alive to answer. A second pull aimed at memory, restart counts and exit codes returned none of those series.

Traces were a dead end too, usefully. Ten traces, 134 spans, no error status anywhere; GetAds completed in 0.3–4.7ms with no outbound call consuming time. That kills the hang-to-deadline, bottleneck and slow-dependency stories. What traces cannot show is a process that is not running.

## The log read that turned it, and the change behind it

Reading ad's raw log stream changed the picture. At the oldest end, around T-51m, ad is plainly healthy — ad requests handled with trace context, routine no-baggage notices. Then from roughly T+15m to T+20m, at least eight distinct JVM startup sequences repeat inside about four minutes. Several reach the application's own "service starting" line before vanishing again. That is a loop, not one restart, and it rules out a clean redeploy and a container that never boots. The agent attaches successfully every cycle. Logging-provider warnings accompany each startup, so in-process errors may never be written at all.

Searching those logs for the runtime's out-of-memory token returned nothing. For a while that read as refutation; it is better read as a discriminator, since a kill delivered from outside the runtime leaves the process no chance to say anything.

Change history for ad across a full day held exactly one entry: an automated update lowering the container's memory ceiling to 144m at T-4m. No deploy, no image move, no environment edit, no second candidate. Only the new value is recorded, so the size of the reduction is unknown. The flag daemon's change log was entirely empty, and ad logged no flag-evaluation line of any kind — but that query ran forward from the alert only, so pre-incident flag activity was never actually checked.

## Where it landed, and what is still open

The reading that fits everything: under the lowered ceiling ad cannot stay resident. It starts, reaches application init, is killed from outside the runtime, starts again. That explains the missing out-of-memory token, the intervals with no traffic, the deceptively clean error ratio in the intervals it did serve, and the 0-to-11% bursty profile at the edge — a dependency that keeps vanishing and returning produces exactly that shape. Because the ceiling is configuration on the container, recreating the container returns it under the same ceiling; restoring the prior configuration is the fix. Confidence medium.

Three gaps. The kill was never directly observed — no memory-against-limit, restart-count or exit-code series was ever retrieved, so the mechanism is inferred from the restart loop plus timing. There is a roughly sixteen-minute hole at the front: the proxy alerted well before the first visible restart cycle, and with no per-timestamp proxy series the earliest errors are unattributed. And eight edges and nine other services were never measured, so whether ad alone accounts for the full blast radius is untested.
