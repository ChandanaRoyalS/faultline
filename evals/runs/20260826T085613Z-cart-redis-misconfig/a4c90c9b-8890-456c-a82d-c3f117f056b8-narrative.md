# Cart-path failures across the storefront traced to a cartservice Redis address change

## What the responder saw first

The page arrived from three places at once: frontend, loadgenerator, and checkoutservice. Blast radius was scored at twelve services, severity critical, with frontend named as the entry point. That framing is worth flagging up front because it is misleading in a specific way: frontend was where the pain was visible, not where it originated. Triage also noted four edges in the graph that were never measured; they stayed unmeasured through the whole investigation.

First hard look was at frontend's own error ratio. The series swung between zero and roughly 39% of requests at peak inside a fifteen-minute slice. That shape mattered more than the number — an intermittent burst with real zeros in it, not a flat elevated floor, and not a total outage. Whatever this was, most requests were still succeeding.

Checkoutservice looked the same in kind and worse in degree: up to about two-thirds of requests erroring at peak, and again touching zero at other sample points. Two tiers showing the same intermittent signature, one much harder hit than the other.

## The dead end that cost the least and mattered most

With frontend named as the start, the obvious move was change history on frontend. It came back completely empty — no deploys, no config edits, no flag flips. Tempting to read that as "nothing changed anywhere," and it is not that at all. The query as executed covered one service and a fifteen-minute window, and the source is marked untrusted, so an out-of-band edit would not have appeared. What it does legitimately kill is the reflex response: there is no recent frontend change to roll back, so a rollback-first play had no target.

The useful consequence was negative pressure — it pushed the search off frontend and onto the call graph.

## Traces narrow it to one edge

The trace sample is where the shape of the failure became clear. Every error-bearing trace in the window was a POST path, and every erroring span was fast — frontend POST spans in the 0.2–7.4ms range, innermost failing spans under a millisecond. Nothing was slow. That single observation removed a whole family of hypotheses: no timeout cascade, no saturation, no latency sink to hunt for.

The deepest error-carrying span on cart-add traces was frontend's outbound call to CartService/AddItem, and in one trace it bottomed out in a frontend tcp.connect span marked error. Connection establishment, not an application error returned by a downstream handler. On the checkout side, PlaceOrder errors originated at checkoutservice's CartService/GetCart child span, while the parent order-preparation span carried no error status — checkout was aborting at the cart lookup, before doing anything else.

Several suspects were cleared here by absence. No spans naming accountingservice, currencyservice, or paymentservice appear anywhere in the 200-span sample, so none of them could be the sink; execution never reached them. Productcatalogservice, recommendationservice, adservice, and featureflagservice all completed cleanly at normal durations in the same window, which also cleared frontend itself: GET paths through frontend were fine. Only cart-touching POST paths carried error status.

## The cartservice telemetry hole

Next step was metrics on cartservice, and it returned nothing — no series for the error numerator and, critically, none for the unfiltered denominator either. This is the easiest place in the record to make a mistake in either direction. It is not a clean zero error rate, so cartservice could not be cleared. Nor is it proof of a crash, since a scrape or label-naming break produces the same emptiness. No pod restart counts or replica availability came back to separate the two. Treat the empty series as "unmeasured," and go to logs.

## Logs settle it

Cartservice logs at the very start of the window (~T-10m relative to the worst of it) show ordinary cart operations — adds, gets, empties — with no errors. So it was healthy then, and the onset is later.

From roughly T+2m after onset through the end of the retrieved interval, cartservice is in a tight loop: attempt a Redis connection, hang 20–45 seconds, fail, throw an unhandled ApplicationException out of RedisCartStore.InitializeAsync / EnsureRedisConnected at Program.Main, die, restart every 30–60 seconds. The connection target logged on each attempt is host redis-cart on port 6380, ssl disabled, abortConnect false.

Because the exception escapes from store initialization in Main, the process never reaches request handling — which is exactly why the frontend saw a connect-level error rather than a cart RPC error, and why the metrics query found no request-volume series to divide by. Three further explanations died here: it is not intermittent connectivity that self-heals (every observed cycle ends the same way, no successful connect is ever logged); it is not TLS, since ssl is disabled and no handshake occurs; and it is not auth rejection, since the failure is an inability to reach the endpoint at all with attempts hanging tens of seconds, not a credential refusal.

## The change

Change history on cartservice returned exactly one entry, roughly two and a half minutes before the recorded onset: platform-automation applied an environment update setting the cart service's Redis backend address, with a non-default port value. The prior value is recorded as absent — the variable was newly introduced, so the service moved from an implicit default target to an explicit one.

Single candidate, automated actor, environment edit rather than a code deploy or a flag flip. That also rules out an organic explanation (traffic surge, hardware, noisy neighbour) as the default reading, and rules out a human remediation edit inside the window.

The chain reads: config edit introduces redis-cart:6380 → cartservice cannot connect and crash-loops before serving → frontend's AddItem and checkoutservice's GetCart fail at connection establishment → intermittent error bursts confined to POST/cart paths at both tiers, while read paths stay clean. Confidence high. Fix class: revert the config.

## What is still open — read this before reverting

The most important gap is directional. Nobody queried the Redis instance itself for its listening port or health. If redis-cart was supposed to move to 6380 and failed to, then 6380 is the correct value and the fix belongs on the Redis side, not as a revert of cartservice. Verify the backend's actual listening port before rolling anything back.

There is a roughly two-minute hole between onset and the first observed crash-loop line; that log interval was never retrieved, so the exact first failure and whether old pods drained gradually are unknown.

Blast radius on the change is unestablished. The change queries covered only frontend and cartservice — not the nine downstream dependencies, and not other environments. The frontend query also used a fifteen-minute window where ninety minutes was intended.

The cartservice metrics gap remains undiagnosed: crash-looping pods and a scrape/label break are both consistent with what came back, and nothing was retrieved to distinguish them.

The four edges triage flagged as unmeasured were never probed. Loadgenerator alerted but was never examined on its own terms; the rest of the evidence suggests it is only restating storefront failures, but that is inference, not measurement.

Finally, there is no post-change verification anywhere in this record. Nothing confirms that changing the Redis address back restores cartservice startup. Treat the fix as a hypothesis and watch cartservice logs for a successful Redis connect on rollout.
