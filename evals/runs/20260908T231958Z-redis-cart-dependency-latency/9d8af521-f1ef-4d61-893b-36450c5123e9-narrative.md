# Cart operations blocked on a fixed ~300ms delay to the cart cache

## What was visible first, and the dead end

The page opened on cartservice at warning severity, twelve services in the blast radius, with frontend, checkoutservice and loadgenerator alerting about fifteen seconds later. Nothing in the initial signal named a failure kind: no error alarm, no service-down alarm.

The first check — is cartservice alive — came back clean and led nowhere useful. Its log stream across the half hour spanning onset holds only routine cart get, add and empty operations, steady at several per second at both ends of the window, with no startup banners, no exception traces, no cache connection errors, no lifecycle messages. Note the stream was truncated to the oldest eight and newest thirty-two lines, so the onset minute itself is inferred from health on both sides rather than observed.

The expensive dead end was metrics. The cartservice error-ratio query returned no samples at all — and, critically, none in the preceding two-hour baseline either. The denominator series is equally absent, so this is an instrumentation or label gap, not traffic vanishing at onset. Two tempting stories died here without replacement: no error spike can be sourced, and the silence is not an onset event because it predates the incident. It also leaves cartservice with no latency baseline. A future responder should skip this query and go straight to traces or pod-level metrics.

## Traces: where the time actually goes

Ten traces were available, all landing inside a single ~14-second slice near the end of the window. Within it the picture is unambiguous: GetCart 301–306ms, EmptyCart ~302ms, AddItem 603–611ms, while handler self-time is 0.3–1.3ms. Nearly all elapsed time sits in the cache client spans, each HGET and HMSET costing ~300–306ms. AddItem doubles because it does one HGET then one HMSET, each paying the same toll.

The tightness matters as much as the size — every cache operation lands within a ~5ms band around 300ms. That is a fixed cost per operation, not queueing or contention, and it scales with operation count rather than load.

Ruled out against this evidence: cartservice's own logic (the handler is blocked, not busy); neighbouring services (catalog, currency, payment, shipping, email all sub-millisecond to ~11ms); the frontend and the gRPC hop into cartservice (self-times 0.4–4ms, client-to-server offsets 1–3ms); a read-only cache problem (writes pay the same); and retry storms or N+1 fan-out (exactly one operation per call path). No span carries an error status. The latency propagates upward — frontend GET 305–310ms, POST 906–921ms — which explains the downstream alerts. checkoutservice was checked separately and cleared: its error ratio during the window ran about half the baseline mean, with the same spiky pattern and identical maxima present beforehand.

## The change record, the conclusion, and what is still open

The cartservice change log holds twenty entries, all by platform-automation, no human actor, in tight apply-and-revert pairs of three repeating kinds: a hotfix image tag, a REDIS_ADDR override to a cache endpoint on a non-default port, and a traffic-shaping container attached to the cart-service network namespace with a fixed egress delay. The third matches the observed signature exactly.

The contradiction must be preserved: by its own account the log says the shaper was removed about two hours before onset with no later attach, the last REDIS_ADDR revert landed 1.7h prior, the last image revert 2.3h prior, and nothing changed in the hour before onset. Taken at face value it alibis every mechanism it describes. Taken with the traces, one source is wrong. The likely reading is an unrecorded re-attach, but that is inference. The source is untrusted.

Conclusion: cart requests are blocked on a fixed delay in the network path between cartservice and its cache. Confidence medium; fix class is a configuration revert, then confirm cache operations return to single-digit milliseconds.

Still open: (1) whether the shaper was re-attached after its recorded removal; (2) the cache backend was never queried, so a server-side ~300ms floor is unlikely but not excluded; (3) coverage is one ~14-second slice, so onset time and whether the delay has cleared are unestablished.
