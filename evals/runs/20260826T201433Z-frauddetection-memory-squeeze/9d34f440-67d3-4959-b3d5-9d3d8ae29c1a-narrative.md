# frauddetectionservice silent restart loop after an automated resource-limit edit

## What the responder saw first

The page named a single service, frauddetectionservice, at critical severity, with the alert timestamp landing about ten minutes into the window I ended up reviewing (I'll call the start of that fifteen-minute window T+0). Blast radius as presented was one service and no unmeasured edges crossed, so there was no immediate pressure to chase neighbours. The first instinct — check whether the service was throwing something new — turned out to be the wrong first move, and it cost time. What actually mattered was the shape of the log stream, not its content.

## The change that landed just before onset

The change history for the service returned exactly one entry in the window: at roughly T+4m an automated platform process lowered the container memory limit on the frauddetection-service resource spec to a value recorded as '200m'. No named human operator is attached; the actor is machine, consistent with an automated resource-tuning process rather than someone typing during a response. That single entry also does the work of clearing several suspects at once — there was no deploy, no image rollout, no flag flip, and no manual edit in the window. Equally, it means the service cannot be waved off as change-quiescent and the origin pushed upstream. One thing the entry does not carry is the prior value of the limit, so the size of the reduction is unknown from this evidence alone.

## What the logs actually showed

Normal Kafka consumption logging — records consumed with an incrementing counter — runs from the start of the window and stops around T+1m. Nothing resembling application work appears after that. From about T+4m15s the stream is nothing but repeated container and JVM startup sequences: the JAVA_TOOL_OPTIONS pickup line, the JVM boot-classpath class-sharing warning, the OpenTelemetry agent version banner, and then silence until the next cycle begins. There is a burst of fast restarts for the first minute or so, after which the loop settles into a near-constant cadence of roughly one restart every sixty-two seconds, running through about T+11m. At least eight distinct startup sequences are visible in that span. Crucially, there is no exception, no stack trace, and no ERROR-level line anywhere in the returned lines. Each cycle gets far enough to initialise the agent and then dies without saying anything.

That combination — successful JVM boot, silent death before any work, on a metronomic cadence — is what carried the conclusion. A process that is terminated from outside leaves no application-level trace; a process failing on its own usually does.

## Dead end: the class-sharing warning

The only warning-class line in the whole stream is the JVM boot-classpath class-sharing warning. It is tempting, because it is the sole non-informational line present. It is also worthless here: it appears exactly once inside every single startup sequence, including the ones long before and long after anything interesting. It is startup boilerplate, not a signal that changed at onset. If you find yourself reading it closely, move on.

## Dead end: span-derived call metrics

Two separate attempts to characterise the incident through the span-derived call counters returned nothing. An error-ratio query over the full window matched no series at all — not the error-status numerator and not the total-call denominator. That is worth stating plainly because an empty result is easy to misread as a flat, healthy zero. It is not; it is absence of series. It means no throughput signal, no error-rate spike to time against the change, and no way to tell whether traffic collapsed or whether the service was simply never instrumented into that metric family under the service_name label being queried. Further slicing of the same series will also come back empty. The second attempt on this path was in effect a repeat of the first and produced no new ground.

## Reading and confidence

The reading is that the process could not fit inside the memory ceiling it was permitted and was terminated for it, repeatedly. The automated limit edit at T+4m is how that state was entered; it is not itself the mechanism. Confidence is medium, not high, and the honest reason is that the mechanism was inferred from timing plus the shape of a silent death, never confirmed directly. Fix class is a revert of the configuration.

One detail deserves a second look from whoever picks this up. The recorded value '200m' uses a milli-unit suffix. For a memory quantity that would be a fractional byte, not two hundred mebibytes. If the automation wrote a CPU-style unit into a memory field, the value is malformed rather than merely tight, and the reading shifts from 'limit set too low' to 'limit set to something nonsensical'. Nothing available resolves whether that string is the raw spec value or an artefact of how the change log renders it.

## What was never checked

The container-level series that would settle this were never queried: the pod's resource limits, the container working-set bytes, the restart counter, and the pod's last-terminated reason or exit code. Any one of those would convert a medium-confidence inference into a confirmed one, and they are the first thing to run if this recurs.

The prior memory limit is unrecorded, so neither the magnitude of the reduction nor whether the JVM heap configuration was ever compatible with the new ceiling can be established.

The log stream stops entirely at about T+11m, roughly three and a half minutes before the window ends. Whether the pod went into backoff, was descheduled, or logging itself failed is unknown — and so is the state of the service at the time this record's conclusion was reached.

Blast radius beyond this one service was not investigated. Consumption stopped at about T+1m; the resulting backlog and any effect on upstream producers is unmeasured.

Finally, nobody established what prompted the automation to resize this container, or whether the same process has applied or will apply comparable limits elsewhere. That is the recurrence question and it is still open.
