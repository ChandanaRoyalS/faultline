# frauddetectionservice crash loop following a memory ceiling change

## What the responder saw first

The page named a single service: frauddetectionservice. Blast radius stayed at one service throughout, and no unmeasured edges were crossed, so there was never a moment where the investigation had to guess about a neighbour it couldn't see.

The first instinct was to characterise the failure with metrics, and that instinct went nowhere. The standard error-ratio comparison for the service returned nothing at all — not a flat line, not a drop to zero, but an empty result in both the incident window and the baseline window before it. Because the baseline was equally empty, the emptiness could not be read as the service going dark at onset; it predated the alert by at least half an hour, and a second, wider run over the preceding three hours confirmed the same emptiness. The honest reading is that this service does not emit call-count span metrics under that service_name label at all. That is a real gap worth fixing, but it is not the incident.

## The signal that actually carried

Logs were where the picture arrived. Early in the window the service is doing ordinary work — steady Kafka record-consumption lines running through roughly 09:41:49. After that, application output stops entirely and is replaced by a three-line JVM startup sequence: the java tool options pickup, an OpenJDK class-sharing warning, and the OpenTelemetry javaagent version banner. That triple repeats at least twelve times between about 10:05:00 and 10:12:01 — first a burst of restarts seconds apart, then settling into a stable cadence near 62 seconds that runs straight through the 10:10:45 alert.

What is absent matters as much as what is present. No exception, no stack trace, no panic, no graceful-shutdown line. Each cycle ends immediately after the agent banner and the next one begins. Nothing resembling steady-state work follows any restart, so the process is dying during early initialization, before it ever reaches the consumer loop.

## Hypotheses eliminated on the way

Several plausible readings were closed off by the same log evidence. An application-level crash with a named cause: ruled out, because nothing is written to stdout beyond startup. A clean scale-down or operator stop: ruled out, since there are no shutdown lines and the process keeps returning on a tight cadence. A hung or wedged single process: ruled out, because fresh JVM banners mean the process identity is recreated each cycle rather than one process stalling. A routine rollout producing one restart: ruled out by twelve-plus restarts across roughly seven minutes.

On the change side, the history for this service in the window is complete and non-truncated, and contains only resource_limits edits. No code deployment, no version bump, no dependency upgrade, no feature flag flip. All three entries are attributed to platform-automation rather than a person, which closes off the ad-hoc-human theory. And the timing does not exculpate: the closest change lands about five minutes before onset, tight enough to be consistent with causation.

## The cause

About five minutes before onset, platform-automation applied a 200m memory ceiling to the frauddetection-service container — a JVM workload that had previously run with no explicit memory limit. A JVM plus the OpenTelemetry javaagent cannot finish heap initialization inside that ceiling, so the container is terminated during early startup. That matches the log shape exactly: startup banner, silence, restart, with no application output and nothing for the process to complain about because it never gets far enough to complain.

The most persuasive detail is that the same lowering had already been applied roughly 2.2 hours before onset and reverted about 2.1 hours before onset, restoring the unlimited state. The pre-onset change re-applies a constraint someone or something had already decided to back out. That repeat-then-revert-then-reapply pattern is what tips the conclusion toward the constraint rather than the code. Fix class is a configuration revert: restore the workload to its prior unlimited state, or size the ceiling to what a JVM with the agent actually needs.

Confidence here is medium, not high, and the next section explains why.

## What remains unproven

The kill reason was never directly observed. No OOMKilled counter, no container_memory_working_set_bytes series, no restart-count series was queried. The exhaustion mechanism is inferred from log shape plus change timing. It fits well, but a responder returning to this should pull those container-level series first — the error-ratio result contains no memory or restart data and neither supports nor excludes the theory.

Onset is not pinned. The log result retained only the oldest eight and newest thirty-two lines of the window, so the true start of the loop lies somewhere between 09:41:49 and 10:05:00. If the loop began before the limit change landed, the change cannot be the trigger and the whole conclusion collapses. This is the single most load-bearing unknown.

The natural control experiment was never run. Service health during the earlier apply and revert was not measured. If the service crash-looped then too and recovered on revert, the case is essentially closed; that check is cheap and was skipped.

Three smaller threads are open. Why the service emits no call-count span metrics under that label at all is unexplained and predates the incident — possibly an instrumentation or label mismatch that is masking other signal. Downstream impact was never assessed: the service consumes Kafka order records and nobody looked at consumer lag growth or effects on upstream producers during the minutes of non-consumption. And nobody established what drove platform-automation to re-apply a limit that had been reverted two hours earlier; if that logic is still live, a manual revert may simply be re-applied.
