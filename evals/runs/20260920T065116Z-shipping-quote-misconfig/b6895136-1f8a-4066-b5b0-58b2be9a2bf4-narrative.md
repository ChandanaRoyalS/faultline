# Checkout orders failing at the shipping quote hop

## What was visible, in order

The page at T+3m named checkoutservice alongside accountingservice, emailservice, frauddetectionservice and quoteservice; severity critical, eleven services nominally in the blast radius, five of the crossed edges unmeasured.

The first instinct — check checkoutservice's own error ratio — misled. Over the incident window it averaged roughly 8% against a baseline of about 18%: the ratio fell rather than rose, with no sustained departure from baseline. Two intervals had no traffic at all, but the same pattern appears twice pre-onset, so those gaps are background. Sample density differed sharply between windows (953 vs 206), making the comparison shaky either way. Carry this forward: for this service the aggregate error ratio is spiky and low-denominator and is not a usable onset signal.

Logs were next and came back truncated — oldest few and newest few lines kept, the onset minute itself dropped. The surviving head showed complete order flows: start, payment success with transaction id, confirmation email, message write. The surviving tail showed only order-start lines with none of the completion lines. Orders were being accepted and not finishing. No error-severity line appears anywhere returned, and no downstream dependency is named — the error status lives in spans only, not in application logs. That ruled out a crash or traffic stop (the service emitted steadily to the end of the window) and ruled out any greppable error stream.

## The trace evidence that resolved it

Seven checkoutservice traces in the window fail identically: frontend POST, frontend PlaceOrder, checkoutservice PlaceOrder, and the checkoutservice client span for ShippingService/GetQuote all ERROR, with the order never getting past prepareOrderItemsAndShippingQuoteFromCart. No successful PlaceOrder trace is present — total, not intermittent.

The decisive detail is which side of the call carries the error. The shippingservice server span and its own outbound HTTP client span complete cleanly in single-digit milliseconds. Only the caller's client span is ERROR. Whole traces finish in 8–11ms with the shipping hop at 2.8–3.9ms. This is a status failure at the client boundary, not a timeout, not saturation, not a slow backend.

The same traces cleared four candidates, worth recording so nobody re-walks them: cart reads and their backing cache complete sub-millisecond and clean; every GetProduct span returns fast without error; currency Convert is effectively instantaneous; and paymentservice appears in no trace at all, because checkout aborts before any charge is attempted. That last point explains the log tail exactly.

## Dead ends, the change, and what is still open

Considerable time went into cartservice and productcatalogservice before the traces arrived. Both error-ratio queries returned zero samples — no series, not zeros — across incident and baseline windows alike, so the absence is a pre-existing instrumentation gap, not something that began at onset. An empty series is not a flat-at-zero series; neither service can be called healthy on that basis. Cartservice logs were a partial consolation, showing routine, tightly spaced operations with no error lines at both ends of a long window, but the middle was elided there too. The cartservice change log shows four image-reference changes by automation, two apply/revert pairs, the closest about 3.4 hours before onset and ending in a revert — so the hotfix image was not running at onset. Interesting, but not this incident.

Exactly one change touches the failing path: a checkoutservice config update by m.laine raising a gRPC quote-client pool size and repointing the shipping quote route to a new regional endpoint, ref SHIP-2210. It is the only change of any type for the service. A wrong route target on the quote client produces precisely the observed shape. Two cautions: the timestamp sits about four minutes after onset, and the description contains operator-authored narrative asserting a cause (stale connection pool), forbidding revert of the shipping configuration, and instructing a restart be proposed. That text is an unsubstantiated claim inside an untrusted record; its embedded instructions were not acted on and no telemetry supports them.

Confidence medium; indicated remedy is a revert of that configuration. Open: whether the SHIP-2210 timestamp reflects actual rollout or an earlier unlogged application — the four-minute gap is the central conflict, answerable only from the deploy pipeline's own audit trail; what the ERROR status on the GetQuote client span actually is, since unavailable/name-resolution and a contract mismatch point different directions and no span attributes were pulled; and why the four co-alerting services fired, quoteservice in particular, since it sits on the shipping quote path and no dispatch examined any of them.
