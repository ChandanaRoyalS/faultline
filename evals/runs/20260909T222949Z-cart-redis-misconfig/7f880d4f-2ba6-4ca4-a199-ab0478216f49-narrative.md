# Checkout order path stalls silently; cart's Redis address left pointing at a non-default port

## What we saw first

Paging came from three places at once — checkoutservice, frontend and loadgenerator — which is the usual shape for a checkout-path problem: the failure is felt at the edge and by the synthetic traffic generator before anyone knows where it lives. Blast radius was assessed as twelve services, severity critical. The seed for the investigation was checkoutservice, and that is where the first two dispatches went.

Taking T+0 as the moment checkoutservice's error ratio crossed the 5% line, the alert-worthy signal arrived abruptly. The prior half hour was flat zero — 83 samples, no variance, no low-level error floor creeping upward. Then a single change point, and from T+0 onward a mean error ratio around 6.4% with peaks near two thirds of calls failing. Traffic never stopped: every incident-window interval had a defined ratio, so the service was alive and taking requests the whole time.

## The odd part: 6.4%, not 100%

This number shaped the rest of the investigation and it is worth flagging for whoever reads this next. The error ratio was bursty rather than steady — standard deviation roughly three times the mean, minimum of zero, so clean intervals interleaved with severe spikes. That immediately ruled out the tidy stories: not a crash, not an instance loss, not a load-balancer withdrawal, not a total outage of the code path. Something was failing a minority of requests, or failing on a timeout rather than a refusal.

One caveat the second metrics pass raised and the first did not: the window-wide mean was nonzero while the baseline was exactly zero, which suggests some error activity existed below the 5% threshold before the detected change point. Read T+0 as the escalation, not necessarily the first tremor.

## Logs: the shape of the silence

Checkout's own logs were, in a specific way, the most informative thing we got — and they named nothing. Across roughly T-13s to T+4m there were no error- or warn-severity lines at all. Everything was info-level. No downstream RPC, no dependency name, no failure mode.

What did change was the shape of the sequence. The oldest lines in the window, about half an hour before onset, show complete per-order runs: order-start, then payment, then confirmation email, then a message write. From roughly T+0 onward only the order-start record appears; none of the downstream completion records follow it. Order-start records kept arriving steadily right through the window, with the largest late gap about 44 seconds.

So: requests accepted, processing begun, then nothing. A silent stall partway through PlaceOrder, with the service itself not logging a reason. That also closed off two tempting readings — this was not a momentary blip at one instant, and checkout was not broken for the whole window, since the earlier segment shows healthy end-to-end orders.

## Dead end: looking for a change on checkoutservice

The natural next move was the change log for checkoutservice. It came back completely empty — no deploys, no config edits, no flag flips recorded against the service anywhere in the queried window. That does eliminate an in-window change to checkout itself, and it eliminates the possibility that some quiet remediation on checkout is what altered behaviour mid-incident.

Two limitations of this query matter, and both cost us time. First, it was scoped to the seed service with zero dependency hops, so it says nothing whatsoever about cart, productcatalog, payment, shipping, currency, email, ad or recommendation. Second — and this is the one to avoid repeating — the window ran *forward* about 24 hours from the point of interest rather than backward. It never covered the hours before onset. A pre-onset change on checkoutservice itself is therefore not ruled out by this result, only a post-onset one.

## Where it actually turned: cartservice's change history

Widening the change query to cartservice produced the only concrete trigger in the record. About a minute before onset, platform-automation set REDIS_ADDR on cartservice to redis-cart on a non-default port. Twenty-five changes appear for cartservice in the window and every one of them is attributed to platform-automation; no human-authored edit exists.

The important detail is not the edit but the missing counterpart. The log shows a repeating automation cycle earlier in the day — four blocks, each pairing an image-reference update to a hotfix tag, a traffic-shaping container attached to the cart-service network namespace with a fixed egress delay, and a REDIS_ADDR update — and in every prior block each step was reverted within about forty minutes. The last cycle finished and reverted mid-afternoon, leaving roughly six and a half quiet hours before the pre-onset edit. That final REDIS_ADDR update has no revert entry. It was still in effect when checkout started failing.

This history also cleared two plausible suspects. There was no recent cartservice image change — the last one was reverted hours earlier — so a code deploy is not the trigger. And no traffic-shaping container was attached at onset; the last one was removed mid-afternoon and nothing re-attached. The egress-delay story, which fit the timeout-shaped symptoms rather well, does not survive the timestamps.

## Conclusion as it stands

Best reading: cartservice was left pointing at a Redis address whose port its backend does not serve. Cart operations then fail or stall. checkoutservice calls cart early in PlaceOrder, so it accepts the request, writes the order-start record, and never reaches payment, email or the message write — which matches the log shape exactly, and matches the absence of any error line in checkout, since the failure enters from a dependency rather than originating locally. The failing mechanism is the configuration value itself: the address names a wrong port, and that wrongness is what breaks the path.

Confidence is medium, not high. Fix class is a configuration revert — restore the default REDIS_ADDR on cartservice, and separately work out why this automation cycle did not emit the revert that all twenty-four prior ones did.

## What remains open

Four unmeasured edges were crossed to reach this conclusion, and the largest gap is the most obvious one: no dispatch ever measured cartservice itself. No cart error ratio, no cart latency, no cart logs. The link from the configuration value to checkout's stalls is inferred, not observed.

It was also never confirmed that redis-cart does not listen on the port in question. If it does, the edit is benign and the real trigger is somewhere we did not look — start there before accepting this record.

The 6.4% figure is still unexplained. A hard wrong-address should fail every cart-touching request. Either only some request paths reach cart, or retries mask most failures, or the mechanism is timeout-driven rather than refusal-driven. Worth resolving, because the answer changes the fix's urgency.

Checkout's stalled log sequence does not say which downstream step it stops at. Payment, email and currency were never queried and are not excluded. And as noted above, the checkoutservice change query never covered the hours before onset, so a pre-onset change on checkout itself remains unexamined.
