# Critical alert on paymentservice with a healthy request path

## What was visible, in order

The page came from paymentservice at T+0, severity critical, with an initial blast radius of three services and two unmeasured edges. That estimate was drawn before anyone had checked whether payment was actually failing, and it shaped the first stretch of work.

Logs came first and were quiet in a way that should have been the tell. Every returned paymentservice line is info level: paired charge-request and transaction-complete records, request-to-completion deltas sub-millisecond to about a millisecond both immediately before and immediately after T+0, and successful charges continuing through T+2m on the same host. No errors, no rejections, no crash, no named downstream.

The nearest upstream agreed. checkoutservice logs are all info severity, and from about T+12s onward each PlaceOrder is followed within ~20ms by a successful payment with a transaction id, a confirmation email, and a message write with monotonically advancing offsets. Its error ratio is a defined zero across all 128 incident-window samples, which also proves it was still serving traffic.

Then the metric that mattered: the error-ratio query for paymentservice returned no samples at all. Not zero — nothing — and equally nothing in the preceding baseline half hour. Empty is not healthy and it is not an outage either; it means the span-derived call-count series is simply not present in the backend under that name and label set.

## Dead ends worth keeping

The largest one: a trace query returned 21 traces and 200 spans for paymentservice, all structurally complete end to end, every Charge span correctly parented under checkout. It looked like proof that span export was fine and killed the telemetry hypothesis for a while. It was scoped to a window running roughly T-12h to T-6h. It says nothing about export state after the change five minutes before onset. Re-scope that query first if you are re-running this.

That same result flagged shippingservice's outbound call into quoteservice as 17–24% of trace self-time. Real, consistent, and unrelated to the page; it absorbed attention. Payment spans there are 0.0–0.5ms and could not account for anything.

Smaller ones: a ~3.5 second gap in charge traffic straddling T+0 looked meaningful until comparable ~25s and ~34s gaps appeared later in the same window. A hostname change between the oldest and newest log blocks suggests a pod replacement somewhere in the truncated middle; it was never dated and never connected to anything.

## Where it landed, and what is still open

Every recorded change to paymentservice in the window is the same environment-variable edit to one key, the OTLP traces exporter endpoint, made by platform-automation. No deploy, no rotation, no flag flip, no dependency bump, no human operator. The key was set and reverted three times; the most recent set landed about T-5m and was still applied at onset, pointing span export at a loopback address where nothing listens.

Conclusion: the request path was healthy throughout and the alert fired on missing telemetry, not failing requests. Fix class is a configuration revert. Confidence medium — the loopback effect is inferred from the change record plus the empty series, never observed directly during the incident window.

Still open. First, no span query was ever run against the incident window itself; do that before accepting this. Second, two earlier identical set/revert cycles, roughly five and eleven hours before onset, produced no page, so either a second condition coincided or the threshold was only crossed this time. Third, no request-rate, latency, CPU, memory or saturation data was ever retrieved for paymentservice, so a real but silent degradation cannot be fully excluded — and separately, checkoutservice's baseline half hour averaged ~15% errors that vanished at the window boundary, a transition running the wrong direction for this page and possibly an earlier, unrelated problem.
