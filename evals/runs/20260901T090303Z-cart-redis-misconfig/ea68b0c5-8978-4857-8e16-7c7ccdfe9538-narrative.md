# Checkout failures traced to a cart cache endpoint configuration change

## What was visible, in order

Three alerts landed together at about T+2m20s: checkoutservice, frontend, loadgenerator. Triage called it critical, twelve services in the blast radius, entry point checkoutservice, four unmeasured edges crossed — so part of the graph was going to stay invisible no matter what we asked.

The first instinct was that something shipped on checkoutservice. Change history for the service across the onset window came back completely empty: no deploys, no config edits, no flag flips. That closed three lines at once, including the one management wanted — there was nothing on checkoutservice to roll back. Caveat worth recording: that query covered only about ten minutes before onset and only checkoutservice itself, not its synchronous dependencies. The answer held up later, but the coverage was narrower than the question deserved.

Metrics for checkoutservice showed a span error ratio peaking near 0.67 with clean zero points in the same window — enough to confirm checkoutservice was on the failing path and that this was episodic rather than a standing error floor. No latency percentiles and no per-downstream breakdown were returned, so the metric could not name the culprit. Two readings we took from it were wrong: the sub-1.0 peak looked like partial impact, and the defined ratio looked like proof traffic was flowing normally. Traces later contradicted the first. Treat the aggregate ratio as a presence signal, not a severity measure.

## The logs that pointed sideways, and the traces that broke it open

checkoutservice logs cost us the most time. In the healthy baseline each accepted PlaceOrder is followed within about twenty milliseconds by a payment-completed line, an order-email line, and a message-write line. From roughly T+16s onward only the first line ever appears. Orders keep arriving at a steady several-per-minute rate in both USD and CAD and none reach a terminal log. Every line is severity info — no exception type, no stack, no named downstream host. A service failing on a dependency usually says which one; this one did not, which pushed us toward theories about checkoutservice's own internals.

Useful eliminations from those logs: checkoutservice did not crash or restart, it kept accepting intake throughout; requests were not rejected at entry by shedding, validation, or auth; the stall was not currency-specific; and it was not the message-bus write alone, since the payment line that precedes it was also missing. The logs also corrected our anchor — the stall was already present at T+16s, well before the alert, so we had been scoping queries around the wrong moment. A loose thread we never pulled: checkoutservice stopped emitting any lines after about T+5m while intake was still steady.

Traces did in one query what the logs refused to. Every failing checkout trace had the same shape — frontend POST, frontend PlaceOrder, checkoutservice PlaceOrder, prepareOrderItemsAndShippingQuoteFromCart, then a cart retrieval child span carrying the error and propagating it upward. The prepare span is the only non-error span, marking the cart call as the originating point. End to end these run one to seven milliseconds: fast failures, not timeouts. No catalog, shipping, payment, currency, or email child spans appear at all across forty sampled traces — checkout aborts during cart retrieval before those are attempted. That killed the hidden-untraced-leg theory, the catalog/shipping theory, the recommendation/ad theory, the deadline-exceeded theory, and the checkoutservice-own-logic theory. Every sampled trace failed identically, which contradicts the partial-impact reading from the error ratio; trust the traces.

## cartservice, the cause, and what stays open

cartservice metrics were a hole. The error-ratio query matched no series — not just an empty numerator but an empty unfiltered denominator too. Request rate, latency and cache saturation for cartservice are unmeasured for this incident. We deliberately refused to read that emptiness as zero traffic; a scrape gap, collector problem, or label mismatch looks identical. Any dashboard assuming cartservice exports standard call metrics under that label is silently blank.

cartservice logs were decisive. At baseline, well before onset, it logs ordinary cart operations with no errors. From about T+4m to the end of the window it is in a startup loop: connect attempt to the cart cache, connect failure, unhandled ApplicationException terminating the process from Main. The stack runs EnsureRedisConnected → InitializeAsync → Main — bootstrap, not a request path — so the service never reaches a serving state. Restarts recur every thirty to sixty seconds across at least five cycles. Every attempt names host redis-cart on port 6380 with TLS disabled, and each hangs ten to forty seconds before failing: timeout-shaped, with no connection-refused message anywhere. That ruled out a request-handler bug, a different dependency, an actively refusing cache, and restarts driven by memory or probes.

Change history for cartservice held exactly one entry, at T+0: an automation actor set the cache address environment variable, previously unset, to redis-cart:6380 — a non-default port. One change, unambiguous attribution, an automated push rather than a human edit. That value is the cause: cartservice cannot connect, crashes at bootstrap, cart retrieval fails instantly for callers, and checkoutservice and frontend propagate it. Fix class is a config revert. Confidence high.

Still open, and each of these deserves its own look. We never verified what redis-cart is actually listening on; a TLS listener with TLS disabled client-side, or a blocked network path, fit the same timeout shape and the same remediation, but the wrong field differs. Onset timing disagrees across sources — checkoutservice completions vanish at T+16s, the alert fires at T+2m20s, the cart loop is only observed from T+4m. checkoutservice going log-silent after T+5m is unexamined and could be a secondary failure. Only two of the twelve named services were dispatched, so the other nine are assumed propagators without test. And nobody established why the automation pushed this value, which decides whether a revert simply gets re-applied.
