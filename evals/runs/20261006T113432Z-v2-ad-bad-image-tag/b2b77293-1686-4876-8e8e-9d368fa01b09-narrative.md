# Frontend gRPC UNAVAILABLE against a vanished ad endpoint

## What was visible, in order

The page came from frontend and frontend-proxy, tagged eight services and critical, which set an expectation of something broad. That expectation was wrong.

First check was frontend itself, and it had not regressed. The span-derived error ratio around onset averaged about 2% against a baseline hour closer to 4.5%, with no step change at onset. The series is noisy in both windows, so occasional spikes toward 7-9% are this service's normal texture. Note the gap: no latency percentiles and no per-downstream breakdown were pulled, only the aggregate ratio.

Frontend's logs resolved the picture. Every error line is the same shape: gRPC status 14 UNAVAILABLE, a host-unreachable connect failure against one address, 172.18.0.19 on port 9555, with no connection ever established. Continuous from the oldest retained line around T-5m through roughly T+2m. Lines after onset carry a cached last-error timestamp from seconds before onset, i.e. failing fast against remembered state.

That single detail closed several doors. Not a deadline or timeout, since nothing got far enough to have one. Not an upstream application error, since no request reached upstream logic. Not DNS, since a concrete pod IP was resolved before the network layer refused. Not TLS or authorization, since the failure precedes any handshake. Not broad frontend degradation, since no other upstream address appears anywhere.

## Following the address

On the topology assumption that 9555 is ad, ad's logs end at roughly T-6m with an orderly gRPC server stop driven by a JVM shutdown hook and a clean-shutdown confirmation. Nothing after. The preceding forty-odd seconds are unremarkable: routine request handling, no errors or warnings, traffic continuous to the last second with no visible drain.

So ad was healthy, then deliberately stopped, and six minutes later frontend was still dialling where it used to be. That ordering rules out a crash, rules out gradual degradation, rules out a malformed request category as trigger, and rules out any explanation living inside ad's own code path.

Ad's change history is the most interesting record here. Nine changes in two hours, all from platform-automation, all the same type: image reference set, then reverted to unset, then set again, cycling every eleven to thirteen minutes. The last set landed one second after the shutdown line. Only one artifact is ever involved, so the obvious bad-new-build story does not fit — there is nothing new to be bad. The mechanism is the churn itself: during the unset phases nothing listens on 9555. No config change, no scaling change, and no human operator appears anywhere in those nine entries.

## Dead ends, and what is still open

Frontend's change history returned nothing at all over roughly twenty-four hours — no deploys, no config pushes, no flag flips — and is explicitly empty rather than truncated. That kills the frontend-deploy and frontend-config theories. But the window begins at onset and runs forward, so it says nothing about the hours before. Do not over-read it. Flagd gave the same empty answer with the same window defect; it is a static surface and deserves no further attention.

The sharpest trap: the ad error-ratio query was run against a window one day before the incident. At face value it shows a service pinned at 100% errors across 209 samples with zero variance, 312 undefined intervals, and an empty incident window. It was initially read as a dramatic finding. It may describe an entirely different period. Re-run it before building on it.

Still open. The address-to-service mapping is unproven — everything after the frontend logs rests on 172.18.0.19:9555 being ad, which came from convention, not evidence. Why the automation is flapping the image reference, and whether ad came back on a later cycle, is unestablished. Six of the eight services in the blast radius were never queried.

Frontend is the reporter, not the origin. Fix class is rollback: stop the loop and pin the image reference to a stable artifact so a listener exists on 9555 continuously. Confidence medium, for the three reasons above.
