# Accounting cannot persist orders: database credential rejected at connection open

## What the page looked like

The alert named a single service, accounting, at critical severity. Nothing else in the graph was implicated, and the starting point was not a node the topology knew about — so the first few minutes were spent deciding whether accounting was the origin or a mirror of something upstream. Throughout this record T+0 is the alert reference point; the observation window the responders worked in opened at T-30m and closed at about T+2m.

## First look at metrics, and the first dead end

The opening move was a baseline comparison of accounting's span error ratio over a six-hour span ending roughly at T+0. It came back flat zero — 217 samples, mean, min and max all zero, standard deviation zero, and a baseline that was also identically zero. Read literally this said accounting was serving traffic and failing nothing, which would have pushed the whole investigation upstream. That reading was wrong, and it cost time. The six-hour window diluted a problem that had only existed for tens of minutes, and the request-rate, latency, heap, CPU, pool and queue-depth series in the same request were never returned at all, so there was no second signal to cross-check against. The one thing worth keeping from this pass is the denominator argument: the ratio was defined at every point, which requires non-zero call volume, so accounting was never silent.

## Narrowing the metric window

Re-running the same comparison against a two-hour window ending at the close of the incident window told a different story: mean error ratio up about 6.4x over baseline, peaks near a third of all calls failing, variance widened. ## The logs settle it

A broad log pull over the window gave the decisive evidence. At the oldest retained lines, around T-30m, accounting was processing orders normally — info-level consumer records with full order payloads, no warnings. By the newest lines, around T+2m, it was emitting a fatal PostgreSQL exception: SqlState 28P01, password authentication failed for the application role, raised during SASL authentication at connection open. The stack runs from the message consumer's ProcessMessage into EF Core SaveChanges, which asks the pool for a connector and is rejected before any statement is issued. So messages are being consumed and cannot be written.

That single stack eliminates a cluster of plausible theories at once. The database is not down or unreachable — it accepted the socket, ran the authentication exchange, and returned a structured server-side FATAL. The broker is not at fault; the message was already in hand. It is not schema drift, a migration or a bad query; nothing reached the server. It is not pool exhaustion; the pool opened a connector and the connector was refused on credentials. And it will not self-heal, because a credential rejection is deterministic on every retry.

## When it actually started

A filtered pull on the error code pinned the earliest rejection at T-22m. Nothing matching appears between the window opening at T-30m and that point, so onset sits inside the window rather than being inherited from before it. Rejections continue every few seconds through the end of the window — including after the last configuration write at roughly T-3m, which therefore neither caused the onset nor repaired it. Every line names the same single database role, which argues against a broad authentication-system outage. Both log results were truncated to the oldest eight and newest thirty-two lines, so the stretch from T-22m to about T+0 is unobserved and the volume of failures through the middle cannot be characterised.

## What changed

Five changes landed on accounting in the ~45 minutes before T+0, all by the same actor, platform-automation, and all touching one surface: the DB_CONNECTION_STRING environment variable. They alternate — set, reverted, set, reverted, set — at approximately T-42m, T-36m, T-22m, T-16m and T-3m, leaving the variable in the 'set' state when the incident ran. The alternation reads like an automated reconciliation loop contending over the value rather than a deliberate operator action; no human actor appears in the record.

Other shapes of change are absent from the window: no deploy or release event, no flag toggle, no second configuration surface, no human ad-hoc edit. The change surface is narrow and it is exactly the database connectivity string.

The temporally honest reading is that failures begin at T-22m, aligned with a mid-sequence write, not the final one at T-3m. The value the automation settles on is itself wrong, and that wrongness is the failure.

## Conclusion

Accounting cannot persist consumed order messages because every database connection open is rejected server-side on password authentication for the application role, before any SQL is issued. The cause is the credential carried in DB_CONNECTION_STRING, which platform-automation rewrote five times in an alternating pattern and left in the state whose credential the server will not accept. Confidence is high. The remediation class is reverting the configuration to the known-good value and stopping the automation loop from re-applying the bad one.

## Dead ends worth remembering

Three things did not matter and consumed effort. First, the six-hour error-ratio baseline, which showed a clean zero and nearly sent the investigation upstream; window choice decided the answer, not the data. Second, the hypothesis that the last write before the alert was the trigger — the error log predates it by about nineteen minutes. Third, the whole family of dependency, network, broker, pool and query theories, every one of which the single authentication stack disposes of in one line. If you arrive at a service-local critical alert and the metrics look clean, go to the logs before you widen the blast radius.

## Still open

The change record redacts the password, so nothing in the evidence shows which of the two alternating states holds the credential the server accepts. No one queried the database's own logs or its secret-rotation history, so a server-side password rotation around T-22m remains unexcluded as a contributing or alternative explanation — it would fit the onset time as well as the mid-sequence write does. Both log results were truncated, leaving roughly T-22m to T+0 unobserved. Request rate, connection-pool utilisation and consumer lag were requested twice and returned neither time, so the backlog of unpersisted messages is unquantified.
