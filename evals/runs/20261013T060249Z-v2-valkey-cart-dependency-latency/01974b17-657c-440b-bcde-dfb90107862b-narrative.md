# Frontend cart endpoint override behind a page that named cart

## What was visible, and why cart was a dead end

At T+0 a warning page landed naming cart as origin, with cart, frontend, frontend-proxy and load-generator alerting; checkout joined about a minute later and was never dispatched on. The investigation started on cart and found nothing. Cart's error ratio is flat at exactly zero for every sample in the incident window and identically zero across the preceding two-hour baseline, with zero variance - no ramp, no contaminated baseline. Its logs bookend the window with ordinary ValkeyCartStore work (AddItem/GetCart/EmptyCart) across distinct user sessions, ruling out a crash or a lost Valkey connection. The change log for cart is empty: no deploys, no config edits, no flag flips. Caveats worth inheriting: that change-log query only covers the window forward from T+0, not the hours before it, and the cart log result was truncated to the oldest eight and newest thirty-two lines, so T+0 itself sits in the unreturned middle. Only the error-ratio template was fetched; cart's request rate, latency and saturation were never measured.

## What turned up on frontend

Frontend's change history over twenty-four hours touches exactly one key: the cart dependency address. It was set to a non-default endpoint and reverted five times, all by the same platform-automation actor, nine to nineteen minutes between each set and its revert - a loop fighting a desired-state controller, not a human or a release. No other frontend setting was modified. The frontend process started fresh at about T-3h46m and within roughly three seconds logged a single gRPC UNAVAILABLE, connection refused to 172.18.0.24 on port 7071 - the non-default port from that change log. Independently, frontend's error ratio has one change point at about T-3h43m and then holds near 3.2x the four-hour baseline mean across roughly 969 samples: a sustained elevated floor, not a single burst. Conclusion: the failure is in frontend, not cart. The wrong address is itself the mechanism - requests to that port are refused - and the page on cart and its neighbours is caller-side propagation. Fix class: revert the configuration and stop the loop re-applying it. Confidence is low.

## Dead ends and open questions

The evidence disagrees with itself in one important place. The change-log reading explicitly ruled out the override being live at T+0, since it was reverted about 3.6 hours earlier; our conclusion goes the other way, arguing the process booted with the override and may hold the boot-time value regardless of later reverts. Nobody read the running frontend environment directly, which is the one check that would settle it. Note too that the same set/revert pattern recurs a day earlier, so the behaviour predates this incident. Other lines that went nowhere: nothing explains T+0 itself - every frontend signal predates it, logs stop at about T-54m and traces at about T-10m, which could be a crash, a log-pipeline break, or sampler truncation. The refused connection was first dismissed as a boot-time readiness race because it appears once and never recurs; that dismissal only falls once paired with the change log. The last frontend activity before the logs stop is a cluster of gRPC NOT_FOUND responses for several product identifiers against product-catalog - application-level answers from a reachable dependency, possibly a second unrelated problem, never chased. And traces sampled in the half hour before the page are all clean: ten traces, 167 spans, no error spans, a full checkout fan-out touching cart, currency, product-catalog, shipping, payment, email and flagd all returning in milliseconds, with sub-10ms catalog SQL children.
