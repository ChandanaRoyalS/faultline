# Fraud detection service restart loop following an unreverted memory ceiling change

## What the alert showed

The page named a single service — frauddetectionservice — at critical severity, with no downstream services flagged and no unmeasured edges crossed. That framing is worth noting up front because it shaped the first half of the investigation: with a blast radius of one, the instinct was to look for something wrong inside the service rather than something done to it. Treat T+0 as the moment the alert fired. Everything below is offset from that point, and the single most useful correction the record can give you is that T+0 is not onset. The failure was already roughly six minutes old when the page arrived.

## First look: metrics, and why they told us nothing

The opening move was a baseline comparison of the service's error ratio, built from span-derived call counts, over the incident window against the equivalent period before it. It came back empty. Not flat, not healthy — empty. No samples in the incident window and none in the baseline.

The tempting read is that the service stopped serving and its telemetry went dark at onset. That read is wrong, and the baseline is what disproves it: a service that died at onset would still leave healthy samples in the pre-incident window. The uniform absence across both windows means the underlying call-count series does not exist for this service name at all — a naming mismatch, a missing span-metrics path, or no instrumentation. Widening to a two-hour baseline reproduced exactly the same emptiness, which closed the question.

So the metric channel was neither exculpatory nor incriminating. It was simply not a channel. Any responder who reaches for the error-ratio dashboard here should expect blank panels and move on quickly rather than spending time convincing themselves the blankness is meaningful. Request rate, latency, CPU and memory were never actually retrieved; only the error-ratio template ran.

## Logs: the shape of the failure

The service's own log stream carried the whole story, in shape if not in words.

Early in the window, around T-30m, the service was plainly healthy: it was consuming order records with a steadily advancing counter, continuing through roughly T-29m. Normal operation preceded whatever happened next.

Starting at about T-5m31s, the stream turns into nothing but JVM startup boilerplate, repeating as a fixed three-line sequence — the tool-options pickup, a benign class-data-sharing notice, and the telemetry agent's version line. The first three cycles land seconds apart (T-5m31s, T-5m26s, T-5m17s), then the pattern settles into a near-exact ~62-second cadence and holds it: T-4m34s, T-3m41s, T-2m39s, T-1m36s, T-34m... more precisely, cycles continue at roughly one-minute intervals right through T+28s and T+1m31s. At least ten distinct startups appear.

Two negatives matter more than the positives. First, there is no exception, no stack trace, no error-level line, and no shutdown message anywhere. The process comes up, prints its banners, and vanishes. Second, once the loop begins, no record-consumption lines appear at all — every instance dies before it does any work. The service processed nothing from onset onward.

A process that reaches its agent banner and then dies silently on a fixed external cadence is not crashing of its own accord; it is being terminated by something outside it, on a supervisor's clock.

## Change history: what was done to the service

The change record for the service in the window contains exactly one kind of entry: nine memory-limit mutations, all attributed to the platform automation actor. No code releases. No flag flips. No human-authored edits.

Eight of those nine form four matched pairs stretching back about sixteen hours — the limit lowered to a constrained value, then restored, each pair lasting somewhere between ten minutes and an hour. The transitions are consistently unset → constrained → unset, which reads as an automation loop applying and reverting the same ceiling rather than a progressive tightening.

The ninth is the one that matters. At roughly T-5m44s the memory ceiling was lowered to a 200m value, and unlike the four prior cycles, no restore ever followed. The constrained state was still in effect when the log stream broke, thirteen seconds later.

## Conclusion, and how firm it is

The cause is the unreverted memory ceiling. A JVM that starts cleanly, reaches its agent banner, and is killed silently on a fixed external cadence beginning thirteen seconds after its memory ceiling is cut to 200m is being killed for exceeding that ceiling. The fix class is a straight revert of the change.

Confidence is medium, not high, and the gap is honest: the termination reason was never observed. No container or kubelet evidence was collected — last-terminated-reason, working set against the 200m ceiling, and the restart counter are all unretrieved. The conclusion rests on timing and on the shape of the log stream, not on a recorded kill.

## Dead ends worth keeping

These were checked and eliminated. If you land on this service again, you can skip them.

A bad release. The change history for the window contains no deployment or release events whatsoever — every entry is a limit mutation.

A feature flag. No flag-change entries exist for the service in the window.

A human operator making an ad-hoc edit. All nine changes carry the automation actor.

A novel one-off action. The same lowering had been applied and reverted four times in the preceding sixteen hours. The action is routine; only its persistence is new.

Long-standing configuration drift. The constrained state had repeatedly been undone. The active lowering was under six minutes old at onset.

An application-level exception explaining the crash. Nothing of the kind appears; the process is terminated before it can emit an application error, so stdout will never show you the cause here.

A degraded-but-running service — hung threads, backpressure. The repeating startup banners rule this out; the process is being recreated, not limping.

A single restart or rollout blip. Ten-plus startup sequences over about seven minutes is a sustained loop.

The telemetry agent or JVM options failing to load. The agent loads and logs its version in every cycle; the only JVM warning is the benign sharing notice.

An error-rate spike at the alert time. The backing series has no samples at all, in any window.

A telemetry dropout at onset. The pre-incident baseline is equally empty, so the gap predates the incident.

## Open questions for whoever picks this up

Three things are unresolved.

The kill reason is inferred, not observed. Pull the container's last-terminated-reason, its memory working set against the 200m ceiling, and its restart counter. That converts medium confidence to high in one query, and it is the first thing to do if this recurs.

Why the automation applied the ceiling a fifth time and omitted its usual restore is unknown. This determines whether the condition self-heals on the next cycle or persists indefinitely — a materially different operational posture.

Blast radius beyond this service was never measured. The alert reported one service, but the log evidence shows the service consumed no order records from onset onward. Anything downstream of that consumption was silently unserved for the duration, and nobody looked.
