# Cart backend unreachable after a configuration value change

## What was visible, in order

The page named frontend, loadgenerator and checkoutservice together — the shape of a shared dependency vanishing rather than one service breaking. Metrics confirmed it was new: frontend's error ratio sat at exactly zero across the whole baseline, then stepped up at T-2m; checkoutservice stepped thirty seconds later. Both were discrete steps, not ramps. The window-mean ratios (about 3.6% and 6.7%) looked like partial, bursty failure, but those series were aggregated by service name only and the window opened long before the break — treat the small means as averaging artefacts, not as evidence that failure was partial.

Traces narrowed it in one step. Every failing trace terminated at a cart call: frontend's GetCart and AddItem client spans and checkoutservice's GetCart client span were the deepest error spans. Everything above them carried the error upward; checkoutservice's own order-preparation span was clean, which demoted it from suspect to propagator. No cartservice server spans appeared anywhere, and the failing spans were sub-millisecond — hard unavailability, not slowness. Paths that never touched the cart (catalog, recommendations, ads) succeeded.

cartservice logs closed it. Healthy traffic at T-28m; from T-1m to the end of the window, a crash-loop: each start logged a connection to the redis-cart host on port 6380, hung fifteen to forty seconds, threw an unhandled exception out of Redis store initialisation, died, restarted about a second later. Its change history shows a platform-automation config entry setting that address roughly two minutes before onset, with no previous value recorded.

## Dead ends worth keeping

A traffic-shaping sidecar had been attached to the cart-service network namespace at T-21m and removed at T-12m. Both precede onset and the delay was no longer applied when symptoms began. It is the exact artefact that pulls an investigator toward a latency story the traces had already excluded.

Four image-reference events sit three-plus hours back: a hotfix applied and reverted twice, ending reverted. The running binary was unchanged for hours, so no code release explains this.

checkoutservice logs pointed the wrong way for a long time. They contain no error-severity lines at all. Early orders emit a full pipeline — start, payment, email, publish. Late in the window only order-start lines appear at a steady rate, which reads like requests stalling before payment and invites a hunt for a slow payment dependency. The traces say the cart lookup fast-fails instead. Whether checkoutservice swallows that error or genuinely blocks was never resolved.

The metrics query against cartservice returned nothing in either window. Because both are equally empty, that is a coverage gap in the call-count series, not a signal of anything at onset — neither exculpatory nor confirmatory.

## Conclusion and open items

High confidence: the configuration value names an endpoint and port with no listener, cartservice cannot finish startup against it, and every path through the cart fails. Fix class: revert the configuration value.

Mind the direction of the argument. The evidence shows nothing answers on 6380; it does not show the correct value is 6379. No evidence was gathered against the Redis instance itself. If 6380 were the target of an intended migration, the wrong side would be the unmigrated server and remediation would shift.

The crash-loop rests entirely on log evidence from a single query, with no restart counts, pod availability or saturation data. The change queries that cleared frontend and checkoutservice are weaker than they look: the frontend query covered onset-forward rather than the pre-onset period, and the checkoutservice one was scoped to that service alone with no hops, so its other dependencies are not excluded. Per-minute error ratios after the break were never pulled to confirm the averaging explanation. Finally, the four unmeasured edges were never identified, the seven other services in the blast radius were untouched, and what drove platform-automation to introduce this variable is unknown — so recurrence risk after a manual revert is unquantified.
