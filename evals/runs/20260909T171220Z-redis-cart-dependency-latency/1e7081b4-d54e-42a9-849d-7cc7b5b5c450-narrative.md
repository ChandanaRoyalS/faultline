# Cart path slow but successful: a fixed per-round-trip delay on the cart-to-Redis hop

## What was visible, and the two dead ends

The page arrived as a warning-severity degradation starting at cartservice, twelve services in the blast radius, four unmeasured edges crossed. cartservice, frontend, loadgenerator and checkoutservice all alerted within seconds. No error-rate page, no crash alarm — the shape said one call path, one origin, everything above it inheriting.

The first two sources we opened were both dead ends, and both are worth keeping.

First, cartservice metrics do not exist. The error-ratio query returned no samples in the incident window — and none in the preceding baseline hour either. That symmetry is what stopped us wasting time: empty-during, populated-before would have been a signal; empty on both sides means the series is missing or mislabeled and predates the incident. Cost: cartservice's latency percentiles, request rate, restarts and readiness were never measured by anyone. Fixing those labels is the highest-value pre-work before this recurs.

Second, logs, containing two red herrings. cartservice's own stream was clean — routine cart operations at sub-second cadence to the window edge, no panics, no restart banners, no connection-refused text — but truncated to the oldest 8 and newest 32 lines, so onset was never actually covered. In its final thirty seconds, cart reads with an empty user identifier became the dominant line, which pulled attention toward a caller-side session-propagation defect; checkoutservice's logs killed that, every PlaceOrder line at both window edges carrying a well-formed UUID. frontend's logs held real errors that were not ours: product-catalog INTERNAL errors behind a failure feature flag, and a connection refusal against an upstream on port 50053 — a listener not accepting, a different class from what we were chasing, and nothing naming cartservice. frontend then went fully silent for the last ~16 minutes (real absence, not truncation). That silence was never explained and appears unconnected.

## The traces, which settled it

Ten sampled traces over a ~36s span told one clean story. All the latency sat in the Redis client spans cartservice itself emits: every HGET and HMSET consumed roughly 300–310ms of self-time, while the enclosing gRPC handlers used under ~2ms. Latency tracked round-trip count exactly — GetCart (one HGET) ~305ms, EmptyCart (one HMSET) ~303ms, AddItem (HGET then HMSET) ~600–615ms. Everything else on the checkout path was fast: currency and catalog effectively zero, payment sub-millisecond, shipping ~17–19ms, email ~6–7ms. Both callers were hit, across three operations, placing the cause downstream of the callers and shared between them.

Two negatives mattered as much. None of the 140 spans carried an error or non-OK status and every trace reached its normal terminal operations — slow-but-successful, not a correctness problem. And command counts were exactly as expected: no retry inflation, no fan-out; duration was inflated, not call count.

The distribution is the tell. A loaded Redis server gives a long tail. We saw a tight band with no outliers. A fixed per-round-trip penalty, no errors, no refusals, points at an artificial egress delay on the cart-to-Redis network path rather than a saturated server.

User-facing: frontend POST roots 668–927ms, GET roots 306–312ms; the cart Redis hop was ~33% of AddItem traces, ~45% of checkout traces, 99% of simple GetCart traces.

## The change record, the upstream alerts, and what stays open

cartservice's change log held 34 entries, all from one automated actor, in six identical cycles: image set to a hotfix tag then reverted; a traffic-shaping container attached to the cart-service network namespace with a fixed egress delay then removed; a REDIS_ADDR override to an alternate port then reverted. No human-authored change, no version progression — scheduled automated experiment activity, not delivery. The middle element is exactly the mechanism the traces demand.

Read literally, though, the log exonerates itself: every apply has a matching revert, the last event before onset is a revert, and nothing lands in the ~78 minutes before onset (nearest change ~1.3h earlier, the REDIS_ADDR revert closing the final cycle). No net drift. But the traces are flatly incompatible with a clean namespace — something added a fixed ~300ms per round trip while the log said nothing was applied. Two readings fit equally: an unrecorded further cycle beginning near onset, or a removal written to the log while the queueing discipline or sidecar persisted. Nothing we collected distinguishes them, because nobody inspected the cart-service namespace during the incident.

frontend and checkoutservice alerted seconds later purely by inheritance. frontend's error ratio ran about a sixth of its prior-hour baseline with no sustained departure — the slowness never surfaced as errors. Note for anyone re-running this: the noisy, higher-error period was the hour *before* onset, so anchoring on that baseline makes the incident look like an improvement. checkoutservice's tail showed six complete order flows with consecutive queue offsets: healthy, just slow.

Still open: which of the two readings above is true; redis-cart was never queried at all, so server-side latency, connections and slowlog are unexamined and Redis-side slowness is only inferred against from the delay's uniformity; and cartservice has no usable metric series in either window. Fix class: revert the configuration and verify the namespace directly. Confidence medium.
