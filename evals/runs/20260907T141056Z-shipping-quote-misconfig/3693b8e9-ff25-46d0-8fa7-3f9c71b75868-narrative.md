# Checkout PlaceOrder failures traced to the shipping quote call

## What we saw first

The page came in on checkoutservice, with loadgenerator, accountingservice and quoteservice alerting alongside it within a few minutes. Blast radius was eleven services and severity was called critical, which set the initial expectation of something broad. What was actually visible from the responder's chair at T+0 was narrower: checkout was still up, still taking traffic, and a minority of PlaceOrder requests were failing.

The first useful measurement was the checkout error ratio. The baseline was a hard zero — not a low noisy floor, an exact zero across every sample in the preceding half hour — and then it moved. Mean around 3.9%, peaks near 28%, with the crossing point two minutes earlier than the reference time we had been handed. That mattered twice over: it told us the onset was abrupt rather than a slow degradation finally tripping a threshold, and it told us to stop looking at anything that landed after the reference time and look slightly earlier instead. The spikiness also argued against a hard dependency being wholly gone; a request-critical dependency at zero availability would have pinned the ratio far higher and held it there.

## The logs were the first dead end

The obvious next move was to read checkout's own logs and find the error line naming the culprit. There was no such line. The entire window contained only info-severity output — no warnings, no errors, no status codes, no gRPC or HTTP error strings, no named dependency. This cost time, because the absence looked at first like a log-shipping problem rather than a property of the failure.

What the logs did give us was shape. Early in the window each PlaceOrder entry was followed within tens of milliseconds by a full downstream sequence: payment authorization with a transaction id, a confirmation email, a successful broker write with an increasing offset. Later in the window only the entry lines remained, one every few seconds, with nothing after them. Requests were being admitted and then producing no further output at all.

That pattern retired three theories on the spot. Checkout had not crashed or restarted — the entry cadence never broke, and a restart would have shown a total gap plus startup lines. Upstream traffic had not stopped and loadgenerator had not died — arrivals were steady to the end of the window. And it was not a currency problem: the stalled requests carried the same USD-dominant mix, with a couple of CAD, as the healthy traffic earlier. The broker producer was also healthy at the start of the window, with sequential offsets recorded, so any breakage there began later rather than being the origin.

With no status code anywhere in the log stream, the log-based route to naming a dependency was closed and we moved to traces.

## Traces named the boundary

Traces answered in one query what the logs could not. Every sampled PlaceOrder trace ended at the same place: the checkoutservice client span for the shipping quote call, flagged ERROR, with the error propagating up through checkout's PlaceOrder span, the frontend PlaceOrder span, and the frontend HTTP root span.

All of the failing work sat inside prepareOrderItemsAndShippingQuoteFromCart. The sibling calls in that same block were clean: cart lookup and its Redis read completed in a fraction of a millisecond, product catalog lookups in under a millisecond, currency conversion in zero to two milliseconds, every one of them unflagged. A feature-flag lookup from the catalog service also succeeded where it appeared. So checkout was not failing internally before reaching out — it issued and completed several downstream calls successfully, and only the shipping quote errored.

The failure was fast rather than stalled. Quote spans ran two to three milliseconds; whole traces finished in eight to twelve. Nothing was hanging on a deadline, which ruled out the timeout hypothesis we had been carrying since the log gap appeared.

The most informative detail was an asymmetry across the shipping boundary. The checkout-side quote span carried ERROR, while shippingservice's own server span and its outbound HTTP client span did not. Shipping was returning a bad status to its caller rather than crashing, stalling, or dying mid-handler.

Traces also cleared, definitively, the dependencies the log gap had implicated by omission. No payment span appears in any sampled trace, because the quote runs before the charge and execution never reaches it. No email span. No producer span. Those stages were absent from the logs not because they were broken but because the request died upstream of them. That inversion — the missing log stages pointing at the wrong suspects — was the single biggest time sink of the incident.

## Change hunting, and where it went sideways

We queried the change log for checkoutservice across the full window and got nothing: no deploy, no config edit, no flag flip, no image-tag bump attributed to checkout itself. That removed a self-inflicted change as the origin and left no in-window event on the seed service to anchor a timeline against.

Attention then went to paymentservice, which at that point still looked plausible from the log-gap reading. Two changes existed for it in the surrounding day, both by platform automation, both touching only the traces-export endpoint variable: set roughly forty minutes before onset, reverted roughly twenty-nine minutes before onset. A set-then-revert pair leaves no persistent delta, so payment's environment at onset matched its state beforehand. No deploy, no image-tag change, no flag, no scaling or replica edit, and no human actor. Combined with the trace evidence that payment is never reached, this whole branch was a dead end — worth recording precisely because the automation entries looked, at first glance, like the correlated change we were hunting.

A payment error-ratio query returned no samples at all — and, importantly, returned none in the baseline window either. That is a silent series, most likely an instrumentation or label-name gap, not telemetry collapsing at onset and not a clean zero. It cannot be used to exonerate payment any more than to implicate it.

Emailservice's change log came back empty too, but the window we ran started about two minutes after onset and ran forward a day. It therefore says nothing about the hours before onset; it only rules out a post-onset change on email prolonging things, and rules out ongoing change churn there. Note the window bug if you re-run it.

## Where we stopped

The conclusion we reached: PlaceOrder fails inside prepareOrderItemsAndShippingQuoteFromCart when checkout's client call for a shipping quote returns an immediate error. Failure is fast, intermittent, and unlogged by checkout, which keeps admitting traffic and simply emits no post-entry stages. Checkout itself carries no change of its own. The downstream shipping quote path is the failing mechanism.

Confidence is low and no fix class is identified, because we stopped at the boundary rather than crossing it. No change record, config, or resource evidence was gathered for shippingservice at all, so the mechanism inside it is not pinned down. Five edges in the blast radius were crossed without measurement.

For whoever picks this up: run the change log against shippingservice for the hours before onset, not after — that query was never run. Get the actual status code and error message shipping returns on the failing quote calls, and check whether shipping's own logs record them, since checkout's do not. Work out why only about four percent fail: one bad replica, or a specific input class such as an address or item mix. And establish whether shipping depends on quoteservice for the calculation — if it does, quoteservice's alert a few minutes after onset is causal rather than consequent, and the ordering we assumed is backwards.
