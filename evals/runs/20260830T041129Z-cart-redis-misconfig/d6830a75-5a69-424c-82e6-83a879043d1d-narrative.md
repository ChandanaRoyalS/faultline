# Checkout failures traced to cartservice startup crash on unreachable cart Redis endpoint

## What we saw, and where it sent us wrong

Pages arrived from checkoutservice, frontend, and loadgenerator; checkoutservice was named as the origin. That framing cost us time — checkout turned out to be a faithful reporter of someone else's problem.

Checkout's change history came back completely empty: no deploys, config edits, flag flips, or dependency bumps. That closed the obvious hypotheses but left a gap worth recording — the window actually covered was only 04:04 to 04:19, and only checkoutservice itself, so anything from 02:14 to 04:04 and anything on its dependencies was never queried.

Checkout's error-ratio series was the most misleading artifact of the incident: non-zero, peaking near two-thirds, touching zero at points, continuous across all samples. Read at face value it says intermittent and bounded, majority of calls succeeding. We worked that reading for a while. Traces later said something incompatible, and the discrepancy was never resolved.

Checkout logs returned nothing above severity info, so no downstream call site was named. What they did show was a shape change: early orders logged accepted, payment succeeded, email sent, queue write; from roughly 04:13:14 only the acceptance line appeared. Intake lines continued at normal cadence to 04:16:28, which ruled out a crash on checkout, rejection at intake, and a log-shipping gap. Both currencies appeared among the incomplete orders, so no cohort effect. The result was truncated between 04:04:07 and 04:13:14, so exact onset is not pinned.

## The turn, and the dead end that mattered most

Traces resolved direction. Every failing checkout trace had one identical five-span shape ending in an ERROR on checkoutservice's outbound call to CartService/GetCart; all spans carried ERROR except checkout's internal prepare step. Root spans ran roughly 1.2–5.3ms with the erroring child 0.4–1.0ms — sub-millisecond failure, not deadline exhaustion. This killed the nine-dependency fan-out premise (execution never reaches a second dependency), exonerated payment, shipping, email, currency, and catalog, and cleared checkout's own logic. Across ~40 traces there was no successful checkout and no alternative shape: a total failure mode, which is exactly what conflicts with the partial error ratio above.

Then the expensive dead end. Cartservice's error ratio was flat zero — 61 consecutive samples, min and max both zero, no gaps. On that basis we briefly cleared cartservice as error origin, cleared a crash or restart, and cleared a backing-store problem surfacing as failed calls. Two of those three were wrong. The ratio counts error spans over served spans; cartservice was never serving, so there were no calls to mark as errors and no gap to betray the outage. A responder trusting a zero error ratio as proof of health should read this paragraph twice.

## Cause, and what stayed open

Cartservice logs settled it. Around 04:04 they show ordinary cart operations, so the transition happened inside the window. By 04:15–04:18 the service is in a startup loop: each cycle logs a connect attempt to redis-cart:6380 from RedisCartStore.EnsureRedisConnected/InitializeAsync in Program.Main, hangs 15–35 seconds, then dies on an unhandled ApplicationException — repeating every 30–45 seconds to the window edge, never succeeding. The crash precedes gRPC readiness, which is the mechanical reason GetCart fails in under a millisecond. No other backing store appears in any error path.

Cartservice's change history held exactly one entry: at 04:11:30 UTC, actor platform-automation updated the environment to point the Redis endpoint at redis-cart:6380, replacing a previously unset value. Environment update only — no image deploy, no flag flip. Conclusion: the configured endpoint is not one cartservice can reach, breaking every cart lookup and therefore every checkout. Confidence high; fix class is reverting the config.

Still open. Nobody verified what redis-cart actually listens on; port 6380 differing from the 6379 default is suggestive but weak, and the alternative — host down or unroutable, port incidental — was not excluded. The 15–35s hang argues for no route or a dropped handshake rather than a wrong port on a live host, which normally refuses immediately. The prior value was recorded as unset, so a plain revert needs confirmation it restores a working path rather than a different failure. The push came from automation, not a human, so whether the pipeline re-pushes the same endpoint after a manual revert is unknown and determines whether the fix holds. And the partial-versus-total error discrepancy above is unexplained.
