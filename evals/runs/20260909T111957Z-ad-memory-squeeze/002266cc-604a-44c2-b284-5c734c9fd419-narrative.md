# Frontend ad-path failures traced to a constrained adservice memory ceiling

## What woke us, and the first two dead ends

The page came from frontend and loadgenerator, marked critical with a seven-service blast radius. That framing cost time: it suggested something broad. Treat T+0 as the alert.

First pull was frontend's aggregate error ratio against the preceding hour. The mean roughly doubled (~1.9x) but nothing else supported alarm: no sustained departure from baseline, an incident-window peak actually lower than the baseline peak, baseline variability exceeding incident variability, mean ratio around 2.5% with brief excursions near 10%. That killed 'frontend broke out on its own' and 'double-digit sustained failure'. More importantly, the query aggregates by service name with no downstream dimension and no latency series, so it could never have attributed blame to a callee. Roughly fifteen minutes spent for no attribution.

Second, a full 24h change query on frontend came back empty — no deploys, config edits, flag flips or dependency bumps. Neither a shipped change nor an ongoing rollout could be the origin. Frontend is the reporter.

## Traces narrow it, logs give the mechanism

Sampled traces collapsed the radius. Exactly one downstream edge errored: frontend -> AdService/GetAds, with the parent HTTP GET also marked ERROR. Productcatalog (including nested flag lookups), cartservice with its sub-2ms Redis children, and recommendation all completed cleanly in the same minutes. Onset was late: errored spans from ~T+34s onward, everything earlier clean. The ad call failed in well under a millisecond — fail-fast, not a timeout, not saturation. A companion trace showed a frontend GET with no child spans at all beside a successful sibling. Ruled out: broad fan-out outage, cart/Redis, productcatalog, recommendation, and any slow-failure shape. Recorded as absence rather than evidence: no shipping or checkout spans appeared under frontend at all.

Logs confirmed the stage. Frontend emitted client-side grpc-js stack traces on outbound calls — status 14 UNAVAILABLE naming DNS resolution failure for adservice:9555, repeating around T+2m. That rules out an upstream application-level rejection, a connect/TLS/deadline problem, and a frontend handler bug. One complication kept deliberately: ~30 minutes before the alert, frontend logged a status 13 wrapping a failed hostname lookup for shippingservice against the container-local resolver at 127.0.0.11:53 — same class, different upstream, wrong time. Enough to say the resolver is internal, not enough to make it the cause. The log result was truncated to the oldest 8 and newest 32 lines, so roughly T-30m to T+2m is unobserved; nothing was seen at the alert instant itself.

## The change record, the hole, and where it landed

Every adservice change in 24h is a resource-limit adjustment by the same non-human actor: seven events forming a repeating lower-then-restore cycle on the container memory ceiling (down to 256m, back up). Three earlier cycles that day restored within about nine to fifteen minutes. The fourth lowering landed at T-4m with no matching restore, so the constrained ceiling was in force at alert time. Ruled out from the same record: code deploy or image rollout, replica scale-down, operator restart, and any rename/port/discovery edit that could break addressing directly.

The hole: we never observed adservice itself. Its span-derived call metric returned no samples in the incident window — and none across the full preceding-hour baseline either. That is uninformative rather than exonerating. It does rule out a loud measurable error spike, rules out the reading that adservice went silent at onset (the silence predates it), and rules out window sizing. It leaves open whether adservice ever emitted these metrics, or was already unhealthy before the limit dropped. No container logs, exit codes, restart counts or memory series exist; the kill itself was inferred, never observed.

Working conclusion, medium confidence: the automated loop lowered the ceiling and this time did not restore it; adservice went away, its name stopped resolving, and frontend's ad calls failed fast at resolution while every other edge stayed healthy. Fix class is a config revert — restore the limit, then investigate the loop. The three silent self-healing cycles earlier that day are the alarming part.
