# frauddetectionservice restart loop after a container memory limit reduction

## What the responder saw first

The page named a single service, frauddetectionservice, at critical severity. Triage scoped the blast radius to that one service with no unmeasured edges crossed, so there was no immediate pressure to chase neighbours — a scoping decision that later turned out to be worth revisiting (see Still open). Call T+0 the moment of the alert. Nothing else was paging, and there was no customer-facing symptom handed over with the alert beyond the service itself.

## First line of inquiry: span metrics (a dead end)

The instinctive first move was to characterise the incident with RED metrics — plot the error ratio for frauddetectionservice over a window spanning roughly ten minutes either side of T+0. The query returned nothing. Not a flat line, not zeros: no matching series at all, for the entire window.

The important detail, and the one that cost time to appreciate, is that the denominator was empty too. Total call rate matched nothing. So this was not "errors went to zero" or "status codes shifted" — the whole series family was missing. That admits two readings: the service genuinely emitted no span metrics because it was not running, or the metric name and service_name label being queried simply do not match what this service exports.

A second pass at metrics was attempted and issued the same error-ratio query, returning the same empty result. No memory, limit, restart, or kill-related series were ever pulled. Anyone reading this record should treat the metric path as unexplored rather than exhausted: the only thing genuinely ruled out is that this particular query shape produces a signal here.

## Logs: where the shape of the failure appeared

With metrics silent, logs carried the investigation. At the start of the window — around T-10m — the service was emitting steady Kafka record-consumption lines with a monotonically increasing counter. Normal operation, clearly visible, through at least T-9m.

From roughly T-6m onward the stream changes character completely. Consumption lines stop and never return. In their place, a repeating triplet: JVM tool-options pickup, a JVM class-sharing warning, and an OpenTelemetry agent version banner. That triplet recurs on a roughly 60-second cadence and is still recurring past T+1m. It is the only warning-severity text anywhere in the window, and its first appearance coincides with the disappearance of steady traffic.

Several tempting readings were closed off here. There is no application exception, no exception class name, no stack frame anywhere in the returned lines — including around T+0, where a responder would most want one. The service was not healthy-but-quiet and it was not scaled to zero or merely stripped of its partition assignment: full JVM and agent initialisation banners mean the process is genuinely being torn down and re-launched, not idling. And it was not a single restart at T+0; the same triplet appears at T-6m, T-5m, T-4m, T-3m, T-1m, T+0 and T+1m, so the loop had been running for several minutes before the page fired.

The most useful negative finding: each cycle ends immediately after the agent banner with no shutdown message and no failure text. The process dies without writing a reason. That means the cause was never going to be found in application logs, and the search had to move to container-level exit codes, kill events, or resource metrics.

## The change log

A single change landed on frauddetectionservice in the fifteen minutes before the alert: a resource-limits update at roughly T-6m, made by platform-automation, lowering the container memory limit to 200m. Its timing lines up with the first startup banner almost exactly — within about thirty seconds.

No code deploy, no release event, no feature-flag flip, and no dependency version bump appears anywhere in the window for this service. Each of those was checked and each came back empty. The possibility that the incident had no associated change at all — purely environmental or traffic-driven — is also closed by this record.

One gap worth flagging now because it bites later: the change log did not record the prior limit value.

## Conclusion, and how firmly it rests

The reading that fits the evidence: a process dying mid-run without logging a reason, immediately re-launched, starting within seconds of a container memory ceiling being lowered, is the classic profile of a JVM whose committed heap exceeds the new limit and is terminated by the kernel out of band. That also explains the empty span-metric series cleanly — a service that is never up long enough to serve or consume anything produces neither numerator nor denominator.

The mechanism in the world is the process running out of the memory it needs and being killed for it. The limit edit is how that state was entered, not the mechanism itself. Fix class is a revert of the change; confidence is medium, and the medium is doing real work in that sentence.

## Still open — read this before acting

The kernel-kill mechanism is inferred from log shape and timing. No exit code, kill event, or container restart counter was ever queried. Pulling container working-set bytes, the limit series, and pod restart/termination reason across the window either side of the alert would settle it in one step.

The prior limit value is unrecorded, so it is unknown how far below the JVM's real footprint 200m sits — and therefore what number a revert should restore. Reverting blind is not obviously safe.

The empty call metrics are attributed to the crash loop, but the label/name mismatch possibility was raised and never eliminated. Nobody enumerated the available service_name label values. Do that before trusting any future span-metric query against this service.

The JVM's own heap settings (-Xmx, MaxRAMPercentage) were never inspected. If the container was already sized tightly, the same limit might be survivable with a heap adjustment, which would change the correct fix from a revert to a tuning change.

Nothing was dispatched to upstream or downstream consumers. Whether Kafka topic backlog grew or any dependent service degraded while this one was down is simply unexamined — the zero-unmeasured-edges scoping is an assertion about the triage graph, not a measurement of neighbours.

Finally: why platform-automation lowered the limit is unknown. Policy rollout, quota rebalance, autoscaler action — it matters, because if the automation will re-apply the same value, a revert buys minutes rather than a resolution.
