**Neither aggregate should be quoted alone, and the table shows two different reasons why.**

**One: `bad_config` is behaving as a default.** The agent returned it for **five of seven**
scenarios. It is right on both that are `bad_config` and wrong on all three that are not. An
aggregate of 4/7 reads as "somewhat accurate"; the per-class table reads as "correct on two
classes, and answers `bad_config` when it is neither". Those are different systems.

**Two: the 6/7 class-of-fix figure is inflated by label collinearity.** `resource_exhaustion`
and `bad_config` **share** `config_revert`, so both resource-exhaustion runs got the class of fix
right *while getting the fault class wrong*. Six of seven overstates what was understood. The
one class of fix that is not shared with the returned class — `restart` on
`cart-dependency-latency` — is the one that is wrong.

n per class is 1–2 before repeats. A 95% CI on any of these spans most of the unit interval, and
the table is printed anyway because printing it is the honest form of that finding (ADR-0022 §5).

### The contradiction checker's ledger is now 0 true positives, 4 false positives

Both firings on `cart-bad-image-tag` are wrong, and each is a different accident:

1. > "Why did cartservice never come back after the 06:55:25 shutdown? **No dispatch examined**
   > pod/container state, image-pull results, or restart counts"

   The clause splitter breaks on `.`, `;`, `:` and dashes — **not on `?`** — so the service named
   in the question joined the negation in the answer. The answer is about *pod state*, and it
   matched the `changes` evidence vocabulary only because `image-pull` contains **`image`**.

2. > "Nine of checkoutservice's dependency services and the 4 unmeasured edges **flagged** by
   > triage were **never queried**"

   True, and about dependencies rather than about checkoutservice's change history. It matched
   because `flagged` contains **`flag`**.

Neither cites its dispatch's `result_id`, so T3.4c's citation escape did not apply. Both are the
shape ADR-0022 said must not fire: a statement about what an investigation did not cover, read as
a claim that a dispatch never happened.

**ADR-0022 §Consequences set the condition:** "If a first batch does not improve it, the honest
options are to narrow it further or to retire it — and either is a decision with an ADR, not a
quiet edit." The first batch has run and did not improve it. **The decision is owed and is not
taken here**, because taking it inside the sweep that produced the evidence is the quiet edit
that consequence forbids.

## Discards — recorded, then re-run

| run id | scenario | reason | outcome |
|---|---|---|---|
| `20260826T061939Z` | cart-redis-misconfig | API **529 Overloaded** on the first model call | re-run at `20260826T085613Z`, scored |
| `20260826T073342Z` | frauddetection-memory-squeeze | **harness defect** — see below | re-run at `20260826T083358Z`, scored |

Both discard directories stay in `evals/runs/` with their `DISCARDED.md`. The sweep continued
past each rather than stopping.

**The 529** cost a whole scenario slot — an injection, a correlation wait, a revert, ten minutes —
for a transient API error on the first call. The failed-start rule handled it correctly (no
trajectory, incident left `triaging` rather than terminal `FAILED`, revert ran from its
`finally`), but the harness has no retry on transient API failures and a sweep is exactly where
that costs the most.

**The harness defect is mine and the sweep found it.** `wait_for_incident` hard-coded
`min_episodes=2`. `frauddetection-memory-squeeze` alerts on **exactly one service** — a sparse
service failing quietly pages nobody downstream — so it could never satisfy the wait, timed out
at 900s, and was recorded as though the world had not reacted. The world reacted exactly as its
bundle says it does. The wait now comes from the bundle: two, or the whole radius if the radius
is smaller than two. Fixed and pinned before the re-run.

**Why re-running these is legitimate and re-running a holdout would not be.** Both fixes are to
the *harness's* waiting and transport, not to the agent pipeline: `runtime_version` is derived
from the prompts and contracts, and it did not move. Both re-runs carry the same stamp as the
other five. ADR-0022 §3.3's rule against re-running to fix a disappointing number is about
scores, and neither discard produced one.
