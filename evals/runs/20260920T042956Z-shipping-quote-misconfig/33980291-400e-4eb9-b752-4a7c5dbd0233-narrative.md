# Checkout orders halted at the shipping-quote hop

## What the responder saw first

The page arrived for checkoutservice at T+0. Within about three and a half minutes four more services lit up — accountingservice, emailservice, frauddetectionservice and quoteservice — which read at first glance like a spreading outage across eleven services. It was not spreading; those four are all consumers of work that checkout emits, and they went quiet-then-alerting because checkout stopped producing. Severity was set critical because order placement was visibly not completing. Five of the edges crossed during the walk were never measured, so treat the blast-radius count as a topology statement, not a damage assessment.

## The first instinct, and why it went nowhere

The obvious opening move was to check whether checkoutservice itself had turned unhealthy. The error-ratio comparison against the preceding baseline showed a modest lift (roughly 0.13 during the window against 0.08 before), but no sustained departure: the baseline window actually contained a higher single-interval peak and more variance than the incident window. Errors on checkoutservice were chronic background, not new. More usefully, the ratio was defined in every sampling interval, which requires non-zero traffic throughout — so checkout never stopped serving. No latency, CPU, memory or restart series came back at all from that query, so the saturation half of the question was never actually answered. Do not read this evidence as clearing those; it simply did not look.

## The cartservice detour

A substantial slice of effort went into cartservice on the theory that a cart or Redis-backed dependency was dragging checkout down. This was a dead end, and an instructive one. The error-ratio query for cartservice returned no samples at all — and critically, none in the baseline window either, so the emptiness predates the incident and reflects a missing or differently-labelled series rather than telemetry dying at onset. An empty result is not a flat line; it cleared nothing. Cart logs showed normal AddItem/GetCart/EmptyCart handling at both ends of the window, sub-millisecond-to-millisecond spacing, no errors, no restart banners, and a recurring empty-user-id GetCart pattern that is almost certainly a health probe. Note the log result was truncated to the oldest 8 and newest 32 lines, so the minutes immediately around onset were never returned for cart.

## Cart change history: churn that looked damning and wasn't

Cartservice's change record showed four image-reference changes in roughly two hours, all from platform automation: the same hotfix tag applied and reverted, then applied and reverted again, the last revert landing about an hour before onset. This looked like a strong lead for about ten minutes. It isn't the cause — the revert means the pre-hotfix baseline image was the one in effect at onset, and nothing lands at onset. Worth leaving on the record anyway: four flips on one tag in two hours suggests a reconciliation or rollback loop, and that loop is its own problem regardless of this incident.

## What the traces actually showed

The traces closed the question. Ten sampled checkout traces all share one shape: frontend HTTP POST, frontend PlaceOrder, checkoutservice PlaceOrder, then prepareOrderItemsAndShippingQuoteFromCart. ERROR status originates on checkoutservice's ShippingService/GetQuote client span and propagates up to the root. That client span is the only errored child. Cart (including HGET), currency Convert, and product-catalog GetProduct spans all complete sub-millisecond and clean. No paymentservice, emailservice or shipping-order spans appear anywhere in 176 spans — execution short-circuits at the quote step and never reaches charging or placement completion. Two details matter for classifying this. First, timing: whole traces finish in 9-12ms and the failing hop returns in 2.5-3.8ms. These are fast rejections, not stalls, deadline expiries or pool exhaustion. Second, sidedness: the shippingservice server span and its own outbound HTTP client span both complete without error. The error exists only on the caller's side of that boundary, which points at the response contract or endpoint configuration rather than anything breaking inside shippingservice.

## The logs, read against the traces

Checkout's logs corroborate without ever admitting failure. Early in the window every order produces a full sequence: placement, payment confirmation with a transaction id, confirmation email, and a message write with an increasing offset. In the final four minutes only placement entries appear — the downstream completions are simply absent. Placements keep arriving every 5-15 seconds to the last second, so inbound traffic never stopped and the process never restarted. Every returned line is informational severity: no exception, no stack trace, no line naming a downstream address. Both USD and CAD placements appear in the late segment and both lack completions, so this is not currency-specific. Same truncation caveat as cart — only the oldest 8 and newest 32 lines were kept, so roughly T-30m through T+1m of log content is unobserved and an error burst in there cannot be excluded.

## The change queries that answered the wrong question

Checkoutservice change history was queried twice, and both times came back completely empty — no deploys, config edits, flag flips, image or dependency bumps. That legitimately rules out a concurrent checkout deploy, a mid-incident config edit, and an unlogged remediation explaining any recovery. What it does not do is answer the question that was asked. Both windows begin at the onset timestamp and run roughly twenty-four hours forward. The hours before onset — the only place an originating change could live — were never queried. Two independent runs reproduced the same misaligned window. If you are picking this up cold, re-run the change query for shippingservice and quoteservice, backwards from onset, before anything else.

## Where this landed

Checkout requests fail at the shipping-quote hop. The caller-side GetQuote span errors in every sampled trace while the callee completes cleanly and fast, so the best reading is a rejected or unusable response at the checkout-to-shipping boundary: a wrong value in the call path from a contract or endpoint configuration mismatch, not slowness and not exhaustion. Order preparation short-circuits there, which is why payment, email and order-placement never run, and why the four consumer services alerted about three minutes behind checkout. Fix class is a configuration revert on the shipping-quote path. Confidence is low, and honestly so — the mechanism is inferred from span topology and timing, never from an error code.

## Open threads for whoever reads this next

Four things were never established. What error code or message does checkoutservice's GetQuote client span actually carry? No span attribute or log line naming the failure was ever retrieved, and this is the single highest-value missing item. Were there changes to shippingservice or quoteservice in the hours before onset? Never asked — both change queries covered only the post-onset window. Why did quoteservice alert at T+3m: as a victim of checkout short-circuiting, or as the origin of the unusable quote response? That dispatch never happened, and it is the difference between a downstream symptom and the actual origin. And was there any checkoutservice change before onset? That surface is entirely unobserved.
