# Frontend ad calls fail with UNAVAILABLE after an automated memory-limit reduction

## What the responder saw first

The page came from two places at once: frontend and loadgenerator. Blast radius was scored across seven services, severity critical, with frontend as the seed. The first instinct — that frontend was melting down and shedding user traffic — did not survive the first query. Frontend's aggregate error ratio over the window averaged roughly 3.2%, against a preceding baseline that averaged about 8.3% and never dipped below ~4.9%. Errors went *down*, to roughly 0.4x baseline. That single measurement reframed the whole investigation: whatever was breaking was not showing up as served error statuses at the frontend edge, and this service carries a chronic few-percent error floor even when healthy, so small error numbers here mean nothing on their own.

The same metric also had a limitation worth writing down for the next person: it is aggregated by service only, with no dimension for outbound peer. There is no way to ask it "which dependency is failing" — that question has to be answered somewhere else.

## The signal that actually mattered

Frontend's log stream carried the finding. The newest retained lines, clustered near the end of the window (about T+32m from the window open), are repeated gRPC client errors with status code 14, UNAVAILABLE, whose detail says no connection could be established to the callee. The stack resolves entirely through the grpc-js client receive-status path. That placement matters: these are failures of outbound calls that frontend is surfacing, not frontend crashing, and not an upstream returning an application-level error response. Code 14 with a no-connection detail means the call never reached a serving peer at all — connectivity, resolution, or pod availability.

Two negatives fell out of the same evidence. There were no deadline-exceeded or timeout statuses anywhere in the returned lines, so the timeout hypothesis was closed. And there were no HTTP statuses at all — no 503s from a proxy or load balancer — only gRPC codes raised in the client.

## The dead end that cost the most time: the earlier error regime

At the very start of the window frontend was emitting something entirely different — gRPC code 13, INTERNAL, with a message attributing the failure to a deliberately enabled fail feature flag in the product catalog service. It is tempting to read the incident as a continuation of that. It is not. The 13s appear only at the window open; the recent lines are a distinct connection-level 14 signature. The failure mode changed under us.

This is also the record's largest observational hole. The log result was truncated to the oldest 8 and newest 32 lines, so the transition between the two regimes, and most of the period after onset, was never seen. The current state of that product-catalog flag is unknown. A responder revisiting this should pull the middle of the window with a narrower query before assuming the flag is irrelevant.

## Traces: fast, complete, and missing something

Twenty sampled frontend traces, 92 spans. Root durations ran from about 1ms to 48ms; the slowest was a loadgenerator-rooted POST at 46.7ms, and that time was almost entirely frontend self-time. Downstream services visible under frontend were cartservice (with Redis HGET/HMSET children at 0.3–0.6ms), productcatalogservice (server spans frequently sub-millisecond), recommendationservice and featureflagservice. None exceeded a few milliseconds. No span carried an error status, and every trace was structurally complete — no truncated or orphaned branches, no mid-flight cutoffs.

So three latency theories died here: a specific slow backend holding requests open (the callee server spans cannot account for the parent durations — one GetProduct client span of ~17.9ms sat against a ~0.0ms server span), cart/Redis contention, and request timeouts leaving incomplete traces. A checkoutservice involvement was also ruled out: across all 92 spans, nothing belongs to checkoutservice and no frontend client span targets a CheckoutService method.

The useful observation was an absence. adservice appears nowhere in the 92 spans. Combined with the code 14 errors, that absence is the closest thing to a positive identification of the unreachable peer — but note it is an inference, not a measurement. The sampled traces also cluster into two groups with a gap between them, which may be sampling and may not be.

## Change history: two empty answers and one hit

Change history for frontend across a full 24-hour window returned nothing at all — no deploys, no config edits, no flag toggles, no resource adjustments. The query was scoped to the seed service only, so this speaks to frontend itself and not its neighbours. Rollback of frontend is not an available remediation path; there is nothing to roll back to. The same query against checkoutservice, at one-hop radius, was equally empty across onset and the following day, closing both the deploy and config paths for that service and its immediate neighbours, and ruling out any undocumented in-incident hotfix there.

The hit was on adservice. Exactly one change is recorded in the window: platform-automation lowered the ad-service workload memory limit to 256m, where no explicit limit had previously been recorded. It landed roughly three minutes before onset. No deploy, no image rollout, no replica or scaling change, no feature-flag entry — the change set is that one limit edit. The actor is automation, not a human, which matters for remediation: there is no on-call engineer who owns this rollback, and reapplying the old state likely requires disabling or overriding the controller that applied it.

## Two adservice dispatches that answered the wrong question

Both adservice investigations covered a window roughly a day earlier than the incident, and neither queried the series that would have settled things.

The metrics dispatch ran an error-ratio query and got no samples at all — not in the window, not in the six-hour baseline before it. Because the absence is identical in both periods, it reads as missing or mislabeled call instrumentation under that service name, not as a service that went silent at onset. That symmetry is what kills the seductive reading of the empty result: a signal already absent while the system was healthy cannot mark onset. Critically, this result says nothing about restarts, kills, memory growth against the limit, or container availability, because none of those series were asked for.

The log dispatch found only routine per-request ad-serving lines with trace context across its six hours — no startup, no shutdown, no memory-kill, no listener-bind errors. The service was demonstrably alive and serving at several points. But the window is the wrong day, and the result was truncated to the oldest 8 and newest 32 lines, so the tight bursts separated by long silences are a truncation artifact and must not be read as traffic gaps. Treat both of these as unexecuted work rather than as exculpatory evidence for adservice.

## Where it landed

The coherent reading: adservice containers began exceeding the newly imposed 256m cap and were killed and restarted, leaving no reachable endpoint for frontend's ad RPCs. Frontend's calls to it fail at the connection layer with code 14 rather than returning served errors, which is exactly why the aggregate error ratio fell instead of rose — the ad path contributes fewer completed error-status spans, not more. The mechanism is memory pressure against the cap; the limit edit is the trigger, not the failure itself. Fix class is a revert of that configuration, applied against the automation that set it.

Confidence is medium, and the reasons are specific. There is no direct evidence of kills, restarts, or memory-versus-limit for adservice in the incident window — both adservice dispatches looked at the wrong day and never queried those series. The code 14 errors name no host and no callee, so the identity of the unreachable peer rests on the change record plus adservice's absence from 92 spans, not on observation. And the truncated frontend log leaves the earlier code-13 regime's decay and the product-catalog flag's current state unknown. The first three queries for anyone picking this up: container restart and OOM-kill counters for adservice in the actual incident window, memory usage against the 256m limit for the same period, and the untruncated middle of the frontend log stream.
