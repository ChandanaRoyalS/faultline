# Checkout failures traced to an absent cart backend after a cart image update

## What was visible, in order

Offsets are relative to T+0, the cart image reference update. Three alerts fired: checkoutservice, frontend, loadgenerator. Only checkoutservice was ever dispatched to; frontend and loadgenerator were never investigated, so nothing here is a finding about them.

The first framing error was the clock. The page landed around T+3m15s and we initially hunted for a trigger there. checkoutservice's error ratio actually steps up at a single change point near T+1m30s, so the search had to be pushed earlier, not later. That ratio averaged ~0.077 against a ~0.0036 baseline, peaking near 0.67. One change point, not a drift - so this was neither a chronic problem finally noticed nor a slow ramp. And with the minimum still touching zero, it was not a total outage either.

checkoutservice's own logs carried nothing above info severity: no exception, no gRPC status, no named downstream. Early in the window PlaceOrder completed a full sequence - start, payment with transaction id, confirmation email, queue write. Late in the window only request-start lines remained. Payment, email, and the queue write were therefore all discarded: execution never reached even the payment line, so the break sits upstream of all three. Those continuing start lines also proved checkoutservice itself was alive and taking traffic throughout.

## The one hop that ended it

Ten failed checkout traces, all identical: frontend HTTP POST, frontend PlaceOrder, checkoutservice PlaceOrder, prepareOrderItemsAndShippingQuoteFromCart, then checkoutservice's client span to CartService GetCart. That leaf is the only erroring span and the deepest error in every trace; ancestors are propagation. Leaf durations 1.8-4.2ms, whole traces 2.6-8.1ms - fast refusals, nowhere near a deadline. This killed latency exhaustion outright, killed the frontend/checkout handler as origin (PlaceOrder self time ~0.1ms, the preparation span near zero with no error of its own), and killed per-request triage since ten of ten were the same shape.

Then the change history. cartservice's image reference moved to hotfix tag v1.2.1-cartservice-hotfix.2 at T+0 - the only change in effect at onset, and the only one in a day of nineteen automated changes without a paired revert. cartservice logged an orderly application-shutdown at that same moment and emitted nothing for the rest of the window, after serving normal traffic right up to the final seconds. The replacement artifact never resumed serving. Fix class: rollback.

## Dead ends worth keeping

Four unmeasured edges were crossed, and the natural fear was that the true first failure hid on one of them - accounting, currency, payment. Trace topology settles it without measurement: no span for any of those three appears in any of the ten traces, because checkout aborts at the cart lookup before they are attempted. Unmeasured does not mean unranked when ordering is visible.

The checkoutservice change query returned nothing at all, which reads reassuringly but is partly an artifact: the window began at the page time and ran forward a day, so it could never have shown a pre-onset change on that service. Treat 'no changes on checkoutservice' as covering onset onward only.

cartservice's busy change history offered two tempting culprits - a cache address override to redis-cart:6380, and a traffic-shaping sidecar with a 300ms delay. Both were reverted or removed more than four hours before onset and never reapplied. Neither was live.

Attempting to confirm cartservice from metrics failed: the span-derived error-ratio query returned zero samples in both the incident and baseline windows. The absence predates the incident, so it is not a symptom of it - but an empty result is not a healthy result either.

Still open: no pod-level evidence, so whether the hotfix image failed to pull, crash-looped, or exited at startup is inferred from log silence alone. And a mean error ratio of only ~0.077 with a minimum at zero is hard to square with cartservice being wholly absent; a partial rollout with surviving replicas, or a client-side fallback, would explain it but was never checked.
