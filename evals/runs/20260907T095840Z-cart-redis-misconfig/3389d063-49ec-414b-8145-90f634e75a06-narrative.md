# Checkout orders begin and never finish; blocking dependency unidentified

## What we saw first

The page came from three places at once: checkoutservice, frontend, and loadgenerator. That combination reads as "orders are not completing," not "a box is down" — loadgenerator only complains when the synthetic checkout path stops returning. Declared blast radius was twelve services, severity critical, with checkoutservice as the origin point. Four edges out of checkout were never measured by any tool during the investigation, and that gap is the reason this record ends without a named culprit.

The first useful shape came from checkout's own error ratio at its service boundary. Over roughly two hours of samples the ratio averaged about 28%, peaked near 0.67, and repeatedly dipped all the way to zero. Dispersion was nearly as large as the mean. That is a bursty, partial signal — not a plateau, not a smooth ramp. Two hypotheses died right there: checkout is not in a hard outage (a majority of requests still succeed on average, and the ratio never touches 1.0), and checkout is not innocently propagating someone else's clean-status failure (it is emitting error-status spans on a substantial fraction of its own calls).

## The log sequence that decided it

Checkout's logs were the strongest evidence in the whole record, and they were strong by what they omitted.

Early in the window — around T-60m relative to the alert — every order printed a complete four-step sequence: PlaceOrder start, payment confirmation, order-confirmation email, then a successful broker write with an incrementing offset. From roughly 09:58 onward, only the PlaceOrder start line appears. Steadily. At a normal rate. And then nothing. No payment line, no email line, no broker write.

Critically, checkout logs no diagnostic at all when the sequence stops. Every retained line in the window is informational severity; there are no error or warning lines anywhere, and no downstream service name or RPC target appears in any of them. A call that returned an error would have been handled and logged. A call that blocks forever produces exactly this: an accepted request, a start line, and silence. That is the signature we built the conclusion on.

Three candidate stories were eliminated by the same lines. Checkout did not crash or lose traffic — PlaceOrder start lines continue steadily right through the end of the window, so the process is alive and serving. This is not a payment-decline surge — payment lines are absent entirely rather than showing failures, so the stall is upstream of any payment outcome. And it is not the broker write, the final step: the sequence never reaches the payment or email steps that precede the write.

## Dead end: paymentservice

paymentservice was the obvious suspect and it took real work to clear it, so keep this section — the next responder will suspect it too.

Inbound charge requests kept arriving well after the order completions stopped; the newest retained lines cluster from 09:57:01 to 09:58:35. Every received-request line has a matching completion line under the same trace_id, usually within about a millisecond. No orphaned request lines, so the classic "accepts and never answers" pattern is absent here. All lines informational — no declines, no timeouts. Request-to-completion deltas in the post-onset slice match the earlier baseline lines in the same result, so no latency degradation. Same pid and hostname in the oldest and newest lines, so no restart.

The one thing that looks damning is that paymentservice emits nothing after 09:58:35, roughly 4.7 minutes before the window end. Read in isolation that looks like a hard stop. Read alongside checkout's logs, it is the consequence: checkout stopped reaching the payment step at almost exactly that moment. paymentservice went quiet because nobody was calling it.

A second attempt to reason about payment from metrics was worthless and should not be repeated as-is. The error-ratio query returned zero samples in both the incident window and the preceding baseline hour. The "no departure from baseline" verdict there is vacuous — it comes from absent data on both sides, not from observed health. Because the gap predates onset by a full hour, this is a naming, label, or instrumentation gap in the calls_total series for this service, not a window-specific collection failure. Do not treat that empty result as evidence that payment is fine; treat it as a broken measurement.

## Dead end: the change log

We queried change history for checkoutservice, paymentservice, and currencyservice. All three came back completely empty — no deploys, no config edits, no flag flips.

What that legitimately rules out: no in-incident change on any of the three prolonged or worsened the symptom, no ongoing deploy churn, and there is nothing to roll back as an immediate remediation. For checkoutservice the window extends more than 24 hours past onset and records no activity of any kind, including remediation deploys.

What it does not rule out, and this is the trap: the windows for paymentservice and currencyservice both begin at alert time and run forward. They cover the aftermath, not the run-up. The period a change would actually have landed in — before onset — was never examined for those two services. An empty change log with a badly placed window is not a clean bill of health.

## The gap that stopped the investigation

The single query that would have named the blocking dependency did not run. The trace lookup for checkoutservice over the incident window came back with a server-side error, HTTP 500, and returned no span data at all.

This must not be misread as "there were no failing checkout spans." It is an execution failure, not an empty result set. It carries zero information about whether failing spans exist. With no spans, there is no way to order the cascade across the four unmeasured edges out of PlaceOrder, and no way to see which child call errors or times out first.

Worth noting for whoever picks this up: the tracing backend being degraded during this exact window may itself be a secondary symptom of the same event, or it may be independently unhealthy. We did not distinguish the two. Retrying the trace query is the highest-value next action by a wide margin.

## Where we landed

Checkout requests are hanging rather than erroring. A synchronous downstream call on the PlaceOrder path, upstream of the charge call, has become unresponsive and is holding checkout's request threads. That mechanism explains both the log signature (start line, then silence, no diagnostic) and the bursty partial error ratio at checkout's boundary — deadline expiry on a subset of in-flight orders, which is why the ratio oscillates between zero and roughly two-thirds instead of pinning high.

Confidence: medium. The mechanism is well supported; the culprit is not identified. No fix was applied.

Open questions, in the order worth attacking them:

Which call in PlaceOrder is blocking? Currency, cart, product catalog, shipping, or something else entirely. The trace query failed and no specialist measured those edges directly. Start by retrying traces; failing that, go to the client-side error counters or the candidate dependencies' own logs.

Was there any change on paymentservice or currencyservice before onset? Both change-history windows start at alert time and only cover the aftermath. Re-query with a window that reaches backward.

Is checkout thread- or connection-pool saturation amplifying this? Plausible given the blocking mechanism, but entirely unmeasured — we retrieved no saturation, latency, or request-rate metrics for checkoutservice, only the error ratio.
