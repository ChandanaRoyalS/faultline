# Checkout EOFs traced to a silently restarting email service

## What was visible, in order

The page came from checkout. Set T+0 at the alert; the metric change point sits about two minutes earlier, when the span error ratio crossed 5%. Shape mattered more than magnitude: the 32-minute baseline was flat at exactly zero across 129 samples, so there is no chronic error floor to blame. During the window the ratio averaged about 1.2% with a peak near 7.4% and a standard deviation of about 2.5% — bursty, partial, not an outage. Roughly 93% of spans still completed clean even at peak. Onset was abrupt and bounded, so there was no reason to hunt hours earlier. Note that only the error-ratio template actually ran; request rate and latency percentiles for checkout were never retrieved, and nothing was broken out by RPC method.

Traces then gave the real shape. In all three erroring traces the error sits in the same place: a checkout-side outbound HTTP POST client span, child of PlaceOrder, with status message EOF — the connection closed before a response arrived. That span has no child span from any downstream service, so no server side was ever recorded and the callee cannot be named from topology. It is also the latency sink: roughly 458ms, 654ms and 488ms, about 89%, 91% and 80% of their traces, essentially all self-time. Checkout does not abort — it goes on to EmptyCart, ship-order and an orders publish, which is why the error ratio is partial. One sampled trace in the window has no error at all but carries a large unexplained self-time block inside PlaceOrder, so the behaviour is intermittent. Ten traces matched and four were shown, so the sample is partial.

## Dead ends worth keeping

Checkout's own logs returned nothing — not at onset, not anywhere in the 32-minute window. The absence is total, which rules out both an explicit error message from checkout and the idea that it was logging normally with a brief burst. Everything had to come from metrics, traces and neighbouring services. Do not re-run that query expecting more.

Change history on both services looked promising for about as long as it took to read the timestamps. Checkout had eight entries, all one environment variable (CURRENCY_ADDR) alternately set and unset in four matched pairs by the same automated actor on a 10–20 minute cadence, reading like a reconciliation loop fighting itself. No deploys, no releases, no human edits. It stopped roughly 19.8 hours before onset and ended on the revert side. Email had the same shape: eight image-reference updates and reverts in four matched pairs by the same automation, net state unchanged, last event a revert about 16.4 hours before the alert. Nothing landed near onset on either service and there is nothing pending to roll back.

The traces cleared every instrumented dependency. Cart (with its Redis and flagd children), currency on both client and server side, payment's Charge, and product catalog's GetProduct with its SQL children all completed without error in single-digit milliseconds. Shipping was the most tempting wrong answer because checkout does POST to it — but the get-quote and ship-order spans all succeed and all have shipping child spans, while the erroring POST has none. Aggregated slowness also fails: one span owns 80–91% of each failing trace, entirely self-time.

## Where it landed, and what is still open

Email was nearly missed because it is invisible to both tools that were working. Its error-ratio query returned no samples in the incident window and none in the baseline either — the silence is not new, so it is not a service that went quiet at onset but one that emits no span-call metrics under that name at all. Consequently no email span appears anywhere in the sampled traces. That looks like exoneration and is not.

The log told the story. Early in the window email was handling order-confirmation POSTs with 200s and single-digit-millisecond latencies from one upstream client — healthy. The tail contains no request handling whatsoever, only three complete Sinatra/Puma boot sequences at roughly T+1m, T+1m30s and T+2m: version, thread settings, environment, PID 1, listener bound on port 6060, each one running to completion and reaching a serving state before dying again. A cycle of about 22–28 seconds. There is no exception, no stack trace, no 4xx/5xx line, no rejected or malformed request anywhere in the output. That rules out a silent hang, a startup or bind failure, and a bad-payload theory. A process that boots cleanly, serves briefly and is killed with no application-level error is being terminated from outside for exceeding a resource limit; each kill severs in-flight connections, which is precisely what checkout records as EOF on a childless POST to a plain HTTP service on port 6060. Fix class: scale. Confidence: medium.

Three things remain unproven. No memory, CPU, file-descriptor or kill evidence for email was gathered — the mechanism is inferred from the silent-kill signature, and container exit codes, restart counts and a memory series would settle it. The erroring callee is inferred, not proven: the POST span names no target, so confirming checkout's outbound host and port for the confirmation call would close it. And email's log was truncated to the oldest 8 and newest 32 lines, leaving roughly the middle half-hour of the window unobserved and the first crash time unknown.
