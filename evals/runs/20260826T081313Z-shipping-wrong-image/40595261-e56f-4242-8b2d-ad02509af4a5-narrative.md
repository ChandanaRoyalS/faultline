# Checkout order placement failing on shipping quote calls after an automated image update

## What was visible, in order

Take the checkout alert marker as T+0. checkoutservice paged first, with loadgenerator behind it; a second wave followed at roughly T+3m30s (quoteservice) and T+3m45s (accountingservice, emailservice, frauddetectionservice). Metrics confirmed the checkout alert was real and not a telemetry gap: a dense, unbroken 61-point series over the fifteen-minute window, error-to-total call ratio running from zero at the low end to roughly 0.28 at peak. The genuine zero minimum means onset is visible inside the window rather than predating it, and the 0.28 ceiling means the majority of checkout calls still succeeded — a partial failure, never a total outage. No data came back for cartservice, currencyservice, paymentservice or productcatalogservice, and no latency percentiles for anything, so metrics alone could not order degradation across services.

Traces settled direction of causality. Every failing trace has the same spine — frontend POST, frontend PlaceOrder, checkoutservice PlaceOrder — and the deepest span carrying an error is always checkoutservice's outbound call to ShippingService/GetQuote. The statuses above it are inherited. Two details did the work: no shippingservice server span exists beneath the erroring client span in any sampled trace, and the failures are fast (2–3ms on GetQuote, under ~12ms end to end). That is an RPC refused at connect time, not a handler returning an error and not a deadline breach. The pattern held across every sampled failing trace.

## Dead ends worth keeping

Cartservice and its Redis backend were the first suspect, sitting directly on the checkout path — GetCart and the nested HGET spans complete sub-millisecond and error-free in every failing trace. Productcatalogservice and the featureflagservice lookup it makes were next, since a flag-driven behaviour change would have fit the timing; both GetProduct and the nested GetFlag spans are sub-millisecond and clean even inside traces whose root fails. Currencyservice Convert spans appear repeatedly at effectively zero server-side duration with no error flag. Frontend and checkoutservice's own order-preparation logic were cleared by attribution: their error statuses are inherited upward from the shipping child.

The timeout theory consumed real effort and was wrong. The durations contradict it outright — nothing shows the elongation a deadline breach produces. Chasing latency percentiles here was wasted work; this is error propagation, not slowness.

Because checkout paged first, its change history was queried before shipping's. It came back empty: no deploy, no config edit, no flag flip in the interval. That kills three hypotheses at once — no checkout rollout before the marker, no config or flag flip at onset, nothing still landing during impact (the query ran to about T+5m and stayed empty). Caveat for the next reader: that query covered only about T-10m to T+5m and only checkoutservice's own stream. The intended sixty-minute lookback was not run, and the four direct dependencies were never queried for changes at all.

## The cause, and what remains unresolved

Shipping's change stream had exactly one entry in the window: an image reference update by an automation principal, platform-automation, about two and a half minutes before the marker. Two attributes make it causal rather than coincidental — the new reference carries a tag naming a different service than the one being deployed, and the prior image value is recorded as absent. That reads as a mistargeted automated rollout, not a version bump. No config or flag mutation appears for shipping in the window; the image reference is the only change type recorded.

Shipping's logs confirm it without needing the change record. Up to about T-9m40s the service logs normal work: quotes served with amounts returned, ship orders producing tracking IDs, no error-severity lines. Serving lines then stop. From about T-2m07s to the end of the window the only output is JVM and OpenTelemetry Java agent startup lines — options pickup, boot classpath warning, agent banner — repeating rapidly at first, then every 60–65 seconds. No request-handling line appears anywhere in that tail. The tell is the emitter change: the earlier serving lines are Rust-style tonic gRPC output, the later ones Java. Two runtimes under one service label in one window is what a wrongly-tagged image produces, and a process cycling through startup has no listener to answer GetQuote — which is exactly the trace picture. Ruled out here: no logged RPC failures against quoteservice (no status codes, no upstream named), no panic or stack trace, not healthy, and not cleanly down. Fix class is rollback; confidence high.

Open items. The shippingservice error-ratio query returned no series at all — numerator and denominator both empty. That cannot distinguish a crash-looping process that never gets scraped from a wrong metric or label schema; an empty result is not a healthy result, and a live service should show some non-error calls, so suspect the selector. Until it is settled there is no quantified baseline for shipping and no independent metric confirmation. quoteservice alerted and was never dispatched on; shipping's logs name no upstream, so whether it is a second victim, a co-casualty of the same automation run, or unrelated is unknown. The three T+3m45s services were not investigated — their link to checkout is inferred, and triage flagged five unmeasured edges. The identity of the wrongly-tagged image was not confirmed, and because the prior value is absent, the last-known-good reference must be recovered before reverting. Nobody checked whether the same automation run mistargeted other services. Finally, why checkout peaks near 0.28 rather than failing outright is plausibly explained by requests landing between restart attempts, but that was never confirmed against per-minute restart-versus-error timing.
