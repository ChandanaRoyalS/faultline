# Partial GetProduct failures from the product catalog service surfacing at the frontend

## What was visible, in order

Take T+0 as the moment error ratios crossed threshold. Frontend, loadgenerator and productcatalogservice all paged within minutes; the declared radius was seven services and the investigation started at frontend.

The first thing on screen was that this was not a slow burn. Frontend's error ratio had been exactly zero, with no variance, across the preceding half hour, then stepped up at a single change point with a peak near 8.4%. Productcatalogservice matched it against a four-hour baseline: 324 samples at zero, one change point at the same instant, peak near 9.3%. Two independent series agreeing on one change point set the search window for everything after. The failure was also clearly partial — nine in ten calls still succeeded — which killed the "service is down" model early.

By about T+2m the frontend logs were up. Every retained error line was the same gRPC status 13 INTERNAL, with detail text naming ProductCatalogService and attributing the refusal to an enabled failure feature flag. The stack frames sat entirely in the gRPC client's receive-status path, so frontend was reporting a status handed to it, not throwing. Status 13 with an application-level detail also rules out the transport family — the callee was reachable and answered fast.

Traces then fixed the origin. In every failing trace the deepest error-marked span was productcatalogservice's own GetProduct handler; its FeatureFlagService/GetFlag child, the cart and Redis spans, and the whole recommendation subtree were clean. Failing spans completed in about a millisecond, so nothing was waiting on anything. Only GetProduct failed — ListProducts succeeded inside a trace where GetProduct did not.

## Dead ends worth keeping

**The product catalog log query returned nothing, and that was the query's fault.** The Loki selector used the hyphenated value `product-catalog-service`; the service is named without hyphens. Four hours of total silence, including demonstrably healthy periods, is the tell. Nothing can be concluded from an empty result — and as a consequence the service's own logs were never actually read during this incident.

**Change history for productcatalogservice looked promising and led nowhere.** Two entries, both automation, both a traffic-shaping container attached to and detached from the network namespace with a fixed per-packet delay. Attractive, but attached and fully removed roughly fourteen and a half hours before onset. The same log showed no deploy, image bump, config edit or flag change for the service anywhere in the window.

**Cartservice's change history was the bigger rabbit hole.** Twenty automation entries in matched pairs — hotfix image tags, REDIS_ADDR pointed at an alternate port, traffic-shaping attachments — each reverted within eight to twelve minutes. Obviously synthetic exercise traffic, but every condition was rolled back before onset, with nothing at all in the hour prior. Traces independently cleared the cart and Redis path.

Also worth noting: frontend's error-ratio metric aggregates by service name with no downstream-target dimension. It proves the errors are new and abrupt; it cannot attribute them to any dependency. Don't try to read a per-path breakdown from it.

## Conclusion and what stayed open

Productcatalogservice is deliberately refusing a subset of GetProduct calls because its "ProductCatalogService Fail" feature flag is enabled. The unusual part is that there is no separate breakage to find: the wrong configuration value is itself the mechanism. Confidence high; remediation class is a configuration revert.

Open items for the next reader. First, no change record shows the flag being flipped, by whom or when — the state is inferred from error detail text and trace topology, and the flag service's own change history was never queried. Second, the timing does not line up cleanly: frontend errors appear roughly 90 seconds before the metric change point, and the log result kept only the oldest eight and newest thirty-two lines, dropping the middle of the burst. Third, why only 8–9% of calls, and only GetProduct, is unexplained; four of the seven in-radius services were never measured at all.
