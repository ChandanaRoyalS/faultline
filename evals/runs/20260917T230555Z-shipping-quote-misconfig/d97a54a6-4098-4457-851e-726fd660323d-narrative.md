# Checkout order flow halts on shipping quote lookup after a pre-onset endpoint edit

## What was visible, and the dead ends

The page arrived with checkoutservice as the seed and a wide blast radius: fourteen services touched, seven alerting (checkoutservice, loadgenerator, frontend, accountingservice, emailservice, frauddetectionservice, quoteservice). That breadth is misleading — it was one broken edge and six services noticing.

Checkout was alive. PlaceOrder entry lines continued at normal cadence through the end of the window, so nothing had crashed or lost its ingress path. What vanished was everything that used to follow them: earlier in the window each PlaceOrder was followed within ~20ms by a completion triplet (payment confirmation with transaction id, order confirmation email, successful message write with advancing offset). From T+0 onward the entry lines keep coming every 5-15s and the triplet never appears.

Two queries on the seed service were dead ends, and both are worth keeping. Checkout's change history returned nothing at all — but note the window *started at onset*, so it had zero coverage of the minutes before, which is exactly where the answer lived. It does legitimately exclude an in-window change to checkout, or a botched remediation there. The checkout error-ratio metric was more actively misleading: incident-window mean error share came in *below* baseline (~0.068 vs ~0.083) with identical maxima, and the only change points were hours early, peaking at a value already present in baseline — low-call-count spikiness, not onset. Traffic was continuous in every interval, so no silent outage either. Whatever paged us, it was not a checkout error-rate regression. Do not keep digging here.

## Traces narrow it to one edge; shipping is up and silent

Every failed checkout span after onset — eight traces from roughly T+2m to T+3m40s — carried exactly one error-bearing child: checkoutservice's client-side ShippingService/GetQuote call, propagating up through PlaceOrder to the frontend root. That explains the frontend and loadgenerator alerts without either being broken. The degrading hop was identical in all eight: prepareOrderItemsAndShippingQuoteFromCart to GetQuote. Because the abort happens inside that prepare step, all later stages are simply absent — no Charge, no EmptyCart, no ShipOrder, no email, no order publish, which is the likeliest source of the accounting, email, and fraud-detection alerts.

The pointer downstream: in failing traces the shippingservice HTTP client span has no quoteservice child, while the pre-onset baseline trace has shipping to quoteservice/getquote as the dominant hop. The call was not slow; it was not happening. Traces also closed off currencyservice (sub-2ms, clean), cartservice and its Redis HGET (sub-1ms), productcatalogservice and its flag lookup (sub-1ms), and paymentservice (never reached). It is not a latency story either: failing traces run 8.8-16.1ms, shorter than the 25.2ms healthy baseline.

Shipping logs confirmed it and added the odd part. From T+28s onward, ~30 inbound GetQuote lines arrive steadily and not one quote value is emitted — and no error, timeout, retry, fallback, or endpoint-resolution line anywhere. Silent, not a logged RPC error, which is why log searches for a named failing dependency came up empty on both services. Shipping did not crash (still accepting connections), traffic did not stop (normal gRPC metadata and trace context from a healthy Go client), no fallback engaged, the stall was total rather than selective across cities and cart shapes, and every request carried a populated address and at least one item.

## The cause, the fix, and what is still open

Shipping's change history — the query that should have run first, with a window reaching back past onset — has it. About three minutes before onset, platform-automation set shippingservice's quote endpoint environment variable from unset to an address that does not point at a live quote backend. The configured target is itself the mechanism. Two supporting details: the same set-and-revert pair had cycled roughly every four hours all day, with every prior set reverted within 10-40 minutes, and this one is the first with no revert recorded; and shipping's image reference, which had also been churning, last moved ~3.1h before onset with a revert to no override, so no code deploy is involved. All seventeen changes came from the same automation actor, and there were no flag flips.

Fix class: config revert — return the quote endpoint variable to unset. Confidence high.

Still open. Traces show fast failures (8.8-16.1ms) while both shipping and checkout logs read like hangs; whether shipping fast-fails and swallows the status or genuinely blocks was never settled. quoteservice's own health was never probed: its error-ratio series is empty in both incident and baseline windows, so the emptiness predates onset and is a never-populated series rather than a symptom — an independently-down quoteservice remains unmeasured, and it is unconfirmed that unsetting the variable restores a working default. The shippingservice error-ratio series is empty the same way, so metrics neither implicate nor exonerate shipping. We also never observed why the automation's usual revert did not fire this cycle, nor confirmed directly that the downstream alerters follow purely from the missing order-publish step. Five unmeasured edges were crossed and left unprobed.
