# Fraud detection service stuck in a silent restart loop after a memory ceiling reduction

## What the responder saw first

The page named a single service, frauddetectionservice, and nothing else. Blast radius stayed at one service for the life of the investigation; no downstream or upstream component was implicated and no unmeasured edges were crossed. Take T+0 as the moment of the alert.

The first instinct was to confirm the failing component through its error rate. That path went nowhere, and it is worth knowing why before you try it again. The span-derived call metrics for this service returned nothing at all — not zeros, not a flat line, but an empty result — and the pre-alert baseline window was equally empty. Because the silence predates the alert by the full baseline period, it is not a collection break that started with the incident; the series simply is not populated for this service name in this environment. Treat its absence as a gap in instrumentation, not as evidence of health. A second, wider metric pull over an earlier six-hour range produced the same empty answer and, being over the wrong hours, could not have characterised the period of interest anyway. Throughput, latency percentiles, restart counts and memory saturation were never retrieved.

## The logs, which is where the shape appeared

Logs told the story metrics could not. Early in the window the service is plainly healthy: Kafka record consumption logging with a steadily advancing order counter, running through roughly T-26m. After that, consumption logging stops entirely and never returns.

From about T-5m40s onward, the same three-line JVM and agent startup sequence repeats over and over — the tool-options pickup, a benign VM class-sharing warning, and the agent version banner. A full boot sequence is only re-emitted by a fresh process, so this is termination and respawn, not a hung or merely slow process. The first few restarts are seconds apart (roughly T-5m37s, T-5m28s, T-5m13s, T-4m46s), then the cadence settles into a near-exact 62-second rhythm that continues through the end of the window, past T+1m20s.

Two things a responder should carry away. First, the alert timestamp sits inside an already-running loop, not at its onset — at least ten distinct startups precede and follow it, so do not read T+0 as the beginning of anything. Second, every cycle dies silently: no exception, no panic, no stack trace, nothing between the agent banner and the point where application logging should have begun. The agent attaches cleanly every single time, so "instrumentation failed to load" is not it. Whatever kills the process leaves no trace on stdout, which means exit codes and container events — not logs — are where a definitive answer lives.

## The change log, and the pattern hiding in it

The change history for this service in the window contains seven entries, all of one kind: memory resource-limit adjustments, all issued by the same platform-automation actor. There are no deployments, no version bumps, no flag flips, no shared-config edits, no library upgrades, and no human-operator actions. Each of those was checked and each was ruled out on the same basis — the records simply do not exist for this service in this window.

The most recent entry, at roughly T-6m, lowered the memory ceiling to a tightly constrained value. The restart loop becomes visible about thirteen seconds later.

The part that took longest to make sense of: this exact lower-then-restore cycle had already happened three times in the preceding fifteen hours or so, at roughly fourteen, ten and seven hours before the alert. Each of those earlier lowerings was followed by a restore within eight to twelve minutes and produced no sustained outage. The pre-alert lowering is the only one with no matching restore in the window, and the constrained state is therefore the one still in effect at onset. So the action itself is routine; what is anomalous is that nothing undid it.

## How the conclusion was assembled

Nothing directly observed says the process was killed for exceeding its allocation. The reasoning is: a JVM that dies repeatedly and silently after its agent banner, on a fixed cadence, immediately after its memory ceiling was cut, with no application error of any kind, is the signature of the process being terminated externally rather than failing on its own logic. The automated edit is the trigger; the mechanism is the process being unable to run inside the allocation it was given.

Confidence is medium, and the medium is doing real work. Fix class is a revert of the change — restore the prior memory ceiling and confirm the loop clears.

## Dead ends and what is still open

Dead ends worth not repeating: the error-ratio metric for this service is not a usable detection channel and will return empty no matter which window you point it at; and any attempt to find a named crash cause in stdout will fail, because the process leaves none.

Still open, in order of usefulness:

First, no termination-reason, restart-count, or memory working-set data was ever pulled. The kill mechanism is inferred, not observed. Fetching container termination reasons and restart counts is the single cheapest step that would convert this from medium to high confidence.

Second, the log window is truncated at its early edge, so the loop's true beginning is not visible. It is not proven that the loop started after the change rather than shortly before it. Extending the log window backwards would settle the ordering.

Third, and most interesting for prevention: why did three identical lowerings to the same value produce no comparable outage, and why did the usual restore never fire this time? Either the earlier windows were short enough that the loop never became visible, or something about the restore path did not run. That question is entirely unevidenced by what was gathered.
