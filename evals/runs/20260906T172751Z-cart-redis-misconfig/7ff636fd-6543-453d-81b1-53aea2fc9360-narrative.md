# Checkout failures traced to the cart dependency; email template defect a decoy

## What we saw first

The page came in on three services at once: checkoutservice, frontend, and loadgenerator. That shape — a leaf-ish business service plus the web tier plus the traffic generator — reads at first glance like a frontend or checkout outage, and that is how the first hour was spent. Blast radius as counted at the time was twelve services, with the seed set at checkoutservice. Four edges in that radius were never measured at all, and one of them turned out to be the important one.

First hard signal was checkoutservice's error ratio. The three-hour baseline is flat zero — mean, min, and max all zero, no variance — and then the ratio climbs to roughly 12% mean with peaks near 67%. It never reaches 1.0 and it repeatedly falls back to zero. Threshold crossings land at about T+78m into the metric window, then again roughly an hour later, then again near the end. That pattern said three useful things early: this is new, this is partial, and this recurs. It also said the trouble did not begin when our query window began.

One metric interval had no defined ratio at all — no traffic in that bucket, which is not the same as no errors. Worth remembering when reading the burst pattern.

## The dead end that cost the most time: emailservice

checkoutservice logs at onset are full of warnings about failing to send order confirmation. The only downstream named anywhere in those lines is the email service, over an HTTP POST returning 500 where 200 was expected. No gRPC target appears in any error line. That is an extremely inviting thread and it was pulled hard.

emailservice's own logs confirmed the 500s and explained them: an unhandled Ruby NoMethodError — a method call on nil — raised while rendering the order-confirmation view template, with the stack trace running through the templating layer inside the Sinatra handler. In-process, deterministic, before any delivery step. That rules out SMTP trouble, an unreachable service, network problems between the two, and any saturation story: the handler was up, routing worked, and later successful sends complete in single-digit milliseconds.

The reason this is a dead end and not the answer: checkoutservice logs those confirmation failures at warning severity, and each affected PlaceOrder is preceded by a successful payment with a transaction id and followed by a successful message write with an incrementing offset. The order pipeline walks straight past the email problem. It is a real defect. It is not what broke checkout.

Also note emailservice had recovered on its own well before the log window closed — from roughly T+26m in that window onward, the confirmation endpoint returns success continuously. The log result was truncated (oldest 8 and newest 32 lines), so error volume and the exact moment the 500s stopped are not recoverable from what we have.

## Where the traces actually pointed

Traces settled it. Every sampled PlaceOrder trace in the three-hour window has the same five-span shape: frontend HTTP POST, frontend PlaceOrder client span, checkoutservice PlaceOrder handler, prepareOrderItemsAndShippingQuoteFromCart, and a CartService GetCart call. The deepest span marked ERROR is the cart lookup. The error status then propagates up through the checkoutservice handler, the frontend gRPC client span, and the frontend HTTP span. Critically, the intermediate prepare-items span carries no error status of its own — the failure is inherited from the cart call, not generated in checkoutservice logic.

The flow aborts at cart, which happens before payment, shipping, or confirmation. That is why no email span appears in any erroring trace, and it is the cleanest disproof of the email hypothesis available: those requests never reach the confirmation step at all.

Timing rules out anything patient. Root spans sit in the 1–3ms range, the cart child spans under about 1.2ms. One root reached roughly 10ms but its checkout subtree stayed sub-millisecond. Failures return immediately. There is no deadline being exhausted and no queue backing up.

By elimination the later gRPC dependencies — payment, shipping, currency, order placement — cannot be the origin, because no spans for them are emitted at all.

## Change history: two empty windows

Change history for checkoutservice over the window returned nothing — no deploys, no config edits, no flag flips. Same for emailservice. Both queries were scoped to the seed service only (hops=0), so neither says anything about the dependencies.

Both windows also share a defect the reader should not repeat: they open at the onset timestamp and run forward about a day. They cover changes concurrent with and after onset, and say nothing about the hours preceding it. So "a change during the incident triggered this" is unsupported for both services, and "a rollback explains recovery" is likewise unsupported — but "something changed shortly before onset" was never actually tested.

## Conclusion, and its limits

The requests that error originate one hop downstream of checkoutservice, in the cart dependency. checkoutservice is reachable, executing normally, and emitting spans right up to the GetCart call it inherits the error from. The email template defect is a genuine but separate, non-fatal bug that happened to be loud in the logs.

Confidence is medium, and the honest reason is that no dispatch touched cartservice. We can name the failing service; we cannot name the mechanism. No cartservice logs, metrics, resource data, or change history were collected, so crash, memory pressure, a backing-store refusal, or a bad rollout are all still live and mutually undistinguished. No fix class is proposed.

One unreconciled conflict remains on the record. The metrics show episodic bursts peaking near 67% and returning to zero; the traces show uniform total failure with every sampled trace in error and an identical shape. Those two readings do not sit comfortably together. The sampling windows differ and that difference was never chased down — it may be trace sampling bias, it may be that the trace window overlaps only the burst intervals. Whoever picks this up next should start there, and should start with cartservice.

## What did not matter

For the next responder, the following were checked and are not worth re-running: payment (completes with transaction ids immediately before the confirmation warnings), the order-placed message write (sequential offsets, all successful), a single-customer or single-currency theory (distinct user ids, both CAD and USD affected), a chronic pre-existing error background on checkoutservice (baseline is exactly zero), a small-denominator artifact in the error ratio (431 defined samples, one gap), a timeout or saturation story (everything returns in single-digit milliseconds), and any theory that checkoutservice itself is broken.
