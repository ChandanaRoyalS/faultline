# Frontend partial errors traced to an adservice restart loop after a memory ceiling change

## What was visible, in order

Offsets run from the start of the observed window; the pages land around T+10m on frontend, loadgenerator, and adservice. Frontend's error ratio is real but partial — it moves between zero and about 9.1% and returns to zero before the series ends. Not a total outage, not flat noise. Coverage is incomplete: only about T+0 to T+15m of the requested half hour was returned.

Frontend stdout is full of Node gRPC client errors, status 14 UNAVAILABLE, with a connection-not-established detail and grpc-js stack traces — oldest kept lines near T+5m25s, a dense burst near T+12m55s. These are outbound client failures, not frontend's own handling, and there are no deadline-class statuses at all, which rules out a slow-but-reachable upstream.

Traces localize it. Checkout is clean: PlaceOrder at 26–28ms, every child bounded and accounted for, no errored span on that path; productcatalog, cart, and recommendations are all healthy. The failing edge is elsewhere — an errored frontend GET of ~3095ms wrapping an errored AdService/GetAds span (~3094ms) wrapping an errored frontend-side tcp.connect of ~3092ms, with no server span on the callee at all. A loadgenerator-driven trace shows the same ~3.1s ceiling, which reads as a fixed deadline rather than variable slowness.

## Dead ends worth keeping

Frontend change history returned nothing for the window — no deploys, no config or routing edits, no client dependency bumps. Worth recording, because the instinct on a frontend page is to roll back the last frontend release; there was nothing to roll back.

The frontend log lines name no upstream. Only the status code, detail string, empty metadata, and library frames. A responder can burn real time trying to extract a target from them. It isn't there — the callee had to come from traces.

adservice call metrics were queried twice and came back empty both times. Critically the unfiltered denominator is empty too, so this is not 'zero errors' but 'no call telemetry at all'. No error-rate spike will ever appear here, and re-running the query is wasted effort. adservice CPU, heap, thread-pool, and GC were never measured, and neither were working set against the limit, restart counts, or last-terminated reason.

## Cause as it stood, and what remained open

adservice logs normal ad-request handling early in the window, then from about T+5m30s the stream becomes nothing but repeated JVM and OTel-agent startup banners on a ~60s cadence through at least T+13m35s — ten-plus cycles, a sustained loop rather than one crash or a rolling restart. No cycle reaches an application-level 'listening' line and no request handling resumes. Notably absent: any exit-137 notice, memory error, or startup exception; each cycle simply stops after the banner.

One change landed on adservice: platform-automation lowered the container memory limit to 256m at about T+5m08s, roughly twenty-two seconds before the loop begins. No deploy, image rollout, or flag change exists in the window, and no prior limit value is recorded. Read forward: the process apparently needs more memory than the new ceiling allows, dies during startup, restarts, and never binds its listener — hence connection-establishment failures at frontend, absent adservice metrics, and impact confined to ad-bearing renders. Confidence medium; indicated fix is reverting the configuration.

Open items: the memory-kill is inferred, not confirmed — a kubelet-level kill would surface in pod events nobody retrieved, and a liveness-probe or other silent-termination cause is not excluded. The prior limit is unknown, so the safe restore value is unknown until the actual working set is measured. Whether every status-14 burst, including the earliest lines, targeted adservice is unsettled. One unmeasured edge flagged at triage was never identified or probed. Nothing covers the period after T+15m, so it is unknown whether the loop is still running or whether automation will re-apply 256m after a manual revert. loadgenerator alerted but was never investigated; its role is assumed to be synthetic client impact.
