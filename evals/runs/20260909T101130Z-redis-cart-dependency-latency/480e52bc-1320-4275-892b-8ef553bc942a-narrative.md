# Cart reads and writes stuck at a fixed ~300ms floor per cache round trip

## What was visible first

Four services paged together at warning severity: cartservice, checkoutservice, frontend, loadgenerator. Blast radius was drawn at twelve services from cartservice, though four of the edges crossed were unmeasured, so that figure is partly inference.

The first move was to ask cartservice what it thought was happening. The answer was: nothing. Its logs show a single clean startup roughly two hours before onset — backend connection established, self-test passed, listening on its port — followed by a dense, uninterrupted stream of cart read, add, and empty operations running past the end of the window. No error lines, no retries, no connection failures. That single startup followed by continuous traffic also closed crash-looping and image-pull problems without further work. A service healthy in its own eyes, while three callers page, pushes the problem toward latency or toward something the logs cannot see.

## The metrics detour

Pulling cartservice's error ratio against a two-hour baseline produced the least useful result of the investigation, and it cost time. The query returned no samples at all — not in the incident window, and not in the baseline either. The tempting reading is that traffic collapsed to zero at onset. That is wrong: the baseline is equally empty, so there is no healthy stretch to contrast against and the gap cannot be dated to onset. The emptiness describes the instrumentation for that series, not an event. The run also only exercised the error-ratio template; request rate, replica readiness, restart count, and latency were requested and none were answered.

checkoutservice's error ratio was populated and pointed the same way: well under one percent, roughly thirty times lower than the preceding hour, no sustained departure. Its erratic baseline (mean near fifteen percent, standard deviation exceeding the mean) reads as low or bursty volume destabilising a ratio, not a prior outage. That query carried no callee dimension, so it could say nothing about the cart-bound call specifically.

## Where it became visible

Traces were the turn. Ten traces, one hundred thirty-six spans. Every cartservice cache operation — reads and writes alike — landed between roughly 300 and 310 milliseconds. Not a distribution with a tail. A floor. cartservice's own handler self-time stayed under about 1.3ms, so the handler was blocked waiting, not working.

The arithmetic explains the whole radius: one cache call per GetCart is ~300ms, two serialized calls per AddItem is ~600ms, frontend roots chaining both land at 910–926ms. Everything else in the same traces was fast — currency, catalog, payment, ship-order sub-millisecond to a few ms, shipping quotes 10–19ms. No span carried an error status and every trace completed through payment, shipping, email, and order publish.

The tightness of that band is the most valuable fact in the record. Contention produces spread; a near-constant per-round-trip cost points at a fixed added delay on the cartservice-to-cache hop. Both callers showed it equally, which closed any single bad client.

## The change log, and why it argues with the traces

cartservice's change history shows twenty-four entries in twenty-four hours, all from one automated actor, forming a repeating three-part cycle: a hotfix image tag, attachment of a traffic-shaping container adding fixed egress delay on the primary interface, and a cache connection-string override. Each part is explicitly reverted. Four complete cycles, starting roughly 20.8h, 15.9h, 13.3h, and 2.1h before onset.

Read literally the log says nothing was applied at onset: image revert ~1.9h before, shaping detach ~1.6h before, connection-string revert ~1.3h before, leaving a gap with no change of any kind. The traces disagree — a fixed per-round-trip delay on exactly the hop the shaping container targets is still in effect. Either that detach did not clear the rule from the interface, or a re-application went unrecorded. The log is an untrusted record of intent; the traces are observed behaviour. Believe the traces and go inspect the pod.

The log did legitimately close the hotfix image and the connection-string override, and confirmed no human change preceded onset.

## Dead ends worth keeping

Empty user id in cart-read logs. Real, present, and irrelevant. Trace data carried no span attributes so calls could not be partitioned by user id — but the outcome side closed it anyway: every cart-read span had the same outcome and the same 301–307ms band regardless of caller. There is no bimodal behaviour for a blank identifier to explain. checkoutservice's logs separately showed every placement carrying a well-formed UUID and valid currency.

The empty cartservice error metric as a traffic-collapse signal. The baseline is equally empty; the gap predates onset.

Frontend as trigger. Its change log is completely empty over the full twenty-four hours, closing session-id generation changes, cookie attribute edits, and any frontend-side reconfiguration of the cart client. No timestamp correlation is available there at all.

## Where it was left

Conclusion, at medium confidence: a fixed delay per cache round trip on the cartservice hop. Fix class is a configuration revert. checkoutservice and frontend paged because they waited, not because they failed.

Three things were never done and should be done first next time. Nobody inspected the cartservice pods or their interfaces directly to confirm whether the shaping rule was still present — that single check would have settled the disagreement between the log and the traces. The cache backend itself was never examined; a server-side slow log, CPU saturation, or a persistence stall could in principle produce a similar flat floor, and nothing here excludes that. And there is no pre-incident latency baseline: the returned traces all cluster inside a thirty-second span around onset despite a two-hour query window, so onset timing itself is unconfirmed.
