# Checkout failures traced to cartservice crash-loop on a wrong cart-store address

## What was visible first

Three alerts fired together: checkoutservice, frontend, loadgenerator. Blast radius was reported as twelve services with checkoutservice as the seed and four unmeasured edges out of it. The simultaneity reads like a checkout regression; it is in fact what a single failing leaf propagating error status up one call path looks like. The seed service turned out to be innocent, and everything below flows from that.

## Working the seed

Change history for checkoutservice over a day-long window came back entirely empty: no rollouts, no environment edits, no flag flips, no limit changes. That removed the obvious first hypothesis and also removed rollback of checkoutservice as a remediation path, since there was no prior revision to return to. Note the scope limit for anyone re-running it: seed only, zero hops, so it said nothing about dependencies.

The error-ratio baseline moved only about 1.1x against the preceding three hours, with no sustained departure. The series is naturally spiky, with bursts reaching two-thirds of requests in the baseline too, so no burst can date onset. Only the error-ratio template ran; request rate and latency percentiles were never retrieved.

Logs pointed somewhere. Early in the window each order line is followed within tens of milliseconds by payment confirmation, confirmation email, and a message-write offset. From roughly T-1m onward only order-start lines remain. Arrivals continue at several per minute to the end, so the process was alive and stalling silently, not rejecting. No warn or error lines appeared, and the result was truncated to the oldest eight and newest thirty-two lines, so the transition itself is unobserved.

## Traces narrow it to one hop

Ten sampled traces from roughly T+1m to T+2m are identical: frontend POST, frontend PlaceOrder, checkoutservice PlaceOrder, prepareOrderItemsAndShippingQuoteFromCart, and an outbound CartService/GetCart leaf. Five spans each, ten of ten. The error status sits on the GetCart leaf and is inherited upward to the frontend root, which fully explains the three simultaneous alerts.

This is not latency: roots complete in 1.2-2.7ms and the leaf is sub-millisecond. The tooling flags GetCart as 24-34% of trace time only because it is the sole leaf in a very short trace. No spans appear on any other checkout downstream edge, because execution aborts at cart retrieval before those calls are made, which retires the four unmeasured edges. One apparent conflict worth sitting with: logs describe a silent stall while traces show fast errors. Both are real; the log view is dominated by the truncated tail.

## The cause

cartservice never reaches request handling. From about T-1m its logs repeat every 30-60 seconds: a connection attempt to redis-cart on port 6380, a failure, then an unhandled exception that kills the process. Stack frames name the Redis cart store's connection-check and initialization routines called from program main, not any RPC handler. An hour earlier the same service logged ordinary successful cart operations.

Change history for cartservice gives the why: thirteen changes in the window, all from a platform-automation actor, none human. The nearest is an environment edit about two minutes before onset setting the Redis address to port 6380 from a previously unset state, with no matching revert. The identical edit was applied about 4.9 hours earlier and backed out nine minutes later, which is why it had not surfaced before.

## Dead ends worth keeping

A cartservice hotfix image was rolled out about 42 minutes before onset and reverted about 31 minutes before, so it was not the running image; the same roll-and-revert cycle appears twice more earlier in the window. A traffic-shaping sidecar adding roughly 300ms egress delay was attached about 21 minutes before onset and removed about 11 minutes before, so it was not active either. No resource-limit, quota, scaling, or flag change is recorded for cartservice at all.

On the checkout side: the service did not crash or restart (steady order-start cadence, no startup banner), inbound traffic did not dry up (arrivals continue; it is the completion steps that vanish), payment was not rejecting (no declination line, the step is simply never reached), and the failure is not user- or currency-specific.

cartservice metrics are a trap. The error-ratio query returned zero samples in both the incident window and a three-hour baseline. That is a missing series, not a telemetry loss at onset and not evidence of health. Do not spend time there.

## Fix and what remains open

Remediation class is a configuration revert: restore the cart service's Redis address to its prior unset default. The same edit has been backed out cleanly once before in this window.

Three things were never closed. First, redis-cart itself was never queried, so it is unknown whether nothing listens on 6380 or whether Redis was deliberately moved there and a missing listener, policy, or DNS entry blocks the path; that distinction decides whether the revert is the whole fix. Second, each connect attempt hangs 20-40 seconds before failing, which reads as an unreachable address or dropped packets rather than refusal on a closed port, and residual network-namespace state from the removed shaping sidecar was never examined. Third, coverage is thin: checkout logs were truncated so onset is unobserved, nine of the twelve services in the blast radius were never dispatched, and the seed change query covered zero hops.
