# Cart requests stalled by a fixed ~300ms per-command wait to redis

## What was visible, and the dead ends

The page named four services at once — cartservice, checkoutservice, frontend, loadgenerator — with a blast radius of twelve and four edges never measured at all. That breadth was the first thing that misled; it reads like a platform-wide event when only one hop was actually sick.

First move was cartservice error ratio against baseline. Empty. Not zero — no samples in the incident window and none in the baseline hour, and the same on a shorter window. The tempting read is that cartservice went silent at onset; that is wrong, because the absence predates the incident. The series simply is not collected under the service_name label used. Do not spend time here, and distrust other queries built on the same label. Request rate, latency percentiles, restarts and readiness were never retrieved for cartservice at all.

Cart logs were the second dead end: routine add/get/empty handler lines at both ends of the window, distinct sessions still being served in the final minute, no exceptions, no startup banners, no cache connection or auth errors. That closes crash-loop, image-pull, and hard-backend-loss theories but yields no lead. The result was truncated in the middle, so nothing here dates the change in behaviour.

Third, frontend's error ratio ran well below its own baseline with no sustained departure — the pre-incident hour was actually the noisier one. Frontend is not the origin and there is no broad fan-out failure. But the series has no route or peer dimension, so it neither confirms nor refutes a cart-specific story.

## The signal, from traces

Ten traces with cartservice as callee, all inside a narrow twenty-six-second slice late in the window. GetCart ~300-303ms, EmptyCart ~301-306ms, AddItem ~604-617ms — double because it issues two sequential cache commands.

The shape is the story. cartservice's own server-span self-time is sub-millisecond; essentially all duration sits in the client child spans, each HGET and HMSET costing ~300-310ms. Across three operations and ten independent traces the values pin into a ten-millisecond band just above 300ms. A fixed floor, not a tail.

That one observation killed most remaining candidates: not application logic or GC, since the server span is negligible; not shared infrastructure, since currency, catalog, payment, shipping and email calls in the same traces finish in 0-18ms; not errors, since every cart span completed OK and parent checkouts ran through to order publish; not N+1, since it is per-command cost not count; not upstream overhead, since caller spans exceed the callee by 1-3ms; not load-proportional queueing, which would not pin to a round number. The cart hop was the degrading hop in all ten traces, ~45-46% of checkout self-time, with frontend roots at 650-927ms.

## The change record, the conclusion, and what is still open

All twenty-eight cartservice changes in the window came from one automated actor, no humans. They form a six-step cycle repeated five times (roughly 19.4h, 16.9h, 10.6h, 5.6h and 2.1h before onset): hotfix image set then reverted; a traffic-shaping sidecar attached to the cart-service network namespace with a fixed 300ms egress delay then removed; REDIS_ADDR pointed at a non-default port then reverted. The 300ms figure matches the observed floor exactly.

But the log's bookkeeping argues against itself being relevant: every mutation has a matching revert, the shaper is recorded as detached ~1.6h before onset, and nothing is recorded as changing in the final ~78 minutes. Taken at face value it rules out all three mechanisms. The traces say otherwise. Two readings survive: the detach was recorded without taking effect, leaving the shaping discipline in the namespace, or an unrecorded sixth iteration landed and was never written down. Treat the change log as narration of intent, not live state.

Working conclusion at medium confidence: cartservice waits ~300ms on every cache round-trip, inflating AddItem and frontend roots; the frontend, checkout and loadgen alerts are propagated wait, not independent problems. Fix class is a config revert.

Still open, in order: nobody inspected live pod state to see whether shaping is present in the cart-service namespace right now; no redis-side metrics, logs or config were examined, so a ~300ms per-command cost originating in the backend itself is untested; and onset is unverified, since traces cover only a twenty-six-second slice and the logs were truncated mid-window.
