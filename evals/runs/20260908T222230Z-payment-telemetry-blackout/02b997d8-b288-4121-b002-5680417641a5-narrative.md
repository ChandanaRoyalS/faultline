# paymentservice paged while its charge path kept working: telemetry endpoint pointed at loopback

## What was visible, in order

The page named paymentservice alone. The first move was to find the error spike, and there wasn't one.

The span-derived error ratio for paymentservice returned zero samples in both the alert window and the two-hour comparison window. Not zero errors — no series at all. The tempting reading was that telemetry died at onset, but the comparison window is equally empty well before anything happened, so the silence predates the event and cannot time it. It may not even be about this event: four hours with no samples is at least as consistent with the query's service name label not matching reality. Unresolved.

Logs told the opposite story. Dense, regularly spaced, entirely info level: charges received, transactions completed about a millisecond later, each with a transaction id and card metadata. Continuous from roughly T+0.5m to T+2m, so no sustained error stream existed there and the charge path was still working at window close. Two caveats carried forward — the result is truncated to the oldest eight and newest thirty-two lines, so the instant of the page sits in the unreturned middle; and the reporting hostname differs between the head and tail blocks while the process id holds constant, consistent with a pod replacement at an unknown time. Never dated, never excluded.

Checking the caller: checkoutservice aggregate error ratio is flat zero across the whole window, 129 samples, max zero. Payment calls are a subset, so no error-status payment spans came from the caller. The surprise is direction — the prior baseline averaged around 0.16 with excursions to 0.67. Errors fell going into the incident. That query aggregates by service name only with no peer dimension, so it bounds rather than measures the checkout-to-payment edge, and it returned no latency or throughput.

## The dead end that nearly closed it wrongly

A trace query looked decisive against the eventual conclusion: paymentservice spans present in every completed checkout trace, correctly parented, no error markers, Charge finishing in a fraction of a millisecond. A black-holed exporter would leave a visible gap; instead the spans were there.

It does not hold, because of the window. The range runs 04:28 to 10:28 with samples clustered 08:02 to 08:16 — after the earlier revert and about fourteen hours before the re-application at T-6m. It shows healthy export under the correct value, not the post-onset state. This is the most useful mistake in the record: an authoritative-sounding negative scoped to a period where the condition was absent. Check the window before accepting a rule-out.

The same result surfaced something unrelated: in its slow traces, roughly 906 to 916ms of self-time sat on the checkout-to-product-catalog hop, about seventy percent of the trace, with payment contributing two to three milliseconds. One trace ended before reaching payment at all. A lead for someone else. Also truncated to six of sixty traces.

## Where it landed and what is still open

Only three changes touched paymentservice in the window, all from platform-automation, all the same environment variable: the OTLP traces endpoint set to a loopback address, reverted, set again. The most recent landed at T-6m — the only change with plausible proximity to the page. No collector listens at that address, so spans go nowhere and call metrics cannot be computed while the service keeps serving, which reconciles silent telemetry with healthy charges. The record also clears a deploy, a credential rotation, a flag flip, a dependency-side edit, and a human actor: none appear. The identical edit applied and reverted about sixteen hours earlier suggests an automation loop, so a revert alone will not hold.

Confidence medium. Still open: no trace query was run after T-6m, so span absence is inferred from the change record rather than observed — that is the highest-value next step. What the alert actually fired on is unknown; no latency, throughput, or saturation series was retrieved for either service. The empty paymentservice metrics may be a label mismatch, which would undercut metric silence as a signal. And the undated hostname change remains an alternative explanation for part of what we saw.
