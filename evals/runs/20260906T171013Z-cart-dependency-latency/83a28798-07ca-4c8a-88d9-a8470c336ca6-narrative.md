# Cart cache path stalls at a fixed 300ms, dragging checkout to ~2.5s

## What was visible, and the first dead end

The page was warning severity: twelve services in the blast radius, cartservice named as origin, alerts on cartservice, frontend, checkoutservice and loadgenerator. Triage also noted four unmeasured edges crossed; those gaps were never closed.

The obvious first move — check cartservice's own health — wasted time. The error-ratio metric came back clean, and the clean verdict was worthless: zero samples in the incident window and zero in the two-hour baseline. Empty compared against empty reads as "no departure from baseline" and means nothing. Only that one query ran; request rate, latency percentiles, restarts and readiness were requested and never answered. One genuinely useful byproduct: because the gap predates onset by hours, this is not a signal blackout caused by the incident, so "cartservice crashed and went silent" is off the table.

Logs were better. Across two hours cartservice logged only routine handler lines for cart read, add-item and empty-cart — no exceptions, no connection failures, no startup banners — and in the final thirty seconds it was serving many distinct users at sub-second spacing. That rules out crash-looping, being down, losing its cache connection, and persistent post-onset degradation. Caveat: only the oldest 8 and newest 32 lines came back, so the onset minute itself was never retrieved. A recurring cart read with an empty user id appears in both segments and is background noise, not a symptom.

## Traces gave the shape; the change log gave the name

Every cartservice server span is a near-exact multiple of ~300ms — GetCart and EmptyCart ~301-306ms, AddItem ~602-607ms — and each decomposes into cache round trips (HGET, or HGET plus HMSET) of ~300-305ms apiece. The handler exceeds the sum of its cache children by one or two milliseconds, leaving no room for application compute. Across ~30 operations the spread stays 300-305ms with no tail, so this is a fixed quantum, not queuing, contention or GC. Non-cart links in the same traces are all under 20ms, several under 1ms, which rules out a mesh-wide or network-wide condition. End-to-end cost scales with cart-call count: ~605ms for a cart page, ~1.5s for add-to-cart, ~2.47s for PlaceOrder where checkoutservice's span is almost entirely its two cart calls. frontend and checkoutservice have no independent regression; payment, shipping, email and fraud are single-digit milliseconds.

At T-3m (17:10:22) platform-automation attached a traffic-shaping container to cartservice's network namespace, imposing a fixed 300ms delay with zero jitter on eth0. Right magnitude, right interface, right moment.

The change log also killed three plausible theories: the v1.2.1 hotfix image was reverted ~13 minutes before onset and was not running; the REDIS_ADDR override to redis-cart:6380 was reverted ~1.3 hours before onset and never re-applied; and no human actor appears anywhere — all 32 changes are platform-automation. Nothing near onset was novel either. The same three-action cycle repeats every four to five hours across the window, and prior attach cycles lasted about ten minutes. This one was still in place at onset.

## Conclusion and what remains open

cartservice is healthy; it simply waits ~300ms on every cache round trip because the traffic-shaping attachment was left in place. Downstream alerts are that wait propagating. Confidence high; remedy class is reverting the change.

Still open. First, caller-side excess: frontend client spans run ~604-613ms against ~302ms server spans, checkoutservice client spans ~1206-1216ms against ~301-303ms. The excess is itself a multiple of 300ms, hinting at retries or per-attempt connection cost, but only one server span is recorded per call and no dispatch confirmed retry or timeout settings. Second, no dispatch checked whether the attachment is still present, and prior cycles self-resolved in ~10 minutes, so the incident may already be over. Third, cartservice's actual error behaviour was never measured, redis-cart was never examined directly, the four unmeasured edges were never identified, and it is unsettled why this cycle produced an incident when at least seven identical earlier ones did not.
