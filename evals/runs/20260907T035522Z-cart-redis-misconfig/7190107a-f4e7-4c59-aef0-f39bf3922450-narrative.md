# Checkout cart lookup refused at the connection level; frontend only reported it

## What was visible first

Frontend, loadgenerator and checkoutservice alerted together; twelve services in the blast radius, seed at frontend, four uninstrumented edges. Frontend's own error ratio ran about 12% mean with roughly 30% peaks and repeated returns to zero across ~178 samples. That shape argues against a peer that is hard down for the whole window — a constant outage gives a floor, not a series that keeps touching zero. It also excludes both extremes: frontend is not quietly healthy, and it is not in total failure. One trap in the same result: the comparison hour returned no samples, so the tool's claim that the mean 'moved from zero' is an artefact of missing data. Read it as no comparison possible.

The logs opened the case. Frontend's errors are all Node grpc-js client errors on the outbound path, stack frames from the receive-status handler. Mostly status 14 UNAVAILABLE, no connection established, first around T+17m and still arriving at T+62m. A rarer status 13 INTERNAL from a checkout call carries the useful detail: a cart failure while fetching the user cart during checkout, wrapping a transport dial error — TCP connect refused to a resolved IP on port 7070, the cart service port. Refused, to an address that resolved, means nothing was listening. Frontend itself started once near T-5m and the same process was still erroring an hour later.

## What the error shape closes

Slowness or saturation: excluded. No DEADLINE_EXCEEDED, no timeout details anywhere. Refused is an active rejection, not a slow peer.

DNS or service discovery: excluded. The dial error carries a concrete resolved IP and port, so resolution succeeded and the failure is one layer later.

TLS, authentication or authorization: excluded. Only codes 14 and 13 appear, with transport-level details; no handshake, certificate or credential errors.

Frontend's own logic, or an HTTP 5xx it was surfacing: excluded. Every error originates in outbound gRPC client status handling and attributes the failure downstream. Cart, on 7070, reached via checkout, is the only dependency named in any error detail.

## Dead ends, and what is still open

Change history on frontend came back empty — no deploys, config edits or flag flips — which kills the roll-back reflex, but the query was scoped to the seed service only, zero hops. The nine downstream services were never queried; empty here does not mean absent there. Change history on checkoutservice was likewise empty, with a sharper caveat: the window began at declared onset and ran forward a day, so it says nothing about the hours before. The source is untrusted, so a recording gap is an alternative reading.

checkoutservice metrics pointed the other way from the alert: in-window error ratio averaged roughly a fifth of its immediately preceding baseline, with no sustained departure. It was relaying, not escalating. Awkwardly, its baseline hour already showed a majority-error ratio with a nonzero floor, so degradation predates the declared window and onset is unsettled. Only one aggregate series returned — no per-dependency breakdown, no latency, no per-timestamp points, so no lead/lag alignment against frontend's bursts.

currencyservice logged only successful conversions at both ends of the window, dense late on, no restarts. Truncation leaves about twenty minutes in the middle unobserved, so the clearing is strong but not total.

The trace query is the important dead end: it returned HTTP 503, a failed query rather than an empty one. It carries no information about whether erroring spans existed, and it shows the retrieval path itself was degraded. Any plan resting on reading the deepest erroring span closed there.

Still open: cartservice was never queried directly — restarts, OOM kills, image or config changes and listener state on 7070 are all unobserved, and that is the highest-value gap. Get traces and latency once the backend is healthy. Treat the declared start as when someone noticed. Confidence medium: the failing service is named on strong evidence, the mechanism inside it on none. Indicated fix class is a restart, with verification that it holds.
