# Cart service crash loop from a non-default Redis port override

## What was visible, and in what order

Alerts paged on frontend, loadgenerator and checkoutservice; nothing paged for the cart service, which is the first trap in this record — the service that broke was the quietest in the alerting layer. Blast radius was scored at twelve services, critical, seeded from the frontend, four unmeasured edges crossed.

Because the seed was the frontend and the loudest alert was checkoutservice, attention went there first. Post-onset PlaceOrder traces are the turn: they collapse from ~42-55 spans and ~25ms to 3-5 spans aborting in under 3ms, and in two of three the erroring span is the checkoutservice-side CartService/GetCart under prepareOrderItemsAndShippingQuoteFromCart. Those spans have no cart-service server child and no HGET grandchild, unlike the healthy traces — the call fails without a served response. The error propagates up through checkoutservice PlaceOrder, frontend PlaceOrder and the HTTP POST root. The frontend's only error trace in its whole window is the same two-span GetCart shape, under a millisecond. A fast error, not a wait.

Cart service logs then close it. Five full cycles of: startup, connect attempt to the redis-cart host on port 6380, a 15-35s hang, connection failure, unhandled exception from the cart-store initialize path, termination, restart. Stack frames run from the program entry point through ensure-connected, so this is startup initialization — the process never binds its gRPC server. No GetCart or AddItem request lines appear at all in that period. The nearest change is an environment edit ~2 minutes before onset setting REDIS_ADDR to that host and port, where no such override existed before; unlike five earlier set-then-revert cycles in the same 24h, it was still in the 'set' state at onset. Fix class: configuration revert.

## Dead ends worth keeping

Checkoutservice's own change history, over the full 24h, was empty — no deploys, config edits or flag flips. That closed the self-inflicted-change story and also closed rollback for that service, since there was nothing to roll back. But the query's radius was seed-only, so it never touched cartservice or the other synchronous dependencies. That gap is what delayed finding the real change; widen the radius one hop on the first attempt.

Checkoutservice's aggregate error ratio averaged roughly a third of its at-rest baseline with no sustained departure. Read naively that exonerates it, and it is flatly contradicted by the traces. The signal is bursty (identical maxima, large deviations in both windows, low or intermittent volume), the baseline itself was not clean, and no p95 or per-dependency breakdown was returned — so latency-only degradation was never tested. Treat this path as insufficient, not reassuring.

Checkoutservice logs contained no error-severity lines anywhere and never named a downstream service. Order arrivals continued steadily throughout, so the process stayed up. The useful signal was structural: early orders produced four lines (request received, payment authorized, confirmation email, message-write offset); from onset only the request-received line appears. Execution never reached payment, email or the order publish, ruling those out despite their silence. The truncation appeared on both USD and CAD orders, so it was not currency-scoped.

## Things that looked relevant and were not, plus what is still open

Frontend traces had no coverage at the nominal failure minute — the sampled set jumps from about eight minutes before to four minutes after. Anchoring on that minute finds nothing. A ~2.5s loadgenerator POST outlier carries all its duration as frontend self-time with no children, so it measures nothing downstream. The four unmeasured edges — currency Convert, payment Charge, accounting orders receive — appear in one checkout trace, all under ~2ms, no errors. Productcatalog, recommendation, ad, shipping/quote, email and the Redis-backed cart data ops were all sub-millisecond to a few ms. On the cart service side, a 300ms egress-delay container was removed ~10m before onset, and a hotfix image tag was applied ~40m and reverted ~31m before onset, so neither was in force. All 37 recorded changes belong to the same automated actor; no human edit exists. EmptyCart, the 230ms emailservice outlier and the shipping→quote hop all belong to healthy pre-onset traces.

Still open. No one probed redis-cart: that it listens on 6379 rather than 6380 is inferred from the non-default port and from connects hanging rather than being refused. If redis-cart genuinely serves 6380 and is down, blame shifts to it. Second, why this cycle's override did not self-revert after ~8 minutes as the prior five did — late, wedged, or disabled automation decides whether manual action is needed. Third, cart-service error-ratio metrics returned no samples in either the incident or baseline window, which is a telemetry gap predating the incident, not a signal; combined with the checkoutservice ratio contradiction and the frontend trace hole, true blast radius remains unquantified.
