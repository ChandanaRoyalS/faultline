# frauddetectionservice restart loop under a lowered memory limit

## What the page looked like

The alert named a single service, frauddetectionservice, at critical severity. Blast radius stayed at one service for the whole investigation; no unmeasured edges were crossed to reach it, and no caller or downstream consumer was ever dispatched. Onset is treated as T+0 (wall clock 21:51:15 in the source windows).

The first thing worth saying is that the page itself was never explained. The obvious corroborating signal — error ratio for the service — was queried twice, once against a four-hour baseline and once against a thirty-minute baseline, and came back empty in both the incident window and the reference window. So whatever fired at T+0, it was not this series crossing a threshold, and we never identified the actual alerting signal. That remains open.

## Logs: the loop shows up immediately, the cause does not

An unfiltered selector on the service was the productive query. Early in the lookback window (roughly T-4h) the service was doing ordinary work: Kafka record-consumption lines with a monotonically increasing counter. That matters — it establishes that the failure mode began inside the window rather than having always been there.

From about T-5m30s the picture changes completely. The same three-line JVM startup sequence — tool-options pickup, VM class-sharing warning, OpenTelemetry javaagent version banner — repeats at least ten times in under eight minutes. The earliest repeats are tightly spaced (T-5m35s, T-5m22s, T-5m07s, T-4m39s), then the loop settles into a near-constant ~62-second cadence: T-3m45s, T-2m43s, T-1m41s, T-39m... read that as T-39s, then T+23s, then T+1m26s. The cycle that spans the alert timestamp is the one beginning at roughly T+23s.

What is *not* in the logs is the useful negative. No error level lines. No exception. No stack trace. No panic. Every cycle terminates at the agent banner with zero application output afterward — no readiness message, no consumption line. The process is dying during or immediately after startup, and whatever kills it writes nothing to stdout. A fixed ~62s spacing with no process-emitted failure text reads as an external termination, not an in-process crash.

## The change history

Nine changes landed on the service across roughly the preceding sixteen and a half hours, and every single one is the same type: a container memory resource limit lowered to 200m, then reverted. Same shape, over and over, all attributed to a platform-automation actor — no human hand anywhere in the record.

The decisive detail is the tail. The most recent entry is a lowering applied about five minutes before onset, and unlike the four earlier lowerings it has no matching revert in the window. The constrained limit was therefore in force at T+0. That lines up with the first startup repeats appearing at roughly T-5m30s.

## Conclusion as it stands

Read together: a JVM cannot reach steady state inside a 200m container memory budget. The service was placed under that budget by automation about five minutes before onset, the revert that had closed every previous occurrence never arrived, and from that moment the process enters a silent, externally-terminated restart loop at fixed cadence. The lowered limit is how it started; exhaustion of the available memory allowance is the mechanism operating during the incident. The service is down.

Fix class is a configuration revert — restore the prior memory limit. Confidence is medium, and the reason it is not higher is spelled out in the open items below.

## Dead ends worth keeping

These consumed time and produced nothing; do not repeat them.

The span-derived error-ratio metric is a dead path for this service. Two separate baseline comparisons, two different window lengths, both empty on both sides. Because the *baseline* is equally empty, the emptiness is not a mid-window collapse and does not mark a transition at onset — it looks like this service simply does not produce that series in this environment. A tempting misreading is that an out-of-memory kill silenced the exporter mid-window; the empty baseline rules that out. Related: this series cannot be used as a proxy for container-level memory pressure or restarts. It carries no samples at all.

Log-based root cause is also a dead path. Searching for the exception that names the cause will not work; there isn't one anywhere in the window, including the cycle covering the alert.

Ruled out on the change side: no deploy, no image rollout, no feature-flag flip, no application config change, no human operator action. Every record is a resource-limit mutation by the same automation actor. Also ruled out: the idea that the environment was quiet before onset and the trigger must be external traffic — a change did land five minutes prior.

Ruled out on the log side: that this was a single restart or a rollout (at least ten cycles in eight minutes is a sustained loop); that the service was actually healthy and the problem was downstream; that the JVM was crashing after reaching steady state during record processing (no cycle ever produces a consumption line, so it never resumes work); and that the OpenTelemetry agent was failing to load (its banner prints successfully every cycle, so agent init completes before the process is lost).

## Still open

The largest gap: there is no direct confirmation of an out-of-memory kill. Container memory working-set, the effective limit value in force, exit code 137, and kubelet termination events were never queried. Query those first if this recurs — the conclusion rests on inference from cadence and timing, not on a measured kill.

Second: we do not know whether 200m is genuinely below this JVM's startup footprint, or whether startup merely overruns a liveness/startup probe deadline when constrained. Both produce a silent external kill at fixed cadence and the logs cannot distinguish them.

Third: why did four earlier lowerings of the identical limit pass without incident? Each constrained period ran only about ten to twelve minutes. Either those windows were too short to matter, or load and heap conditions differed this time. Unresolved.

Fourth: what fired the alert. Unknown, as above.

Fifth: whether the automation loop will re-apply the lowering after a manual revert, and what drives that loop. This determines whether a revert is a fix or a temporary reprieve.

Sixth: downstream reach. Consumers of the Kafka topic the service was reading were never investigated. Blast radius of one reflects where we looked, not necessarily where the effect landed.
