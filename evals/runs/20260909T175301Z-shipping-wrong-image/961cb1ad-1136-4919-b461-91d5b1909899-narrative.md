# Checkout order failures traced to a shipping container that never reached serving state

## What was visible, in order

The page came from checkoutservice: error ratio roughly nineteen times baseline. Two features of that series shaped everything. First, the earliest change point sat about twenty-five minutes before onset, so we could not assume the trigger lived at T+0. Second, errors were bursty — intervals at zero, a peak near three in ten calls — which kept a partial-degradation theory alive longer than it deserved. Fourteen services showed in the blast radius; most were downstream consumers of order events that simply stopped arriving.

Checkout's own logs held no error or warning lines at all. What they gave us was shape: early in the window each order produced a clean four-line sequence (order start, payment with transaction id, confirmation email, message write with an advancing offset). From about T+1m to T+4m only the order-start line repeated, with none of the three completions following. Order-start lines kept arriving every five to twelve seconds, so the process was alive and serving. The break sat after intake and before payment.

Traces localised it. In every failing trace containing a shipping call, the deepest erroring span was checkout's own client span for the shipping quote call, with no shipping server child beneath it. Failing traces ran six to twelve milliseconds end to end, the erroring span about two — a fast failure, not a timeout. A healthy comparison trace roughly nine minutes before onset completed the full path, and one trace three minutes before onset already showed the failing pattern.

## Dead ends worth keeping

Cart, currency and product-catalog spans, including their server children and Redis calls, were present and clean in every failing trace. No payment span appears in any failing trace — the missing payment log line is a consequence of the abort, not a cause. Adservice and recommendationservice never appear on this path at all, which matters because adservice's name surfaces later in a completely unrelated way and briefly looked like a lead.

The change log for checkoutservice, queried across a full day past onset, came back empty: no deployments, config edits, flag flips, or client repointing. That closes those four theories, with one scope caveat — it covered the seed service only, nothing about neighbours.

Shipping's server-side error-ratio metrics returned no samples. We first read that as evidence of a crash. It is not: the two-hour baseline is equally empty, so the absence is a standing property of that service's telemetry. Confirmation had to come from logs and caller-side traces instead.

One more distinction that cost time: the traces rule out the failure being inside shipping's handler. There is no shipping server span under the erroring client span, so this is "nothing listening," not "listening and erroring."

## The cause, and what remains open

Shipping's change log showed twenty-three entries in roughly twenty-two hours, all from one automation actor, in a rigid cycle: endpoint override set, reverted, image reference updated, reverted. The override pointing shipping's quote lookup at a non-existent host was set about twenty-five minutes before onset and cleared about fourteen minutes before it, so it was not active at T+0. The image update landed about two minutes before onset, moving shipping to a demo artifact whose tag names a different service — and unlike all four prior cycles, no revert was recorded. It was in effect throughout.

Shipping's logs confirm the consequence. Two hours earlier the service was healthy, with paired Rust/tonic quote and ship-order handler entries. From about two and a half minutes before onset through T+4m the only output is a JVM and telemetry-agent bootstrap block repeating roughly every sixty seconds, with zero handler activity. A process that starts and never reaches serving state. That also killed the TLS, listener-bind, and connection-reset theories: the output stops before any of those stages would log.

Fix class: rollback the image reference and confirm the revert lands.

Still open. The earliest metric change point precedes the image update by about twenty-five minutes and coincides with the endpoint override being set; whether this is one continuous failure with two successive causes, or a partial recovery after that override was cleared, is unsettled. The bursty error ratio also sits awkwardly with a fully looping shipping, which should fail every quote — whether some replicas still ran the correct image is unresolved, and there is no server-side series to check. Finally, the shipping log selector returns two different runtimes under one label and the middle of the window is truncated, so it is not fully excluded that the restart loop belongs to a co-labelled workload. Pod and image inspection would settle it.
