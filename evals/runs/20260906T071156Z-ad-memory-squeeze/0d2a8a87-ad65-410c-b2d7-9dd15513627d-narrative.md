# Frontend UNAVAILABLE errors with no named peer; unobserved ad path the likely target

## What the page looked like

Two alerts came in together: frontend and loadgenerator, severity critical, blast radius counted at seven services. The obvious reading was that frontend was broken. It was not. Everything below is the work of establishing that frontend is the reporter, not the failing party.

Call the alert onset T+0. The first thing worth knowing is that the error condition already existed roughly 46 minutes earlier: the oldest retained frontend log line, at about T-46m, carries the same signature as the newest lines at T+2m. Whatever tripped the alert at T+0, it was not the arrival of the errors.

## The frontend error signature

Frontend's logs are uniform: gRPC status 14 UNAVAILABLE, a detail string saying no connection was established, and stack frames that live entirely inside the grpc-js client library. Nothing server-side, nothing application-level. That combination says the call never reached a peer that could answer.

Two things this rules out immediately. It is not a slow downstream — that surfaces as code 4 DEADLINE_EXCEEDED, and none of the retained lines show it. And it is not a downstream returning INTERNAL or 5xx from a process that is up; there is no responding peer at all.

The frustrating part: not one retained line names a host, port, service, or RPC method. The error metadata is empty. So the log tells you precisely what kind of failure it is and refuses to tell you who it is with. Identifying the peer had to come from somewhere else.

## Walking the frontend edges in traces

The trace sample was the productive step. Every frontend downstream edge that appears at all appears healthy, with a matching callee-side span: product catalog GetProduct, cart GetCart and AddItem with sub-millisecond redis HGET/HMSET children, recommendations ListRecommendations, and checkout PlaceOrder. The checkout fan-out runs several hops deep — cart, catalog, currency, shipping (which itself reaches the quote service over HTTP), payment, email, and the orders topic consumed downstream — with no orphaned parents anywhere. Slowest thing in the sample is a ~34ms checkout POST. There are no timeout-scale durations and no retry-backoff tails.

The interesting result is negative. The ad path never appears in the sample at all, while every other frontend dependency appears repeatedly. That is exactly the shape a connection-refusing target makes: if nothing accepts the connection, no server span is ever created and no edge is recorded. It is also the one edge triage had flagged as unmeasured, and the only frontend dependency nobody was sent to look at.

## Impact was smaller than the severity implied

Frontend's aggregate error ratio during the window ran at roughly two-thirds of the preceding hour's mean, with no sustained departure from baseline. Spikes exist inside the window, but comparable spikes exist in the baseline too. Whatever is failing is failing soft — the page still renders, the aggregate goes down rather than up.

Checkout confirms this from the other side: full order flows completing end to end with sub-second latency, and order-topic write offsets advancing one at a time with no gaps. Comparing the offset at the oldest retained checkout line to the newest implies a few hundred successful order publishes across the intervening half hour, so there was no prolonged halt hiding in the unreturned middle.

## Dead ends worth keeping

**Change history on frontend, catalog, and checkout: all empty.** No deploys, no config edits, no flag flips. Worth noting a trap in the frontend query — the window actually ran from onset *forward* about 24 hours, not backward. So the empty result speaks confidently to the post-onset day and only weakly to the hours before. If you re-run this, check the window direction before treating the emptiness as exculpatory.

**Cart's change log looked alarming and was not.** Twenty-three entries, all from one platform-automation actor, in three repeating apply/revert pairs: a hotfix image reference, a REDIS_ADDR override pointing at port 6380, and a sidecar adding 300ms egress delay. Every apply has a matching revert recorded *before* onset — the delay sidecar removed ~54m prior, the image reverted ~1.3h prior, the Redis override reverted ~37m prior. Nothing was still in force. This burned real time and produced nothing; the pattern is scheduled experimentation, not a release pipeline.

**Cart metrics and catalog metrics returned nothing at all** — no samples in the incident window *or* the baseline. Because both windows are equally empty, this is missing instrumentation, not a telemetry blackout at onset. Do not read it as a signal.

**Checkout's error ratio is flat zero in-window** but shows substantial, spiky errors in the baseline hour immediately before. The only movement is a drop to zero. That is the opposite of what the alert implied and deserves its own look someday, but it is not this incident.

**Cart logs** are routine request handling throughout, dense right up to the end of the window, with no startup banner, no crash, no Redis connection errors. A handful of cart reads carry an empty user identifier — minor, unexplained, and not time-correlatable because the middle of the window was truncated away.

## Where it landed

Frontend is the caller reporting a downstream that never accepts a connection. Every measured frontend edge is healthy. The ad path is the only frontend dependency absent from the traces, and absence is the expected signature of a target refusing connections. Fix class: restart the ad service. Confidence medium — the attribution rests on an inference from an absence, not a positive observation.

What is actually wrong inside that service — dead process, wrong listen port, bad artifact — is not established by anything gathered here.

## Still open

Three loose ends, in descending order of how much they should bother you.

One: nobody looked at the ad service. Its logs, restart history, and pod state are entirely unobserved. The whole conclusion hangs on an edge missing from a trace sample that was itself truncated at 200 spans. One direct query would convert this from medium to high confidence or overturn it.

Two: the frontend errors name no target. The peer is inferred by elimination, not identified. If the trace sample was unrepresentative, the elimination fails.

Three: the 07:15 alert onset is unexplained. The error condition was already present at T-46m. Frontend, cart, and checkout logs are all truncated around the onset minute, so the specific moment is unobserved in every log source we pulled. Something changed at T+0 to trip the alert and we do not know what it was.
