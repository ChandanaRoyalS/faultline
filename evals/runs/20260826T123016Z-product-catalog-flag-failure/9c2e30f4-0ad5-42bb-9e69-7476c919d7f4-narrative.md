# Partial user-facing errors at the edge with an unidentified mechanism

## What we saw first

Three alerts arrived close together: frontend, loadgenerator, and productcatalogservice. Triage drew a blast radius of seven services and flagged one edge as unmeasured. The starting point was the frontend, because that is where a user would feel it.

The first useful reading was the frontend error ratio over the fifteen minutes around onset. It was non-zero but nowhere near total: peaks around 11.7% of calls, and — importantly — returning to zero between peaks across 58 samples. That single shape did most of the early work for us. It told us we were looking at something episodic, that the frontend process was alive and serving the large majority of requests, and that telemetry was flowing continuously (no gap in the scrape).

What that series did not do, and this cost us later, was attribute anything. It was aggregated by service name only, with no dependency dimension. So at T+0 we knew the edge was hurting and we did not know who was hurting it.

## The second reading, and the correlation we leaned on

Next we pulled the same style of error ratio for productcatalogservice over the same window. It came back with the same character: non-zero, peaking near 12%, dropping back to zero at points, 57 samples, a single service-wide label set rather than one bad instance hiding in an aggregate.

Two services, same window, similar magnitude, similar episodic shape. That is a plausible pass-through story — the frontend surfacing productcatalogservice failures — and it is the strongest thing in this record. It is also, and a responder should be honest about this, a correlation of shape and timing only. Nothing measured attributed a single frontend error to productcatalogservice. Read that sentence twice before you build on it.

The same query returned no latency, CPU, memory, goroutine, or absolute request-volume series. The volume absence matters more than it looks: a 12% error ratio on normal traffic and a 12% error ratio on a collapsed denominator are different incidents, and we never learned which one we had.

## Dead end: the logs we never read

This is the most useful part of the record, so it gets its own section.

We went to logs twice for productcatalogservice, expecting error text that would name a failing operation or an upstream. Both attempts returned zero lines over the full window. Both used a hyphenated form of the service label — product-catalog-service — while the brief named the service unhyphenated.

A fifteen-minute empty result during an active, error-emitting window is far more consistent with a label value that matches no stream than with a genuinely silent service. So the correct reading of those two results is not "productcatalogservice logged nothing"; it is "we asked a question that could not return an answer." We burned two dispatches on it and never exercised the unhyphenated form. If you are picking this up, start here: establish the working label value first, then re-ask for error and panic lines. Every mechanism hypothesis in this incident is blocked behind that one selector.

## Dead end: the change history, half-asked

We queried change history for productcatalogservice twice. Both times the answer was clean — no deployments, no config edits, no flag flips — and both times the answer covered only the fifteen minutes around onset, roughly T-10m to T+5m.

Within that narrow window the conclusions are solid and worth keeping. Nothing landed concurrently with onset. There was no flag flip at the moment behaviour turned. There was no rollout still in flight to halt, and no remediation push that could have produced the state we were looking at.

What both dispatches asked for and neither actually queried was the preceding hour. So a change that landed forty minutes before symptoms and took time to bite remains entirely unexamined. Two attempts, same coverage, same blind spot — the second added no new ground over the first.

## Dead end: adservice, unmeasured rather than clean

Triage's unmeasured edge pointed at adservice, so we asked for its error ratio from call counts, hoping for a signal that led the onset.

Both halves came back empty — the error-filtered numerator and the unfiltered denominator. That is the distinction to hold onto: an empty denominator is not a low error rate. There are no call-count series for adservice in this metric source at all. The window was the right one and the result was not truncated, so this is not a range-boundary artifact.

The consequence is that adservice is neither implicated nor cleared. It cannot be the evidenced leading indicator, because there is no series that could lead anything; and it cannot be written off as healthy either. Clearing it needs a different telemetry source or a direct health check, not another query against this one.

## What turned out not to matter

Several early worries died cheaply and should not be re-litigated.

It was not a total outage or a crash-loop at either service. Both error ratios peak near 12% and touch zero, with populated denominators throughout. It was not a telemetry gap at the frontend or productcatalogservice — both series are full and continuous over the window. It was not a change that landed inside the alert window. And it was not a false alarm confined to something downstream that never reached users; the frontend genuinely served errors.

The episodic pattern also argues against a static wrong value sitting in config, which would tend to produce a flat error floor rather than errors that return to zero between peaks. That is a shape argument, not evidence, and it does not select between load-correlated pressure and intermittent upstream slowness. Neither of those was evidenced.

## Where it stands

Not established. Low confidence. No fix class, because no mechanism was identified.

What we can defend is narrow: a real, user-facing, partial and intermittent degradation at the frontend, concurrent with a service-wide degradation of similar magnitude at productcatalogservice, with no change landing in the alert window, no crash-loop, and no telemetry gap. The mechanism — pressure on a resource, waiting on a dependency, a bad artifact, a config value — is unsourced.

Open, in the order I would work them:

Find the correct log label value for productcatalogservice and read actual lines; the hyphenated form is ruled out and the unhyphenated form is untried. Then query changes for productcatalogservice across the full preceding hour, not just the incident window. Then pull p99 latency, CPU, memory, goroutines, and absolute request volume for productcatalogservice — without those you cannot separate resource pressure from dependency wait, and you cannot interpret the 12% figure. Then get a dependency-dimensioned error breakdown at the frontend, so the pass-through story is measured rather than inferred. Then establish adservice health from some source other than call-count metrics.

One coverage note for whoever picks this up: triage named seven affected services. Only three were dispatched against — frontend, productcatalogservice, adservice. The other four were never examined at all.
