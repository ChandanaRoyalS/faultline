# Frontend errors traced to an ad backend restart loop under a lowered memory limit

## What paged, and what turned out not to matter

Two alerts arrived together: frontend and loadgenerator. The visible symptom was an error-rate spike, not an outage — frontend averaged about 4.2% errors against a 1.4% baseline, peaking near 11.5%, so roughly nine in ten requests still completed. The most useful detail in that metric was its shape: three separate threshold crossings, about 27 minutes before onset, about 22 minutes before, and one at T+0, all peaking at the same 10-11%. Episodic, not a step change. That single observation is what eventually pointed at an automated loop rather than a one-time event.

Frontend's own change record came back completely empty — no deploys, no config edits, no flag flips attributed to frontend or its client configuration. That closed the cheapest hypothesis fast. Loadgenerator was a victim, not a source: its error spans are parents inheriting latency from the failing frontend child, and its spans on healthy paths look normal.

The most expensive dead end: we expected frontend logs to name the broken downstream. They do not. Every retained error line is the same shape — outbound gRPC status 14 UNAVAILABLE, detail indicating no connection established, raised in the Node gRPC client stack — with no target host, no port, no service name, and empty metadata. Useful for confirming this was a connect-time failure (not a deadline, not resource rejection, not auth), useless for identifying the peer. Skip straight to traces next time. The log result was also truncated to oldest-8/newest-32 lines and returned nothing at or near T+0, though the same pattern appears in the oldest lines about half an hour early — a second hint that onset predated the page.

## Traces named the path; the ad backend was cycling

Sampled traces resolved it. Every failing request fails on the same call: frontend's client span for AdService/GetAds, in error, consuming essentially the whole parent duration. In two traces the GetAds span's only child is a frontend tcp.connect span, also in error, eating nearly all of it. No server-side ad backend span appears anywhere — the traces bottom out on the frontend side. The callee never accepted the connection. Frontend handler self-time is negligible, so frontend was not internally slow. The failing requests cluster just under three seconds, suggesting a client deadline on the ad call.

The same traces cleared a lot of ground: product catalog spans complete in single-digit milliseconds (slowest ~16ms), cart operations around a millisecond, recommendations a few milliseconds, all error-free; checkout appears nowhere in the sampled spans. Because those healthy calls run concurrently with the failing one, a shared network or DNS-wide problem is excluded too.

Ad backend logs showed the other side. At window open it was serving normally. In the final five minutes the stream is nothing but a dozen repeated JVM and tracing-agent bootstrap preambles with no request handling between them, and the gaps grow monotonically — roughly 3s, 4s, 6s, 9s, 15s, 28s, 54s, then about a minute. That is an orchestrator backing off a container that keeps exiting shortly after launch. Each attempt reaches only agent initialization and never logs a listener bound. So the process starts and dies before anything can accept connections. This also excludes scheduling or image-pull problems (the runtime initializes every time), port-bind conflicts (no bind error, and each attempt ends before any socket stage), and GC pauses (the processes never live long enough).

## The change behind the cadence, and what is still open

The ad backend's change record holds five entries over the lookback, all from the same platform-automation actor, and all resource-limit edits to the pod spec: the memory limit repeatedly lowered to 256m and reverted to no limit, on a rough ten-to-twenty-minute cycle. The most recent lowering landed about three minutes before onset. That cadence matches the three episodic frontend spikes. The mechanism: a JVM handed a 256m ceiling is terminated for exceeding it before startup finishes, so there is no listener. The same record excludes a deploy, a flag flip, an application config edit, a scaling event, and manual operator action. Fix class is a revert of that limit.

Confidence is medium, and here is why. The termination reason is not directly evidenced — the application logs carry no heap-exhaustion or memory-kill lines, so this needs kubelet or kernel events, container working-set, or restart-count metrics to confirm. The one metric query run against the ad backend covered call-status ratios only and returned nothing in either the incident or the four-hour baseline window; because both are empty, this is an instrumentation gap rather than a traffic collapse, and it means the service's health cannot be tracked from metrics at all and the earlier cycles cannot be corroborated on that side.

Three other loose ends. Both log results were truncated, so whether the backend was crash-looping continuously or only during discrete lowered-limit intervals is unsettled. Nothing identifies why the automation is flapping the limit — no controller, policy, or reconciliation conflict is named, so a manual revert may simply be overwritten. Triage reported one unmeasured edge crossed and nothing here identifies it, so a contributing path outside the frontend-to-ad-backend hop remains unexamined. Separately, the apparent three-second deadline with no fallback for a non-critical ad panel is a secondary exposure: whether users should see errors at all when ads are unavailable was never assessed.
