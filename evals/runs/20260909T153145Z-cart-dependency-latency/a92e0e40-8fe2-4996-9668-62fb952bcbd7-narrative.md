# Cart path acquires a fixed ~300ms network penalty; checkout and frontend alert

## What was visible, in order

Four services paged together: cartservice, checkoutservice, frontend, loadgenerator. Blast radius twelve services, severity warning. Nothing was down — the shape was a slow checkout funnel with an intact success path.

The first two lines of inquiry were dead ends. Cartservice's own logs across roughly T-30m to T+2m held only routine add/get/empty cart traces: no errors, no panics, no Redis connection messages, no startup lines. Request handling continued with sub-second spacing throughout, ruling out a restart or crash loop. The result was truncated to the oldest eight and newest thirty-two lines, so onset itself was never actually returned — do not read "no errors" as full coverage.

Cartservice's error-ratio metric returned no samples at all. The tempting read is that traffic to cart stopped. It did not: the same query is equally empty across a six-hour healthy baseline, so this is a pre-existing collection or label-matching gap, not an incident signal. No latency, request-rate, restart or replica series came back for cart either. Cart has no usable metrics here.

## Checkout: errors without error text, then the mechanism in traces

Checkout's error ratio rose about 9.5x over baseline (~1.9% to ~18.4% mean, peaking near two-thirds of requests), bursty rather than total — window minimum zero, standard deviation above the mean. Yet checkout's logs are entirely info-severity: no connection-refused, no DNS failure, no deadline text, nothing naming cartservice. Orders complete end to end, roughly one every three to five seconds, with sequential queue offsets. What changed is spacing: early in the window each order step was tens of milliseconds apart; by the end, about 1.2 seconds each. A latency-shaped incident wearing an error-ratio costume. That cleared payment, email and the publishing pipeline, and showed log text would never find this.

Traces resolved it. Every cartservice Redis leaf — about twenty spans — sits at a tight 300-310ms floor, and each caller's client span into cartservice carries a further ~300ms of self-time. Cartservice's own in-process work is 0.3-1.2ms. The penalty is additive per crossing: AddItem reaches ~904ms for the hop and ~1510ms end to end, near-identical across five traces. Non-cart dependencies in the same traces stay sub-millisecond to ~18ms, which kills any cluster-wide network story; the tight jitter-free floor kills load-driven queuing.

## The change, the dead ends, and what is still open

Cartservice's change history holds 31 entries over 24 hours, all from platform-automation, repeating a fixed cycle every four to five hours. That repetition is the trap: no single change type is discriminating on its own. The only distinguishing fact is pairing — at T-3m a traffic-shaping sidecar was attached to cartservice's network namespace imposing a fixed 300ms egress delay with zero jitter on eth0, and unlike every prior instance no matching removal followed. The previous attachment had been explicitly removed hours earlier. This one was live at onset, and it matches the trace evidence exactly.

Dead ends worth keeping: a cartservice hotfix image landed ~23 minutes before onset but was reverted ~13 minutes before, so the baseline artifact was running. A REDIS_ADDR override to port 6380 existed but every instance is paired with a revert, the last completing ~3.1h before onset. Cart application code is excluded by the sub-1.2ms server self-time. A single slow downstream Redis call does not fit, because the ~300ms unit appears both in the leaves and separately in the caller's own gap. Checkout fan-out does not fit either — the single checkout-to-cart GetCart hop accounts for ~49% of trace time.

Still open. Checkout's error-ratio change point is a discrete step roughly 19 minutes before the sidecar attachment; that gap is unexplained and overlaps the hotfix apply/revert window. No latency or request-rate series were returned for either service, traces cover only a ~37-second band, and both log queries were truncated, so nothing directly observed the transition. And checkout's client spans into cart carry ~905ms of self-time — three 300ms units — above a ~305ms server span, which one egress delay does not account for. Fix is a config revert: remove the orphaned sidecar. Confidence medium.
