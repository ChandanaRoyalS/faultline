# Frontend gRPC connect failures traced to a memory-capped upstream

## What was visible, in order

Alerts fired on frontend and frontend-proxy; eight services in the blast radius, seven edges with no measurement. Offsets are against the start of the evidence window (T+0); the timestamp attached to the page was T+30m, and that turned out to be a late observation, not an onset.

First pull was the frontend's error-to-total call ratio against its baseline: roughly doubled, 0.0165 to 0.0364, peaks near one call in ten. The elevation was intermittent rather than a step, with threshold crossings already at ~T+4m and ~T+7m and the last at T+29m. So this did not begin at the paged timestamp. It was also not latency-only, and not a hard outage — the window mean sits under 4% with stretches at zero. The series was aggregated by service name alone, with no target or route label, so it could never name the dependency.

Logs gave the shape. One repeating line dominates the window: gRPC code 14 UNAVAILABLE, 'no connection established', against exactly one upstream, 172.18.0.27:9001, identified only by address. The socket error escalates over time — connection-refused in the oldest retained lines (~T+0), host-unreachable in the newest (~T+32m). That is a listener that keeps vanishing and returning, not a slow or erroring callee. Embedded 'last error' timestamps lag emission, so the client was replaying a cached connect failure. No DEADLINE_EXCEEDED anywhere, no application/auth/TLS rejections, no second upstream, and the frontend itself logs continuously and healthily throughout.

## Dead ends worth keeping

Traces were the expensive detour. Across seven traces and two hundred spans, no span carried an error status; every frontend-rooted chain completed to a database query, Redis command, or template render, and the slowest trace spent its time in the load generator's own self-time. Read naively this says the frontend reaches everything fine. What it actually means is that sampling only captured successes — a connect-level failure leaves no server-side child span to find. Worse, the spans carry no peer address or port attributes at all, so trace data was structurally incapable of confirming whether any downstream is 172.18.0.27:9001. Go to service discovery instead.

Frontend change history came back entirely empty: no deploys, no config edits, no discovery or endpoint updates. That clears a frontend rollout, a gRPC client config change, and a registry repoint, and it also removes rollback as a first action. Caveat: the query window started at onset rather than before it, so it would not show a change landing just beforehand.

## What it was, and what is still open

Change history for recommendation held exactly three entries over twenty-four hours, all from platform-automation, all memory limit adjustments. A 16m limit was applied about four minutes before onset and never reverted in the window; the same limit had been applied and reverted earlier, so this is a repeating automation cycle. No deploy, no operator restart, no scaling, no port or DNS change, no human actor.

recommendation's own metrics corroborate a process dying and returning: the series is still scraped, but 33 of 96 incident-window samples have a zero request denominator, against zero such gaps in 129 baseline samples. Where traffic exists the error ratio is low and actually below baseline — the service is not failing requests, it is intermittently absent.

Conclusion: recommendation is being killed under an unsustainable 16m cap, its listener on 9001 disappears in cycles, and the frontend's calls to it fail at connect, producing the intermittent ~2.2x error rise. Fix class is a configuration revert, and the automation loop reapplying the limit must be stopped too. Confidence medium.

Still open: (1) 172.18.0.27:9001 was never resolved to a service name — nothing confirms that address is recommendation, and the whole chain rests on that link. (2) No logs, memory metrics, or termination events were gathered for recommendation; memory exhaustion is inferred, not observed. (3) Frontend errors crossed threshold at ~T+4m and ~T+7m, before the limit was applied at ~T+25m; the earlier apply/revert cycle may explain it but nothing confirms that, and the other five services in the blast radius were never investigated.
