# Critical multi-service alert starting at ad; readable failure was in cart's stored carts

## Where triage began, and the dead ends there

Three services paged: ad, frontend-proxy, and load-generator. Two of those three are reporters — the proxy forwards what frontend returns, the load generator counts its own failed synthetic shoppers — so the question from the first minute was which service behind them was failing. Triage was handed ad.

The change log was the first stop and the first dead end. ad has exactly two entries in a 24-hour window, both resource-limit edits by platform automation: a memory limit lowered, then removed again about nine minutes later, both roughly 4.5 hours before onset. At onset the configuration was back to its prior state with no explicit limit. No image, build, deploy, or environment change anywhere. The shape resembles a previously recorded ad memory incident, which is exactly why it is worth keeping on the record as ruled out rather than quietly dropped.

ad's metrics did show an elevation — error ratio around 1.8% against a ~0.4% baseline, one change point about 41 minutes into the window, peak near 36% — but the shape is spiky, with dispersion exceeding the mean, not a sustained plateau. Request rate, p95, and memory-against-limit were never returned and remain unmeasured.

## ad's serving path is clean; the noise is telemetry

Ten sampled ad traces all complete normally: no error-status span, no status message text anywhere, and a shallow path — frontend calls GetAds, which fans out only to in-process children. No outbound client span under ad at all, so no slow or failing dependency beneath it. Latency is single-digit to low-double-digit milliseconds, and in half the samples the largest self-time hop is in the load generator rather than ad.

ad's logs agree. Early in the window it serves normally. At T+0.5m and T+1.5m it emits Java stack traces, but they come from the telemetry agent's metric exporter failing to resolve the collector hostname during DNS lookup — the agent's own thread pool, off the request path. No allocation failure, no out-of-memory signature, no startup banner; the process is alive and logging ninety seconds past onset. Separately, a runtime-toggle hypothesis was closed twice: the change log holds nothing for flagd, and an unfiltered log query against flagd returned not one line.

## What it actually was, and what is still open

frontend's metrics looked like nothing — a 1.46x mean shift with an incident-window peak below the baseline peak — and I nearly stopped there. The logs held the answer. frontend carries gRPC failures returned from cart, clustered roughly T-28m to T-16m: FAILED_PRECONDITION with cart's own "can't access cart storage" text, and INTERNAL from checkout wrapping the same thing. The named path is cart's Valkey-backed store, failing in get-cart as a protobuf decode error on data ending mid-field. The exception body and stack are entirely cart's; frontend contributes only gRPC client wrapper frames. The codes are not UNAVAILABLE or DEADLINE_EXCEEDED — the connection succeeded and the RPC returned an application-level error, so this is stored contents that cannot be decoded, not an unreachable store. Every alerting service sits upstream of that single read. Fix class: restore the store's contents; the executor cannot perform it today.

Confidence is medium, and three things stay open. No query ever ran against cart or its store — cart's own logs, error ratio, and store health are unmeasured, and the verdict rests entirely on cart's exception quoted back through frontend. The cart errors stop about 16–27 minutes before onset and frontend's log stream ends there, so whether the condition was still active at onset is unestablished. And why ad paged first is unexplained; the agent's unresolvable-host failure may be unrelated telemetry breakage or a wider resolution problem.
