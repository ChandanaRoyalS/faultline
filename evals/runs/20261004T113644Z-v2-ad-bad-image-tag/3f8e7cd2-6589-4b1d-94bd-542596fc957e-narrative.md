# Ad backend vanished from the network; frontend reported it

## What the page looked like

Two alerts arrived together, from frontend and frontend-proxy, with eight services in the blast radius and severity set to critical. That framing cost time: it read as a storefront-wide problem, when frontend was only the reporter. Seven edges in the dependency map were uninstrumented, so progress depended on following frontend's own outbound errors one hop at a time.

Frontend's logs were the first useful signal. One signature dominated the whole retained window: gRPC status 14 UNAVAILABLE with an underlying host-unreachable connect error against a single peer at 172.18.0.28:9555, raised from server-side rendering. It is present at the oldest retained line (~T-20m) and the newest (~T+2m) — about 22 minutes with no recovery. Retries are visible as repeated errors carrying the same cached last-error timestamp. The connection was attempted against a concrete address, so resolution worked and the failure happened before any session existed; no handshake or authorization explanation survives. Every error pointed at one address, so this was never a broad fan-out outage.

## Two dead ends on frontend

Baselining frontend's error ratio went nowhere, and the null result is itself a trap. The errored-call fraction during the incident was statistically indistinguishable from baseline — mean slightly below baseline, comparable spread and maximum across 129 samples, with the ratio swinging between zero and roughly ten percent in both windows. A dependency that disappears entirely breaks one route while every other route keeps succeeding, so proportionally nothing moves. Read it narrowly: frontend is not broadly failing. Note also that only the error-ratio series came back; request rate and latency percentiles for frontend were never measured.

The frontend change log came back completely empty, ruling out a frontend rollout as trigger and any frontend-side change as the explanation for continuation. But the window queried starts at alert time and runs forward ~24h — the hours before onset were never sampled. It is an honest answer about the wrong interval. The query was also scoped to the seed service, so frontend-proxy was not covered.

## Traces narrowed it to one call

Exactly one of ten sampled frontend traces carried an error, terminating at frontend -> AdService/GetAds and propagating up through the frontend API route, frontend-proxy and the load generator — which explains why both alerting services fired on one underlying problem. The failing call is sub-millisecond: a refusal, not a slow response. Cart spans and their Redis operations all complete in fractions of a millisecond without error; no checkout span appears anywhere; proxy self time stays at a few tenths of a millisecond even in the slowest traces.

The same sample holds a second, unrelated signal. AI-assistant traces run 31-33ms with 26-28ms inside the product-reviews handler, and the recommendations route shows ~30ms dominated by server-side self time in product-catalog (its SQL children stay at 0.2-2.0ms). Baseline browse traces run 2.8-4.2ms. These slow traces carry no error and the errored trace carries no latency — at least two distinct signals. Nobody dispatched against the latency one. If the storefront is still slow after the ad path is restored, start there.

## Crossing to ad: the service had already stopped

Ad logged normal request handling with no errors right up to T-5m15s, then two lines at T-5m12s: the gRPC ads server stopping because the JVM is shutting down, and confirmation it shut down. Orderly, self-reported, shutdown hooks firing normally. After that, nothing at all — no startup banner, no first-request line, no second shutdown. Not a crash or memory kill (those cut the process off before hooks log, and there is no stack trace or fatal-signal line). Not a crash loop (one shutdown, no restart cycle). Not alive-and-erroring at alert time, because there was no traffic to fail.

The key correction: the state change is at T-5m12s, not T+0. The alert lagged the failure by five minutes.

Ad's metrics reinforce absence rather than failure. Its error ratio matches baseline (~0.42% vs ~0.49%, no sustained departure; the doubled peak is a brief low-volume excursion). The telling number is 53 sampling intervals with an undefined ratio during the incident versus zero in baseline — intervals with no ad requests at all. Traffic was interrupted even though the error rate was not. Request rate and instance availability were not returned, so that gap count is the only traffic evidence.

## The change record and the verdict

Five changes to the ad workload appear in the 24-hour window, all from platform automation, all clustered in the 45 minutes before onset. Every one is an image-reference change alternating set and unset: update, revert, update, revert, update — the same 2.2.0 ad hotfix tag throughout. The final change re-applied that tag and left it in place, about one second after the JVM logged its shutdown. The replacement never produced a log line.

This closes several doors: the artifact was not novel (already run and pulled back twice that hour), there are no config or flag entries anywhere in the window, no human actor appears, and nothing landed outside that final 45 minutes. Verdict, held with high confidence: the ad endpoint ceased to exist on the network, and frontend's UNAVAILABLE errors are the downstream symptom. Fix class is rollback.

Three things remain open. Nothing observed the ad workload's orchestration state after the final application — whether the image failed to pull, died before logging, or was never scheduled is unconfirmed, and the verdict rests on absence of logs. The mapping of 172.18.0.28:9555 to ad is inferred from the port and the trace endpoint, not confirmed against service discovery. And severity was critical while frontend's error ratio stayed flat with only one errored trace in ten; the product-reviews and product-catalog latency may be a separate, unexamined failure.
