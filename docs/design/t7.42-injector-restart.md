# T7.42 — the restart that belongs to the injector

**Conclusion: it is not a confound, and the concern that prompted this does not survive the survey.**
Recorded as a known property rather than fixed, because there is nothing to fix.

## What prompted it, and why that prompt is weak evidence

T7.41's abstaining `payment-telemetry-blackout` run asked *"Why was the paymentservice container
replaced?"* — one run, at n = 2. **The survey below is the evidence; the run is only what prompted
the look.**

**And the run does not support the concern.** Its **first tool call** was
`change_history("paymentservice")`, and it returned:

```
2026-08-31T04:34:08  platform-automation  environment updated:
  OTEL_EXPORTER_OTLP_TRACES_ENDPOINT updated on paymentservice
  None  ->  http://127.0.0.1:4317
```

**The agent was told why the container was replaced, in its first query, and listed it as an open
question anyway.** Whatever produced that abstention, it was not an absence of evidence.

## Scope, from the bundles

**7 of 13 valid scenarios are injected by a mechanism that recreates the container.** The other 6
are named too, because a clean result is what bounds the finding.

| mechanism | recreates | scenarios |
|---|---|---|
| `BadDeployFault` — image swap via compose override | **yes** | `cart-bad-image-tag`, `email-wrong-image`, `shipping-wrong-image` |
| `BadConfigFault` — env var via compose override | **yes** | `cart-redis-misconfig`, `product-catalog-flag-failure`, `shipping-quote-misconfig`, `payment-telemetry-blackout` |
| `ResourceExhaustionFault` — memory via `docker update` | **no**, a live property | `ad-memory-squeeze`, `frauddetection-memory-squeeze`, `recommendation-memory-squeeze` |
| `DependencyLatencyFault` — pumba sidecar, netem | **no**, target untouched | `cart-dependency-latency`, `productcatalog-dependency-latency`, `redis-cart-dependency-latency` |

`starting|started|listening|bootstrap|JAVA_TOOL_OPTIONS|ready|init`, so read the ordering rather
than the exact counts):

| scenario | recreates | log lines | startup-ish |
|---|---|---:|---:|
| `frauddetection-memory-squeeze` | **no** | 227 | **38** |
| `ad-memory-squeeze` | **no** | 145 | **37** |
| `shipping-wrong-image` | yes | 358 | **33** |
| `cart-redis-misconfig` | yes | 500 | 6 |
| `cart-bad-image-tag` | yes | 500 | 3 |
| `redis-cart-dependency-latency` | no | 18 | 3 |
| `payment-telemetry-blackout` | yes | 328 | 2 |
| `product-catalog-flag-failure` | yes | 2 | 2 |
| `shipping-quote-misconfig` | yes | 387 | 2 |

| `productcatalog-dependency-latency` | no | 0 | **0** |

**The two loudest restart signatures in the catalog belong to scenarios that do not recreate at
all.** `frauddetection-memory-squeeze` (38) and `ad-memory-squeeze` (37) are memory squeezes applied
by `docker update` — the container is restarted repeatedly **by the fault**, which is the incident
being modelled. `shipping-wrong-image` (33) is a deploy that starts and fails, so its restarts are
also the fault.

**The apparatus signature is the quiet one: 2–6 lines, one recreate.** It is an order of magnitude
smaller than the fault-driven restarts sitting beside it in the same catalog.

## What kind of problem this is — named rather than stretched to fit

**It is not contamination in ADR-0008's sense.** Nothing about the answer leaks; no holdout is
touched; no corpus is involved.

The category it *would* belong to is **a signature of the apparatus appearing in the measurement** —
the bundle containing evidence of an event that is part of *how* the fault was applied rather than
*what* the fault is. That is a real category and worth having a name for.

**But this does not belong to it, for two reasons, and the second is the stronger.**

**1. For `bad_deploy` it is not apparatus at all.** A real bad deploy replaces the container. The
recreate *is* the fault, faithfully modelled. Three of the seven fall out immediately.

**2. For `bad_config` the recreate is faithful, not artificial.** An environment variable cannot be
changed on a running container — `docker update` has no `--env`, and every orchestrator that sets
env at creation behaves the same way. **A responder in a real incident who sees "config changed,
container replaced" is seeing the normal consequence of a config change**, not an artifact of a test
harness. The apparatus is doing what the modelled event does.

## Easier, harder, or neither — neither

**Neither, and the one honest caveat is small.** The restart is explicable from `change_history`,
which every one of these scenarios records by construction: the injector writes a change record with
a timestamp, the variable, and the old and new values. The responder must connect *"config changed
at T"* to *"container replaced at T"* — **one inference step, and a realistic one.**

It is not *easier*: the change record names the change, not the diagnosis, and three of the four
`bad_config` scenarios still require working out what the changed value does.

It is not *harder* in any way that shows: T7.41's abstaining run had the change record and the
scenario's other run, with the same evidence, answered correctly.

**So the difficulty is not an accident of tooling, because there is no added difficulty to
attribute.** Had the survey come out the other way — a large apparatus signature with no
corresponding change record — that distinction would have mattered and belonged in the record.

## Is it avoidable? — no, not while the fault stays a config change

- **`docker update` cannot change environment.** Its options are resource limits only; env is fixed
  at container creation. Verified.
- **No demo service re-reads its configuration at runtime.** All 15 services take the OTLP endpoint
  from env at startup.
- **A mechanism that changes what the service sees without replacing it would change what the fault
  is.** Blackholing the collector's address with iptables avoids the recreate — and models a network
  fault, not a `bad_config` one. That is a different scenario, not the same one applied better.

**And the cost of switching would be paid twice.** `scenario_fingerprint` covers `injection`, so
changing the mechanism moves the fingerprint on **all four `bad_config` scenarios** and invalidates
their recorded bundles — a four-bundle re-record for a confound the survey says is not there.

## Decision: record it as a known property, and correct the framing that prompted it

**No mechanism change. No capture change. Recorded in ADR-0009's addendum and in the CATALOG entries
of the four `bad_config` scenarios**, so a reader of a bundle knows the single restart is the config
change taking effect and can stop looking for a second cause.

**And T7.41's framing is corrected rather than carried forward.** That entry called this *"a
permanent unanswerable question sitting inside the evidence"*. **It is answerable**, by the first
tool the abstaining run happened to call, and the phrase overstated a one-run observation into a
property of the catalog. The survey is what settles it.

## What would reopen this

A scenario where the recreate is **not** explicable from `change_history` — for instance a mechanism
that restarts a container without writing a change record — or a measured association between the
apparatus restart and abstention across enough runs to be more than the single run that prompted
this. **n = 2 is not that**, and this entry does not claim otherwise.
