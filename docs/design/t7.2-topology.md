# T7.2 step 5: where topology comes from

**Decided 2026-10-01 by the owner: a committed dependency snapshot per world and per
application, captured offline, never queried during a scored run.** This note records the
decision, what it was decided on, and what it costs. It also records the defect found while
answering it (**Q122**): Faultline's own v2 world has no topology today. Nothing here is built
yet.

## The question

`docs/design/t7.2-scoping.md` §5 step 5: *"Decide where topology comes from on a foreign
application. Jaeger's `get_dependency_graph` is mounted and is the candidate; deriving a graph from
live traces is a component this repository does not have. Price it before the run."*

## What Faultline does with topology now

`faultline.context.graph.ServiceGraph.from_snapshot` loads **one** file,
`docs/evidence/t2.4-dependency-graph/dependencies.json`. That is Jaeger's `/api/dependencies` reply,
captured from the v1 world on 2026-08-24. `ServiceCatalog` is that graph's nodes plus
`KNOWN_ABSENT`. Triage's blast radius (`ServiceGraph.blast_radius`) and its `start_from`, the
contracts' service checks, the executor, `evalharness.visibility`, `storm` and `run` all read the
catalog or the graph.

ADR-0017 is why it is a committed file and not a runtime query. Jaeger's store is in memory and
covers only its lookback, so *"a correlation rule that changes its mind because the tracing
backend restarted is worse than one that is merely stale"*. ADR-0008 also requires that what a
scored run sees be fixed in advance.

## Q122, found on the way: the v2 world has no topology

The snapshot's nodes are v1's: `cartservice`, `checkoutservice` and the rest. On v2,
`canonical_service` is the identity (correctly, since T7.0 #6), so v2's names never meet the
snapshot's. Measured on 2026-10-01 with `FAULTLINE_TOOLS_WORLD=v2` (this said `FAULTLINE_WORLD` until corrected 2026-10-01; the run used the right one) against the code at `43e1db4`:

- **`ServiceCatalog.get`** returns `None` for `checkout`, `cart`, `email` and `product-catalog`,
  and `PRESENT` only for `frontend`, the one name v1 and v2 share.
- **`blast_radius(["checkout"], 2)`** reaches nothing.
- **So on every v2 incident:**
  - triage's blast radius is its seeds alone;
  - every member's `presence` is `None`;
  - `start_from` is `frontend` if it alerted, and `None` otherwise.

**Nothing scored is stranded.** README's own first line says no scored run exists on v2. Any v2
agent run would have triaged on a graph that does not contain its world. The recordings'
read-backs call the tools, not triage, so no label rests on it. **SREGym's astronomy-shop has the
same names and the same gap.**

## The options, and the decision

| option | for | against |
|---|---|---|
| **A. A committed snapshot per world and per application, captured offline** (decided) | keeps ADR-0017 and ADR-0008: a scored run sees a graph fixed before it. The capture is the T2.4 method, already proven. Astronomy-shop and the v2 world share one graph | a capture per application, each needing a deploy (1c measured 5m31s for astronomy-shop). World- and application-aware loading is code that does not exist yet |
| B. SREGym's `get_dependency_graph` at run time | no capture work | the graph moves with traffic and lookback, and **the injected fault can remove the very edges triage needs**. It breaks ADR-0017. Its reply is `str(response.json())`, a Python repr that `json.loads` rejects (the harness read's finding for `get_traces`, true here too) |
| C. No topology on foreign applications | nothing to build | triage's graph reasoning is off for every SREGym problem, at an unmeasured cost. Q122 would still need a v2 snapshot for Faultline's own world |

## The first capture: the v2 world, read-only, 2026-10-01

`capture_v2_graph.py` read Jaeger through frontend-proxy on `:8080` at
`/jaeger/ui/api/dependencies`, checking the reply is JSON (T2.4's trap). The outputs are in
[`docs/evidence/t7.2-topology/`](../evidence/t7.2-topology/).

The edges are not dated reliably by time window. In two runs 2.5 minutes apart:

| lookback | run 1 (07:33:55) | run 2 (07:36:22, the one kept) |
|---|---|---|
| 1 h | 25 edges, 11 nodes, **no order edge** | 29 edges, 13 nodes (checkout and currency appear) |
| 24 h | 25 edges, 11 nodes, **no order edge** | 33 edges, 15 nodes; order edges counted 1 to 4 |
| 72 h | 38 edges, 17 nodes | 38 edges, 17 nodes |
| 168 h | not asked | **38 edges, 17 nodes, the same set as 72 h** |

The first run's files were overwritten by the second, so its counts above are as read at the time.

**The cause is Q121.** Every order passes through quote. Quote's spans now sit **1 day 12h06m10s**
before the rest of their trace: `skew_probe.py`, 07:36 UTC, 8 of 150 traces. Jaeger dates the
trace by its earliest span. So the order path slides out of any window shorter than the skew,
and in and out of windows near it. **The edge set is stable only once the window clears the
skew**, at 72 h and 168 h.

**The 168 h graph** (`v2-dependencies-168h.json`):

- **Services**, 17: accounting, ad, cart, checkout, currency, email, flagd, fraud-detection,
  frontend, frontend-proxy, load-generator, payment, product-catalog, product-reviews, quote,
  recommendation, shipping.
- **Cross-service edges**, 22:
  - **the order path**, 8: `frontend → checkout`, then `checkout →` cart, currency, email,
    payment, product-catalog and shipping, then `shipping → quote`;
  - **the storefront**, 7: `frontend-proxy → frontend`, then `frontend →` ad, cart,
    product-catalog, product-reviews and recommendation, plus `recommendation → product-catalog`;
  - **flag reads**, 6: `cart`, `ad`, `fraud-detection`, `product-reviews` and `recommendation`
    `→ flagd`, plus the load generator's own;
  - **the load generator into the proxy**, 1.
- **Self-edges**, 16 (`frontend → frontend` 75,279). Jaeger v2 counts calls inside a service.
  v1's capture had none, and they are not dependencies.

**What the graph does not hold, and what each means for loading it:**

- **Self-edges** are not dependencies, so they are excluded at load, as an artifact class.
- **`load-generator → frontend-proxy` and `load-generator → flagd`** are the synthetic client, so
  they are artifact edges, as v1's `loadgenerator → frontend` was.
- **`frontend-proxy → frontend` is real.** v1's proxy had only its route to Jaeger and was
  `ARTIFACT_ONLY`; v2's proxy carries the storefront.
- **Kafka's consumers have no incoming edge.** There is no `checkout → accounting` and no
  `checkout → fraud-detection`. v1 had both (`async`). In v2 the consumer spans are not children
  of the producer's span, so the order's async half is invisible. **What triage says about an
  accounting or fraud-detection fault has to come from somewhere else, or be stated as
  unreachable.**
  - **Corrected 2026-10-01** ([Q122's build registration](../../evals/runs/PREREGISTRATION-Q122-v2-graph.md)).
    This said both services sat in the graph on self-edges alone. That is true of `accounting`
    only: `fraud-detection → flagd` (5 calls in the hour) keeps `fraud-detection` in the graph.
    Neither has an incoming edge.
- **`llm`, `image-provider`, `valkey-cart`, `postgresql` and `kafka` never appear.**
  - The three datastores are client spans inside their callers, as v1's `redis-cart` and `kafka`
    were (ADR-0017 Addendum 3), so they are `KNOWN_ABSENT` / `INFRASTRUCTURE` in v2's names.
  - `llm` (product-reviews' model service) and `image-provider` are each measured, not assumed,
    when the snapshot of record is taken.
- **Edge kinds** (`EDGE_KINDS`: `sync` measured by propagation, `async`) are v1's and name v1's
  services. Every v2 edge loads as `UNMEASURED` until measured. That is the honest state, and
  triage already reports `unmeasured_edges`.
