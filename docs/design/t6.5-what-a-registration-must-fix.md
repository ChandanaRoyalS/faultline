# T6.5 — what a pre-registration has to fix before anything is built

**Not a pre-registration.** The phase's rule is that the first PR of a task is a registration and
that the cost is named before it is spent; this is the note that precedes it, listing the decisions
a registration cannot leave open and the facts that were checked rather than assumed.

**$0.00.** Everything below is read off the tree, the catalog and the archive.

---

## 1. Where T6.5 stands

The plan's row: *"Postmortem generation + learning-effect measurement — post-resolution draft for
human edit, accepted postmortems join the corpus, cross-scenario transfer within a fault class
measured with/without."*

| clause | state |
|---|---|
| a post-resolution postmortem step | **absent.** `postmortem` does not occur anywhere in `src/` |
| a human-edit / accept gate before a document joins the corpus | **absent.** Narratives join at seed time as recorded |
| the cross-scenario transfer measurement | **never run** |
| the leak-guarded scribe | **present** (T3.4, ADR-0020 §4) — but it writes *during* the investigation |
| the quarantine half — contamination rules | **present and load-bearing** (T2.4b, T4.1b) |

The `~25%` in the plan is the starting inventory, not progress: the row's own preamble says the
fractions are *"what earlier phases left behind on the way to their own gates"* and that Phase 6
had not begun when they were written.

## 2. Four facts, checked

**Transfer is feasible on this catalog.** Dev scenarios by fault class:

| class | dev scenarios |
|---|---|
| `bad_config` | 4 — cart-redis-misconfig, payment-telemetry-blackout, product-catalog-flag-failure, shipping-quote-misconfig |
| `bad_deploy` | 3 — cart-bad-image-tag, flag-service-crashloop, shipping-wrong-image |
| `dependency_latency` | 3 — ad-dependency-latency, cart-dependency-latency, redis-cart-dependency-latency |
| `resource_exhaustion` | 3 — ad-memory-squeeze, currency-cpu-throttle, frauddetection-memory-squeeze |

Holding one out always leaves donors. **But `ad-dependency-latency` has no narrative bundle** — 12
bundles against 13 dev scenarios — so that class has **one** donor whenever the held-out scenario
is one of the other two. A registration that reports a per-class delta has to say that.

**The exclusion is singular.** `PastIncidentStore.search(query, k, exclude_origin: str | None)`,
and the SQL is `AND origin <> %(origin)s`. Excluding *a class* of origins is not expressible today.

**The A/A check passes, and the number worth reading is not the verdict.** Sweep 12's §5 records
the whole arc: the first execution reported `FAILED` because `aa.Result.passed` requires the words
*"no measurable effect"* in every verdict and the non-proportion branch could not produce them; it
was fixed the same day and **re-run to a pass**. Confirmed again 2026-09-15.

What §5 establishes matters more than the pass: **the instrument produced +10.0pp on fault class
between two halves of one configuration**, against the +20.0pp §3 reports between the arms. *"The
between-arm effect is twice the within-arm noise on the same axis, at the same n and R."*

**Every scored run's corpus is unhashed in the way that matters.** 183 manifests carry a corpus
block; none carries `body_sha256`, which postdates them all (Q36). The corpus currently seeded also
**disagrees with `main` on nine runbooks** (Q45's first run), same shape, different words.

## 3. The design decision that changes the shape of the task

**The plan says "measured with/without" and a reader takes that to mean two corpora. It should not
be two corpora.**

A with/without-*corpus* comparison means seeding, unseeding and re-seeding between arms. That walks
straight into **Q61**: nothing records which corpus a run read in a form `group_by_generation`
respects, so the two arms would group into one table by a route no grouping sees — and the arms
would differ in `body_sha256`, which is the one axis ADR-0014 exists to separate.

**A query-time exclusion is strictly better and is available.** Widen `exclude_origin` to a set, and
the "without" arm becomes *the same corpus, one wider exclusion*:

- **One corpus, one `body_sha256`, one generation.** The comparison never crosses a corpus boundary,
  so Q61 stops blocking T6.5 entirely.
- **The exclusion is already recorded per retrieval** (`trajectory_retrievals.exclude_origin`), so
  what each arm could see is in the record rather than in an operator's memory. That column becomes
  a set and needs a shape that can hold one.
- **It is the mechanism T4.1b already uses**, widened, rather than a second mechanism beside it.
- **No re-seed** — which also means the nine drifted runbooks and Q45's open half stay out of it.

The registration should state this as a correction to the plan's wording and say why, rather than
quietly doing something the row does not describe.

## 4. What a registration must decide, and cannot leave open

**1. What a postmortem is that a narrative is not.** The scribe already writes a leak-guarded
narrative during the investigation, and it already joins the corpus. If a postmortem is the same
text at a later time, the task is a scheduling change and the transfer measurement is testing the
corpus that already exists. If it is a different artefact — written after resolution, with the
outcome and the remediation's *result* in it, which the narrative cannot contain because it does not
exist yet — then it is a new document class with its own leak surface and its own guard. **The
registration has to pick, and the second reading is the one that makes the task worth doing.**

**2. Whether the accept gate is a state or a person.** *"Draft for human edit, never auto-published"*
is a real constraint and the repo has one precedent for it — ADR-0039's approval surface, where a
person acts and the ledger records who. A postmortem accept gate could reuse that shape. What it
must not be is a boolean nobody sets, which is what "accepted" becomes if the only caller is a
seeding script.

**3. What the outcome metric is, and against which floor.** Fault-class accuracy is the obvious
one, and there are **two** thresholds it has to clear, not one. The catalog's MDE is 16.2pp at
`n = 10, R = 3`. But sweep 12's A/A check measured the instrument producing **+10.0pp on that same
axis between a configuration and itself**, so a transfer delta under ~10pp is inside what this
harness generates from nothing. The registration should name both in advance rather than discover
either — the shape Q57 got wrong by predicting a resolvable effect it had no power to see.

**4. What the A/A check is for here, given that it passes.** The plan's row says the transfer
measurement *depends on* an A/A check at R ≥ 2. It exists, it runs, and it passed on sweep 12 — so
the question is not whether the gate clears but **what the registration does with the 10pp**. A
transfer measurement at this catalog's shape either clears that floor or reports a delta the
instrument could have produced unaided, and which of those it is should be decided before the run
rather than argued after it.

**5. The budget, before it is spent.** Thirteen held-out scenarios × two arms × R ≥ 2 is **52 scored
runs**, and at sweep 12's measured $0.59–0.77 that is **$31–40**, plus the harness's 16.7% discard
rate — call it **$37–48**. The registration names a hard ceiling, as Q53's did, or the task does not
start.

## 5. What this note deliberately does not do

**It writes no predictions.** Predictions belong in the registration, and they cannot be written
until §4's five decisions are made — particularly §4.1, because a prediction about transfer means
something different depending on what a postmortem is.

**It proposes no code.** The phase's rule is that the first PR of a task is its registration.

**It does not reopen the plan's wording lightly.** §3 is a correction to one clause — *with/without
corpus* → *with/without the class's documents, at query time* — and it is proposed because the
plan's reading is blocked by Q61 and the alternative is not, not because it is more convenient.
