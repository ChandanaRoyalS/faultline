# T7.2 — the external benchmark run, scoped before anything is built

**Nothing was run and nothing was spent.** This note does the half of T7.2 that
[ADR-0004](../adr/0004-benchmark-target.md)'s addendum said must be done *here* rather than
discovered inside the task: *"Two of Faultline's tool implementations (Jaeger traces, and an MCP
transport for metrics and logs) are prerequisites of T7.2 and should be costed there, not
discovered in it."* Each of that addendum's four corrections is costed below against the tree as it
stands at `e2aaeb6`.

**Why this task and not another.** The execution plan
([`execution-plan-rev9.pdf`](../spec/execution-plan-rev9.pdf), §10) states its own triage rule for
Phase 7: *"If time compresses, triage by artifact value, not by wave: the benchmark run (T7.2) and
the writeup (T7.5) — the number, and the thing that carries the number to readers — outrank the
ablation series and the dashboard."* T7.2 is **unbuilt** — no `sregym`, `itbench` or adapter string
appears anywhere in `src/`, and [T7.62's audit](t7.62-audit-against-the-plan.md) recorded it as
*not built* alongside the observation that **neither of the plan's two priority tasks is among the
sixty things Phase 7 has done under other numbers.**

---

## 1. What the benchmark is for, stated before its cost

The project's sharpest available criticism is that **a system authoring its own world, its own
faults and its own grader is self-referential.** ADR-0004 opens on exactly that. Every number in
[`RESULTS.md`](../RESULTS.md) — 26/27 on fault class, 23/30 on culprit service, the baseline panel
merged 2026-09-21 — is measured on a world this repository built and graded by a judge this
repository wrote. **The baseline suite narrowed that criticism and did not answer it**: B0, B1 and
B2 are also ours.

SREGym answers it in the only way that counts, by putting the same agent in front of ninety
problems nobody here authored. **That is the whole value of the task**, and it is worth keeping in
view while reading the costs below, because the costs are not small.

## 2. The four corrections, costed against the current tree

### Correction 1 — registration is cheap, and it still holds

*"An agent is a row in `agents.yaml` … plus a driver module. T7.2 is a driver, not a port."*
**Unchanged and still the cheapest part.** Nothing in the eleven days since has made the agent
harder to drive from outside: `faultline-investigate` already takes an incident and emits a
structured verdict, and the runtime contract's requirement (c) — *"emits a structured verdict
independent of Faultline's web UI and database"* — is satisfied by the artifact writer the eval
harness already uses.

### Correction 2 — MCP over SSE, and the tool layer is **not** behind an interface

*"Five servers are mounted: `/kubectl`, `/prometheus`, `/loki`, `/jaeger`, `/submit`. Faultline's
tools call Prometheus and Loki over HTTP directly, so the tool layer needs a second implementation
behind the same interface."*

**Half of requirement (a) is met and the half T7.2 needs is not.** `ToolSettings` holds
`prometheus_url`, `loki_url` and `tempo_url` as configuration, so the endpoints are not hard-wired
to the compose network — that is requirement (a) as written, and it paid off. But **`Tools` is a
concrete class, not a protocol**: `faultline/agents/roles.py` annotates `tools: Tools` at both
call sites, and every backend read goes through `Tools._backend` into `telemetry.get_json` over
HTTP. Pointing a URL at an SSE endpoint does not work, because the transport differs, not the
address.

**So the cost is an interface extraction that does not exist yet**: a protocol carrying the four
tool methods, `Tools` renamed to the HTTP implementation behind it, and the annotations widened.
**This is refactoring the tool layer, not adding to it**, and it touches the class the whole agent
reads the world through.

**One thing that makes it safer than it sounds.** `capability.tool_surface()` reads the public
functions off `Tools` and the capability stamp is computed from them, so an extraction that
preserves the four method signatures is checkable against a stamp rather than by inspection. **A
change that moves `cap:` has changed the agent's surface and the stamp will say so.** That guard
should be the first thing this work runs against, not the last.

### Correction 3 — Jaeger, and **there is an implementation in the history**

*"Traces need a second implementation: SREGym serves Jaeger, Faultline queries Tempo."*

**Cheaper than the addendum could know, because Faultline read Jaeger until 2026-09-08.**
`jaeger_url`, `JAEGER_TRACES = "/api/traces"` and a working `trace_query` against it are in the
tree at `73477ce^`, the commit before T6.1 replaced them with Tempo. **This is recovery, not
authorship.**

**What is not recoverable with it, and it is the load-bearing half.** T6.1 did not only swap a
backend: it added `spantree.py`, which builds one tree per trace from `parent_span_id` and names
the **degrading hop** by a deterministic two-rule summariser. The ablation in
[`ABLATIONS.md`](../ABLATIONS.md) §1 says what that is worth — the traces specialist is **the one
effect that shows**, +20 pp on fault class, and §*Where the effect sits* attributes it to the span
tree specifically: *"without a span tree the synthesizer watches checkout's log trail stop and
names the next hop by position."*

**So a recovered Jaeger reader that returns a span list scores a different system from the one
this repository measures.** The real cost of Correction 3 is not the fetch — it is producing what
`spantree.build(spans: list[TraceSpan])` consumes.

**And the target is narrower than "a mapping", which is the useful finding here.** `TraceSpan`
has nine fields, and the two the span tree cannot work without are named in their own docstring:
*"`span_id` / `parent_span_id` … **These two fields are T6.1.** Without them a trace is a list, and
a list cannot say which hop degraded."* Jaeger's trace JSON carries both — `spanID`, and
`references[].spanID` where `refType` is `CHILD_OF` — so the tree is reconstructible in principle.
**What is unverified is `status`**, which `spantree.degrading_hop`'s *deepest error* rule reads and
which `TraceSpan` documents as *"OTLP status code as text"*: Jaeger stores span status as tags
(`otel.status_code`, or `error=true`), not as a field, and whether SREGym's instrumentation emits
the tag at all has not been checked.

**That check is the one thing in this note worth doing against the real harness before anything
else is built**, because if the status tag is absent the degrading-hop rule falls back to
largest-self-time on every span and the traces specialist stops being the component
[`ABLATIONS.md`](../ABLATIONS.md) measured. It is a read of SREGym's own trace output, not a run,
and it is cheap.

### Correction 4 — diagnosis only, and one modality is simply absent

Two separate limits, and only one of them is about mitigation.

**Mitigation scores zero by construction**, and the addendum already settled the consequence: what
T7.2 may claim is *"a diagnosis pass rate on SREGym, never a combined score"*, and any bullet
citing it carries the word **diagnosis**. **One correction to the addendum's own reasoning**: it
gives *"the proposer is unbuilt"* as part of the cause, and the proposer **is** built — it has 223
`PROPOSAL` steps across 356 trajectories, and T6.6 executed one approved action on the deployment.
The conclusion is unaffected, because the binding reason is the other one: **Faultline proposes and
never executes by design** (ADR-0028 §2), and SREGym's mitigation oracles *"inspect the cluster
after the fact"*. A system that never writes scores zero on a graded write whatever its proposer
can do.

**The absent modality is the more interesting limit.** *"Change history has no counterpart — the
harness exposes no deploy or config-change surface, so the change analyst has nothing to call."*
`Tools` already has the right behaviour for this: `changes=None` means change history is
unavailable and is *"reported as an error rather than as an empty result — the difference is the
whole point (ADR-0019)"*. **So the agent degrades honestly rather than silently.** But the number
it produces is then a number about **three specialists, not four**, and
`redis-cart-dependency-latency`'s catalog entry records `change_history` as the only class that can
name its culprit. **That sentence belongs beside the SREGym figure every time it is published**,
which the addendum also says.

## 3. The blocker that is not code, and it is first

ADR-0004's Consequences: *"benchmark runs need a Kubernetes-capable host with more headroom than
the development environment; expect to resize the VM temporarily for benchmark days."*

**The deployment cannot host this and it is not close.** `deploy/README.md` §1 sizes the VM at
**8 vCPU / 16 GB** against the spec's own figure that *"the full stack (demo world + telemetry +
platform) wants ~4 vCPU / 16 GB — the OTel demo alone needs ~6 GB."* SREGym wants Docker, Helm,
kubectl, **kind and a self-managed Kubernetes cluster** on top of that. There is no reading of
those numbers where both run on one 16 GB box.

**Three shapes, and this note does not choose between them:**

1. **A second host for benchmark days**, torn down after. Keeps the deployment untouched, which is
   the boundary ADR-0004's carve-out draws — *"benchmark infrastructure is not product
   infrastructure."* Costs a VM by the day.
2. **Stop the world, run the benchmark, restart it.** Cheapest in money and the most disruptive:
   the deployment is the thing that has been quietly investigating itself since 2026-09-11, and its
   audit log is evidence.
3. **Run it on the development machine.** ADR-0004 notes kind works locally with *"limited problem
   coverage"* — and limited coverage on a ninety-problem suite is a number whose denominator needs
   stating, which is survivable if it is stated.

**Nothing here is decidable from the repository.** What it needs is one measurement of the
deployment's actual free headroom, which is a command, not an argument.

## 4. What this note deliberately does not do

**It does not pre-register anything.** No run is proposed, no ceiling is named, and no prediction
is written, because the host question is open and a pre-registration written before the shape is
known is a pre-registration that will need amending — which this repository treats as not having
been one.

**It does not start the interface extraction.** §2's Correction 2 is a refactor of the class the
whole agent reads the world through, and it should land under its own change with the capability
stamp as its check, not as a step inside a benchmark task.

**And it does not estimate a score.** The one honest thing to say in advance is what the addendum
already says: this exercises a narrower system than the in-house harness does — three modalities
of four, diagnosis only — and the figure means what it means with those two clauses attached.

## 5. The order the record supports

1. **Measure the deployment's free headroom** and decide the host shape. Blocks everything else and
   costs nothing.
2. **Extract the tool interface** (Correction 2), with the capability stamp as the check that the
   agent's surface did not move. No benchmark involvement, lands on its own.
3. **Check SREGym's spans for a status tag** (Correction 3), which is a read rather than a run and
   decides whether the traces specialist SREGym grades is the one `ABLATIONS.md` measured. Then
   price the rest of the Jaeger mapping against what that read finds.
4. **Then** pre-register the run, with the denominator, the modality gap and the diagnosis-only
   clause stated in advance rather than beside the result.
