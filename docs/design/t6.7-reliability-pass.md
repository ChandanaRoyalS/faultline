# T6.7 — the failure table becomes tested behaviour

**Ceiling for the whole task: $1.00**, and most pieces are $0. A storm test that ran two hundred
investigations would be a bill, not a test; every piece here runs against the platform with the
model switched off or faked, except one induced kill of a live investigation on the development
machine, which costs whatever the run had spent when it died.

The plan's row: *"circuit breakers on providers and tools, alert-storm load test at 200+ alerts,
worker-crash chaos test, DB backup/restore drill, timeout audit. The failure-scenario table in the
spec becomes tested behavior instead of claimed behavior — each row gets a test or a drill.
Deliverable: passing storm/crash tests + restore runbook."* The plan's gaps column had it at ~30%
and named four of the five clauses as absent. Read against the tree on 2026-09-19, that is right,
and the survey that produced this note found two things the row did not name: a setting nothing
reads, and a deployment that investigates unattended with no ceiling above the per-incident one.

---

## 1. What is already there

**Retry, not a breaker.** `agents/model.Resilient` (T2.5, ADR-0031) retries a transient failure
on the same model with capped full-jitter backoff, falls back to a second model only when
configured (it is not), records every substitution, and since Q33 checks the run's deadline
between attempts. It keeps no state across calls: every `complete()` starts from closed, nothing
counts failures, nothing trips, nothing half-opens. Tools retry nothing at all
(`agents/budget.py:169`) and a backend that is down costs a specialist every one of its tool calls,
each returning `error=` after `HTTP_TIMEOUT = 20` seconds.

**The mechanisms a crash test would exercise, tested against a fake.** `orchestrator/consumer.py`
reads with `XREADGROUP`, claims stale entries with `XAUTOCLAIM`, acks after the write.
`tests/test_orchestrator.py:670-786` proves the loop survives a worker death *given* those
semantics and says so in its header; `tests/test_integration_consumer.py` proves real Redis has
the semantics. Nothing has ever killed a process. Q72's `orphaned` reconciler closes the trajectory
row a killed investigation leaves.

**Dedupe and correlation fold alerts into incidents at n = 8.** `tests/test_orchestrator.py:110`
is the storm case the gate-1 evidence named, with eight events. The concurrency cap exists with
`max_concurrent = 3`, `claim_idle_seconds = 60` and `settle_window_seconds = 300` all marked
placeholder - a storm is what would size them, and none has run.

**A snapshot, never restored the way the runbook says.** `make deploy-snapshot` dumps with
`--clean --if-exists`; README §3.5 loaded one forward into an empty deployment once (T5.5);
§3.7's destructive-rollback restore - `down`, restore over a populated database, `up` - has never
been executed, and README §4 says *"no backups beyond §3.7's manual snapshot"*. The snapshot that
would matter most sits in `/tmp` on the VM.

**A partial timeout audit.** `tests/test_subprocess_timeouts.py` holds every subprocess call to
a bound by AST. Nothing audits the HTTP, provider or database paths, and listing them for this note
found that `AgentSettings.timeout_seconds` (600 s) has **no reader**: `build_model` never passes it,
so both model clients run on their hardcoded 600 s - equal to the whole wall-clock budget. One
hung call can spend the entire budget before `Resilient`'s deadline is even consulted; Q33's
6596 s run is that shape.

**Six of thirteen failure rows in `FAILURE_ROWS`, tested for reachability only.**
`tests/test_orchestrator.py:563` maps the rows whose Mitigation or Recovery names a lifecycle
state; five more are named as excluded with reasons; rows 9 (wrong-service remediation) and 11
(stale runbook) are in neither list. No row is tested for the behaviour its Mitigation column
describes.

**And from 2026-09-19: the platform paged itself** and ran three investigations unattended for
$0.69 (T6.6 evidence). `faultline-sweep` has `--max-usd`; the orchestrator has per-incident
budgets and nothing above them. That is failure row 10 - *runaway cost* - one level up from where
the spec put it.

## 2. The decisions

**A breaker is state across calls, and the question is where the state lives.** The investigator
is a subprocess per run; the orchestrator is the long-lived process but makes one model call per
incident (triage). So:

- **Provider breaker, inside a run.** `reliability.breaker.CircuitBreaker(threshold, cooldown)` -
  closed, open, half-open. `Resilient` holds one per model. A *trip* is one exhaustion of the
  retry schedule (four transient failures in a row is already the evidence); while open, calls to
  that model raise `ProviderOpen` immediately instead of spending another schedule, fallbacks are
  tried if configured, and after `cooldown` one trial call half-opens it. A run whose primary is
  open and has no fallback ends **fast** with outcome `provider_unavailable` - a new outcome, not
  `failed`, because nothing about the investigation failed - and the incident goes back to
  **`QUEUED`**, the state failure row 1 names, from which the cap re-admits it to `TRIAGING` as
  it does today. That is one new row in `machine.ALLOWED` (agent-driven states → `QUEUED`, on
  this outcome only) and therefore an ADR-0016 addendum, because ADR-0016 owns the table and a
  transition added without one is the defect its addenda exist to prevent. `FAILED` stays what
  it is: an investigation that raised.
- **Provider breaker, across runs.** No new store. The runner reads the record it already has:
  if the last `N = 2` trajectories on this deployment ended `provider_unavailable` within
  `cooldown = 300 s`, it defers every due incident and says so in one log line and one metric
  (`faultline_investigations_deferred_total{reason="provider_open"}`). Half-open is the first
  incident after the cooldown. Row 1's Recovery - *breaker half-opens; queued incidents resume* -
  is those two sentences.
- **Tool breaker, per backend, per run.** `Tools` counts consecutive errors per backend
  (Prometheus, Loki, Tempo, the change log). At `threshold = 3` the backend is open for the rest
  of the run: every further call returns a typed result whose `error` says *"modality
  unavailable: <backend> failed 3 consecutive calls; not retried this run"* without contacting
  it, so a specialist with twelve tool calls against a dead Loki spends one, not twelve, at
  20 s each. Row 12's Detection (*consecutive tool-error threshold*) and Mitigation (*specialist
  reports "modality unavailable" as typed evidence*). No half-open within a run: runs are minutes
  long and the next run starts closed.

**A storm is a harness, run with the model off, and its numbers are pre-registered.**
`faultline-storm`: N alerts in Alertmanager webhook shape, drawn over the catalog's services and
the two alert names the rules define, posted to the receiver at a rate, with the orchestrator
consuming and correlating and **not investigating** (`FAULTLINE_ORCH_INVESTIGATE` unset - the
development default). It records: accepted, deduped, stream length over time, incidents opened,
episodes per incident, `faultline_incidents_queued` over time, time to drain, receiver latency,
and container memory against the limits. The predictions - how many incidents 200 alerts fold
into, that no fingerprint opens two incidents, that the queue drains inside the settle window,
that no 5xx is returned - are written in `PREREGISTRATION-T6.7.md` before the first run. **Never
on the VM**: its orchestrator investigates, and 200 alerts there is up to 200 × $0.70. Row 5's
Recovery, *post-hoc merge of duplicate incidents*, is **not built here**; the storm measures how
many duplicates arise, and that number decides whether a merge path is worth its own row.

**The crash test kills real processes, twice.** (a) In integration tests against real Redis:
a consumer subprocess reads an entry and is `SIGKILL`ed before it acks; a second consumer claims
it after the idle threshold and the event is applied exactly once. (b) As a drill on the
development machine: one live investigation, `kill -9` on `faultline-investigate` mid-run, then
read what the record says - the orchestrator's exit line, the incident's state, the trajectory
row with no outcome, `orphaned` after the ceiling, and the runner's second attempt. **What
"resumes" means here is a fresh run, not a resume from the last step.** The spec's Recovery
column says *"resumes from last completed agent step (idempotent steps, keyed writes)"*; the
runtime restarts an investigation from triage, and this note says so rather than claiming the
sentence. Making steps resumable is a design change to the investigation loop and is not T6.7.

**The restore drill runs the runbook's own words on the VM, over live data.** Snapshot, count
rows, `down`, restore with `--clean --if-exists`, `up`, count again, equal. Then the two things
the drill will obviously want: snapshots out of `/tmp` into a dated directory the VM keeps, and a
nightly `pg_dump` with a seven-day window, so *"no backups beyond the manual snapshot"* stops being
true. The restore runbook is §3.7 rewritten from what was actually typed, with the timings.

**The timeout audit is a test, and a fix.** `tests/test_timeouts.py` extends the AST audit to
every `urlopen`, every model-client construction and every HTTP client: each carries a bound,
each bound is named in one table in this note with its value and its reason, and each is smaller
than the budget it runs inside. The dead `AgentSettings.timeout_seconds` gets a reader
(`build_model` passes it) and a value that is not the whole budget: **180 s**, three times the
longest model call T6.6 measured (1 m 9 s). `statement_timeout` on the API's read connection.

**Every failure row gets a line.** `tests/test_failure_table.py` holds all thirteen rows, each
pointing at the test function or the evidence directory that demonstrates its Mitigation - and
for the rows this task does not fully meet (5's merge, 6's resume, 11's stale runbook: Q43/Q44),
the line says *not met* and names the row that owns it. A table whose every row is either a test,
a drill or an honest *not yet* is what the plan row asks for.

**And the ceiling the orchestrator does not have.** `FAULTLINE_ORCH_MAX_USD_PER_DAY` (default
$5, roughly seven investigations): before spawning, the runner sums the last 24 h of trajectory
tokens at the harness's prices; at or above the ceiling it defers and says so, the same one line
and one metric as the provider breaker with `reason="spend_ceiling"`. Yesterday's loop would have
stopped at the third investigation instead of at the stale series.

## 2a. The timeout table (piece 1)

Every bound an external call runs under, with what it sits inside. `tests/test_timeouts.py`
asserts each value and each relation; the subprocess half is `tests/test_subprocess_timeouts.py`.

| call | bound | sits inside | why this value |
|---|---|---|---|
| one model call, either client (`AgentSettings.timeout_seconds`) | **180 s** | the run's wall clock, **600 s** (`Budget.wall_clock_seconds`) | three times the longest call T6.6 measured (1 m 9 s); a hang costs one call's budget, and the retry after it is still inside the run. **Was 600 s and had no reader** |
| the SDK's own retries | **0** | `Resilient`'s 4 attempts | one retry loop, the one that counts, records and honours the deadline; the judge keeps the SDK's default because it has no outer loop |
| `Resilient`'s schedule | 4 attempts, backoff ≤ 30 s, deadline = wall clock | the run | Q33 |
| one telemetry read (`telemetry.HTTP_TIMEOUT`) | **20 s** | a specialist's 12 tool calls, 240 s worst case, inside 600 s | the trace tool's largest legitimate read is seconds; before the tool breaker (piece 5) a dead backend costs 12 × 20 s |
| the approve route waiting on the executor (`ApiSettings.executor_timeout_seconds`) | **330 s** | the browser's click | the executor's compose command is bounded at **300 s** (`COMMAND_TIMEOUT_SECONDS`) + 30 s bookkeeping. **Was 30 s**: a slow recreate would have shown *timed out* over an action that completed |
| the executor's compose verb | 300 s | the approve route | `injector.docker` |
| a statement on the read surface's connection | **30 000 ms** | a page, a scrape, an approve | longer than any read the surface makes; a migration's lock cannot hold a request forever. **New** |

| a Slack post | **5 s** | one orchestrator poll (15 s) | a courtesy |
| orphan ceiling | **1200 s** | - | twice the wall clock (Q72) |

## 4. What this does not claim

**No accuracy number.** Nothing here touches what the agent concludes; the storm runs with no
model, the kill test's investigation is not scored, and every breaker test uses a fake. The
storm's numbers are about the platform - incidents per alert, drain time, memory - and they are
pre-registered because they will be printed.

**Not a resume.** A killed investigation is re-run, not resumed (§2). Not a merge: duplicate
incidents from a storm are counted, not merged. Not row 11: stale-runbook retrieval stays with
Q43/Q44.

**Not `tenacity`.** The spec names it; `Resilient` already does what it would do, with the
deadline bound Q33 added and a substitution record `tenacity` would not keep. Adding a dependency
to do the same thing less legibly is not reliability.

**Not the world's reliability.** Every test here is about the platform. The world's collector,
Tempo (Q76) and Prometheus are somebody else's compose file and this repository's digest.

## 5. Amendment, 2026-09-19 — the ceiling, and two predictions

**The $1.00 ceiling was exceeded: T6.7 ends at $1.85.** All of it is the crash drill (*the crash
drill* in the evidence): $0.63 on a run two kill attempts never reached (no `pkill` in the image;
a shell that matched its own command line), $0.47 on the run killed at step 19, $0.76 on the retry
that the drill existed to observe. Not raised; recorded. Every remaining piece is $0.

**§2's kill prediction was wrong in the way that matters.** The incident was not stranded: the
runner writes state transitions after the run returns, so a killed run leaves `triaging`, which
is due, and attempt 2 followed in fifteen seconds. The design's *"a fresh run, not a resume"* is
what the deployment already did. What the drill found instead: the trajectory row was first
written after synthesis, so a kill before that left nothing to reconcile (fixed - piece 3b), and
the incident reads `triaging` for the whole of a healthy run (Q78).

**§2's `QUEUED` row for `orphaned` is withdrawn.** It was drawn for a stranding that does not
happen; a killed run's incident is already where the runner will find it. The `QUEUED` row stays
for `provider_unavailable` alone (piece 5), where the incident has genuinely nowhere to go.

## 6. Amendment, 2026-09-20 — piece 5 as built

**`QUEUED` is withdrawn for `provider_unavailable` too.** §2 sent an incident back to `QUEUED`
when its run ended on an open provider. Building it showed two things: the run's state
transitions are written after it returns (Q78), so at the moment of the write the incident is
`TRIAGING`, not an agent-driven state; and the cap re-admits from `QUEUED` only when another
incident resolves (`_promote_from_queue`), so an incident parked there by an outage would wait for
somebody else's resolution rather than the provider's return. The incident therefore stays
`TRIAGING` - where `due()` finds it - and no `machine.ALLOWED` row changes; ADR-0016 has no
addendum to write. What changes is the runner: exit code **6** (`Exit.PROVIDER_UNAVAILABLE`) is
not counted as an attempt, and the cross-run breaker is read from the last two trajectories'
outcomes (§2's *"no new store"* stands). The one metric §2 promised is the queue gauge the
platform already has; no counter was added, because the deployment's `/metrics` is read from
Postgres and a counter in the orchestrator's process would not reach it.

**Failure row 1's `QUEUED` in `FAILURE_ROWS` stays true** - the state is reachable through the
cap, which is what the reachability test checks - and piece 7's line for row 1 says what the
behaviour actually is: breaker in the run, breaker across runs, incident admitted throughout.

## 7. Where it ended — 2026-09-20

Every piece in §3 landed. Against the plan row: circuit breakers on providers and tools (piece 5,
three of them); the 200-alert storm (piece 4, pre-registered, ten of ten, one incident); the
worker-crash test (piece 3, a real `SIGKILL` against real Redis and a live kill on the VM); the
backup/restore drill (piece 2, executed over the live database, the runbook corrected, nightly
snapshots); the timeout audit (piece 1, three bounds fixed and a test over all of them). The
failure table has thirteen lines (piece 7), four of them *not met* with owners. The deliverable's
*restore runbook* is deploy/README §3.7, rewritten from the drill.

Spend: **$1.85**, all of it the crash drill, against a $1.00 ceiling - §5 has the accounting.

What the task found that it was not asked for: three timeouts that did not bind; a runbook wrong
in its first word; a trajectory row that did not exist while the run was running; an orchestrator
that never reconciled its own kills; an incident that reads `triaging` for its whole
investigation (Q78); and a deployment with no ceiling above the per-incident one, which now has
one. Two of the design's own decisions were withdrawn while building them (§5, §6).

Open behind it: Q78. Not this task's: row 11 (Q43/Q44), row 7's scenarios (T6.8), a resumable
investigation loop (nobody's yet).
