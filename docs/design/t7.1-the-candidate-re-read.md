# T7.1 — ADR-0029 §5 re-read under the mechanism criterion, and where the eighth class actually comes from

**\$0, no model call, no world time.** ADR-0043 closes by naming this:

> **ADR-0029 §5's candidate table is re-read under this rule and not discarded.** Its deaths were
> adjudicated on the fix test; several were mechanisms the world did not have, which is still
> disqualifying. **The re-read is owed before the injector is extended and is T7.1's next step.**

This is that re-read. **Its main finding is that ADR-0043's "nearly free" is wrong**, for a reason
neither that ADR nor the assessment it cites resolved — and that the specified eight classes are
still reachable, by a route that has nothing to do with the world move.

## 1. The question the mechanism criterion did not answer: how finely is a mechanism individuated?

ADR-0043 decides *class ≡ injector mechanism* and cites
[`t7.1-v2-mechanisms-assessed.md`](t7.1-v2-mechanisms-assessed.md) §3, which says:

> under §3, v2's fifteen flags *are* fifteen candidate mechanisms, and a `FeatureFlagFault`
> **(or one class per flag family)** would reach eight classes without difficulty.

**The parenthesis is the whole question and it was never settled.** One `FeatureFlagFault` gives
**one** new class. One per flag family gives up to eleven. ADR-0043 adopted the criterion and
inherited the ambiguity, then concluded eight was "nearly free" — which is true under the second
reading and false under the first.

**The existing table settles it, and it settles it against the flags.**

| mechanism in `injector.faults` | tool | surface | class |
|---|---|---|---|
| `BadDeployFault` | compose override | the image | `bad_deploy` |
| `BadConfigFault` | compose override | an env var | `bad_config` |
| `ResourceExhaustionFault` | compose override | a memory **or CPU** limit | `resource_exhaustion` |
| `DependencyLatencyFault` | pumba sidecar | `tc netem` delay | `dependency_latency` |

Two things are visible here and both bear on the flags.

**Individuation is by (tool, surface), not by tool.** Three of the four share one tool — a compose
override — and are three classes because they override three different *kinds of thing*. So "it is
all flagd" does not by itself collapse the flags.

**But `ResourceExhaustionFault` is the decisive precedent.** Memory exhaustion and CPU starvation
are two physically different faults with different symptoms, and they are **one class**, because
they are one field-kind reached by one tool. **Fifteen flags set in one JSON file read through one
OpenFeature client are one field-kind reached by one tool**, by exactly that standard.

**So: one `FeatureFlagFault`, one new class.** Splitting `productCatalogFailure` from `adHighCpu`
while memory and CPU stay married would be special pleading to reach a number, which is the failure
mode this repository names in three separate places as tuning the benchmark to its last result.

## 2. And splitting them anyway does not survive the distinctness criterion

Suppose the flags were split by what they do to the service — errors, latency, resource burn. Each
split then collides with a class that already exists, **on evidence rather than on taxonomy**:

| flag family | what pages | the class it is indistinguishable from |
|---|---|---|
| `imageSlowLoad`, `kafkaQueueProblems` (1 s sleep per record) | `ServiceHighLatency` | `dependency_latency` |
| `adHighCpu`, `recommendationCacheFailure`, `emailMemoryLeak` | latency, then the container's own limits | `resource_exhaustion` |
| `productCatalogFailure`, `cartFailure`, `paymentFailure`, `adFailure`, `llmRateLimitError` | `ServiceHighErrorRate` | each other |

ADR-0043's own *what would change it* names this:

> If the agent cannot tell two mechanisms apart from metrics, logs, traces and change history …
> then they are one class for every purpose the benchmark has, whatever the injector did. …
> **distinctness of alert shape is a pre-registered acceptance criterion for the new catalog.**

**So the flags collapse from either direction.** Treated as one mechanism they are one class;
split by effect, the splits merge into classes that already exist. **Either way v2's fifteen flags
deliver one new fault class, not four and not eleven.**

That is 4 + 1 = **five**. The specification asks for about eight.

## 3. The re-read itself

| ADR-0029 §5 candidate | died on the fix test because | under the mechanism criterion |
|---|---|---|
| **DNS failure** | env var → `bad_config`/`config_revert` | **still dead** — an env var *is* `BadConfigFault`'s surface. Same mechanism, not a new one |
| **Partition** | cleared by recreate or qdisc delete — `dependency_latency`'s two fixes | **survives the fix test's objection.** `docker network disconnect` is a different tool and a different surface from `tc netem`. Must still pass distinctness — see §4 |
| **Expired or wrong credential** | env var → `bad_config`; and the flag store pages nothing | **still dead, twice over.** The mechanism is `BadConfigFault`, and on v2 it is flagd rather than a flag-service stub, which pages no more than v1's did |
| **Clock skew** | nothing the injector could do | **still dead.** ADR-0043 is explicit that *"mechanisms the world did not have … is still disqualifying"*, and `CAP_SYS_TIME` moves the host's clock while `libfaketime` needs a built image against ADR-0026 |
| **Queue or pool exhausted** | no knob; reachable only by load | **dead as a class, alive as a scenario.** v2's `kafkaQueueProblems` supplies the knob — the sentence ADR-0042 correctly says was false of v2 — but the knob is a flag, and flags are one mechanism (§1). A good scenario for `feature_flag`; not a class |
| **Downstream returns wrong data** | image swap → `bad_deploy`/`rollback` | **dead as a class, alive as a scenario**, on the same reading. v2's `llmInaccurateResponse` moves it from the image surface to the flag surface, which is `feature_flag`, not a fifth mechanism |
| **Rate limit** | nothing rate-limits; Envoy's config is a world file | **same** — `llmRateLimitError` is a flag |
| **Disk fill** (the seventh, T7.0's addendum) | zero named volumes | **still dead.** v2 declares no named volumes either; every mount is a read-only config bind |
| **`redis-cart` corruption** (recorded unresolved) | *could not be resolved at desk* — the fix is `restart` or a new flush remediation | **the fix question is now moot**, which is exactly what ADR-0043 changes. `docker exec` into the store is a new tool and a new surface. **This candidate is revived**, and on v2 the target is `valkey-cart` |

**Three of §5's six deaths were adjudicated on a criterion that no longer governs**, and re-reading
them returns exactly one revived candidate — the one ADR-0029 already flagged as unresolved rather
than dead, and which T7.56's rule kept it from claiming.

## 4. Where the eighth class actually comes from, and the uncomfortable part

To reach about eight, three new (tool, surface) pairs are needed beyond `feature_flag`. The
candidates the world supports:

| candidate mechanism | tool | surface | what has to be established |
|---|---|---|---|
| **`feature_flag`** | flagd JSON, hot-reloaded | a flag | **nothing — proven end to end** on 2026-09-22: `productCatalogFailure` gave 200 → 500 → 200 with a control product at 200 throughout |
| **data corruption** | `docker exec` into the store | the data | does corrupting `valkey-cart` page at all, and is the page distinct from `bad_deploy`'s? ADR-0029's unresolved candidate, needing the world time it always needed |
| **process freeze** | `docker pause` | process scheduling | does a paused container page as no-traffic, latency, or errors upstream — and is that distinct from `dependency_latency`? |
| **network partition** | `docker network disconnect` | network attachment | §5 says a partition's *fix* collides; the open question is whether its *page* does |
| ~~packet loss~~ | pumba sidecar | `tc netem` loss | **not a new mechanism.** Same tool, same surface as delay — `ResourceExhaustionFault`'s memory-or-CPU precedent applies directly |

**The uncomfortable part: none of those three depends on v2.** `docker exec`, `docker pause` and
`docker network disconnect` were all available on v1.2.1. ADR-0029 never assessed them as
mechanisms because it was asking the fix question, under which all three collide with something.

**So the world move did not supply the route to eight classes.** It supplied the catalog — fifteen
flags across twenty-odd services is the 30+ scenarios with genuine variety in alert shape, and that
is T7.1's stated statistical rationale, which v2 delivers in full. **The taxonomy half comes from
injector mechanisms that were always there and were never assessed under the criterion that now
governs.**

This is not an argument against the move. ADR-0042's case stands on the count, the statistical
rationale, the native-arm64 finding, and the sunk holdout cost — none of which this touches. It is
an argument against the sentence *"the mechanism criterion makes eight reachable"* being read as
*"v2 makes eight reachable"*.

## 5. What this says to do, in order

1. **Record the granularity decision.** One `FeatureFlagFault`, one class, on
   `ResourceExhaustionFault`'s precedent. ADR-0043 gets an addendum rather than a rewrite; the
   decision it made is unchanged and the "nearly free" characterisation is withdrawn.
2. **Build `feature_flag` first.** It is the only candidate with nothing left to establish, it is
   the one the world move actually bought, and it unblocks the 30+ catalog on its own.
3. **Then establish the other three, each with world time and a pre-registered distinctness
   test** against the class it is most likely to be confused with. Any that fails is merged and the
   merge is recorded — ADR-0043 says so already.
4. **Do not author the catalog against a class that has not passed §3 of this list.** The cost of
   discovering a merge after thirty scenarios are recorded is the re-record this task exists to do
   once.

**The honest forecast is five classes guaranteed and eight contingent on three measurements**, each
of which can fail. That is a weaker claim than the plan's "~8" and a stronger one than ADR-0029's
"four, and no fifth is possible in this world".
