# T7.40 — is the capture set's exclusion of container state a hole?

Decision task. No world time, no money, and **no code, because the decision is not to build.**

## 1. Chosen, or never considered? — never considered, and the hole is narrower than T7.39 said

**Never considered.** ADR-0009 fixes the bundle shape — `manifest.json`, `incident.md`,
`queries.md`, `metrics/*.json`, `logs/*.txt` — and **nowhere weighs and rejects container state**.
`CAPTURE_SET`'s docstring argues only about `runtime.json` and about why set 2 was not a
`bundle_schema_version` bump. No document declines container capture; it simply never comes up.

**But T7.39 overstated the absence, and this corrects it.** ADR-0009 itself reads restart evidence
out of captured logs — *"cartservice crash-loops on `EnsureRedisConnected` while it comes back —
the captured logs show restarts 42 and 47 seconds apart."* Measured across the two recorded OOM
bundles:

| bundle | startup banners in logs | mentions of OOM / killed / sigkill |
|---|---:|---:|
| `ad-memory-squeeze` | **36** | **0** |
| `frauddetection-memory-squeeze` | **38** | **0** |

**Logs carry *that* a container restarted. They never carry *why*.** A SIGKILLed process logs
nothing on the way out. So the hole is not "restarts are invisible" — it is narrower and sharper:

> **The exit *reason* is absent, for every service, in every bundle.**

T7.39's phrasing ("restart count … absent from bundles") was loose. The count as a *field* is
absent; the *evidence* is present wherever a service logs at startup. `cart-bad-image-tag` is the
exception that misled — its container never started, so it produced no logs at all, and its
narrative's *"not visible from here"* is about that case rather than about flapping generally.

## 2. Scope — and the case against closing is stronger than the case for

**Which recorded items would have had a different evidence shape:**

| item | today | with container state |
|---|---|---|
| `ad-memory-squeeze` | 36 restart banners + 48 runtime series climbing → **infer OOM** | `OOMKilled: true` |
| `frauddetection-memory-squeeze` | 38 banners + runtime series → **infer OOM** | `OOMKilled: true` |
| `recommendation-memory-squeeze` | same shape | `OOMKilled: true` |
| `cart-bad-image-tag` | no container, no logs; answer via `change_history` | exit reason / never-created |
| `shipping-wrong-image` | starts, serves wrong protocol | unchanged |

**The case for closing.** Three `resource_exhaustion` items and one `bad_deploy` item currently
require an inference that a single captured field would answer outright. `cart-bad-image-tag`'s
narrative explicitly records wanting evidence it could not get. D3-shaped items become possible.

**The case against, which is stronger.** **The inference is the item.** What
`ad-memory-squeeze` tests is precisely the step from *"this container keeps restarting and its heap
is pinned at the ceiling"* to *"it is being OOM-killed"* — and the measurement above shows the
evidence is deliberately partial: 36 restarts and zero kill words. **A capture that prints
`OOMKilled: true` does not make that item harder or fairer; it deletes the question.** Three of
thirteen valid items would be weakened, which is a real cost against a hypothetical gain.

**And the gain is more hypothetical than it looks.** D3 — the candidate that exposed this — **did
not fail only on capture.** It also had no mechanism: `BadDeployFault` swaps an image, a flap needs
an image whose entrypoint exits, and all seventeen demo images present locally are servers.
**Closing this hole would not have made D3 buildable.**

## 3. Cost, stated precisely

**A `CAPTURE_SET` bump moves `CAPABILITY_VERSION`.** `capability_inputs()` is
`{capture_set, tool_behaviour_revision, tools}`, so `cap:9c416e0a` changes by construction.

| what it invalidates | scale |
|---|---|
| narrative capability stamps | **15 narratives** carry `capability: cap:…`; the guard fires on every one, so all 15 need **re-review**, not merely a stamp edit |
| recorded bundles | **13 valid bundles** would hold set 2 while the catalog claims set 3. Container state is point-in-time and **cannot be backfilled** — the containers are gone |
| precedent | **T7.28's eleven-bundle re-record is the shape**, now 13 |
| world time | ~25–30 min per recording (T7.34's measured figure) → **~6 hours**, plus kafka recycles, inter-scenario settles, and the 31–35% historical failure rate |

**The holdout ledger is the part that does not recover.** The holdout has been entered **three
times** (`HOLDOUT-2026-08-26`, `-entry2`, `-entry3`, each with a freeze). Those entries were scored
under the capability that existed then. **Holdout entries cannot be re-run** — T4.15's addendum
records that the set should not be entered a fourth time before it is re-authored or extended, and
the whole point of a holdout is that it is spent once.

> **So a capability bump permanently strands every holdout figure this project has.** They would
> describe a capability the system no longer has, with no mechanism to refresh them, and the next
> holdout entry would be the first under the new capability with nothing to compare it against.
> **That is not a cost that is paid and recovered; it is a cost that stays paid.**

## 4. Decision: record the boundary as deliberate

**The capture set excludes container state on purpose. It is not a gap and should stop being
treated as one.**

The reasoning is primarily about the benchmark and only secondarily about cost. **The exclusion is
what makes `resource_exhaustion` require inference**, and the measurement in §1 shows the evidence
is partial in exactly the way that creates the question: restarts visible, cause not. Closing it
would trade three working items for candidates that are blocked on mechanism anyway, and would
strand three unrepeatable holdout entries to do it.

**This is a decision, not a deferral.** It is deliberately *not* queued as digest-locked — the
established pattern for changes whose only obstacle is cost. Cost is not the objection here.

### What this does to the allocation, recorded rather than implied

**It does not cap the catalog at 13.** That framing is too broad, and the slots differ:

| free slot | under this decision |
|---|---|
| `dependency_latency-4` | **buildable** — T7.34's D2, no capture dependency. Filler, and its only argument is the dev floor |
| `bad_config-5`, `bad_config-6` (holdout) | **buildable** — D5's shape needs no container state |
| `bad_deploy-4`, `bad_deploy-5` | **no non-filler candidate.** The distinct fourth shape needs the exit reason; a third image swap does not |
| `bad_deploy-6` (holdout) | same |
| `resource_exhaustion-4` | **T7.34's D6 inherits the same defect — see below** |

**A downstream finding this surfaces.** T7.34's D6 is `payment-memory-squeeze`, and
**`paymentservice` exports zero runtime-family series** (measured at T7.36 and again here). An OOM
there would produce restart banners with **no memory evidence and no exit reason** — precisely the
shape that made D3 unanswerable. **D6 as specified is disqualified for the same reason D3 was**, and
needs a target that exports runtime families or it is not an answerable item. That is a correction to
the audit's candidate list, found without world time.

**So `bad_deploy` dev stands at 2 against a floor of 3, and `resource_exhaustion` dev at 2, with the
allocation for both unfillable by any candidate now on the table.** SPLIT.md's allocation is not
edited to accommodate this — it is not editable to accommodate a scenario, and it is not editable to
accommodate the absence of one either. The fact is recorded beside the empty slots instead.

## 5. What would reverse this

1. **A capture that adds the exit reason without answering the question** — for instance recording
   only *that* a container was replaced and when, and not *why* it died. That would help
   `cart-bad-image-tag`'s never-started case without handing `OOMKilled` to the three memory items.
   **This is the reversal most likely to be right**, and it is a different design rather than this
   one at lower cost.
2. **A world move that forces a re-record anyway.** The marginal cost of adding a capture during a
   re-record already being paid is small — but the holdout stranding is not marginal and would still
   have to be argued separately.
3. **Evidence that the inference is not actually being tested** — if a scored run showed agents
   reaching "OOM" from something other than the restart-plus-memory step, the thing this boundary
   protects would not exist and the argument against closing would fall.
4. **A candidate that needs container state, has a working mechanism, and is not made trivial by the
   capture.** D3 was none of these three.

## 6. Does T7.34's audit have a second wrong premise? — no, and the error class is identifiable

T7.39 found the audit asserting a property of the injector by reading a document that asserted it
first. Every load-bearing claim re-checked **against source**:

| claim | rests on | verdict |
|---|---|---|
| "the injector documents three `bad_deploy` shapes, **and says so in as many words**" | a claim about **source** | **WRONG** — two, corrected at T7.39 |
| "`bad_config` has at least three shapes" | diagnosis paths, borne out by three recorded scenarios | **holds** — `BadConfigFault` is one *mechanism* (`"one environment variable set wrong"`), and the claim was never about mechanisms |
| "`dependency_latency` has one mechanism" | a claim about source | **confirmed against source** — one class, netem, parameterised |
| "CPU is retired (ADR-0013), leaving memory" | scenario usability, backed by measurement | **holds** — but note the code still implements CPU quota (`ResourceExhaustionFault`: *"memory ceiling, or CPU quota"*). "Retired" means *no usable scenario*, proven by `currency-cpu-throttle`'s `INVALID.md`, **not** removed from the injector |
| slot derivation reproduces all assignments | computation | **verified at T7.35** |
| "no timeout env var in the demo" | direct read of `world/docker-compose.yml` | **held** — checked against source when written |
| deficit counts | computed from files | **held** |

**One wrong premise, not two.** And the error class is precise: **of all the audit's claims, exactly
one asserted what the code says, and that one was wrong.** The others are claims about diagnosis
paths, about scenario usability backed by measurement, or about computation — and none of them is
the kind that can be falsified by opening a source file, which is why none of them was.

**The rule this yields:** a sentence claiming what the code does is checkable against the code, and
must be, at the moment it is written. A sentence about what a *scenario* does is checkable against a
recording. The two were mixed in one paragraph of SPLIT.md, and the mixed paragraph is where the
error lived.
