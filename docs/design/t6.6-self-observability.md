# T6.6 — the agent's trace beside the outage it is investigating

**$0.00 for the whole task.** Nothing here calls a model; every span and every metric is a
side-effect of work the pipeline already does.

The plan's row: *"a span per agent step, tool call and model call, exported to the same
Tempo/Grafana as the demo app; structured JSON logs; Prometheus metrics for queue depth,
investigation latency and eval scores; a trajectory view in the UI."* The trajectory view exists
(T5.1). Nothing else does — no SDK, no span, no `/metrics`, no formatter — and the plan's own
gaps column had it at ~15%, which was right.

---

## 1. What is already there, and it is more than nothing

**The trajectory store is a trace in everything but export.** `agents/trajectory.py` writes every
step — role, kind, wall-clock instant, tokens in and out, the tool-call envelope by digest, the
retrieval with its exclusions — to five Postgres tables. That is what T4.3's metric panel and the
eval harness read from, and it is what T5.1 renders.

**Two things it does not measure.** `latency_ms` is set in exactly one place —
`Investigation._run_dispatch`, around the tool query — so **every COMPLETION step records
`latency_ms = 0`**: the trajectory has never known how long a model call took. And it is written
when a step *finishes*, so it cannot show work in progress.

**The two counters the plan names as the point of the metrics already exist**:
`OrchestratorStore.active_count()` and `len(store.queued())` are what T2.2's admission reads to
decide whether an incident waits. Nothing exports them. The plan says queue depth *"is the metric
that makes T2.2's concurrency cap observable, which is why it's named rather than left to 'misc
metrics'"* — the number is computed on every event and thrown away.

**Logging is unconfigured.** Eleven `getLogger` calls, no formatter, no `dictConfig`, no handler
of this repository's own; output depends on whatever uvicorn or the root logger does. Eighty-seven
`print` calls, almost all in CLIs where a person is reading.

## 2. The decision: spans at the seams, joined to the trajectory by id

Three shapes were possible, and the choice is the repository's recurring question — two records
of one thing — in a new place.

**Derive spans from the trajectory.** One emission point, no drift. Declined: a step is recorded
when its work finishes, so the span arrives late and the live beat is lost; and there is no
model-call latency to derive, because the trajectory never had it.

**Spans only; retire the trajectory's timing.** Cleanest separation. Declined: the harness reads
latency and tokens off the trajectory today, so this changes every manifest and every consumer,
for a task whose value is a demo beat and an operator's dashboard.

**Spans at the seams, joined by id — chosen.** Live spans at the four chokepoints the work passes
through, and every `TrajectoryStep` written inside one carries its `trace_id` and `span_id`. Two
records, joinable rather than parallel: the span is what Grafana shows while the agent thinks,
the trajectory is what the harness scores, and either leads to the other. The duplication is
deliberate and bounded: timing and attributes on the span, content and envelopes on the step.

## 3. The four seams

Found by reading rather than assumed. Every model call, every tool call and every backend read in
the agent runtime passes through exactly one function each:

| span | chokepoint | attributes |
|---|---|---|
| `investigation` | `Investigation.run` | `incident_id`, `trajectory_id`, `model`, `outcome`, `tokens_in`, `tokens_out`, `usd` |
| `model.call` | `roles.ask` | `role`, `model`, `attempts`, `tokens_in`, `tokens_out`, `stop_reason` |
| `tool.call` | `Investigation._run_dispatch` | `tool`, `service`, `window_seconds`, `envelope_bytes` |
| `backend.get` | `telemetry.get_json` | `backend`, `path`, `status`, `bytes` |

**`ask` is a logical call.** One `ask` may make two `complete` calls — the contract is checked and
the model is re-asked on a rejection. The span wraps the logical call and `attempts` records how
many wire calls it took. A span per wire call would need `Resilient._try`, which exists only when
a `Resilient` wrapper is installed, and would give two spans a reader has to add up.

**Baselines bypass `_run_dispatch`** (`evalharness.baselines.signals_from_tools`). They are
controls, and a trace of a control is not something anyone has asked for; if they are ever
instrumented it is through the same `span()` call and not a second mechanism.

## 4. No-op by default, and what that costs

`make check` runs in under three seconds and imports no SDK. The `agents` and `embeddings` extras
exist for that reason and `observability` follows them: the packages are optional, `configure()`
imports them lazily, and `span()` yields a handle with empty ids when nothing is configured.
**Call sites never branch.** A `TrajectoryStep` carries `trace_id = ""` on an unconfigured
process, which reads as *not traced* rather than as a fake id.

The standard `OTEL_EXPORTER_OTLP_ENDPOINT` variable is the switch — not a `FAULTLINE_` one — so
the compose files set the same thing the world's collector and every other client already read.
gRPC, because the world's Tempo (`compose/tempo.yaml`) listens on 4317 and has no HTTP receiver.

**The cost is silence.** A process nobody configured emits nothing and does not complain.
`configure()` returns whether tracing is live and each entry point prints which, so an operator
expecting traces has one line to read.

## 5. What lands, in order

1. **This note, the extra, `observability/tracing.py`** — the no-op contract and its tests. *(piece 1)*
2. **The four spans**, `trace_id`/`span_id` on `TrajectoryStep`, a migration for the columns.
3. **`/metrics`** on the API: `faultline_incidents_queued`, `faultline_investigations_active`
   (both read from the store on scrape — a gauge that mirrors state rather than a counter that
   drifts from it), `faultline_investigation_seconds` histogram, tokens and USD counters.
4. **JSON logs** with the trace id injected, on the three daemons — API, orchestrator,
   investigator. CLIs keep their prints; a person is reading those.
5. **One dashboard**, provisioned beside `compose/dashboards/shop-health.json`, with a Tempo
   panel — and a Prometheus scrape job for the API's `/metrics`.
6. **Durations in the trajectory UI**, which `TimelineEntry.as_dict` currently drops, and the
   compose wiring for `OTEL_EXPORTER_OTLP_ENDPOINT`.

## 6. What this does not claim

**No number.** This task is instrumentation; it registers no figure and needs no
pre-registration. The eval-score gauge the plan names is a convenience for a dashboard — the
eval database is the record, and a Prometheus gauge that holds the last score is not a
measurement of anything.

**Not the executor.** The plan's ordering note said *"T6.6 alongside [T6.2/T6.3], because
instrumenting the executor from its first commit is cheaper than retrofitting it."* That
ordering did not happen; this is the retrofit, and the executor's spans are a follow-up once the
four above are exporting.

## 7. What landed differently — 2026-09-18, after the six pieces

Written after, kept apart from §5 rather than folded into it, so the list above stays what was
planned and this stays what happened.

**§5.5's scrape job did not land.** `compose/prometheus/prometheus-config.yaml` is inside
`observability_digest`, and the argument ADR-0030 made for a dashboard — nothing measurable
moves — does not carry: `evalharness.run` counts scrapes with `max(count_over_time(up[…]))`
across that Prometheus' targets, so the target set is a measurement input. Queued as **Q73**
with a trigger; the dashboard's Prometheus panels are empty until then and a panel says so.

**§5.2 found `configure()` had no caller** (piece 2b), **§5.4 found nothing had ever configured
logging** (the orchestrator's `investigating` line had never been printed), and **§5.3's first
scrape found four trajectory rows reading `running` in a process where nothing was** (Q72).
Instrumentation found three defects on the way to being switched on, which is roughly the
argument for it.

**Two pieces §5 did not list.** The image and `make install` had to gain `--extra observability`
— the published image was handed the endpoint and had no SDK to honour it — and the eval-score
gauge in §6 is now declined rather than deferred, for §6's reason.

**Not yet shown on the VM.** Every live proof in `evidence/` is from a development machine.
The first image built after piece 6 is the first that can trace and serve `/metrics` there;
deploying it is the remaining step, and costs nothing.

**§4's table has a fifth row now.** `incident`, in `agents.runner.run_investigation`, around
triage and the investigation both, carrying the incident id, the disposition, the states walked
and any error. It exists because the first traced run made two traces: triage's `model.call`
ran before `investigation` opened and had no parent (first-trace note, addendum 2). The four
seams stand; this is the seam above them, and it is where a run triage declines leaves its
trace.

**§7's first paragraph is superseded, the same day.** Q73 closed - not with the scrape job in the
world's Prometheus, but with a Prometheus of the platform's own (`prometheus-self`) and a
datasource for it pushed beside the dashboards. Writing the pre-registration §7 proposed found
that `CURRENT_OBSERVABILITY` pins the digest the scrape job would have moved, so the four lines
would have cost every recorded figure its stamp; and that the world's Prometheus is the one the
agent queries, so the platform's counters had no business there at all. ADR-0030 addendum 3 has
the argument. The dashboard's Prometheus panels read `faultline-self-metrics`, and §5.5's *"a
Prometheus scrape job for the API's `/metrics`"* is met, by a Prometheus §5 did not have in mind.

**And a sixth row: `retrieval`.** In `Investigation._search`, around both corpus searches an
investigation makes (the planner's and the synthesizer's), carrying role, `k`, how many origins
were excluded and how many chunks came back; the RETRIEVAL step carries its duration and its
span's ids. Found by reading the plan row's *"a span per agent step"* against the trajectory: the
pgvector search was the one step that shared the root's ids and recorded no duration.

**§7's last paragraph is no longer true.** `a1a6c412` runs on the VM since 2026-09-18 ~10:40 UTC
with every surface live (evidence: *the deployment watches itself*). What the rollout found -
the platform holding a lock against its own migration through never-ended read transactions - is
`faultline.pgread`, and it is not in that image; the next one carries it.

**§6's second paragraph is done, and a seventh row with it.** `action.execute`, in
`Executor.execute`, around the whole of an execution or a refusal, carrying the audit row's
structural fields - incident, action, target, outcome, token *id*, audit id, exit code - and never
the token, the refusal reason, the command or its output. `faultline-execute` configures logs and
tracing like the other three daemons and gets the collector's endpoint in `deploy/compose.yml`
(Q74). Nothing propagates trace context across the HTTP hop from the approval surface, so the
action's trace is its own and joins the investigation's by incident id; that hop is not
instrumented and this note does not say it is. The same change closed Q72 - `faultline-sweep`
now closes a killed run's trajectory row as `orphaned` before it starts, so the `running` line
§5.3's first scrape found four of has a reconciler - and Q75, so the image that carries all of
this is the first the workflow could not have published red.
