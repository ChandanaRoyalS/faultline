# T7.2 step 3 — SREGym read at source, and the finding is not the one that was scoped

**Nothing was run and nothing was spent.** SREGym cloned and read at
**`46c853db3a79332ea1c0ada076d888cec7a02f7e`** (2026-09-18), with the `SREGym-applications`
submodule at `887d093e`. [The scoping note](t7.2-scoping.md)'s step 3 asked one question — *do
SREGym's spans carry a status tag, which `spantree.degrading_hop`'s deepest-error rule reads?* —
and called it *"a read rather than a run."*

**That framing was wrong, and three findings turned up that the step did not go looking for.** The
most important one is about what a SREGym score would mean, not about how to get one.

**ADR-0004's pin has moved.** T0.5 read the harness at `fe4f8c7c` (2026-08-31); this is fifty
commits later. The ADR says *"Revisit if: SREGym's agent-container interface changes materially"* —
nothing below contradicts its four corrections, but they were checked against a different tree and
that is stated rather than assumed.

---

## 1. A substantial part of the benchmark runs Faultline's own world

`SREGym-applications/.gitmodules` resolves **`astronomy-shop` to
`github.com/xlab-uiuc/opentelemetry-helm-charts`**, and `docker/audit_images.py` deploys it from
`astronomy-shop/charts/opentelemetry-demo`. **Astronomy Shop is the OpenTelemetry Demo** — the
same application Faultline's world is (ADR-0026 pins it at v1.2.1), deployed by Helm onto
Kubernetes instead of by compose.

**This is the point of the task, and it lands on it.** ADR-0004 opens on the criticism T7.2 exists
to answer: *"a system authoring its own world, its own faults and its own grader is
self-referential."* SREGym replaces the faults and the grader. **On this subset it does not
replace the world**, and the world is where Faultline's prompts, its service catalog, its
retrieval corpus and its ten dev scenarios were all fitted.

**The overlap is visible in the problem names.** `incorrect_image` on `product-catalog`,
`missing_env_variable_astronomy_shop` (`CART_ADDR` on `frontend`),
`env_variable_shadowing_astronomy_shop` (`FRONTEND_HOST`), `incorrect_port_assignment`
(`PRODUCT_CATALOG_ADDR` on `checkout`) — against Faultline's own `cart-bad-image-tag`,
`cart-redis-misconfig`, `shipping-quote-misconfig`, `product-catalog-flag-failure`. Same services,
same failure vocabulary.

**The count, and what kind of number it is.** `Problem List.md` holds **116 problems**; **24 name
astronomy-shop in their own row text**, 25 hotel-reservation, 16 social-network, and **49 name no
application in the row at all**, because the attribution lives in the problem definition rather
than the table. **So 24 is a floor and not the share**, and this note does not report a share it
has not computed. The exact per-problem attribution is needed anyway to design the run, and it is
owed there.

**What follows for the report, and it is not *do not run it*.** The other applications —
`hotelReservation` and `socialNetwork`, both DeathStarBench — are genuinely foreign worlds and
genuinely answer the criticism. The consequence is narrower and firm: **a single pooled "SREGym
diagnosis pass rate" would mix a subset where Faultline has a home-field advantage with subsets
where it has none**, and this repository does not publish figures that mislead in its own favour.
**The score is reported per application or it is not reported.** That belongs in the
pre-registration, written before the runs, not discovered in the results.

## 2. The agent is handed no topology, and Faultline's depends on having one

`/get_app` returns exactly four fields (`sregym/conductor/conductor_api.py:243`):

```python
{"app_name": ..., "namespace": ..., "namespaces": [...], "descriptions": str(...)}
```

**A name, a namespace and a prose description.** No service list, no dependency graph, no topology.

Faultline's investigation is built on having one: `ServiceCatalog.from_snapshot()` reads its own
world's catalog, triage computes a **blast radius** over the dependency graph, and
`visibility.target_visibility` reports `NOT_IN_GRAPH` for services the graph does not hold — the
machinery Q27 and Q28 exist inside. **On a foreign application none of that has a source**, and
the catalog Faultline would otherwise carry is a catalog of the wrong system.

**There is a candidate and it is already mounted.** The Jaeger MCP server exposes
`get_dependency_graph` (`/api/dependencies`), alongside `get_services` and `get_operations`. So
topology is derivable from the traces the harness already serves. **But deriving it is a component
Faultline does not have** — its graph comes from a captured snapshot, not from a live query — and
building one is not in any estimate written so far.

**This is a larger unpriced item than the Jaeger mapping**, and it was not in the scoping note at
all.

## 3. Traces are raw Jaeger, and stringified

`mcp_server/jaeger_server.py`'s `get_traces(service, last_n_minutes)` ends:

```python
traces = str(response.json()["data"])
```

**Two concrete consequences.** The payload is Jaeger's `/api/traces` response — the same API
Faultline read until T6.1 replaced it with Tempo, so the reader recoverable at `73477ce^` parses
the right shape, exactly as the scoping note said. And it arrives as **`str()` of a parsed
object**: a Python repr with single quotes and `True`/`False`/`None`, **not JSON**. A driver
consuming this tool needs `ast.literal_eval`, and `json.loads` will fail on every call. The
server also hard-codes `limit: 20` and an in-cluster Jaeger address, so it runs inside the cluster
and the depth of a trace search is not the driver's to choose.

## 4. The status-tag question, and why a read cannot answer it

**SREGym normalises nothing.** It passes Jaeger's payload through untouched — no file in the
harness mentions `otel.status_code`, `refType` or `CHILD_OF` — so **the harness makes no guarantee
about span structure either way**, and what a span carries is a property of the application's
instrumentation, not of the benchmark.

That splits the answer and leaves half of it open:

- **Astronomy Shop is the OpenTelemetry Demo**, natively OTLP-instrumented. Its spans carry OTel
  status, and Faultline has been reading this application's traces since T2.6. For this subset the
  question is effectively settled.
- **hotelReservation and socialNetwork are DeathStarBench**, instrumented against OpenTracing and
  Jaeger directly, in C++, Go and Python. Their tag vocabulary is a different one and **this read
  does not establish what it contains.**

**So step 3's own framing was wrong**: *a read rather than a run* is true for one application
because Faultline already knows it, and false for the other two, where the answer needs a trace
off a running problem. The scoping note said the status tag *"decides whether the traces specialist
SREGym grades is the one `ABLATIONS.md` measured"* — that remains exactly right, and it is now a
question with two answers that have to be got separately.

## 5. What this changes

**It does not change the verdict.** ADR-0004's **Adapt** stands; nothing here blocks a run.

**It adds a claim-shaping constraint** (§1), **an unpriced component** (§2), **a parsing detail
that would otherwise have been discovered at runtime** (§3), and **splits a question that was
booked as closed by a read** (§4).

**And it sharpens what T7.2 can say.** ADR-0004's addendum already limits the claim to *a diagnosis
pass rate, never a combined score*, and requires the absent change-history modality to travel
beside the number. This adds a third clause: **the score is reported per application**, because a
pooled figure over a suite that partly runs Faultline's own world is not the external measurement
the task exists to produce.

## 6. The order, revised

1. ~~Check SREGym's spans for a status tag — a read rather than a run.~~ **Answered for Astronomy
   Shop, open for the two DeathStarBench applications**, and it needs a live trace rather than
   a read.
2. **Attribute all 116 problems to their applications**, from the problem definitions rather than
   the table's row text. Free, and both the stratified report and any subset choice depend on it.
3. **Decide where the topology comes from** on a foreign application — Jaeger's dependency graph is
   the candidate and is not a component this repository has. **Price it before the run**, which is
   the same instruction T0.5 gave about the tool implementations and which this note exists because
   nobody followed for the catalog.
4. **Then** pre-register, with the per-application split, the modality gap and the diagnosis-only
   clause all written in advance.

## Addendum — the attribution computed, and the overlap is narrower and stranger than §1 said

**Same day, \$0, still nothing run.** §1 reported *24 of 116* as a floor read off a table and said
the real attribution was owed. It is computed below, and it changes §1 in **both** directions.

### The number, and it was not derivable by reading

**42 of 125 registered problems — 33.6% — run the Astronomy Shop.** The harness names the
application itself: its `app_name` is literally **"OpenTelemetry Demo Astronomy Shop"**. Beside it,
Hotel Reservation 50, Social Network 21 (+1 that failed to instantiate), Blueprint Hotel
Reservation 3, Train Ticket 2, FleetCast 6. 118 of 125 instantiated; the seven failures are six
FleetCast problems whose submodule is unfetched and one network timeout.

**`Problem List.md` has 116 rows and the registry has 125 entries**, so the table is not the
population either.

**Step 4 was published as *free*, and that was wrong.** Three separate static passes over the
source returned **29, 42 and 39** for this one figure — the first two were unstable because class
names were being substring-matched inside a dumped AST, so which class matched depended on dict
ordering. **Three different answers is a broken method, not a converging one**, and none of them
should have been published. The number above comes from instantiating every registered problem and
asking it which app it holds, which needed a Python 3.12 venv, an editable install, two submodule
fetches and a stub `KUBECONFIG` before a single problem would construct. Cheap, and **not free, and
not a read**.

### The overlap is the same application at a different major version

**SREGym deploys `opentelemetry-demo` chart 0.40.4, `appVersion` 2.2.0. Faultline pins v1.2.1**
(ADR-0026). That is a major version apart, and **v2 renamed the services**:

| Faultline, demo v1.2.1 | SREGym, demo v2.2.0 |
|---|---|
| `cartservice` | `cart` |
| `adservice` | `ad` |
| `frauddetectionservice` | `fraud-detection` |
| `checkoutservice` | `checkout` |
| `accountingservice` | `accounting` |
| `frontendproxy` | `frontend-proxy` |
| `featureflagservice` | `flagd` |
| `redis-cart` | `valkey-cart` |
| **`frontend`** | **`frontend`** |

**`frontend` is the only service whose name survives.** And two of Faultline's own dev scenarios
name components that no longer exist under those names: `cart-redis-misconfig` is about
`redis-cart`, which is `valkey-cart` in v2 — SREGym has `valkey_auth_disruption` and
`valkey_memory_disruption` — and `product-catalog-flag-failure` is about `featureflagservice`,
which is `flagd`. v2 also adds components v1 had none of: `image-provider`, `product-reviews`,
`llm`.

### What that does to §1, in both directions

**The contamination concern is weaker than §1 stated.** Faultline's prompts and retrieval were
fitted against a topology whose service names are almost entirely absent from the world SREGym
deploys. Whatever advantage the shared lineage confers, it is **not** the agent recognising names
it was tuned on.

**A worse practical problem replaces it, and it is a scoring hazard.** The service names are
*near misses* rather than unrelated: an agent carrying a v1 catalog into a v2 world reasons about
`cartservice` while the graded answer is `cart`. **On the benchmark's culprit-service axis that
scores as a miss for a naming difference rather than a reasoning failure** — and culprit service is
the axis [`RESULTS.md`](../RESULTS.md) leads with. Whether the harness's judge normalises service
names is **not established here** and has to be, before any run, because it decides whether a
diagnosis figure means what it appears to mean.

**§1's conclusion stands, on a different argument.** The score is still reported per application —
not because Astronomy Shop is a home field, but because it is a **third of the suite** and is the
one application whose relationship to Faultline's own world is neither *foreign* nor *familiar* but
*a version apart*, which is its own thing and has to be described rather than averaged away.

### What this adds to the order

**Before the run**: establish whether SREGym's judge normalises service names, and decide what
catalog the agent carries into a v2 world. `ServiceCatalog.from_snapshot()` holds v1's, and
handing it to an agent investigating v2 is handing it a map of a different city with the same
street plan.

## Second addendum — the grader is an LLM judge, and that reframes the whole task

**Same day, \$0, still nothing run.** The addendum above ended by naming one blocking question:
*does SREGym's judge normalise service names?* It is answered here, and the answer arrives with
two things that matter more.

### Diagnosis is not graded by an oracle

`DiagnosisOracle.compare_truth` is exact string equality — and **it is not what grades diagnosis.**
Across the problem definitions, **100 of the 101 that set a diagnosis oracle set
`LLMAsAJudgeOracle`**, and one sets `None`.

The judge scores a submission against `rca_checklists.yaml` v3.0: **three dimensions, nine
questions, each answered yes/no by a model**, each dimension scored as its yes-fraction, combined
as a weighted composite (**D1 0.33, D2 0.33, D3 0.34**) and passed at **≥ 0.70**.

- **D1 Fault Localization** — does the diagnosis name the same component as the ground truth, not
  a downstream victim, not a healthy one.
- **D2 Fault Characterization** — the same injected mechanism, **and *"concrete mutated details
  from the injection logic (e.g., env var/key, wrong value, port, selector, image tag, resource
  limit)"***.
- **D3 Scope Precision** — no over-attribution, no under-attribution, impact consistent.

**So the naming answer is: no mechanical normalisation, and no mechanical failure either.**
`cartservice` against a ground truth of `cart` is one model's judgement on D1-Q1, which is softer
than the exact-match hazard the addendum above feared and **less predictable than either**. The
hazard does not disappear; it stops being deterministic, which is worse for planning and better
for the score.

### The independent yardstick is the same kind of instrument this repository already distrusts

**This is the finding that reframes the task.** ADR-0004 buys T7.2 to answer *"a system authoring
its own world, its own faults and its own grader is self-referential."* SREGym genuinely replaces
the world and the faults. **What it replaces the grader with is another LLM judge** — someone
else's, against someone else's checklist, but the same class of instrument.

This repository has been careful about exactly that instrument in its own work: Q3 exists because
the benchmark assesses warrant nowhere, T7.52 measured **6 of 56 answered runs where the label and
the judge disagree, in both directions**, and T6.4's whole corpus argument turns on what a judge
can and cannot see. **None of that scepticism stops applying because the judge belongs to someone
else.**

**What T7.2 may therefore claim gets a fourth clause**, beside diagnosis-only, the absent
change-history modality and the per-application split: **the figure is a pass rate under SREGym's
LLM judge at threshold 0.70**, and it is described that way rather than as *diagnosis accuracy*.
That is still worth having — an external judge, an external checklist and an external world are
three independent things Faultline does not control — but it is a different sentence from *graded
objectively*, and the difference belongs in the writeup rather than in a footnote.

### An adapter constraint that would have cost a whole run to discover

**The submission is free text.** `submit(ans: str, stage: str | None)` posts `{"solution": ans}`,
and the judge reads that string. **Faultline does not produce a string; it produces a `Verdict`** —
`root_cause` (one sentence), `service`, `fault_class`, `remediation_class`, `evidence`,
`reasoning`, `open_questions`, `alternatives`.

**Which field or fields the driver renders decides the score, and the obvious choice is the wrong
one.** Submitting `root_cause` alone — one sentence naming a service and a mechanism — can satisfy
D1 and part of D2, and **cannot** satisfy **D2-Q2's *"concrete mutated details … env var/key,
wrong value, port, image tag"*** or **D3-Q2's *"all components listed in the ground-truth"***. With
D2 and D3 weighted 0.67 between them against a 0.70 threshold, a driver that submits the one-line
root cause is close to arithmetically incapable of passing.

**So the adapter must render the whole verdict** — reasoning, evidence and alternatives included —
into the submitted prose, and **how it renders it is a free parameter that moves the headline
number.** That has to be fixed in the pre-registration and reported, exactly as a prompt would be,
because tuning it after seeing a score is tuning the benchmark to its last result.

### The order, again

**Before the run, now**: fix and freeze the verdict-to-prose rendering, and state it in the
pre-registration. That is a larger design decision than the Jaeger mapping and it was in nobody's
estimate — including both earlier drafts of this note, which is now the third time a T7.2 step
turned out to be bigger than the sentence that scoped it.
