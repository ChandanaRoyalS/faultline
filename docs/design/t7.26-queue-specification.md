## Item 1 — otel-col `memory_limiter`

**File:** `world/src/otelcollector/otelcol-config-extras.yml` — **not** `otelcol-config.yml`.

That file exists precisely as the merge point for local collector settings (*"extra settings to be
merged into OpenTelemetry Collector configuration"*), is loaded by a second `--config` flag in
`world/docker-compose.yml:587`, and is currently two comment lines. Editing it leaves the pinned
clone's own config untouched, which is what ADR-0026 asks for.

**Before** (whole file):
```yaml
# extra settings to be merged into OpenTelemetry Collector configuration
# do not delete this file
```

**After:**
```yaml
# extra settings to be merged into OpenTelemetry Collector configuration
# do not delete this file
processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 450
    spike_limit_mib: 100

service:
  pipelines:
    traces:
      processors: [memory_limiter, spanmetrics, batch]
    metrics:
      processors: [memory_limiter, batch]
```

`limit_mib: 450` against the 600M container limit, `spike_limit_mib: 100` giving a soft limit of
350 MiB. **`memory_limiter` must be first in each pipeline** — it can only refuse data it sees
before other processors buffer it.

**What the evidence says.** Measured now: **144 MiB of 600 MiB, 24%**, after ~2 days of uptime. The
queue entry's own extrapolation was 123.3 MiB at rebuild and 291.7 MiB after a day *at the old
ceiling*, predicting "a week or two". At 144 MiB after two days the collector is growing far more
slowly than that estimate feared, so **the tripwire (540 MiB, the recorder's 90% gate) is not close**.

**What this buys, honestly:** it converts an eventual OOM into backpressure — the collector refuses
and drops rather than dying. **It does not stop growth**, and dropped telemetry under pressure means
gaps in captures, which is a different failure from a collector that died. It is a better failure,
not the absence of one.

**Verification:** `docker compose ... up -d --no-deps otelcol`, then
`docker logs otel-col | grep -i memory_limiter` shows the processor started, and
`docker stats --no-stream otel-col` still reports well under 450 MiB. A negative control matters
here: confirm captures are still complete for one rehearsal window afterwards, because a
mis-ordered pipeline silently drops.

## Item 2 — kafka retention: **the queued change is falsified. Do not execute it.**

The queue says *"the real fix is retention"*, reasoning that a 400m heap cap bounds heap and not
RSS, so bounding the log would bound the rest. **Measured today, that does not hold.**

| measurement | value |
|---|---|
| container | **1.827 GiB / 2 GiB — 91.4%** |
| cgroup `anon` (unreclaimable) | **1,912,799,232 — 1.78 GiB** |
| cgroup `file` (page cache, what retention touches) | 54,476,800 — **52 MB** |
| **entire log directory on disk** | **14 MB** (`orders-0`: 7.9 MB) |
| G1 heap | total 409,600K, used 206,722K — **the cap is working exactly as set** |
| Metaspace | used 53,837K, reserved 1,099,776K |

**Retention bounds log data. The log data is 14 MB.** A retention bound cannot reclaim 1.78 GiB
that is not log data and is not page cache. The heap cap T7.1 applied is doing its job; the growth
is in JVM *native* memory, which neither lever touches.

**What to do instead — and none of it is grounded enough to specify as a change yet.** The honest
next step is a measurement, not an edit: run the JVM's Native Memory Tracking
(`-XX:NativeMemoryTracking=summary`, then `jcmd 1 VM.native_memory summary`) and find which arena
holds the 1.4 GiB the heap does not. Candidates the numbers permit are metaspace, thread stacks,
GC structures and direct buffers; nothing here distinguishes them.

**This item is removed from the queue and replaced by a measurement task.** Executing the queued
change would have moved `compose_digest`, forced a re-record, and fixed nothing.

## Item 3 — redis-cart `maxmemory` and eviction policy

**File:** `compose/world-arm64.override.yml` — this repo's file, not the pinned clone. The base
definition at `world/docker-compose.yml:619-630` sets no `command`, so the override supplies one.

**Before** (no `redis-cart` entry in the override at all).

**After**, inserted in alphabetical position among the service keys:
```yaml
  # T7.19: `noeviction` with no `maxmemory` against a 20M ceiling, and no key carries a TTL
  # (`expires=0`), so cart state accumulates monotonically in cumulative traffic. Measured
  # 0.192 keys/s over a 27.6-hour window, ~55 hours to the ceiling at rest, and it trips the
  # recorder's 90% guard in 23-46 hours - naming a container no scenario touches.
  redis-cart:
    command: ["redis-server", "--maxmemory", "12mb", "--maxmemory-policy", "allkeys-lru"]
```

**The policy choice is real, and `allkeys-lru` is the only one that works here.** T7.19 measured
`expires=0` and it is still true today (`db0:keys=9284,expires=0`). **`volatile-lru` evicts only
among keys with a TTL. With no TTLs it has nothing to evict, so it degrades to `noeviction` and
writes fail with `OOM command not allowed`** — the same failure as today, arriving as cart errors
instead of a container kill. `allkeys-lru` evicts the least-recently-used cart regardless of TTL,
which is the correct behaviour for a cart cache and keeps the store bounded.

**`maxmemory 12mb` against the 20M container limit.** Redis's `maxmemory` governs `used_memory`,
which T7.19 measured at roughly a third of container RSS (3.93 MB used against 13.19 MiB reported)
because of allocator overhead and fragmentation — `mem_fragmentation_ratio` was 2.67. 12 MB of
`used_memory` therefore sits comfortably inside 20 MiB of container with room for the fragmentation
already measured, while being well above the 8.18 MiB it holds now.

**What the evidence says it will do:** bound the store. Redis evicting under `allkeys-lru` is
ordinary documented behaviour, not an inference. **What it changes about the world:** cart contents
become lossy under pressure, which they are not today. No recorded scenario reads old cart state,
but this is a behavioural change and belongs in the batch that re-records rather than slipped in.

**Verification:** `docker exec redis-cart redis-cli CONFIG GET maxmemory maxmemory-policy` returns
`12582912` and `allkeys-lru`; then confirm `INFO stats` shows `evicted_keys` rising once
`used_memory` approaches the bound, and that `docker stats redis-cart` stops climbing across a day.

## Item 4 — checkout recycle: a symptom treated on a schedule

**Say what this is.** T7.23 established what the checkout stall is **not** — not Kafka (the produce
span is 0.00s, the `<-Successes()` receive 0.001s mean, the error drain idle 747 minutes), not a
blocked goroutine (zero in `PlaceOrder` at a dump taken while it was live, against ~2.5 expected),
not a lock or flush after the last child span, not work before the first. What survives is a span
held open after a handler that finished in 20-25ms, with **the mechanism unidentified**.

**A periodic recycle does not fix that. It restarts the process before the unknown state
accumulates enough to matter.** That is treating a symptom on a schedule, and it should be written
into the world as that and nothing more.

**There is no clean compose primitive for "restart every N hours."** The three options, and why the
recommendation is the third:

1. **A sidecar on a timer** calling `docker restart checkout-service` — needs the docker socket
   mounted into the world, which puts a container with host control inside the system under test.
   Rejected: it is a larger change to the world's trust surface than the problem justifies.
2. **A `healthcheck` engineered to fail after N hours** — abuses a mechanism that means "is this
   service healthy" to mean "has it been up too long", and would make every health reading a lie.
   Rejected.
3. **Operational, outside the world: restart it before a recording session**, which is what
   T7.23's recorder refusal already prints. **Recommended, and it means this item leaves the
   digest-locked queue entirely** — it is not a world change and moves no digest.

**What would settle the mechanism properly**, and it is one experiment: T7.23 could not separate
"state inside checkoutservice" from "state in the frontend↔checkout connection", because a checkout
restart clears both. **Restart `frontend` instead, next time the stall is active.** If the excursion
clears, the state is in the caller or the connection; if it does not, it is in checkout. That is a
one-command experiment on a condition that recurs roughly daily, and it costs nothing.

## Recommendation: split the queue three ways, and cash almost none of it now

**Item 4 leaves the queue.** It is operational, not a world change, and the recorder already prints
the remedy. Nothing to cash.

**Item 2 leaves the queue and becomes a measurement task.** The change as written would move
`compose_digest`, force twelve re-records, and fix nothing — the logs are 14 MB against 1.78 GiB of
anon. Run Native Memory Tracking first.

**Item 1 can honestly land without a re-record, and it is the only one that can.** It moves
`observability_digest` and no bundle on `main` carries that field, so nothing is invalidated.
**But it should not land yet**: the collector is at 24% of its limit after two days and the tripwire
is 540 MiB, so there is no pressure, and landing it means the *next* bundle differs from
`shipping-quote-misconfig` in a digest for a change nobody needed. **Land it in the same sitting as
item 3**, where it costs nothing extra.

**Item 3 is the only one that requires the re-record, and it has a deadline.** `redis-cart` trips
the recorder's 90% guard in 23-46 hours from a flush and will keep doing so, naming a container no
scenario touches. Until then a flush is the stopgap and T7.19 records it as one.

**So: do not cash the queue now.** A batch of one is a bad trade against twelve re-records, a
reconciliation pass over every narrative, and every published figure going stale. **Wait for a
second `compose_digest` change to be genuinely needed** — the kafka native-memory finding is the
most likely source, once measured — and cash items 1 and 3 with it. If nothing else arrives before
`redis-cart` becomes a recurring obstruction, cash items 1 and 3 alone at that point and accept the
cost, because a recorder that refuses on an unrelated container is worse than a stale figure.
