# T7.20 stage 1 — three proposed scenarios, gated before recording

**Design only. Nothing recorded, no injection, no agent.** PLAN.md's original T7.1 (catalog
growth), which is why every per-class figure reads n=1 or 2.

## What is actually thin

Seven **valid dev bundles** — three authored scenarios are `blocked` and two of those also carry
`INVALID.md` (`currency-cpu-throttle`, `flag-service-crashloop`, `flag-service-bad-deploy`):

| fault class | valid dev bundles |
|---|---|
| `dependency_latency` | **1** — `cart-dependency-latency` |
| `bad_config` | 2 |
| `bad_deploy` | 2 |
| `resource_exhaustion` | 2 |

So `dependency_latency` is the thinnest and is the clear first pick; the rest is a choice about
*shape* rather than count.

## The four gates, and what each has already cost

| gate | source | what it rejects |
|---|---|---|
| **reachability** | T7.5, against T7.4's census | a target that cannot answer "was it idle or absent" for a narrative that will turn on it |
| **alerting** | T7.13 | a fault the rules cannot see. **The scale attempt died here and cost a day** |
| **injector** | ADR-0007/0010 | anything needing a new handler |
| **onset** | T7.12's 180 scrapes; T7.19's decision | anything slower than 900s of world time |

## A — `ad-dependency-latency` · `dependency_latency` · dev

**Fault.** Pumba `netem` 300ms on container `ad-service`, the same magnitude measured on cart.

**Class, and why not its neighbour.** `dependency_latency`, not `bad_config`, by ADR-0027's
corrected discriminator: `bad_config` means a configuration value was *set wrong*, and nothing on
`adservice` is. Traffic shaping is added alongside it and the service then behaves as a slow
dependency.

**Remediation — a claim, not an assumption.** `restart` is the labelled fix. T7.17 measured
`config_revert` to work on this mechanism, but **on `cart-service`, not here**, and ADR-0027
already carries one scenario (`productcatalog-dependency-latency`) holding that field by inference.
**Recommendation: this scenario ships with `restart` only, and no `also_correct_remediation`,
unless the qdisc-delete is measured on `ad-service` first** — three attempts, the T7.17 protocol.
Adding a third inference-carried claim is how a measured field quietly becomes a habit.

| gate | verdict | basis |
|---|---|---|
| reachability | **PASS** | 48 runtime series (`process_runtime_jvm_*`) + 731 log lines/hr → **2 classes**. The best-instrumented target in the census |
| alerting | **PASS** | p95 1.9ms at rest with **0 of 2398 samples over 250ms** in T7.14's 12-hour census. 300ms is decisive. Measured precedent: the identical mechanism and magnitude took cartservice 1.9 → ~650ms and fired |
| injector | **PASS** | `DependencyLatencyFault`, existing handler; a new `FaultDefinition` only |
| onset | **PASS** | `cart-dependency-latency` recorded 229s. `adservice` runs 0.4 req/s against cart's 3.2, so the 2m rate window fills slower — estimate **250–450s**, inside 900s. Carry an `alert_timeout_seconds` hint |

**Residual risk, stated:** ADR-0013's inversion — if 300ms exceeds the caller's timeout the signal
flips from latency to absence and the scenario silently changes class. `adservice` is a leaf behind
`frontend`'s ad panel. The same 300ms stayed under cart's caller timeout, which is the reason to
expect it holds, not a guarantee.

**Survives all four gates.**

---

## B — `cart-memory-squeeze` · `resource_exhaustion` · dev

**Fault.** `docker update --memory 200m` on `cart-service` (400MiB ceiling, 258.8MiB resting).

**Class, and why not its neighbour.** `resource_exhaustion`. This is the **known-disputed** pair —
`ad-memory-squeeze` already carries a register entry for exactly this reading, and ADR-0022's
addendum records that the fix tiebreak cannot settle it because both readings give `config_revert`.
Adding a third instance adds n to the class already carrying the most disputed rows, and that is a
cost worth naming rather than burying.

**Remediation.** `config_revert` — restore the limit. Undisputed, and identical to the two existing
squeezes.

**What it genuinely adds:** a third runtime (.NET, against two JVMs), with *directly relevant*
runtime evidence — `process_runtime_dotnet_gc_heap_size`, `gc_committed_memory_size`,
`gc_collections_count` — and it completes a four-class discrimination set on one service
(cartservice already carries `bad_config`, `bad_deploy` and `dependency_latency`), which
CATALOG.md's cart pair was designed for.

| gate | verdict | basis |
|---|---|---|
| reachability | **PASS** | 20 runtime series + ~500 log lines → **2 classes**, and the runtime family is the one the narrative would cite |
| alerting | **FAIL — measured, T7.20 probes** | 200m: killed and restarted, **zero alerts, zero errors, cart p95 flat** across two attempts. 32m: alerts, but its runtime evidence goes null under its own fault. See `docs/evidence/t7.20-probes/` |
| injector | **PASS** | `ResourceExhaustionFault` memory param, existing handler |
| onset | **PASS** | `cart-redis-misconfig` fired at 218s with 3 alerts; a cart outage cascades to checkout and frontend the same way |

**Why the alerting gate is not a pass.** `.NET`'s Server GC reads the cgroup limit and sizes a heap
hard limit from it. Lowering the limit underneath a running process may cause the GC to **collect
harder and survive** rather than OOM — which is precisely the shape ADR-0013 retired CPU throttling
for: the mechanism applies correctly and nothing observable happens. The JVM precedents do not
transfer, because a JVM sizes its heap at startup and cannot give memory back.

**Settled by a cheap probe:** apply 200m, watch `docker inspect --format '{{.State.OOMKilled}}'`
and the restart count for ~5 minutes, revert. No recording, no agent. If it survives, either lower
the number or drop the candidate — **do not record it and hope.**

## C — `shipping-quote-misconfig` · `bad_config` · split not ours to choose (see below)

**Fault.** `QUOTE_SERVICE_ADDR` on compose service `shippingservice` pointed at an address that
does not resolve, via the existing env-override handler.

**Class, and why not its neighbour.** `bad_config`, not `dependency_latency`: a configuration value
genuinely *was set wrong*, which is ADR-0027's discriminator, and the dependency is not slow — it
is unreachable. It is also a different `bad_config` shape from both existing ones, which point a
service at a wrong *backing store* and a wrong *flag*; this one breaks a service-to-service address.

**Remediation.** `config_revert`. Undisputed.

| gate | verdict | basis |
|---|---|---|
| reachability | **PASS, weakly** | **0 runtime series**, 2108 log lines/hr → **1 class, logs only**. Recordable — four existing scenarios are verdict 1 — but it must declare `answers_idle_or_absent: [logs]` and **its narrative must not lean on runtime metrics** |
| alerting | **PASS — measured, T7.20 probes** | `ServiceHighErrorRate/checkoutservice` at **T+240s**, both attempts. Shipping's own error rate stays **0.000**: the failure surfaces at the caller |
| injector | **PASS** | `BadConfigFault` env override, existing handler |
| onset | **PASS** | `ServiceHighErrorRate` is `for: 2m` over a 2m window; at `shippingservice`'s 0.5 req/s estimate **300–500s**, inside 900s, with an `alert_timeout_seconds` hint |

**Why the alerting gate is not a pass.** Whether a shipping failure surfaces as an *error rate*
depends on how `checkoutservice` handles a failed `GetQuote`. If it retries, degrades, or returns a
zero quote, the fault is real and produces no 5xx — and the same span-metrics property ADR-0013
documented means a request that never completes never enters the histogram either. Nothing in the
record establishes which happens.

**Settled by a cheap probe:** inject, watch `sum by(service_name) (rate(calls_total{status_code=
"STATUS_CODE_ERROR"}[2m]))` on shipping, checkout and frontend for ~6 minutes, revert.

## Verdict

**Updated after the T7.20 probes. Two of three survive: A and C. B fails.**

- **A — survives**, unprobed and not needing one; its alerting gate was already measured.
- **C — survives**, and is better than designed. `ServiceHighErrorRate/checkoutservice` at T+240s
  in both attempts, and a failed `GetQuote` produces **no error at shippingservice at all** — the
  alerting service is not the faulty one, which makes its logs-only reachability load-bearing.
- **B — fails at both magnitudes probed.** 200m kills and restarts the container with **zero
  alerts and zero errors**; 32m alerts but its runtime evidence **goes null under its own fault**,
  and it then resembles `cart-bad-image-tag`.

**A gate the record did not have, found here:** reachability has to be evaluated **under the
fault**, not at rest. B passed T7.5's gate on 20 runtime series and had none while faulted.

That is the gates working. They exist because two scenarios have already been proposed and
abandoned late, and the cost of finding this out now is two short probes rather than two recording
sessions and a day.

## A prerequisite none of the three can skip: SPLIT.md

All ten slots in SPLIT.md's `n=10` allocation are filled. Three new scenarios need
`dependency_latency-3`, `resource_exhaustion-4` and `bad_config-3`, and **those slots do not
exist**.

SPLIT.md's own rules make extending it a separate, earlier decision:

- *"Committed before authoring. Do not edit to accommodate a scenario."*
- *"Slots are filled alphabetically by injector fault id within each class, no exceptions… slot
  assignment is the only one of them that can bias the split, so it is the one with no judgement
  in it."*

**So the split of these scenarios is not ours to choose**, and proposing all three as `dev` — as
this task's brief does — would be choosing it. Two consequences:

1. **The extension must land first, against unnamed slots**, as its own commit, before any of these
   three is authored. That is a task, and it is the one SPLIT.md already names: *"T7.1 grows the
   catalog to 30+ and every class gets holdout representation there."*
2. **`bad_config` has zero holdout representation**, and SPLIT.md's own rationale sends holdout
   capacity to the classes that lack it. A principled extension is therefore *likely* to make
   `bad_config-3` **holdout** — which would make candidate C a holdout scenario, seeded into no
   corpus and never tuned against. Likely, not decided: the extension decides it, and it must
   decide it without these three in view.

Ratio check, for whoever writes the extension: the catalog is 7 dev / 3 holdout. Three more dev
would make it 10/3 (77/23) and drift off the ~70/30 target; 9 dev / 4 holdout at n=13 holds it.
