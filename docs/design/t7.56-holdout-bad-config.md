# T7.56 — the fifth `bad_config` item, and the criteria that would disqualify it

**Committed before the world was touched.** Magnitudes, order, and the conditions for abandoning
rather than tuning — as at T7.36 and T7.38, and with one difference that raises the bar: **a
holdout scenario is never tuned.** Nothing may run against it until an entry spends it, so there is
no iterating against how it performs. The only feedback available is the gate.

---

## 1. A correction to the brief before anything else: there are four, not three

The task named `cart-redis-misconfig`, `shipping-quote-misconfig` and `payment-telemetry-blackout`.
**`product-catalog-flag-failure` is also `bad_config`** — slot `bad_config-2`, dev, rehearsed. So a
new item is the **fifth**, and it has to be distinct from four pages rather than three. That makes
the bar higher than the brief assumed, and it is stated here because the design turns on it.

| # | slot | item | what it teaches |
|---|---|---|---|
| 1 | `bad_config-1` | `cart-redis-misconfig` | wrong **outbound** address on the failing service; the culprit alerts **and its own logs name the port** |
| 2 | `bad_config-2` | `product-catalog-flag-failure` | the config is on a **third service** (the flag service); failure is **partial** — one product id |
| 3 | `bad_config-3` | `shipping-quote-misconfig` | unresolvable outbound address; the culprit is **silent** and `change_history` is the only witness |
| 4 | `bad_config-4` | `payment-telemetry-blackout` | the **telemetry path** is broken, not the service; `ServiceNoTraffic` on a service that is working perfectly |

## 2. What the world can actually page, and what is left

Read off all fifteen recorded bundles rather than reasoned about — `alerts_at_fire` for every one:

| page | occupied by |
|---|---|
| ErrorRate {frontend, loadgen} | `ad-memory-squeeze`, `cart-redis-misconfig` |
| ErrorRate {frontend, loadgen, checkout} | `cart-bad-image-tag` |
| ErrorRate {loadgen} | `product-catalog-flag-failure`, `recommendation-memory-squeeze` |
| ErrorRate {checkout} | `shipping-quote-misconfig`, `shipping-wrong-image`, `email-wrong-image` |
| Latency {loadgen, frontend, cart} | `cart-dependency-latency` |
| Latency {cart} | `redis-cart-dependency-latency` |
| Latency {loadgen} | `productcatalog-dependency-latency` |
| NoTraffic {frauddetection} | `frauddetection-memory-squeeze` |
| NoTraffic {payment} | `payment-telemetry-blackout` |
| *(nothing fires)* | `currency-cpu-throttle`, `flag-service-crashloop` — both **INVALID** |

**The demo's topology dominates the page.** Anything that breaks a service on the checkout hot path
produces the same alert set — `{frontend, loadgenerator, checkout}` errors plus `NoTraffic` on the
tail — regardless of fault class. Distinctness in this world therefore has to come from **evidence**,
not from the page, except at the two edges: break nothing on the hot path, or break a consumer.

## 3. Candidates considered and rejected, with the reason

**Wrong bind address** (`ASPNETCORE_URLS` on cartservice, or any `*_SERVICE_PORT`) — the service is
up, healthy, and listening where nobody dials. Attractive until checked: **`ServiceNoTraffic/cartservice`
is already in `cart-redis-misconfig`'s and `cart-bad-image-tag`'s recorded alert windows**, so the
claimed novelty — *"the culprit pages on no-traffic while its callers error"* — is **already the
signature of two dev scenarios.** The distinctness would rest entirely on container uptime, and
`cart-bad-image-tag` already teaches that discrimination. **Rejected: the central claim was false
against the record.**

**An address that resolves to a live but wrong service** (point a caller at a healthy service that
does not implement the method). Novel in principle — the only shape where an *innocent* service's
traffic **rises**. Rejected on two grounds: the downstream page is identical to an unreachable
address, so the novelty lives in one log line; and it could not be established at desk that a gRPC
`UNIMPLEMENTED` even produces a server span, so the "traffic appears where it should not" signal is
speculative. **A holdout item may not rest on a speculative signal.**

**`currencyservice`, any fault** — rejected on measured traffic. It serves **0.47 req/s** against
frontend's 10.17, so breaking it moves frontend's error ratio nowhere near the 5% rule.
`currency-cpu-throttle`'s `INVALID.md` records the same service defeating a different fault for the
same reason. The only alert would be `NoTraffic/currencyservice`, which is `payment-telemetry-blackout`'s
page on a quieter service.

**`productcatalogservice`** — good topology, three callers. **Rejected because `productcatalog-dependency-latency`
is already a holdout item on that service.** Two holdout scenarios on one service correlates the arm
the benchmark's headline rests on, which is the opposite of what extending it is for.

**`adservice`** — one caller, and `ad-memory-squeeze` already occupies "adservice stops answering".

**The feature-flag store** (`DATABASE_URL` on the flag service) — genuinely distinct in mechanism, a
DSN rather than a service address. **Rejected on recorded evidence: `flag-service-crashloop` fired
`alerts_at_fire = []`.** Breaking the flag service pages nothing, and a fault that cannot alert is
not a scenario.

**Metrics-only telemetry break** (`OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`) — spans continue, so
`calls_total` continues, so **no rule can fire**. All three alert rules read `calls_total`.

**`OTEL_TRACES_SAMPLER` turned down** — the traffic metric drops but does not reach zero, and
`ServiceNoTraffic` requires `rate == 0`. Nothing fires.

**The frontend proxy's route** (`FRONTEND_PORT` on frontend-proxy) — a total outage whose culprit is
an uninstrumented component (`frontend-proxy` reports 0.00 req/s in `calls_total`). Rejected: the
only witness is `change_history`, which is `shipping-quote-misconfig`'s shape, and a total outage
risks the baseline gate and the recovery window for no new evidence.

### The candidate rejected on the holdout rule, and named because it was the most attractive

**A `bad_config` whose signature is latency** — a black-holed address that drops packets instead of
refusing them, so callers hang on connect timeout. Every latency page in the catalog belongs to
`dependency_latency`, so a *configuration* cause behind a latency page would be a genuine first.

**Not built, and the reason is the rule rather than the design.** T7.51 measured the agent naming
`dependency_latency` 3/3 while the judge rated 2 of 3 `adjacent` — right subsystem, wrong mechanism.
An item that turns on *"is this latency a configuration or a shaping rule?"* would put the holdout
arm directly on top of a documented failure. **The only thing that makes it distinct is the axis the
agent is known to be weak on**, so disclosing the overlap would not rescue it: the reason and the
weakness coincide, and that is steering by another name.

## 4. The candidate: `accounting-kafka-misconfig`

**`KAFKA_SERVICE_ADDR` on `accountingservice`, set to `kafka:9093` — the real host, a port nothing
listens on.**

`accountingservice` is a **Kafka consumer, not a request/response server**, and no scenario in the
catalog breaks a consumer by configuration. It is the empty corner of a square whose other three are
filled:

| the service is… | …and it is | occupied by |
|---|---|---|
| silent, **dead** | genuinely gone | `frauddetection-memory-squeeze` (OOM-killed) |
| silent, **alive and working** | the telemetry lying | `payment-telemetry-blackout` |
| silent, **alive and not working** | **empty** | **this** |

**Why a consumer fails differently, and why that is the point.** Nobody calls it, so it cannot have
an error rate. It serves no requests, so it cannot have latency. The *only* signal it can produce is
absence — and absence is exactly what `frauddetection-memory-squeeze` and `payment-telemetry-blackout`
also produce, from three different causes. The responder's question is the one this world has never
asked: **the consumer is silent — is it dead, is the telemetry broken, or is it alive and consuming
from nowhere?**

**Why it is not steering.** The localisation does not depend on `change_history`: a Kafka client that
cannot reach its broker says so, repeatedly, in its own logs, naming the address. That is
`cart-redis-misconfig`'s evidential virtue on a service and a failure mode that share nothing else
with it. `accountingservice` has **never been the target of any scenario**, so it correlates with no
dev item and no holdout item.

**Slot: `bad_config-5` — holdout, by position.** T7.35's frozen rule puts holdout at the highest
indices in each class; `bad_config-1` … `-4` are dev and filled, so this lands in holdout. **The slot
was not chosen; it is what the rule assigns.** That is what extends the set on T4.15's terms.

## 5. Disqualification criteria — checked in this order, stopping at the first failure

**There is no dial on this fault.** The only parameter is the address, and every wrong address is
equivalent, so **every failure below is a reason to abandon, not to adjust.** The scenario is
recorded as it lands or it is not recorded.

| # | check | passes if | disqualifying because |
|---|---|---|---|
| **G1** | **The container stays up** | `RestartCount` on `accounting-service` is unchanged for the whole window, and uptime is continuous | A restarting container makes this a crashloop page. The whole item is *"alive and not working"*; if it is not alive, there is no item. `flag-service-crashloop` is what that becomes and it is INVALID |
| **G2** | **Something pages, and it is the right thing** | `ServiceNoTraffic/accountingservice` fires within **900 s**, and it is the **only** `alerts_at_fire` entry | Nothing firing is `currency-cpu-throttle`'s failure — a healthy world with a setting changed. **Any `ServiceHighErrorRate` firing anywhere** means the fault reached the hot path, the page is the standard one, and the item is not distinct |
| **G3** | **The logs discriminate** | `accountingservice`'s captured logs under the fault contain at least one line naming the broker address it cannot reach | If the logs are silent, the only witness is `change_history` — which duplicates `shipping-quote-misconfig` **and** leans on the gap T7.51 documented. Both reasons are independently disqualifying |
| **G4** | **Reachability is derived, not declared** | the recorder reports `none_can_answer: false` | A scenario no evidence class can answer is unscoreable (T7.5). **The recorder's answer overrides the authored one; the authored guess is never argued with** (T7.36's correction) |
| **G5** | **The world comes back** | 0 alerts and `accountingservice`'s rate above 0 within the settle window after revert | A world that does not recover is a world-integrity failure, not a scenario failure, and stops everything |

**Magnitudes, measured today before the fault:** `accountingservice` serves **0.16 req/s**; it must
reach **exactly 0** for `ServiceNoTraffic`, whose rule is `rate == 0 AND rate[30m offset 10m] > 0`
for `3m`. Expected onset is the 3-minute rate window draining plus the 3-minute `for:` clause —
roughly **5–7 minutes**, the same shape as `payment-telemetry-blackout`'s measured 319 s. The 900 s
budget is set explicitly for that reason and not left to the default.

**If G1, G2 or G3 fails:** the scenario is abandoned, an `INVALID.md` records what was measured, the
slot is released, and **Q9 is not discharged** — which leaves entry 4 blocked and means the holdout
cannot be extended in `bad_config`. That is a real finding and it will be reported as one rather
than worked around.
