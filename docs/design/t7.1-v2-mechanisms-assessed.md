# T7.1 — v2's fifteen mechanisms against the fix test, and the criterion problem underneath

**Nothing was run and nothing was spent.** OpenTelemetry Demo read at source, tag **2.2.0**
(`b74a7bc7`), against [ADR-0042](../adr/0042-the-world-moves-to-opentelemetry-demo-v2.md)'s own
acceptance gate: *"a measurement, on the new world, showing the fifteen flags do not individuate
into classes under ADR-0022 §1.2 … That is the risk."*

**The risk is real and this is the measurement. ADR-0042's headline framing overstates, and this
note corrects it.** The careful clauses in that ADR — *necessary and not sufficient*, and the risk
named in *What would change it* — were right, and they are what made this check mandatory before
the re-record rather than after. The system worked; the headline did not.

---

## 1. The gate, as ADR-0029 §3 states it

> **"Four mechanisms, four classes, one-to-one and test-enforced. So the question *is there a fifth
> fault class?* is not a question about phenomena. It is: can the injector gain a fifth mechanism
> **whose working fix is not already taken**?"**

**A conjunction.** v2 supplies the first conjunct fifteen times over. The second is where every one
of them dies.

## 2. The fifteen, and what fixes each

All fifteen are **flagd feature flags**, read per request through OpenFeature. The injection is
*set a flag*; the revert is *unset it*. Read at source rather than inferred, except where marked.

| flag | mechanism | read at | working fix |
|---|---|---|---|
| `productCatalogFailure` | returns an error for a product id | `product-catalog/main.go:492` | `config_revert` |
| `recommendationCacheFailure` | unbounded in-process `cached_ids` growth | `recommendation/recommendation_server.py:78` | **`restart`** + `config_revert` |
| `emailMemoryLeak` | multiplies email body length | `email/email_server.rb:67` | `config_revert` |
| `adFailure` / `adHighCpu` / `adManualGc` | error, CPU burn, forced GC | `ad/…/AdService.java:135–172` | `config_revert` |
| `cartFailure` | cart op throws | `cart/…/CartService.cs:83` | `config_revert` |
| `failedReadinessProbe` | health check returns Unhealthy | `cart/…/HealthCheckService.cs:35` | `config_revert` |
| `paymentFailure` / `paymentUnreachable` | charge fails / checkout cannot reach payment | `payment/charge.js:29`, `checkout/main.go:537` | `config_revert` |
| `kafkaQueueProblems` | consumer sleeps 1 s per record | `fraud-detection/…/main.kt:60` | `config_revert` |
| `llmRateLimitError` / `llmInaccurateResponse` | rate-limit error / wrong answer | `product-reviews/product_reviews_server.py:164, 269` | `config_revert` |

**Every working fix is `config_revert`, or `{restart, config_revert}` for the one flag that leaves
process state behind.** Both profiles are taken: `config_revert` by `bad_config`, and
`{restart, config_revert}` is exactly what ADR-0027 measured 3/3 for `dependency_latency`.

**So the candidates do not survive v2. They change how they die** — from ADR-0029 §5's *"the world
has nothing"* to §5's other verdict, the one that killed *expired credential*: **the fix is already
taken.** Net new classes under ADR-0022 §1.2: **zero**.

**And disk fill stays dead for the original reason.** v2's compose declares **no named volumes** —
every mount is a read-only config bind, the same as v1.2.1 — so ADR-0029's addendum verdict *"a
world with no volumes"* holds unchanged in v2.

**New services are new targets, not new classes.** v2 adds `llm`, `product-reviews`,
`image-provider`, `valkey-cart`, `postgresql`, `opensearch`. Each is somewhere to point
`BadDeployFault`, `BadConfigFault`, `ResourceExhaustionFault` or `DependencyLatencyFault` — more
scenarios, the same four mechanisms.

## 3. The finding underneath, which is larger than the flags

**This repository has two criteria for individuating a fault class, they are both written down,
and they disagree.**

- **ADR-0022 §1.2** — *"a fault's class is settled by which fix actually works."*
- **ADR-0029 §3** — *"fault class ≡ injector mechanism,"* one-to-one and enforced by
  `test_scenario_injections_match_the_fault_they_cite`.

**Under the fix test, the four classes that exist are not individuated either.** ADR-0029 §1 says
so in its own words: *"the criterion does not individuate the four classes that exist.
`config_revert` is a working fix for three of the four. It separates `bad_deploy` from the rest and
nothing else."*

So the operative criterion in practice is §3's — **mechanism**. And under §3, v2's fifteen flags
*are* fifteen candidate mechanisms, and a `FeatureFlagFault` (or one class per flag family) would
reach eight classes without difficulty.

**T7.1's "~8 fault classes" is therefore impossible under one criterion and nearly free under the
other**, and which one governs has never been decided — because until v2 no candidate reached the
point where the two disagreed.

**Neither answer is obviously right, and the trade is real.** Classes individuated by mechanism
give the catalog its eight and make `fault_class` a statement about *what was done to the world*.
Classes individuated by fix make `fault_class` a statement about *what an operator should do*,
which is what a remediation-proposing system is for — and on that reading, four classes over three
distinct remediations is already one too many.

## 4. What ADR-0042 got wrong, and what survives

**Wrong: the framing that three of §5's deaths are *overturned*.** They are not. `llmRateLimitError`
and `kafkaQueueProblems` do refute the specific sentence *"the demo exposes no such knob"* — that
sentence was false of v2 and nobody had checked — but the candidates still die one gate later, and
the ADR's table invites a reader to conclude that eight classes are now reachable. **They are not
reachable under the criterion that table cites.**

**Survives, and still justifies the move:**

- **The count is correct and so is its consequence.** v1.2.1 ships 2 failure flags, v2.2.0 ships 15,
  and the world's mechanism surface really was the binding constraint on *scenarios*.
- **T7.1's stated rationale is the statistical one** — *"accuracy claims over 10 scenarios are an
  anecdote; over 30+, a measurement"* — and **v2 delivers that half**. Fifteen mechanisms across
  twenty-odd services is a 30+ catalog with genuine variety in alert shape, which is the thing
  ADR-0029 §4 said this world could not give and which the 16.2 pp MDE has been costing every
  ablation in the repository.
- **ADR-0005's prediction still fails**, and for the reason given: the injector could not exceed
  what the demo exposes.
- **The holdout arithmetic is unchanged**: what a world move would strand is already stranded.

**So the decision to move is not withdrawn by this note. What is withdrawn is the claim that moving
delivers ~8 fault classes for free.** It delivers the catalog; the classes need a taxonomy decision
that is nobody's to make by implication.

## 5. What this changes about the order

**Before any re-record**, the criterion question is answered explicitly and written as an ADR —
because `fault_class` is a `Literal` in a contract, every value is in the prompt digest, and a
taxonomy chosen by accident is one the benchmark then carries forever.

**If the answer is the fix test**: T7.1 lands 30+ scenarios across **four** classes, the plan's
"~8" is recorded as refused with this note as the reason, and the statistical purpose is met in
full.

**If the answer is mechanism**: T7.1 lands 30+ across eight or more, and the cost is that
`fault_class` stops predicting remediation — which should be measured and stated, not discovered by
a reader of the headline table.
