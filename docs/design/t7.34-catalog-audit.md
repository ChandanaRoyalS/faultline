## 3. Which slots are free, and what decides the split

**The split is not chosen. It falls out of position**, and this audit verified the rule rather than
trusting it: assigning each valid scenario to the lowest free slot of its class, in authoring order,
**reproduces all eleven existing split assignments exactly**.

| free slot | split | |
|---|---|---|
| `bad_deploy-4` | **dev** | |
| `bad_deploy-5` | **dev** | |
| `bad_deploy-6` | holdout | |
| `bad_config-4` | **dev** | |
| `bad_config-5` | holdout | |
| `bad_config-6` | holdout | |
| `dependency_latency-3` | **dev** | released by `ad-dependency-latency` |
| `dependency_latency-4` | **dev** | |
| `resource_exhaustion-4` | **dev** | the class's last slot at n=20 |

**Six dev, three holdout — so the next six scenarios authored are dev whatever they are, and the
three after are holdout whatever they are.** No candidate below was placed; each takes the next free
slot in its class. For `dependency_latency` and `resource_exhaustion` this is doubly forced: their
holdout slots are already full, so a candidate in either class **cannot** be holdout.

### An audit finding: the slot rule is prose, and nothing records or enforces it

**No scenario carries a `slot:` field — zero of fifteen.** `tests/test_contamination.py` checks
per-class *counts* (`dev <= dev_slots`, and exact match once a class is full); it does not check
slot identity, because nothing records identity to check. SPLIT.md's occupancy table names **2 of
11** valid scenarios.

So the mechanical anti-steering rule — "slots are filled alphabetically by injector fault id, no
judgement in it" — is **not executed by anything.** What actually constrains an author today is the
per-class ceiling, and within that ceiling the author writes `split:` by hand. That is the third
instance in this arc of a guard that is true when written and unenforced afterwards (T7.31's
precondition, T7.32's opt-in flag, this).

It does not bite for the next six, because every free dev slot in every class comes before every
free holdout slot, so **any** assignment consistent with the counts is also consistent with the
rule. **It bites at the seventh**, where the first genuinely holdout-bound scenario is authored and
nothing computes that it must be. **Recording the slot per scenario, and asserting it, is the
prerequisite task** — it is small, it is desk work, and it should land before authoring resumes.

## 4. Candidates for the six dev slots

Each gives fault, service, mechanism, evidence shape, what it discriminates that the catalog cannot
today, and what gating costs. Where the honest answer is "filler", it says so.

### D1 · `redis-cart-dependency-latency` → `dependency_latency-3` (dev)

**Fault** `dependency_latency` · **target** `redis-cart` · **mechanism** `tc netem` egress delay via
pumba, the catalog's existing latency mechanism, applied to the datastore container rather than to a
service.

**Evidence shape.** `redis-cart` is not an instrumented service: it emits no spans, has no
`service_name` in `calls_total`, and logs ~72 lines/hour (ADR-0005's baseline). Delaying it blocks
`cartservice`'s handler on its own backing-store calls, so **`cartservice` looks slow and the
culprit appears nowhere in the service graph.**

| tool class | sees |
|---|---|
| `promql_query` | `cartservice` p95 up, then `checkoutservice`/`frontend`; **nothing at all for redis-cart** |
| `trace_query` | `cartservice` server spans slow; its client spans to redis carry the time |
| `logql_query` | `cartservice` only; redis says nothing |
| `change_history` | **the only class that can name `redis-cart`** |

**What a correct diagnosis must notice:** the latency is inside cartservice's redis calls, not in
cartservice's own work, and the responsible component never appears as a service.

**Discriminates:** every culprit in the catalog today is an instrumented service. This is **the
first fault whose culprit is outside the service graph.** `cart-redis-misconfig` points *at* redis
but the fault is config on the caller; here the fault is on redis itself.

**Gate risk: MEDIUM.** If cartservice's redis client times out rather than waits, the scenario
presents as errors rather than latency and drifts toward `bad_config`'s shape. Probe the delay
magnitude against the client's timeout before authoring.

### D2 · `recommendation-dependency-latency` → `dependency_latency-4` (dev)

**Fault** `dependency_latency` · **target** `recommendationservice` · **mechanism** the same netem
egress delay. Desk-checked as viable: it holds `PRODUCT_CATALOG_SERVICE_ADDR` and
`FEATURE_FLAG_GRPC_SERVICE_ADDR`, so it has downstream calls to block on and is **not** the leaf that
killed `ad-dependency-latency`.

**What it discriminates: nothing. This is filler for a slot that must be filled.** Same mechanism,
same shape, a different service — exactly the row-in-the-count-and-nothing-in-the-benchmark case.

Its one real justification is statistical and is SPLIT.md's own: three dev scenarios per class is
the floor, *"two cannot show a spread"*, and `dependency_latency` stands at **one**. D1 and D2
together take it to three. That is a reason to build it; it is not a discriminating reason, and it
should not be written up as one.

**Gate risk: LOW.** Nearest analogue to the one latency scenario that already works.

### D3 · `payment-flapping-deploy` → `bad_deploy-4` (dev)

**Fault** `bad_deploy` · **target** `paymentservice` · **mechanism** a deploy that starts, serves,
and exits non-zero on a cycle, so the restart policy makes it flap.

**Evidence shape.** Intermittent errors rather than total failure; `RestartCount` climbing;
successful requests interleaved with failed ones; `ServiceNoTraffic` possibly firing and clearing.

**Discriminates two things.** First, the injector documents three `bad_deploy` shapes — never
starts, starts then fails every call, **flaps** — and the catalog has the first two. Second, and more
useful: **a flapping deploy and a memory squeeze look alike.** Both restart repeatedly, both produce
gaps and partial errors. The discriminator is `change_history` showing a deploy against container
memory showing no OOM and no pressure. S7 caught the agent confusing `bad_config` with `bad_deploy`;
this tests the adjacent confusion deliberately rather than waiting for it.

**Gate risk: MEDIUM-HIGH.** T7.20 measured that fast restart cycles are invisible — `cart-memory-
squeeze` at 200m restarted *faster than detection* and nothing alerted. The flap interval must be
slow enough that errors accumulate over the rules' 2m rate window. **Probe the interval before
authoring**; this is the same failure mode that has already killed two candidates.

### D4 · a fourth `bad_deploy` → `bad_deploy-5` (dev)

**This is filler, and I would leave the slot empty rather than build it.**

The available mechanism space is image substitution and restart behaviour. "Never starts" and
"starts and fails every call" are taken; D3 takes "flaps". A fourth is a third image swap on an
unused service, and it adds a row and nothing else. The genuinely distinct fourth shape — a deploy
that starts, serves, and returns *wrong results* without erroring — is rejected in §5 because this
world cannot alert on it.

SPLIT.md says slots are **capacity, not a promise**. `bad_deploy` dev already clears the floor of 3
with D3. If it is built anyway, it should be built last and labelled filler in CATALOG.md.

### D5 · `payment-telemetry-blackout` → `bad_config-4` (dev)

**Fault** `bad_config` · **target** `paymentservice` · **mechanism** repoint
`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` / `..._METRICS_ENDPOINT` at a dead address. Both are per-service
compose environment variables, so this is an ordinary config change on one service.

> **This replaces the candidate I designed first, which desk-checking killed.** The original was a
> timeout misconfiguration — shrink a caller's deadline so calls that used to succeed now fail while
> the callee stays healthy. **There is no timeout or deadline environment variable anywhere in the
> demo**; every knob is an address. The mechanism does not exist without patching a third party's
> service, which ADR-0005 already ruled out of scope. Recorded so it is not re-proposed.

**Evidence shape — the service is completely healthy and completely invisible.**

| tool class | sees |
|---|---|
| `promql_query` | `paymentservice`'s own series stop; `ServiceNoTraffic` fires on it. **Its callers show no errors and no latency change.** |
| `trace_query` | `checkoutservice`'s **client** spans to payment still succeed, with normal duration — the caller exports them. There are simply no matching **server** spans. |
| `logql_query` | payment's container logs continue normally; it is serving |
| `change_history` | the exporter endpoint change |

**What a correct diagnosis must notice:** the callers are succeeding, so the service is working —
the outage is in the telemetry path, not the service. It must resist the obvious reading of
`ServiceNoTraffic` as "the service is down".

**Discriminates:** every scenario in the catalog has a real service fault. **This one has none**, and
the correct answer requires establishing a negative — that the silent service is alive — from its
callers' evidence. The project already treats this shape as an accident: T7.12 built `metrics-gap`
as a *discard reason* for exactly it. Making it a scenario tests whether the agent can tell a
telemetry outage from a service outage, which nothing in the catalog tests and which is a real
on-call distinction. It is also the closest thing available to a second `shipping-quote-misconfig` —
a culprit exculpated by its own evidence — in a different mechanism.

**Gate risk: MEDIUM.** `ServiceNoTraffic` should fire, so an incident opens. Two things to verify in
the probe: that the harness's own `metrics-gap` detector does not fire (it watches `up` scrapes
across the world, not one service's exporter, so it should not), and that reachability evaluated
**under the fault** is honest — the target's runtime and metrics classes go null by construction, so
`answers_idle_or_absent` must declare them. That is precisely the rule `cart-memory-squeeze` was
disqualified for violating, so it must be declared at authoring rather than discovered.

### D6 · `payment-memory-squeeze` → `resource_exhaustion-4` (dev)

**Fault** `resource_exhaustion` · **target** `paymentservice` (Node.js) · **mechanism** container
memory limit squeeze, the class's one surviving mechanism.

**Discriminates weakly, and the honest label is mostly filler.** The runtime differs from the
catalog's existing three — JVM (`adservice`), JVM (`frauddetectionservice`), Python
(`recommendationservice`) — and a Node heap OOM has a different signature from a container kill. That
is a real but small distinction; the diagnosis path is the same one three scenarios already exercise.

Its justification is the floor: dev `resource_exhaustion` stands at 2 and this takes it to 3.
SPLIT.md is explicit that this class **should grow least**, and this is its last n=20 slot.

**Gate risk: HIGH — the highest of the six.** T7.20 measured the observable band as narrow from both
sides, and `cart-memory-squeeze` was disqualified at *both* magnitudes it was probed at. Node's
behaviour under a cgroup limit is untested here. Expect **two probe magnitudes minimum**, and expect
this to be the candidate most likely to be disqualified. If it is, the slot stays empty and the class
stays at 2 — which is an acceptable outcome and better than a bundle that captures a healthy world.

## 5. Rejected now, so they are not proposed later

| candidate | why it is rejected before any world time |
|---|---|
| **a "wrong but working" deploy** — starts, serves, returns wrong data | Fires **no alert**: the three rules are error rate, latency and no-traffic, and a fast correct-looking service trips none. No alert means no incident, and no incident means nothing to score. The catalog cannot hold a fault this world cannot detect. |
| **a timeout misconfiguration** | **No timeout or deadline env var exists in the demo** — desk-checked across the compose file; every knob is an address. Would require patching a third party's service, which ADR-0005 rules out of scope. |
| **a `redis-cart` eviction / `maxmemory` scenario** | `maxmemory 12mb` and `allkeys-lru` now live in `compose/world-arm64.override.yml`, a **`compose_digest` input** (T7.28). Changing them moves the digest and forces a full re-record of every bundle. **Digest-locked**, and not worth a re-record for one scenario. |
| **any latency injection on a leaf service** | `ad-dependency-latency` established the rule by failing: `tc netem` delays egress, so a service with no downstream calls has nowhere to put the delay. Check for downstream `*_SERVICE_ADDR` before proposing a latency target. |

## 6. What gating costs

**Gating is not agent exposure and does not spend the holdout**, so a holdout candidate costs the
same world time as a dev one and can be gated freely. None of the six below is holdout — all six free
dev slots come first — but the three holdout slots after them carry the same per-candidate cost.

Per candidate, from the record: a probe is roughly gate + inject + up to 900s of alert budget +
revert + settle ≈ **20–25 min**, and T7.20 needed two attempts on one candidate at one magnitude. A
recording is gate + inject + onset (181–375s measured across the catalog) + 90s settle + capture +
revert + recovery ≈ **25–30 min**.

| candidate | probes | est. world time |
|---|---:|---:|
| D1 `redis-cart-dependency-latency` | 1–2 (magnitude vs client timeout) | ~50 min |
| D2 `recommendation-dependency-latency` | 1 | ~45 min |
| D3 `payment-flapping-deploy` | 2 (flap interval) | ~75 min |
| D4 fourth `bad_deploy` *(recommend skipping)* | 1 | ~45 min |
| D5 `payment-telemetry-blackout` | 1–2 (reachability under fault) | ~60 min |
| D6 `payment-memory-squeeze` | 2+ (narrow band) | ~90 min |
| | | **~6 h if every one works first time** |

**Budget 8 hours, not 6.** The historical disqualification rate is 31% (§2), so on this set expect
roughly two candidates to fail and need either a redesign or abandonment.

**Add to that**: kafka must be recycled between batches, not during one (T7.31/T7.33), which is
~2 min plus an `accounting-service` restart each time — and every batch must declare
`--runs-remaining` or `--single-run`, which T7.33 now refuses to proceed without.

## 7. Build order, and why

1. **The slot-recording prerequisite (§3).** Desk work, no world time. It does not block the next six
   — every free dev slot precedes every free holdout slot — but it must land before the seventh, and
   it is cheapest to do while nothing depends on it.
2. **D5 `payment-telemetry-blackout`.** Highest discriminating value in the set: the only candidate
   whose culprit has no fault at all, and the nearest available successor to the shape S7 showed the
   agent failing on. Its mechanism is desk-verified to exist.
3. **D1 `redis-cart-dependency-latency`.** Second-highest: the first culprit outside the service
   graph. Also fills the class the record calls thinnest.
4. **D3 `payment-flapping-deploy`.** Completes the injector's documented third `bad_deploy` shape and
   sets up a deliberate cross-class confusion. Higher gate risk, so it follows the two that are more
   likely to land.
5. **D2 `recommendation-dependency-latency`.** Filler, built for the floor rather than for
   discrimination — worth doing because `dependency_latency` at one dev scenario is the gap the n=20
   extension existed to close, and D1 alone leaves it at two.
6. **D6 `payment-memory-squeeze`.** Highest disqualification risk and lowest marginal value, so it
   goes last, where a failure costs least and the slot can simply stay empty.
7. **D4** — recommend **not building**. Leave `bad_deploy-5` empty.

**On that order:** it is by discriminating value first and gate risk second, not by class. The two
candidates that would merely raise the count (D2, D6) come after the three that change what the
benchmark can tell apart, and the one that would only raise the count is dropped.

## 8. What this does not settle

**It does not close the `bad_config` holdout hole**, which is the largest at both targets and the one
ADR-0008 flagged at n=10. Two of the three remaining holdout slots are `bad_config`, and until they
are authored **no claim about generalising to held-out `bad_config` is available** — the same
sentence the n=10 table could not say. Those candidates are a separate design; this one covers the
dev deficit as scoped.

**It does not reach n=30.** Six of nineteen. The n=30 deficit is stated in §1 so the distance is
visible, not so it is planned here.

**And it assumes the mechanisms behave.** Every gate risk above is a prediction from the record, not
a measurement — which is exactly the error mode §2 says has already killed three candidates. The
probes are what settle them, and any of the six may join the disqualified list.
