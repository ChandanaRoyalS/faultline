# T7.43 — reading the abstention

Reconstructed from the stored envelopes of the two `payment-telemetry-blackout` runs, not from
summaries. **n = 1 against n = 1. This is a hypothesis with a named mechanism, not a measurement.**

| | run 1 | run 3 |
|---|---|---|
| trajectory | `f4a83263-…` | `02497794-…` |
| verdict | **`unknown`**, low confidence | **`bad_config` ✔**, low confidence |

## What was identical

**The step sequences are the same, seventeen steps each:** planner → changes, metrics, logs →
planner → traces, metrics, logs → synthesizer retrieval → verdict → scribe. **Both completed two
dispatch rounds.**

**So the budget hypothesis is out.** No round was cut; the join, had it happened, had a place to
happen in both.

## What each specialist returned

**The `changes` specialist found and reported the change in both, at high confidence.** Run 1's:

> *"Exactly one change landed on paymentservice in the queried window: at 04:34:08 UTC, actor
> platform-automation applied an environment variable update setting the OTLP traces exporter
> endpoint to a loopback address… **the only candidate trigger in the window**."*

**So "a specialist that found the change and did not report it as relevant" is out.**

**And run 1's specialists did not return less.** Findings and rule-outs are comparable
(`found` 2–5, `ruled_out` 3–5 in both), and run 1 referenced the endpoint in **three** steps
(changes, logs, traces) against run 3's **one**.

## What the planner asked

**Both planners named the mechanism in round 2 and dispatched to test it.**

- run 1: *"The leading explanation — a machine-applied OTLP exporter redirect to loopback **causing
  export blocking and a pod restart** — is confirmable or falsifiable only in traces…"*
- run 3: *"Together they test one mechanism: **the loopback OTLP endpoint blocking or exhaust**[ing]…"*

**So "a planner that never asked the question" is out.**

**Both hypothesised the same wrong mechanism.** The real one is that spans stop, so spanmetrics stop,
so `calls_total` drains and `ServiceNoTraffic` fires — **nothing to do with the request path.** Both
runs dispatched round 2 to test a request-path mechanism, and both correctly falsified it.

## Which of the four it was

**The synthesizer had both halves and would not join them.** The divergence is one sentence.

| | |
|---|---|
| **run 1** | *"it specifically tests and rejects the two mechanisms by which the 04:34:08 loopback exporter endpoint could have broken the request path. **That leaves the change record as an upstream act with no demonstrated mechanism, which is exactly the situation where classifying by the change would be wrong.**"* |
| **run 3** | *"The exporter endpoint is wrong as a value — it names an unreachable address — and **that wrongness is the mechanism**, so bad_config over the alternatives."* |

Both cite the change record. Both establish the service is healthy. Both falsify the request-path
mechanism. **They differ on what counts as a mechanism at all:**

- **run 3 treats a wrong configuration value as self-evidently the fault** — the wrongness *is* the
  mechanism, independent of any traced causal path to the symptom.
- **run 1 requires a demonstrated causal path from change to symptom**, finds the one it hypothesised
  falsified, and treats the absence as grounds not to classify.

**The uncomfortable part, stated rather than smoothed over: the run that scored correct reasoned
less strictly, and says so itself** — *"Confidence is low because every symptom probe aimed at
paymentservice came back healthy; **the causal link to the critical severity rests on temporal
proximity and sole-change-in-window**."* That is precisely the inference this project warns against
elsewhere. Run 1 declined to make it and was scored wrong for declining.

### A contributing factor, and it is the boundary T7.40 kept

Run 1's remaining thread was the container replacement, and it says the discriminating data was
**asked for and unavailable**:

> *"A restart is compatible with resource_exhaustion (an OOM kill), with a deployment action, or with
> routine rescheduling, and no returned signal discriminates among them — **the restart counter and
> memory utilization were requested and not returned**."*

**That is T7.40's exit-reason boundary, appearing in an abstention.** T7.42 established the restart
is explicable from `change_history` — and this synthesizer had the change record and still could not
discriminate the restart's cause, because explaining *that a config change happened* is not the same
as explaining *why the container died*. **This does not reopen T7.40** — the survey there stands, and
one run is not evidence — but it is the second time the same absence has surfaced in a live verdict
and it belongs in the record.

## Is this a known abstention shape? — the same rule, a new upstream cause

**The same rule.** S6's `shipping-wrong-image` abstention reads: *"The failing component is localized
with high confidence; the failing mechanism is not, and I decline to infer one from the shape of the
error alone."* Run 1 is the same rule applied: **component localized, mechanism not demonstrated,
decline to infer.** ADR-0022 treats `unknown` as legitimate and this is that behaviour.

**A new upstream cause.** The two differ in *why* the mechanism was undemonstrated:

| | why no mechanism |
|---|---|
| S6 `shipping-wrong-image` | **evidence never gathered** — zero dispatches touched the failing service (T4.12's dispatch collapse) |
| **T7.41 run 1** | **evidence gathered, and the hypothesised mechanism falsified** — the specialists did their work and the candidate mechanism was the wrong one |

**So this is not the dispatch collapse.** It is the abstention rule firing on a well-executed
investigation that tested the wrong hypothesis. **That shape has not been seen before in this
project.**

## What a single pair supports

**Nothing beyond a hypothesis.** n = 1 against n = 1, on runs whose difference could be sampling.
Two things make it more than nothing: the divergence localises to a **single identifiable step**
(the synthesizer, with the other three candidate causes ruled out from the envelope), and the
divergent reasoning is **explicit in both**, not inferred from outcomes.

**It is not evidence that the synthesizer systematically requires a traced mechanism.** It is
evidence that it did once, on one scenario, while another run of the same scenario did not.

### What would test it, and what it costs

**The test:** run `payment-telemetry-blackout` enough times to estimate how often the synthesizer
declines to classify by a change whose mechanism it cannot trace, and pair it with a scenario where
the mechanism *is* traceable (`cart-redis-misconfig` — wrong port, visible connection failures) to
see whether the same synthesizer classifies readily there. **A split by mechanism-traceability is
what would turn this into a finding.**

**The cost:** at T7.29's measured $0.546/scenario, **n = 10 across the pair is ~$5.5 and ~3.5 hours**.
**There is no money — T7.41's sweep ended on an exhausted credit balance — so this task ends at the
hypothesis**, as scoped.

## The proposed change, written down and queued rather than made

**Not made.** Role prompts feed `runtime_version`, so editing one moves the stamp off
`prompts:1b0e7cbb4c47` and **invalidates comparability with every figure recorded under it** — six
dev sweeps, three holdout entries, and both new scenarios.

**The proposal:** the synthesizer's instruction distinguishes *a change with no demonstrated
mechanism* from *a change whose value is self-evidently wrong*. A configuration value naming an
unreachable address is wrong on its face; requiring a traced path from it to the symptom is a
standard that the correct run met by lowering, not by finding more.

**What would justify adopting it:** the split-by-traceability measurement above showing the
abstention concentrates on scenarios whose mechanism is untraceable. **Without that it is one run**,
and changing a prompt on one run is how a benchmark gets tuned to its last result.

**What adopting it would cost:** a stamp move, so every comparison in RESULTS crosses a pipeline
boundary as well as the world boundaries already there — and a re-run of anything that needs to stay
comparable. Queued, not scheduled.
