## Timeline as reconstructed

Roughly T-6m30s: the platform automation actor created the frontend service object and its first workload container. At the same second it created the consul service object and its first workload container. Both are first-creation records, not edits to anything already running.

T-6m29s: the frontend process cold-started — config read, tracing init, discovery agent init, gRPC client init, HTTP listener bound. The restart is visible in its own logs, so the process was not running continuously through the window.

T-6m29s to T-6m25s: a burst of discovery refusals. The frontend's load-balancer client could not pull instances from the discovery agent; the HTTP GET to the health endpoint came back as a refused TCP connection on port 8500 against the cluster VIP. All five downstream lookups failed identically inside that burst.

T-6m25s: last refusal line. The process finished startup and began serving about a second after boot. No further port-8500 line appears anywhere through the end of the window.

T+0: the alert. Nothing in any log, metric, or trace source we queried marks this moment.

## The discovery burst, and why it is not the answer

This is the one concrete anomaly on the board and it is very easy to mistake for the cause. The reasoning that led us to it: frontend logs showed exactly one class of error, and it affected every backend uniformly, which argued the problem sat at the discovery dependency rather than at any single downstream service. The change record then showed the frontend and discovery workloads were stood up in the same second by the same automation — a textbook bootstrap race where the client comes up before the registry is accepting connections.

It does not hold. A narrowed query on the port-8500 string covered the full half-hour window without truncation and showed the refusals confined to a roughly four-second burst, last line at T-6m25s, with nothing in the twenty-three minutes before the restart and nothing in the six and a half minutes between the burst and the alert. Discovery was clean for the entire approach to onset. A transient that stopped six minutes before the symptom and never recurred is not the onset mechanism.

Secondary lines also closed here: the discovery hostname resolved fine (the error text carries the VIP, so this is a refused connection and not a lookup failure); TLS was disabled at startup with no handshake errors; there was no panic, stack trace, or fatal line; and the process reached its serving state rather than crash-looping.

## Dead end: the change log

## Dead end: metrics were never going to answer this

The error-ratio query against Prometheus for frontend did not return an empty series — it failed outright, with an explicit note that this backend holds no span-derived metrics for the service because the service sends no traces that become metrics. The baseline window thirty minutes earlier is equally unpopulated, so there is no before/after comparison available from this source.

The same query against the user service failed the same way for the same stated reason. That is the useful part of running it twice: the gap is not a per-service collection failure and not a scrape outage, and widening the range or retrying will not change the result. It is a standing coverage limitation that predates the incident.

The trap here, and it is a real one at 3am: reading an empty panel as a healthy service. Nothing about frontend's or user's health — traffic, errors, latency, saturation — can be inferred from these results in either direction.

## Dead end: tracing

A trace query for frontend over a full hour spanning the incident returned nothing at all. Not a filtered subset coming back empty — no spans for the service, period. That means no outbound call spans, no dependency edges, and no span statuses to read.

The consequence is blunt: tracing neither implicates nor exonerates any downstream service. All five edges remain equally open on this evidence. And the totality of the absence is itself a signal — a degraded-but-serving frontend would normally still emit error or long-duration spans, so emission or ingestion for this service should be treated as a live question in its own right rather than assumed healthy.

## Where this landed

No cause is established for the T+0 onset. The only concrete anomaly on the board is the discovery burst, and it is temporally disqualified by six and a half clean minutes. Everything that could have named the real mechanism was unavailable by construction: no span metrics for frontend or user in either window, zero frontend traces for the hour, and a log slice that was truncated down to four seconds of cold-start output.

The failure most plausibly sits on one of the five unmeasured edges below frontend, but we cannot say which, and we have no evidence that would distinguish between them. Confidence is low. No fix class is proposed; proposing one here would be guessing.

## Open questions for whoever picks this up

First: what did frontend log between T-6m25s and T+5s? The unfiltered log query was truncated to the cold-start cluster and never reached the onset minute. Re-run it windowed tightly on the minute around T+0, or paginate past the truncation. This is the highest-value gap on the board.

Second: which of the five downstream edges was slow or erroring at onset? No per-service logs and no latency data were gathered for any of user, recommendation, profile, search, or reservation. Pull logs for each directly; do not route through frontend's view of them.

Third: is the discovery service itself healthy after T-6m25s? We queried only its change history, never its own logs or health endpoint. The burst stopping on its own is consistent with it coming up correctly, but that was inferred from the client side, not confirmed from the server side.

Fourth, lower priority but worth a ticket: frontend emits no traces and no span-derived metrics. That is why this record ends where it does.
