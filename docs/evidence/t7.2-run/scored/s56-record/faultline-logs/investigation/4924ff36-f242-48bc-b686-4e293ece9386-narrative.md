# Ad service goes silent behind a live endpoint

## What was visible, in order

Offsets run from the ad pod's cold JVM start; call that T+0. The page arrived at T+2m11s naming both ad and product-catalog, severity warning, seven services in radius and eight edges carrying no measurement at all. Ad's own stream opens at T+0 with a JVM and agent startup (200m max heap, an OpenTelemetry Java agent via JAVA_TOOL_OPTIONS), reports starting at T+15s, and is listening on its gRPC port at T+17s. Between T+41s and T+1m05s it serves four ad requests across different product categories, each with a populated trace id, span id and sampled flag, none with an error beside it. At T+1m06s it logs a graceful gRPC shutdown driven by a JVM shutdown hook, then a server-shutdown confirmation. That is the last line. Nothing is emitted afterwards, so at the alert second the process was producing no output. The termination shape matters: an orderly hook running to completion, no truncation, no memory notice, no stack trace, and no complaint anywhere about an unreachable peer, a full volume, or a bad address or credential. It simply stops after a signalled stop — the silent-culprit signature, a dead process behind a still-advertised endpoint. Tempo holds no ad spans at all for the window, total rather than partial absence. Conclusion at medium confidence: ad stopped serving and never returned; the corrective action is to bring it back up.

## Dead ends worth keeping

Span-derived metrics for ad are a closed road, not a negative result: the error-ratio query returned an availability error because ad emits no spans that become Prometheus metrics here. That is a property of the instrumentation, so retrying or widening the window will not help, an empty series does not exonerate ad, and the errors-up/latency-flat hypothesis simply cannot be tested by that path. Traces are equally barren — no spans of any status or duration, which kills the slow-failure reading, the partial-degradation reading, and downstream attribution via child spans in one stroke, despite the logs clearly showing four sampled requests served. The change log for ad holds exactly two entries in 24 hours, both by platform-automation, both first-creation records: a service/config entry two seconds before the pod start and a workload entry sharing the shutdown timestamp. That rules out a rollout, a config edit, a resource or replica change, a rollback, and any human action. One honest oddity: the change log calls the T+1m06s event a creation while the pod calls it a shutdown; the likeliest reading is first-observation bookkeeping, but that was never confirmed. flagd looked promising on timing — three changes sharing one timestamp two minutes before onset — but all three are creations by the same automation, the ConfigMap contents are not enumerated so no flag can be named, and flagd's logs show a clean start, successful file parse, an independent read by its UI, then silence with no reload or evaluation errors. product-catalog gave nothing either: its error-ratio series is empty across both the incident and the preceding baseline window, so the absence predates the event and no onset second can be correlated with ad; empty is not flat. Its only log query carried a substring filter for "error" and matched nothing, which excludes a loud error stream but says nothing about startup, shutdown, or ordinary activity.

## Still open

Three gaps, and they are why this sits at medium rather than high confidence. First and highest value: what signalled the stop at T+1m06s, and did the container restart afterwards? No pod state, restart count, or exit code was ever retrieved — fetch that first next time. Second: do ad's callers hang to a deadline or fail fast with connection-refused? No caller-side traces or socket evidence was collected, and that distinction separates a frozen-but-listening process from a dead one. Third: why did product-catalog alert in the same second? Its unfiltered logs were never queried and its span metrics do not exist, so no causal link from ad has been demonstrated and a shared upstream trigger remains untested.
