# Frontend goes silent after a CPU ceiling edit

## What the page said and where we started

The page came from the frontend, and the declared blast radius was six services with critical severity. Five of the edges between frontend and its downstream neighbours had no measurement on them at all, which shaped everything that followed: for most of the investigation we were reasoning about a service whose own telemetry was thin and whose dependency links were unobserved. Anchor time (T+0) is the moment of interest the page carried; everything below is written as an offset from it.

## First pass: frontend logs

The obvious first move was to read the frontend's own output across the half hour leading up to T+0. The only error-level lines in the entire window were nine identical availability-check failures from the search handler, all stamped within a single second at roughly T-7m36s. Eight seconds later a complete cold-start sequence appears: config read, tracing agent init, service-discovery agent init, gRPC client setup, and then the serving state. All five downstream gRPC clients connected cleanly. After that the log is quiet — nothing at or near T+0, no panic, no stack trace, no second startup sequence.

This ruled out several comfortable stories in one pass. It was not a crash loop (one startup, run to completion). It was not a service-discovery or client-config problem (every downstream connection succeeded). It was not a TLS or startup-config problem (all those lines are informational). And the errors were not sustained — they are one point burst, not a condition spanning the window. The caveat worth carrying forward: the log result came back flagged truncated, so a later burst cannot be excluded with full certainty.

## Dead end: the frontend error ratio

The natural follow-up was the span-derived error ratio for frontend. It is flat zero — twenty-two samples, mean, min, max and standard deviation all exactly zero — over both the narrow and the widened window. No error creep, no spike, nothing. Whatever was wrong, it was not reaching users or callers as errored frontend spans, and no downstream failure was propagating into frontend as error status.

Two things made this more than a null result. First, three intervals returned no defined value at all. For a ratio of this shape that means no spans whatsoever in those intervals, which is a traffic gap and not a healthy zero — frontend stopped serving at points in the window. Second, the comparison baseline window produced no samples, so there is no before/after delta. The tooling's own 'no sustained departure' verdict rests on an empty baseline and should not be read as reassurance.

We also asked this same path for container-level signal — throttling ratio, restart counts, eviction or out-of-memory events. None of it came back. The only series returned was the error ratio. That gap is still open.

## Dead end: traces

With logs quiet and the error ratio flat, traces were the obvious way to find a terminal error span and rank the downstream callers by latency. The query returned nothing for frontend across the full thirty minutes — not just the failing minute, but the pre-incident stretch too. So there was no span tree, no blame attribution, and no healthy baseline to compare against.

Two plans died here: naming the culprit dependency from span status codes, and identifying a dominant latency contributor by comparing child durations. Both need spans that do not exist in the store. One oddity is worth recording: the empty response was also flagged truncated, which is strange for a zero-result query and weakly hints at something wrong in the trace query path rather than a clean absence of data. That matters, because the 'three intervals with no spans means no traffic' inference above leans on the trace pipeline being honest.

## Dead end: reservation's side of the failing call

The point burst at T-7m36s was an outbound availability check, so the handler name was the one concrete thread we had. Searching the reservation pods for that handler across the same window returned nothing at all — not errors, not ordinary request logs. That is a weaker result than it looks: zero matching lines is equally consistent with reservation genuinely being quiet and with reservation simply not logging under that wording, or logging at a level that suppresses request lines, or not shipping logs from those pods.

So this did not clear reservation, and it did not implicate it. It only closed the log path. Any case for or against reservation has to come from somewhere else.

## What actually turned the investigation

The change record was the thing that moved us. Three entries exist for frontend in the window, all from the same platform automation actor, none human-initiated. The frontend workload and its Service object were created roughly nine minutes before T+0, meaning this instance was newly stood up immediately before the incident rather than long-running. Then, about seven minutes before T+0, a resource-limits edit landed: the CPU ceiling was cut in half and the CPU request was raised to equal the new ceiling.

That edit lines up exactly with what the logs show. The cold start at roughly T-7m28s is one second after the change — the edit recreated the pod. The error burst eight seconds prior is the old instance on its way out.

The change record also closed doors. There is no image or application version change, so a code deploy is out. There is no flag toggle in the window. And 'nothing changed on frontend, this must be environmental' is directly contradicted by three recorded entries, one of which is a CPU ceiling reduction.

## Conclusion

Platform automation halved the frontend's CPU ceiling about seven minutes before onset; the edit recreated the pod, which came up clean and connected to all five downstream services. From that point frontend produces no further log output, zero error spans across twenty-two samples, and three intervals with no spans at all. That shape — silent, error-free, intermittently serving nothing — is what CPU starvation under a tightened ceiling looks like. Requests stall rather than fail, so callers hang while the service itself reports nothing wrong. The limit edit is how it started; starvation under that limit is the failing mechanism. Confidence is medium, and the fix class is reverting the config.

## Still open for the next responder

Three things were never resolved and would change the strength of the conclusion.

No container-level data was ever returned. Throttling ratio, restart counts, and out-of-memory or eviction events were all asked for and all absent. The throttling is inferred from the change plus the silence, not measured. Getting that series is the single highest-value next step.

Frontend traces are missing for the whole window including the pre-incident baseline, and a zero-result query came back marked truncated. If the trace pipeline is itself broken, then 'no spans means no traffic' is unsound and the traffic-gap finding needs re-deriving from another source.

What the burst at T-7m36s actually hit is unknown. The log line carries no peer address and no status code, and reservation's logs are empty under that filter. A broader filter, a different selector, or non-log telemetry would be needed to settle it.
