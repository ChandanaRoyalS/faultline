# Edge failure at nginx-web-server with no usable observability signal

## What was visible at the start

The page came from nginx-web-server. Four services were in the declared blast radius: nginx-web-server at the edge, plus compose-post-service, home-timeline-service and user-timeline-service behind it. Severity was called critical. Three of the edges between those services had never been measured, so there was no prior shape of normal traffic to compare against.

That is, honestly, everything that was visible. Read the rest of this record as an account of an investigation that did not get off the ground, and of which doors were tried.

## First moves: metrics at the edge

The first dispatch was a metric baseline on nginx-web-server — an error-ratio over span-derived call counts, incident window against the half hour before it. It came back empty. The important detail, and the one that cost the most time to internalise, is that it was empty because the request never left the querying environment: the Prometheus hostname could not be resolved. No connection was attempted, no query was evaluated.

So there is no 5xx rate, no latency figure, no per-upstream or per-route breakdown for the edge, for either window.

## Dead end: reading the empty metric result as a finding

The tempting reading was that nginx-web-server had zero 5xx in the window — a flat edge, with the problem necessarily downstream. That reading is wrong. An errored request and a successful request returning no series look alike from a distance and mean opposite things. Nothing here says anything about nginx's error behaviour in either direction.

Two adjacent dead ends, both tried and both worthless: rewriting the PromQL (the expression was never evaluated, so its correctness was never tested) and adjusting the window or baseline range (those parameters rode along in a request that never arrived). Also not supportable: the conclusion that Prometheus had stopped scraping span metrics for the service. The backend was never contacted; its state is untested.

## Dead end worth keeping: treating the resolution failures as the incident

At one point the name-resolution errors looked like the answer — the incident surfacing in the dependency chain. It does not hold up on the evidence collected. The names that failed to resolve are observability backend hosts, failing on the querying client's side, appearing in tool transport errors rather than in any log line emitted by a workload in social-network. No test of in-cluster service-to-service resolution was ever run.

That said, this is a judgement, not a proof. Whether cluster name resolution is degraded in a way that would also break calls between the four services is genuinely open, and a responder picking this up should test it directly rather than inherit the assumption.

## The one channel that worked: the change log

Change history returned real data for all four services, and the four stories are identical. Each service has exactly three entries in the whole 24-hour window, all attributed to platform-automation, all clustered within a second or two at roughly T-7m relative to onset: a ConfigMap created, a Service created, and a container workload created for the first time.

Created, not modified. No prior revision of any of the four exists in the window. The whole stack is about seven minutes old when the page fires.

This closes several hypotheses cleanly. There was no image bump or version rollout regressing a previously healthy service — the only container events are first creations. There was no edit to an existing nginx upstream block or to any ConfigMap value — every config object is a creation, not an update. No human operator touched anything; every entry carries the automated actor. No slow drift from earlier in the day accumulated into this; the 24-hour window holds nothing else.

It also kills the obvious remediation. Rolling back is not available for any of the four, because there is no earlier state to roll back to. A rollback here would be a deletion.

## Where this landed

No cause established. Confidence low, no fix class identified.

What the change log does buy is a reframe. Because every one of these services was born seven minutes before onset, the failure is not a working thing that broke — it is something that never worked correctly from first start. That changes what a responder should look for: original misconfiguration, a container that never reached a healthy running state, a dependency that was never wired up right. Not a regression.

What it does not buy is attribution. nginx-web-server is where the failure was observed, nothing more. It is not a demonstrated culprit, and the three downstream services are equally unexamined.
