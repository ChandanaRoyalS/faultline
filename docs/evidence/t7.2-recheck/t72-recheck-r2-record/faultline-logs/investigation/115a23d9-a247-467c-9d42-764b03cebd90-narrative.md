# Five hotel-reservation mongod instances crash-looping on startup after a pipeline image move

## What was visible, in order

At T+0 five alerts landed together: mongodb-geo, mongodb-profile, mongodb-rate, mongodb-recommendation and mongodb-user. Severity warning, no graph entry point. Simultaneity across five independent databases was the first useful signal — five storage layers do not degrade in lockstep for five separate reasons. Logs then showed the processes were already dead before the alerts fired: mongod exited with code 62 at T-7s (rate), T-5s (geo) and T-1s (user), each shutdown running in the initandlisten thread, meaning the server never reached a listening state. Each teardown was orderly and fast (roughly 14–20 ms total), with WiredTiger closing cleanly via a successful shutdown checkpoint and rollback-to-stable. That shape closes the hard-kill story (no shutdown summary would survive a SIGKILL), the graceful-restart story (that exits zero), the storage-corruption story (the engine closed cleanly), and any load-driven collapse (no client was ever accepted). Change history then supplied the act: a single platform-automation burst about a minute before onset stood up Service, PVC and workload on each service, and last of all moved the container image from mongo:4.4.6 to mongo:8.0.14-rc0 — a multi-major jump onto a pre-release build.

## Dead ends worth keeping

Metrics first, and metrics gave nothing. The error-ratio template here reads span-derived series, and these mongodb targets emit no traces that become metrics, so the backend returned an explicit unavailability for both geo and rate, across the incident window and the baseline. The trap: that empty result is not a zero, and must not be read as 'database healthy'. Widening or shifting the window will not help and neither will trying a sibling instance — use container/node resource metrics or caller-side latency instead. Second, the PVC churn: each claim was created then mutated two to four times in the seconds before the image moved, which looks like a storage-binding problem and is not one; the claims exist and the engine opened and closed them cleanly. Notably recommendation-pvc was created inside the same burst, which rules out the tidy theory that the new binary met leftover 4.4-era data there. Third, the things that never appear in the change record at all: no CPU or memory spec change, no replica or scaling operation, and the existing init-script ConfigMap was created and never modified, with its mount carried through the diff unchanged. Also worth stating plainly — this was not a routine patch bump, and treating the image line as noise would have cost hours.

## Conclusion and what is still open

The pipeline moved every hotel-reservation mongod onto mongo:8.0.14-rc0 as the last change before onset. That binary cannot finish startup here: each process aborts from its startup thread with exit code 62, the version/on-disk-format incompatibility abort, so nothing ever listens and all five services crash-loop and alert together. Confidence high; fix class is rollback — restore the 4.4.6 image and confirm the pods reach a listening state. Three gaps remain. The assertion line immediately before each shutdown was never retrieved; all three log results are truncated to the shutdown tail, so exit 62's meaning rests on mongod convention rather than this environment's own error text — pulling those lines is the highest-value follow-up. Why a freshly created volume would hold anything the new build rejects is unexplained, since recommendation-pvc was created inside the same burst. And mongodb-profile was never dispatched against at all; its participation is inferred from the other four. The failure-admin-geo ConfigMap mounted at /scripts on geo alone was also never read.
