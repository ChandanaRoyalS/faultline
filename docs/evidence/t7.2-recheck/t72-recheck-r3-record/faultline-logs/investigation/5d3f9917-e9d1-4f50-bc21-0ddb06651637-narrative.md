# Critical alert on the nginx front door with no usable telemetry beneath it

## What the responder sees first

The page comes from nginx-web-server at T+0, severity critical, with a declared blast radius of four services. Three of the edges in that radius were never measured, so the shape of the impact is asserted rather than observed. Nothing in the alert itself names a failing dependency.

The honest summary up front: this board did not establish a cause. Every signal reached for either does not exist for the services involved, or returned empty from a selector that was never validated. The one piece of positive evidence is a provisioning burst shortly before the page. Read the rest of this record as a map of which doors are locked, not as a narrowing of suspects.

## First reach: traces from the front door

The obvious first move was to pull traces for nginx-web-server over the roughly thirty minutes ending at the page, expecting either a root span that fails fast at the nginx-thrift boundary or a child span toward compose-post, home-timeline, or user-timeline carrying ERROR. The window came back completely empty — no root spans, no children, nothing at the edges of the range.

At the time this read as a strong signal: total absence, not partial, so it seemed to rule out intermittent degradation and seemed to point at either no admitted traffic or a broken export path. That reading was wrong, and it cost time. See the next section.

## Why the empty trace window turned out not to matter

Two metric attempts explain it. An error-ratio query for nginx-web-server over the onset window and its preceding baseline returned nothing, and the backend was explicit about the reason: this template reads span-derived metrics, and none exist for this service because it does not emit traces that become metrics. The same query against compose-post-service, run over a full preceding hour as well as the onset window, failed identically for the same stated reason.

That reframes the empty Tempo result entirely. For a service that emits no traces, an empty trace window is the expected baseline, not a symptom. There was no transition from data to no-data at onset — the baseline window is just as empty as the onset window — so there is no collector outage, no export break, and no inference about admitted traffic to be drawn. Equally, the empty metric results must not be read as zero errors or zero traffic; they are unavailability. Retrying either query with a wider window or adjusted parameters will return the same nothing. Request rate, status mix and upstream latency for the proxy tier have to come from access logs or an nginx exporter instead.

## Second reach: logs, and why the silence proves nothing

Two log queries were run against the social-network namespace, one for the nginx frontend pods and one for compose-post-service, both over the window ending at the page. Both returned zero lines of any level.

The trap here is that total log silence from a request-serving component looks damning — it suggests the pod is absent, crash-looping before emitting, or has broken shipping. But both queries selected pods by a guessed name regex that was never validated against an actual pod listing, and both results carried a truncation flag despite being empty, meaning the emptiness is a property of whatever stream set matched rather than a confirmed exhaustive scan. If the regex matched nothing, there was never a stream to be silent. Nothing about upstream connection failures, refused backends, identity or peer-verification errors, or onset timing can be read out of these results in either direction. The correct next step is to validate the labels and the shipping path, not to re-run the same selector.

## The only positive evidence: a provisioning burst before the page

The change record for nginx-web-server covers a full day and is empty until a single three-second burst roughly six minutes before the alert, at about T-6m. In that burst, three things are recorded as created for the first time by the same non-human actor, platform-automation: the nginx workload container, the nginx-thrift ConfigMap, and the nginx-thrift Service.

The important detail is that all three are creations, not modifications. The routing surface and the routing config came into existence at the same instant as the workload, which means nginx began serving against config that had never previously been exercised. This is a bootstrap, not a regression away from a known-good state.

Several plausible stories die on this evidence. There is no prior version of the ConfigMap or Service in the window, so a config edit regressing a previously healthy upstream is out. The window spans a day with no activity until the burst, so there is no staged or progressive rollout to blame. Every change is attributed to automation with no human actor present, so an operator hotfix or emergency push is out. The Service was created rather than repointed, so no existing traffic path was redirected from a healthy upstream to a broken one. And the workload is logged as first created, so this is not a restart, reschedule, or rollback of an earlier running instance.

## What remains open

Confidence is low and no fix class is named. Three questions are live for whoever picks this up.

First: do the nginx-thrift and compose-post-service pods actually exist, and are they Running? Until a pod listing confirms the real names and labels, the log silence is uninterpretable.

Second: what do nginx access and error logs show under a relaxed selector, or via an nginx exporter? Span-derived metrics are structurally unavailable for this service, so this is the only route to request rate and status mix.

Third: did the provisioning burst at T-6m actually complete? Specifically, did the container reach Ready, and do the upstreams named in the freshly created nginx-thrift ConfigMap resolve? The timing is suggestive and the config is untested by construction, but suggestive timing is not attribution — nothing here yet names what is failing at T+0.
